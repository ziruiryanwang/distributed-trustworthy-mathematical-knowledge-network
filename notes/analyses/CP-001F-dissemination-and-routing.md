# CP-001F: contribution reachability and bounded rendezvous routing

Date: 2026-09-20  
Status: selected concept amendment for cross-audit; not implemented, benchmarked or deployment-qualified  
Scope: autonomous publication and discovery of existing public mathematics, not a research-task registry

## Outcome

CP-001E provides a much better exact transfer/checking path, but it does not yet select a mechanism by which an ordinary useful contribution escapes its producer's small contact neighborhood and becomes discoverable by distant interested agents. Connected honest participation alone does not repair that omission. The problem precedes theorem checking: likely reusers may never obtain even the provider's address.

Select **ROUTE1**, a separately negotiated bounded iterative rendezvous layer. It routes exact existing-content collection keys to replicated, expiring provider advertisements. The advertisements lead to ordinary public FIND/FIND_WINDOW and exact native acquisition; routing servers need not import each advertised theorem. Explicit local publication/refresh and reader exploration jobs close the operational loop. There is no central registry, universal membership roster, globally authoritative current index, mandatory mathematical investigation, or implication that a routing key certifies truth.

This amendment is not a silent extension of NET2's 256-contact directory or an assertion that the current software already implements a DHT. All CP-001E/frozen documents remain unchanged. The separately negotiated `NET2+ROUTE1` profile below selects new call and record schemas; an implementation claiming that capability must support them rather than guessing at an unknown NET2 operation.

## A fully honest connected counterexecution

Let the physical reachable network and maintained contact graph contain three large communities A, B and C, with publicly shareable bridge contacts between A–B and B–C. The graph is connected throughout; nodes, storage and links do not fail. Each node has at most 256 directory entries, all calls are paid and within budget, and everybody uses the same qualified mathematical foundation. Communities can be replicated along a long ring to make the construction arbitrarily large.

A producer p in C retains and publicly serves a newly checked theorem x. A reuser r in A has an exact formal application for which x would be useful and repeatedly asks a predicate that matches x. Only p indexes x. This is consistent with the absence of compulsory replication or compulsory index ingestion.

Choose the remaining compliant local state as follows:

1. p's bounded publication sends HINT to four established C neighbors. They are honest but their selected collections do not select x. The hints expire. NET1 explicitly forbids automatic forwarding; no recipient must become an index relay merely because it received a hint.
2. r eventually queries every compatible contact in its pinned 256-contact directory, including its A-side bridge service. Each service answers completely over its own public index; none has x. FIND does not recursively query another index.
3. At every bridge queried by r, at least 25 local-community contacts precede the outward bridge contact under the existing key/service-score ordering. GET_ROUTES can return eight contacts and exclude only 16 IDs. Every permitted exclusion set therefore leaves at least nine higher-ranked local contacts; the outward contact need never appear. All contacts can truthfully advertise the same broad formal key. Stable higher local service scores, or canonical tie order, keep this execution stable.
4. Hourly refresh maintains reachable known contacts. A gateway itself knows the next gateway, so the graph remains connected. It has no local reason to search for x and no duty to relay another node's query. Directory replacement may retain the existing useful local contacts; no baseline rule forces an outward exploratory replacement or a routed lookup.

Thus every r lookup and maintenance occurrence can finish correctly forever while r never learns p or x. The fair fourth query slot is fair over r's finite admitted directory, not over graph paths or all providers. BUNDLE1 and native warm reuse cannot help a candidate never discovered. FIND_WINDOW repairs within-provider prefix bias but does not cross this missing routing edge.

This is not an impossibility proof for all decentralized systems. It is a countermodel to the claim that the currently selected rules alone yield useful contribution dissemination in a connected mostly-honest network. Requiring every intermediate agent to import or care about x is unnecessary; a bounded routing/index role can relay provider metadata without sharing the mathematical interest.

## Required and impossible properties

Separate these predicates for an exact contribution x and reuser r:

`PubliclyServed(x,p)`, `ProviderDiscoverable(p,K,r)`, `CandidateReturned(x,K,r)`, `LocallyReusable(x,r)`.

None implies the next without additional conditions. ROUTE1 addresses the second predicate and its recurring operational supply; ordinary provider indexes and application checking address the latter two. A provider advertisement is not proof that its candidate set is complete, or even honest.

No finite system can guarantee timely discovery of every future useful theorem for every unknown agent under arbitrary publication rate, unbounded predicates, partitions, unavailable providers or adversarially selected identities. Even honest connectivity without fair communication/capacity does not imply dissemination. These limits do not excuse the avoidable absence of a selected route from unfamiliar producers to reusers.

The useful target is conditional: under declared stable/reachable routing, successful funded placements, common key interpretation, retained public service, and fair sufficient reader work, a reuser can discover a matching provider without an initial direct acquaintance or mathematical import at every hop. A finite failed attempt reports its explored scope and failure, not universal absence.

## Exact keys and public provider advertisements

The selected routing namespace contains only the following canonical existing-content selectors. Canonical encodings use definite arrays, uints and byte strings; option fields use `[0]` absent or `[1,value]` present.

| Tag | Collection key K | Meaning at a provider |
|---|---|---|
| 0 | `[0,FoundationID]` | Its public indexed collection in that exact foundation |
| 1 | `[1,FoundationID,JudgmentID]` | Ordinary exact-judgment lookup |
| 2 | `[2,FoundationID,ExtractorID,symbolRef]` | One exact symbol membership predicate under the selected STRUCT1 interpretation |
| 3 | `[3,FoundationID,ExtractorID,headOrRawShapeKey]` | One exact existing STRUCT1 head/raw-shape key |

Each key is at most 1024 canonical bytes. A symbol/group reference must use the same external native-reference grammar and exact foundation; new STRUCT2 or learned keys require their own separately fixed negotiated extraction contract. Names, prose descriptions, alleged importance and unsolved questions are not ROUTE1 key kinds. A conjunction can query providers for one of its component keys and then send the full bounded predicate through FIND; the router does not invent a semantic intersection proof.

`ProviderAd = [1,providerNodeID,K,revision,publicContact,anchorPublicDescriptorCID,anchorReplayID]`.

The complete record, including the common Ed25519 signature wrapper, is at most 4096 bytes. Its signature binds the exact typed ROUTE1 record, not a native proof. Select `publicContact = [nodeID,endpoints,nativeProfileIDs,indexKeys]`, exactly the existing GET_ROUTES four-field contact grammar, not the offline contact-bundle or new RouteContact grammar. Its nodeID must equal ProviderAd.providerNodeID; endpoints are at most two explicitly public sorted unique inherited-format endpoints. Native-profile and index-key lists retain the inherited sorted/duplicate-free encoding and maximum 16 entries each; nativeProfileIDs must include K's exact FoundationID. All advertised contact keys remain untrusted coverage hints and the ordinary endpoint validation/connection-admission rules apply. The anchor is an actual currently public local descriptor/replay selected by the honest producer; it witnesses the producer's local reason to advertise coverage, not a guarantee that all matching objects fit in one descriptor.

The producer's authority writer creates/renews this ad only while its exact local index has a matching currently public retained entry and its disclosure policy permits publication of all ad fields. A foundation fallback ad remains useful as the corpus changes; adding another theorem under the same key need not add another routing record. An ad is a provider's collection assertion, not one DHT record per theorem or dependency.

The routing receiver checks canonical shape, key/type/foundation consistency, signature, actual submitting peer identity, byte bounds and local admission. It does **not** independently derive every advertised formal key or import the anchor's native closure. The ad therefore stays in a clearly labeled untrusted routing table. On actual use, the client verifies the requested descriptor binding and checks native material through the existing path. A wrong key/anchor claim can cause bounded false leads, never native acceptance.

Only the advertised provider's authenticated connection can place, renew, replace or withdraw its ad. A third party can return an already stored signed ad as a discovery response, but cannot thereby refresh its storage lease. One live ad exists per `(K,providerNodeID)` at a particular shard cell. Revisions are checked uint64: a larger revision replaces, an equal revision with identical bytes renews, and lower revisions or equal revisions with different bytes reject while the record is live. Exhaustion requires a new provider key/local migration, not wrap. Once all state for an expired ad is forgotten, a later newly authenticated provider submission can be admitted anew; old network CALLs or copied offline signatures are still not fresh authority.

Public disclosure is not revocable knowledge. Withdrawal stops new authorized service and initiates bounded ad withdrawal, but cannot erase already disclosed copies. Native public-root reads retain their own current disclosure guards even if an old routing ad survives until expiry.

## Routed key space and separately funded tables

Let

`nodePosition = SHA256(ASCII("DTMKN-ROUTE1-NODE") || encode(NodeID))`.

The XOR distance orders node positions relative to a 256-bit route target, with NodeID as an exact tie-break. Positions authenticate no real-world uniqueness or independence; deliberate key grinding and eclipse remain possible.

A ROUTE1 service node allocates a **separate** table of at most 16 live contacts for each common-prefix length 0 through 255: at most 4096 contacts and 8 MiB aggregate including statistics. Every stored contact has completed a directly authenticated ROUTE1 exchange, is shareable, and opts into serving this layer. A new contact enters a nonfull applicable bucket; in a full bucket it replaces only an expired/unreachable contact established by an independently funded probe. Live incumbents are retained. A bucket has at most two bounded pending candidates, included in the aggregate count/byte allowance; further suggestions need no durable state.

The existing 256-contact mathematical PeerDirectory is unchanged. ROUTE1 contacts are not 4096 new native query slots. A funded ROUTE1 lookup may keep up to 16 returned provider contacts as transient candidates for separately admitted ordinary FIND/acquisition, without pretending they belonged to an earlier NET2 directory-pinned session.

Clients can use ROUTE1 without storing ads or serving other clients. Services require reachable advertised endpoints and an explicit local serving allocation; an intermittently reachable/private client is not automatically placed in routing tables. Bootstrapping needs at least one willing reachable contact supplied out of band or through an existing contact. Multiple independently obtained contacts reduce one operational dependency but are not a proof of independence. No root server or universal roster is selected.

## Hot-key sharding without a fixed global population ceiling

For provider p let `s(p) = SHA256(ASCII("DTMKN-ROUTE1-SHARD") || encode(NodeID(p)))`. A cell is `(K,d,prefix)`, where `d` is 0 through 32 **bytes**, `prefix` has exactly d bytes, and an ad placed there must satisfy `prefix = first_d(s(p))`. Depth zero has the empty prefix. Its route target is

`SHA256(ASCII("DTMKN-ROUTE1-CELL") || encode([K,d,prefix]))`.

Each service cell holds at most 4096 provider ads and 256 immediate child markers, subject also to node-wide limits. A child marker is the exact next byte `b`, naming `(K,d+1,prefix||b)`. Markers have receiver-local finite expiry and are hints that the child should be explored, not certificates of any child's contents. No children are legal at depth 32. All lists sort canonically; an endpoint cannot rename or redirect a cell to an unrelated key.

A publisher first attempts placement at depth zero. If fewer than four of the at most 16 selected reachable holders admit its ad, it tries the next prefix byte, up to depth 32. This order is fixed; insufficient funded work ends PARTIAL/UNPLACED instead of making an implicit promise to continue forever. Partial shallower placements may remain and cause harmless duplicate discovery.

When a deeper placement obtains at least four admitted copies, the publisher installs the child marker at every ancestor cell, from the leaf's parent toward the root, again seeking at least four successful holders per marker. A complete observed route consists of the leaf ad plus this marker chain. An unannounced leaf is explicitly PARTIAL, not silently counted as discoverable. The publisher can refresh shared ancestor markers without maintaining a separate per-provider permanent marker record at the server: each admitted marker renewal extends only that marker's bounded local expiry. A false marker can waste bounded exploration; it cannot allocate a recursive fetch or prove mathematical content.

The maximum 32-byte depth avoids a 16-bit global hot-key ceiling. Distinct providers with identical full shard hashes, or too many records at a deepest cell under violated hash/randomness assumptions, yield explicit nonplacement. One provider/key still occupies only one row in each individual cell; submitting different signed versions cannot multiply its rows there. New provider identities are not Sybil resistance, and per-cell limits alone do not prevent node-wide overload.

## Exact bounded operations and local state

ROUTE1 is a new negotiated service family, not an unknown NET2 operation smuggled through an old call. It uses the same local one-shot offer/claim/meter/finalization and authenticated-reply rules. `NET2+ROUTE1` mutually negotiates capability code 5, allocates ProviderAd `0x8022/1`, and extends ServiceCall `0x8004/2` with codes 11 through 15 below in row order. These new codes are legal only after mutual capability-5 negotiation; no old operation code is reinterpreted and an old peer is never sent these calls. Existing offer/result records bind the exact typed call CID and do not gain new fields. `RouteContact = [nodeID,endpoints,capabilityCodes]`, with at most two sorted unique inherited-format public endpoints and at most 16 sorted unique uint capability codes including 5; the entire contact is at most 1024 bytes. This is distinct from ProviderAd's ordinary native publicContact, which retains its stated existing contact shape. A contact advert alone does not prove a completed live connection. Native, advisory and export schemas are not reinterpreted.

NET2's HELLO request has no capability field. Mutual negotiation therefore means reciprocal existing HELLO exchanges on the authenticated connection, so each participant has received the other's HELLO_REPLY advertising capability 5 before a ROUTE1 call. No new HELLO array shape or outer wire version is implied. A client-only participant may advertise syntax support while declining storage/serving under its ordinary service policy; capability is not a resource promise. A one-sided old-peer reply is insufficient authorization to send a new operation back to that peer.

| Operation | Arguments | Successful bounded result |
|---|---|---|
| `ROUTE_NEAR` | `[target32,requestedCount]` | `[target32,orderedRouteContacts]`; at most requestedCount contacts ordered by distance/NodeID; at most 32 KiB total |
| `ROUTE_PUT_AD` | `[cell,signedProviderAd,requestedLeaseMillis]` | `[adCID,cell,localObservationID,grantedLeaseMillis]`; authenticated peer must equal provider |
| `ROUTE_PUT_CHILD` | `[parentCell,childByte,requestedLeaseMillis]` | `[parentCell,childByte,localObservationID,grantedLeaseMillis]`; only a marker, no remote child query |
| `ROUTE_LIST` | `[cell,snapshotSelector,startPosition,pageCeilings]` | `[cell,snapshotToken,adRows,childBytesAtCut,processedInterval,nextCursorOption,coverageCode]` |
| `ROUTE_DROP_AD` | `[cell,K,providerNodeID,expectedRevision]` | `[cell,providerNodeID,expectedRevision,dropStatusCode,localObservationID]`; status 0=REMOVED, 1=ALREADY_ABSENT; version mismatch is an error, and only the provider may remove its row |

Here `cell = [K,depthBytes,prefixBytes]`; operation field tags remain the inherited fixed integer codes. The parentCell/key in an operation must be the exact declared canonical cell. A PUT_AD validates provider-prefix consistency and signature before allocation. PUT_CHILD validates only legal next depth/byte and local policy; it does not claim remote existence. Keys, identities or marker topics create no new resource classes. A service may decline because it is not prepared to host the requested cell or lacks capacity; closer contacts remain discoverable separately through ROUTE_NEAR. No node is obligated to store a record merely because its position is near a key.

`target32` is exactly 32 bytes; requestedCount is in 1..16. Every requestedLeaseMillis is a positive uint no greater than 172800000 (48 hours). `pageCeilings=[maxRows,maxEncodedBytes,maxInspectedRows,maxCPUms,maxWallms]`, each positive and no greater than `[64,262144,8192,250,2000]` respectively; actual offered reply/allocation ceilings can be lower. A reply that cannot fit even its required fixed fields is declined under the existing result/allocation rules, not emitted oversized. Redundant K/provider fields in DROP must agree with cell and authenticated peer.

No new top-level RESULT codes are allocated. Route-specific failure bodies are `[reasonCode,groupObservationOption]`, where the option is `[0]` unless the fine-group extension authorizes an exact provider-private `[1,groupObservation]`. The selected reason codes/top-level mappings are: 1=CELL_OR_KEY_MISMATCH/8, 2=PROVIDER_OR_HOLDER_MISMATCH/16, 3=ROW_OWNER_CONFLICT/8, 4=STALE_AD_REVISION/8, 5=EQUAL_REVISION_DIFFERENT_BYTES/8, 6=UNKNOWN_GROUP/2, 7=EXPIRED_GROUP/16, 8=CLOSED_GROUP/16, 9=STATE_VERSION_OR_ROOT_MISMATCH/8, 10=MISSING_EXPECTED_ROW/2, 11=LIMIT_OR_COUNTER_EXHAUSTION/4, 12=TEMPORARY_CAPACITY_REFUSAL/5, 13=UNSUPPORTED_ROUTE_PROFILE/3, 14=INTERNAL_KEY_COMMITMENT_COLLISION/15, and 15=DISCLOSURE_POLICY_REFUSAL/16. Existing cursor/replay/offer/execution errors retain their ordinary NET meanings; they are not repurposed by this reason enum. Unauthorized callers receive no group observation. These are bounded failure data, not new global mathematical judgments.

Every ROUTE1/fine-group result uses `resultMetadata.publicAssessmentDigestOption=[0]`, the inherited NET absent-option encoding. These operational results carry no foreign-native verdict. Each localObservationID is the inherited 16-byte issuer-local outcome/observation identifier bound to the exact committed result; possession of it creates no read, renewal or spend authority.

Initial service allocation: at most 65536 live ads, 8192 live cell records, 65536 total live child markers, and 384 MiB total routing ad/cell/index metadata, all included in the node's actual capacity. The count and byte limits apply together. A full cell declines new providers, while an already admitted provider's funded same-size renewal can preserve its existing allocation. A full node can decline a new cell even when that cell's own limit is empty. Expired records are not served as live and are reclaimed through metered local maintenance; expiry does not fabricate free renewal authority.

Default leases are 48 hours of the holder's own monotonic time, with a maximum of 48 hours. A marker renewal sets its expiry to the later of its existing expiry and the new independently admitted local deadline, never beyond 48 hours from this renewal; it does not accumulate 48 hours per call. The requester cannot turn those ticks into a synchronized global expiry. A receipt means admission at the responder's observation boundary, not future guaranteed storage or proof that the response arrived while every replica was live. Different holders' receipts are not a consensus certificate. Original remote calls remain one-shot. A clean admission seal preserves surviving local ad leases without extending them; actual uncertain clock/recovery continuity expires their current-routing status conservatively until fresh local authority reestablishes it.

ROUTE_LIST pages have at most 64 ads, 256 KiB encoded bytes, 8192 inspected entries, 0.25 CPU-seconds and two wall-seconds. Each reply includes the cell's at most 256 child bytes at the same public snapshot cut. Ad ordering is by exact providerNodeID. Snapshot/start unions follow NET2 FIND_WINDOW: `[0]` current / `[1,token]`; `[0]` BEGIN / `[1,providerNodeID]` inclusive boundary / `[2,cursor]` resume. The holder-authenticated cursor binds exact cell, snapshot, holder, original lower boundary, next unprocessed provider and original expiry; its opaque encoded token is at most 256 bytes, binding large keys through their exact digest. No matching row is skipped because output is full. Snapshot expiry is 120 seconds; at most 32 snapshots and 8 MiB extra copy-on-write/snapshot state per service. New rows beyond a prior snapshot are not falsely included in its coverage.

`processedInterval = [lowerBound,nextPosition]`: lowerBound is `[0]` BEGIN or `[1,providerNodeID]` inclusive; nextPosition is `[0]` END or `[1,providerNodeID]` naming the least unprocessed row, exclusive from this page's completed interval. `coverageCode` is 0=END_OF_THIS_CELL_SNAPSHOT, 1=MORE_ROWS, or 2=WORK_BUDGET_STOP. END requires nextPosition `[0]`; other successful page codes retain the exact next position and, while eligible, a tagged present continuation token. Expired/inconsistent cursors use the existing bounded STALE_CURSOR/REQUEST_MISMATCH outcome, not a fabricated END page. Empty intervals and zero-output budget stops do not advance past an unprocessed row.

Every ad row is `[signedProviderAd,0]`, where 0 means `PRESENT_AT_NAMED_SNAPSHOT_CUT_ONLY`; childBytesAtCut has that same historical interpretation. A captured row or marker is not advertised as live at later delivery time. Expiry between snapshot and reply cannot become a positive current lease claim. Beginning a new current snapshot includes only currently admitted unexpired rows/markers at that writer boundary. A provider must still be contacted and its native public service rechecked to use its mathematics.

PUT, DROP, expiry, snapshots and positive read observations use the authoritative local writer. Each commit checks the exact current lease/allocation/disclosure and expected-row versions. A server never recursively routes a client's request, fetches an ad's anchor, contacts its provider, or follows a child marker as a consequence of serving one call.

## Iterative lookup, cursor and publication algorithms

An initiator's `RouteLookupState` is `[localSessionID,target,candidateContacts,triedNodeIDs,inFlightIDs,successfulContacts,remainingAllocation,deadline]`. Each candidate set has at most 256 contacts and 512 KiB; the tried set has at most 64 IDs per occurrence. Seed from the closest live contacts locally known. Repeatedly query the closest untried candidates, up to four concurrently. A response adds at most its 16 bounded contacts; retain the nearest 256 by exact distance and deduplicate NodeID. No response resets the tried set, deadline or spent work.

One occurrence allows at most 64 remote service operations and 120 seconds, plus separately allocated handshakes/bytes. With fewer than 16 successful contacts, continue every eligible untried candidate until candidate exhaustion or the work/deadline limit; one answered contact is not a 16-holder frontier. After at least 16 successful contacts, let T be the 16th successful contact under `(XOR distance,NodeID)` order. Normal completion requires that no eligible untried candidate is closer than T and every in-flight candidate closer than T has settled; a new closer response can move T and extend this bounded work. Remaining in-flight work is explicitly cancelled/settled under its already spent allocations before fixing the returned holder set. Exhausting work/deadline before this condition gives PARTIAL; fully exhausting fewer than 16 candidates gives an explicitly shorter exhausted set. The successful result is `CLOSEST_SEEN`, not a proof that unseen closer nodes do not exist. Querying these selected holders for ads/markers consumes additional calls, not a free side effect of ROUTE_NEAR. Equality of the stable nearest set is an assumption for the progress proposition below, not a claim furnished by this algorithm in every topology.

The provider maintains at most 16 active key publication intents, with one foundation fallback for each of at most four currently publicly served foundations. Remaining slots cover selected existing exact/STRUCT1 keys. The default chooses keys by descending count of public descriptors actually indexed under that key, with exact canonical key bytes breaking ties; a locally chosen alternative policy must disclose its selection scope. This is provider coverage optimization, not a fairness promise to every result. Unselected finer keys remain reachable through the foundation catalog but may be expensive to find.

These 16 slots are the **coarse catalog lane**, not the claimed solution for exact-target query efficiency. If P honest providers advertise the same fallback/common keys and exactly one has a useful target with an unadvertised rare key, the catalogs are indistinguishable until their actual indexes are probed. A deterministic worst case needs P probes; a uniformly located target is found with probability at most q/P after q distinct probes. Merely routing these same coarse catalogs faster does not remove that lower bound. The selected [exact-routing coverage amendment](CP-001F-exact-routing-coverage.md) therefore adds a separately counted finite FULL_EXACT lane with actual exact-judgment memberships, bounded batches and provider-holder lease groups. It does not redefine 16 as enough for an arbitrarily rich corpus, and unknown-statement structural relevance remains a separate problem.

`PublicationIntent = [localIntentID,K,currentAdCID,disclosureVersion,phase,currentDepth,placementObservations,ancestorFrontier,refreshCursor,spentVector,deadline]`.

Local publication activation/coalescing happens after a public index transaction. One intent per key absorbs repeated corpus changes; a million new theorems cannot create a million protected route jobs. Initial publication and changes get finite jobs. Renewal attempts occur every 12 hours under a standing owner-authorized policy, with fallback keys first and other keys in persistent round-robin order. Each occurrence has fresh finite authority; an admitted scan keeps its progress only under counted local state. Publication intents and their exact observations use at most 8 MiB aggregate persistent metadata; transient route lookup/provider queues have a separate 8 MiB aggregate work allocation. The node admits at most four route publications/read traversals concurrently. One local profile supplies at most 32768 publication/refresh/discovery/route-maintenance calls, 512 MiB application traffic and 1800 CPU-seconds per 24-hour authorized funding interval; these replace allocated shares of the total node budget, not extra free resources. Actual work is limited by every dimension, and no assertion is made that every routine can simultaneously consume its independent per-occurrence maximum under that daily envelope.

One complete deep publication can require many occurrences: up to 33 ad-placement cells and 32 ancestor cells, each with bounded routing and up to 16 PUTs. A publication attempt has at most 8192 total service operations, 64 MiB application traffic and a 24-hour local deadline, charged to its actual periodic and occurrence allocations; whichever limit arrives first stops it. An intent can later hold a newly authorized attempt, but cannot reset its old spent history or relabel old missing leases live. The finite worst-case call envelope is consequently thousands of operations, not one constant-cost announcement. The publication intent reports observed copies and missing ancestor links. Lack of budget marks it delayed/degraded; the system must measure this latency, not call the contribution globally indexed. More capacity can be locally admitted without changing theorem identity.

Reader discovery starts at a chosen K's depth-zero cell. It performs funded routed holder reads, merges ad rows by `(K,providerNodeID)` and exact revision, and explores returned child bytes in canonical depth-first order. A bounded DFS stack needs at most 33 frames; each stores the exact cell, returned child bitmap, next child, holder/page continuation and observed cut. A single traversal occurrence has at most 256 service calls, 4 MiB response bytes, 256 provider candidates and 120 seconds. The stack/counters have at most 256 KiB retained local state. Another occurrence requires fresh authority and revalidates expired cursors; it does not reuse an old lease as execution permission.

Each frame preserves its next unprocessed provider boundary per selected holder even after a snapshot token expires. A later independently funded current-snapshot call resumes with `[1,nextProviderNodeID]`, not BEGIN, and explicitly begins a new observation cut: it is not a completion claim for the expired snapshot. The already observed child bitmap is retained as bounded candidate work, with its cut/age; stale children are probed as stale leads, not asserted live. Newly observed child bits are queued within the fixed 256-bit frame. A child is marked completed for this sweep only after its selected-holder pages and descendants have reached their declared scoped ends. New rows before a passed provider boundary and new markers discovered after a passed child are considered on a later sweep.

A completed sweep discards historical local snapshot tokens and begins another independently authorized root sweep; a restart preserves the bounded DFS/provider lower boundaries and accounting while invalidating noncontinuous remote/local tokens. Thus repeated 120-second leases do not force permanent prefix rescanning. Under a stable finite reachable cell tree and successful fair funding, the cursor can finish that finite sweep. Arbitrarily rapid growth, holder-set churn and repeated errors can prevent sweep completion; statuses report scoped progress and ages rather than claiming a forever-current global catalog.

A cell response supplies only that responder's current local ads/markers. A client seeking the conditional placement guarantee queries all of its selected nearest 16 holders, within its aggregate budget; a low-latency client may stop earlier but must report that smaller scope. Conflicting revisions/signatures and stale endpoints remain separate errors/candidates; no majority becomes a theorem verdict. The publisher's ad signature is verified before presenting it as that provider's assertion.

A local agent's ordinary formal reuse request selects finite exact/STRUCT1 candidate keys and can fall back to the foundation catalog. Additionally, the selected downloadable client supports at most 16 owner-authorized existing-content collection keys and admits at most one 256-call discovery occurrence per hour, rotating those keys; it does not promise an hourly full sweep of all 16 keys. This is local interest in existing records, not a public goal/unsolved-statement registry. It advances persistent key/DFS/provider-query cursors fairly within the independently supplied aggregate budget. Finding a new provider creates only a candidate for separately admitted FIND_WINDOW and native import/application. No remote ad installs a callback or forces continued polling.

Provider discovery does not solve unlimited scanning inside a huge provider. FIND_WINDOW's lower-bound choice can explore beyond repeated prefixes, but new records arriving before an old scan frontier require a later sweep. A stable finite selected provider snapshot can be covered given adequate retained continuation/service; an indefinitely faster-growing corpus cannot be declared covered by this routing note. Candidate-return latency under concurrent growth is a separate end-to-end qualification metric and may require a future explicitly bounded change-feed contract.

## Routing maintenance and authority conservation

A service/client has a persistent bucket-refresh cursor. Every ten minutes a locally funded occurrence selects at most one bucket and obtains one iterative lookup toward a locally random target with that exact prefix-length relation, advancing the cursor only after its attempt is settled. A separate once-hourly local-position lookup maintains nearby contacts. A bounded idle-contact probe is included in the same maintenance envelope, not triggered recursively by every suggestion. A full 256-bucket cycle can take about 42.7 hours at this one-bucket rate, before interruptions; this is not a ten-minute network convergence claim. Empty and stale buckets/coverage age are reported.

All suggested addresses pass existing connection-admission rules; a routing reply cannot compel connections to arbitrary private endpoints or administrative services. Per-key placement receipts cannot spend resources at another node. Table allocation, metered serving, storage leases, refresh and withdrawal have separate counted authority. Unknown foreign records never receive protected incident/repair priority. Aggregate index/store/route limits prevent constructing a new unlimited table per key or public identity. Committed publication intents, spending history and counted directory state can survive ordinary restart under local recovery fencing; old running jobs conservatively terminalize, uncertain lease/cursor time origins do not survive as live authority, and a copied stale disk cannot mint a new funding interval.

The layer's additional identity use is operational: authenticate an endpoint/advertiser and bind replacement authority. It does not prioritize political attribution, require human uniqueness, confer truth authority or establish independent failure domains.

## Conditional reachability argument and costs

Fix a finite observation interval and an advertised provider p/key K. Assume:

1. All involved honest routing servers are reachable and their relevant records do not expire or change during the actual traversal.
2. Publisher and reader iterative lookups for each needed cell reach the same stable nearest-16 holder set within their declared budgets. This requires adequate populated routing buckets and communication; mere physical connectivity is insufficient.
3. At least one of the publisher's admitted ad copies and at least one admitted copy of every required ancestor marker remain in those sets. Successful four-copy placement provides redundancy, not a proof of this premise after arbitrary churn.
4. The reader fairly visits the needed canonical child/page positions, queries the needed holders and has enough actual service/budget to reach p's row. Honest servers return complete admitted pages for the exact snapshots; admission overload has not silently removed the target.

At depth zero the reader finds the retained first child marker, if any. Inductively, at each depth it finds the next marker from a queried retaining holder. Depth is at most 32, so finite successful traversal reaches the leaf cell. Complete paging at a retaining holder returns p's signed ad. This proves `ProviderDiscoverable(p,K,r)` under these explicit premises. Ordinary qualified provider FIND and import/application then need their own availability, predicate and budget premises to yield a usable theorem. The proof does not require intermediate routing holders to adopt p's foundation or retain x's native closure.

The hypothesis that all lookups reach the same holder set is not established just by returning CLOSEST_SEEN. Under an idealized well-maintained uniformly distributed honest routing population of M service nodes, each successful prefix-progress step can reduce the remaining key-distance scale, motivating O(log M) routing rounds and O(k log M) routing-table state in the populated region. The fixed 256-bit namespace bounds the actual table; churn, sparse/incomplete buckets, route poisoning, latency and per-call admission can violate the ideal model. No measured logarithmic latency is asserted.

For a hot key with P uniformly distributed providers and a cell target capacity C=4096, an indicative depth is near `max(0,ceil(log_256(P/C)))`, **not** a maximum-load guarantee: random imbalance and differing holder admissions require deeper cells. At depth d, one completed publisher route uses approximately d ancestor-marker placements plus one leaf placement, each replicated at up to 16 selected holders, in addition to discovering those holders and partial failed attempts. Different providers share markers, but this baseline does not count shared markers as free renewal traffic.

For P=1,000,000, the average at one byte of sharding is about 3906 ads per child, uncomfortably near the 4096 ceiling; some branches can require another byte, and an average alone cannot certify maximum load. This is why a fixed one-byte policy would be a poor completeness assumption. Provider-level catalogs nevertheless avoid multiplying this routing stock by every theorem and native dependency a large provider stores.

At depth zero, 16 selected keys renewed twice per day can require up to `16 * 2 * (64 + 16) = 2560` service operations when each cell lookup spends its full 64-call envelope and placement tries 16 holders. At deeper levels, parent links and failed shallower placements add real work; the 32768-call default can be exhausted. Its roughly 0.38 operations/second daily average is not a latency or concurrency guarantee. Publish-to-discover latency, per-route control bytes and capacity utilization must be measured against realistic libraries and network diversity before calling the selected default adequate.

## Failure distinctions and qualification cases

- Connected clustered honest topology: compare the strict counterexecution above with ROUTE1 after a documented bootstrap/bucket-population phase. Count successful unfamiliar-provider discoveries, not just terminated RPCs.
- Brand-new useful theorem under an already advertised key: no new DHT membership should be necessary; a separately funded ordinary public-index query must actually return it within a declared scope/latency.
- New formal subject or foundation: coarse fallback publication must become visibly pending/placed; old keys cannot silently claim cross-foundation coverage.
- Broad hot key: force a cell over 4096 providers, check deep placement and ancestor-marker visibility; measure the additional calls and partial-publication rate.
- One routing replica refuses or disappears: discover through surviving properly placed replicas when the progress assumptions hold; never label four keys four independent organizations.
- Marker/ad lease expires during traversal: return snapshot/lease nondecision or a fresh scoped lookup, not a proof of global absence. Old cursors do not create renewal authority.
- A route needs more than its 64-call occurrence horizon: repeated PARTIAL route lookup can stall despite persisted catalogue-page/DFS cursors. Record routing-horizon failure separately; the progress proposition assumes the relevant holder sets are reached within actual route budgets and does not prove that restarting a too-short route eventually repairs it.
- Producer crash between child placement and parent publication: remain PARTIAL until new funded continuation installs the missing path or the ad expires.
- Provider withdraws public service after advertisement: routing may return a stale signed lead, but native public reads decline under their current disclosure guards.
- Wrong structural keys or valid-but-useless floods: bounded retrieval/selection waste, not accepted mathematics. Measure false-lead ratio and displacement of useful candidates.
- Sybil-rich nearest holders or bootstrap eclipse: discovery can fail while native truth remains protected. This draft makes no permissionless fair-access or eclipse-resistance theorem.
- Catalogue growth outpaces polling: disclose staleness and missed contributions; bounded successful routing calls alone do not demonstrate reciprocal accumulation.

The goal-fitness metrics are time from public local contribution to discovery by an initially unfamiliar relevant agent; fraction of a declared useful-query pool obtaining a provider, candidate and checked application; metadata/checking cost per successful unfamiliar reuse; publication backlog/expiry; placement diversity observations; hot-key depth and load; and failures separated by routing, candidate recall, service admission, native checking and retention. All denominators/scopes must be recorded. Exponential accumulation is not inferred from announcement counts.

## Existing systems: source-checked reuse and differences

Source inspection was performed on 2026-09-20; no software from these projects was run.

The [libp2p Kademlia specification at commit 78e75c6f4e5dd9de4bc1524c686c0f45df4b461a](https://github.com/libp2p/specs/blob/78e75c6f4e5dd9de4bc1524c686c0f45df4b461a/kad-dht/README.md) selects SHA-256/XOR distance, per-prefix routing buckets, iterative lookup, client/server roles, provider publication at nearby peers, and expiring/republished provider records. Its cited defaults include k=20, lookup concurrency 10, IPFS provider republish at 22 hours and expiry at 48 hours. These are source-spec settings, not measurements or this project's chosen constants. ROUTE1 takes the iterative rendezvous and lease idea, while explicitly adapting its calls to our local admission model, four-call concurrency, typed mathematical keys and counted hot-key catalog traversal. Its truth boundary remains native checking, not DHT validation or a quorum of replies.

The [IPNI specification at commit 1297da07cf3cd77d3b0fcfc1c3e5ac527e7ab4e6](https://github.com/ipni/specs/blob/1297da07cf3cd77d3b0fcfc1c3e5ac527e7ab4e6/IPNI.md) separates providers, publishers, indexers and retrieval clients. Immutable signed advertisement chains describe changes; announcements are transient notifications; indexers ingest and periodically poll; exact content queries return provider records. Its source specifies bounded entry chunks and offers both gossip and direct HTTP announcement paths. That separation demonstrates a concrete way to avoid requiring every discoverer to store all advertised payloads. ROUTE1 borrows the distinction between metadata dissemination and data/native retention, **not** a global ingest topic, recursive unbudgeted chain sync, a trusted indexer, or IPNI's codec-insensitive multihash identity. Our native typed ContentID distinctions remain intact.

Neither source establishes our formal-key relevance, exact native adapter correctness, end-to-end useful-growth rate, or resistance to arbitrarily many malicious identities. Their mechanisms are engineering precedents to qualify, not outsourced proofs of this project's goals.
