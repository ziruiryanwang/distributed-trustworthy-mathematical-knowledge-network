## Foundation identity is not a rule-code label

The integration correctly distinguishes three changes:

- Selecting a different actual seed, export list or reserved-name table changes the corresponding commitments and therefore FoundationID.
- Adding data already expressible by the selected name-local SeedProfile and exact ReservedNames grammars does not by itself require a different NativeRules code. PI1/HEIGHT1 remain code 4.
- Changing the native interpretation, a reference grammar or encoded payload shape requires the explicit rule/schema boundary specified in BOOT1. The unchanged code is not permission to alter those meanings silently.

In particular, the integrated note does not preserve an old FoundationID while adding the five kernel-sensitive roots. It also does not present any final seed/image digest as an already derived artifact. The reviewed revision uses “new selected candidate” semantics, not an in-place mutation of a frozen foundation.

The name-local seed construction resolves the apparent hash cycle: its exact theorem/opaque values are part of the seed, before F-bound ordinary PI1 objects exist. A seed theorem is not a freely replaceable ordinary ProofInstance in B. Thus REDUCE1's local alternate-B procedure cannot silently change a seed proof. Replacing fixed seed evidence would instead change the seed commitment and foundation, with corresponding qualification obligations.

The exact-name barrier remains substantive. `outParam`, `semiOutParam`, `optParam`, `autoParam` and `eagerReduce` are not all treated as disposable frontend metadata; `autoParam` carries its full logical Syntax support. Neither exporting inert logical syntax data nor retaining source bodies authorizes tactics, plugins or native evaluation. `Lean.reduceBool`/`Lean.reduceNat` are forbidden independently of the exact three-axiom whitelist. An unfamiliar compiler-oracle axiom cannot pass merely because it avoids those two names.

The literal-aware bootstrap gate and exact Eq binder information remain visible. The stronger string-support gate may leave a residual cycle. The specification correctly reports this as an unqualified candidate rather than a completed bootstrap or permission to insert provisional axioms. Installed seed axioms also are not automatically charged to every result: per-export actual logical support is separately derived.

## Shared coverage is local bookkeeping, not a wire extension

V5 preserves the frozen routing row key/ownership rule: one provider/key row at a particular cell has one exact group owner. It does not give multiple scopes ownership of the same physical row. The new `SharedFeatureCover` predicate concerns a finite local observed target collection; a borrowed individual scope remains PARTIAL under the inherited FULL_FEATURE predicate.

The provider-level discovery argument has the correct scope. A valid token ad routes to the provider's indexed collection, not only its anchor theorem. The actual FIND postings must contain each borrowed target, and the provider's native/public eligibility and reader progress premises still apply. A foreign row receipt does not prove whole-network liveness, actual continued custody, candidate relevance or successful checked application.

The owner scope's anchor must remain eligible inside that exact scope. An unrelated external target cannot renew the group. The integration also handles the otherwise ambiguous transition case: during sequential old/new holder migration, actual rows can temporarily have different owner scopes. Their exact old/new owners are recorded separately from the intended next owner, and aggregate status is TRANSFERRING/PARTIAL rather than settled single-owner coverage. This conservative status does not assert a physical outage if remaining rows still serve queries.

At each holder the existing removal/insertion fences remain binding; no atomic cross-group move is invented. Old groups, retained anchors, snapshots and unresolved operations remain charged until their actual release/reclamation. No new wire opcode, remote group mode, scopeID interpretation or mathematical authority is introduced.

The selected detailed resource note explicitly supplies larger local envelopes: 4096 targets and 131072 emitted tokens per immutable scope, with 64 charged scope records in total, replacing the old 128/4096/four-scope local limits. This is not an implicit unlimited-library reinterpretation. The separate 33000 owned-token capacity can fail the general maximum-union case, and all record states share the actual metadata budget. Size-tiered amortization remains an insertion-history claim, not a per-day or per-contribution latency guarantee.
