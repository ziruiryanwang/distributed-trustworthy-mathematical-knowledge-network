## Exact purpose and non-goals

Determine whether the new recovery-capable product cut can safely unblock a
genuine interrupted peer acquisition using its original supervisor receipt,
reject an equal-request later-attempt receipt, preserve consumed resources and
partial files, replay exact terminal bytes, and subsequently acquire the real
package under a new request ID.

One fresh receiver builds local support and performs its normal bootstrap. The
fixture is an already-published immutable one-entry view from successful G02;
there is no second producer build, new source contribution, native admission,
invented pending row or fabricated successful receipt. Sender acceptance is not
trusted by the receiver: its ordinary acquisition still performs the unchanged
transport/canonical validation and yields only an untrusted local candidate.

Power loss, nonempty SQLite journals, native-stage recovery, source migration,
quota renewal, broad invalid-input controls and output-loss-after-commit cases
are explicitly outside this allocation. A missing positive premise produces a
retained `STOPPED_NOT_QUALIFIED`, not state fabrication or automatic retry.

## Bounded genuine fault sender

The sender is a trusted cooperative standard-library thread in the coordinator,
not an independent OS process or sandbox. Its CPU is already included in the
coordinator process CPU. It binds literal `127.0.0.1:43173`, accepts at most
three connections and charges at most 4 MiB output. The whole sender session is
90 seconds, socket reads/writes have two-second timeouts, headers are capped at
8 KiB, and there is no automatic restart or alternate port.

The accepted requests must be exactly: catalog, selected bundle, selected
bundle. Readiness is a local thread event, not an extra connection. The second
connection sends the correct full HTTP `Content-Length` and all but the final
64 genuine body bytes, then one further genuine byte every 0.25 seconds. This
maintains progress inside the client's five-second idle timeout while taking
longer than the outer ten-second deadline and remaining below its thirty-second
transfer deadline. Actual body progress, partial byte count and client
disconnection must be observed. A different failure, ordinary terminal timeout,
late setup or prematurely completed body does not qualify interruption.

The third connection sends the original complete bundle promptly. Retry and
recovery/replay checks must leave the connection count exactly two until that
fresh acquisition. At the end the actual listener and connections must be
closed and the actual thread joined; three expected connections with no sender
error are required. On failure the coordinator requests stop, shuts down/closes
its selected sockets, and attempts a five-second thread join. A failed join is
retained uncertainty, never a successful cleanup observation.

## Ledger and retained-file observations

All product mutation occurs through the installed public interfaces or the one
unchanged supervised ordinary call. The test never imports the checker, recovery
worker or control store in-process. It imports only the separately pinned
installed runner/supervisor for the intentional deadline call, plus the pinned
test file helpers. Standard-library SQLite is used solely for bounded read-only
snapshots after real worker process trees have been observed quiescent.

Snapshots require no nonempty journal/WAL/SHM sidecar, SQLite 3.50.4, a read-only
immutable connection, query-only mode, 100,000 VM steps, at most 8,192 rows per
known table and at most 4 MiB serialized data. Fixed queries read the eight
existing ledger tables. BLOB bytes are retained as exact hex, not decoded or
rewritten. The no-concurrent-owner-writer premise matters: read-only snapshots
are observations, not an OS isolation boundary or acceptance authority.
The 4 MiB check bounds the resulting serialization, not peak transient Python
allocation; this fresh tiny trusted-state test has no separate snapshot heap cap.

After interruption, exact table comparison must show only the expected new
pending request, its real original-attempt marker and the normal request/byte
charges, with the original active key. Existing stages, heads, candidates,
providers and unrelated rows must match. No native stage belongs to the
interrupted request. The selected partial work directory must actually exist
and contain files. Its full bounded byte/hash census is captured.

The ordinary pending retry and wrong-receipt recovery must leave the entire
observed ledger unchanged. Correct recovery may change only that request's
terminal phase/response and clear its active slot; exact counters and all other
rows remain. Both forms of replay must leave the ledger unchanged. Fresh
acquisition may consume its new allowance and create a normal candidate entry,
but must leave the head/stages unchanged. Successful terminal recovery must
return the original successful bytes and change no row. The interrupted work
directory's final census must exactly match its earlier census: no partial file
is deleted or rewritten to make recovery appear clean.

Snapshot serialization and expected-state comparison create only test evidence,
never rows in the actual control database. Artificial fixtures can later test
negative guards but are not used for this positive recovery discriminator.

## Resource and result limits

The aggregate allocation is 1,800 active wall seconds and 1,800 observed CPU
seconds, enforced cooperatively at checkpoints, not by an extra outer OS Job.
Direct CLIs have bounded captured stdout/stderr and 500 seconds for build/init;
other selected CLIs are bounded to 150 seconds. Product public/recovery Jobs
retain their own smaller CPU/memory/time/process grants. Cleanup settlement and
final record handling are not hard instantaneous deadlines.

Observed CPU counts coordinator/sender process CPU plus each authenticated
unique support-build/public/recovery Job once. Nested bootstrap Job CPU is
already included in its public worker Job and is not counted again. Actual
failed original Job CPU is included after its cleanup/request binding. Direct
CLI wrapper work and unbound final receipts remain unmetered: no complete total
CPU claim is made. The final data/evidence census is capped at 1 GiB including
the copied fixture and final records, excluding the shared runtime and original
published fixture tree. There is no hard transient disk quota.

Completion is only
`GENUINE_TRANSFER_RECOVERY_SEQUENCE_COMPLETED_AWAITING_INDEPENDENT_AUDIT`.
It is not a claim of general crash recovery, native admission, new mathematics,
permanent availability, quota renewal, independent hosts or overall operability.
All broader controls remain separate allocations. Any unexpected result stops
and retains its actual state/evidence without repair or a replacement attempt.
