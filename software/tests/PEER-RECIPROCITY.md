# Next decisive product qualification: reciprocal offline use

Prospective discriminator, not an executed result or an automatic allocation.
The central question is whether actual installed nodes can contribute to each
other without trusting another node's acceptance and without retaining a live
dependency on its service. Preparatory compilation/bootstrap alone is partial.

## Population and trust boundary

Alpha and Beta have distinct installed source/asset copies, independently built
support, fresh databases, state and scratch. The first same-host test deliberately
shares one explicitly configured immutable Lean distribution and Python runtime.
It tests installation/path and node-state separation, not separate machine
administration or independent runtime failures. No old experiment's prepared
database, `.olean` or theorem offer is an input.

Two local agent authors choose their own mathematics from actual public formal
information. There is no shared unsolved-task list or system-defined intended
question. The test coordinator may ask for a composable result and audit actual
dependency use, but cannot supply private proof steps, patch captured proofs,
insert registry rows or authenticate a success on the node's behalf.

## Positive dependency sequence

1. Prepare: build/configure/initialize both installations through ordinary
   commands. Each initial P1 catalog is empty. Each local bootstrap is freshly
   checked, despite the common foundation bytes.
2. Alpha's author reads only its API and actual public descriptions, requests
   ordinary body inspection if needed, and returns a source contribution G.
   Alpha's normal submit/publish/expose path creates a committed view.
3. Beta knows only its configured alias. `peer_find` returns G's previously
   unknown identity; `peer_acquire` derives its local offer from transferred
   canonical bytes. No receiving head or native-stage count changes yet.
4. Stop and reap Alpha's service. Beta performs fresh local admission, uses
   its own public inspection API if needed, and independently authors H that
   substantively uses G. Its ordinary submit/publish/expose creates another view.
5. Alpha discovers and acquires H from Beta's service. Stop and reap Beta's
   service before Alpha's fresh local admission of H.
6. Audit the exact bound source captures, canonical dependencies and native
   outputs. G and H must have distinct selected identities. A citation, unused
   let-binding, copied response, redundant dependency closure or identity-only
   republication does not demonstrate the intended reciprocal-use observation.

The current pipeline expects two bootstrap stages plus Alpha/Beta submissions
and Beta/Alpha admissions: six mathematical stage allocations in all. A
submission stage contains five serial pipeline commands, not one kernel call.
The two installation builds are separate build allocations. A concrete launch
must bind actual code/input pins, stage/call/resource limits and the public
authoring handoff; this note does not authorize opportunistic retries.

## Required controls and their discriminating layer

| Control | Observation required |
| --- | --- |
| Wrong client or unknown alias | Exact local refusal before connecting; no entry/head promotion. |
| Coherently false advertised metadata | Transport can pass its shallow checks, but full type-sensitive local metadata comparison refuses; no candidate is registered. |
| Changed selected bundle bytes | Transport digest or independent canonical ID gate rejects at the specified layer; no candidate or receiving acceptance. |
| Acquired-only candidate exposure | `NOT_LOCALLY_PUBLISHED`; native admission alone does not grant exposure authority. |
| Exact request replay with sender stopped | Original terminal bytes return without network or new accounting/stage work. |
| New-request duplicate acquisition | New allowance may be spent, but the existing offer path/sequence is reused; no duplicate entry or native stage. |
| Unsupported same-descriptor package variant | Explicit conservative refusal; no unproved semantic equivalence or automatic proof election. |
| Private/unexposed service route | Bounded refusal, without opening source/receipts/database or loading the checker. |
| Lost original worker | Actual interruption and original-attempt-bound recovery, separately reviewed; a later retry receipt cannot stand in for original quiescence. |

Negative senders may serve controlled inert malformed/false-metadata fixtures;
these are adversarial wire inputs, not fabricated accepted node state. Never
create a passing native receipt or receiving database row to reach a test case.
Account for legitimate request/refusal/partial-file deltas. An unchanged whole
database is the wrong invariant when failure accounting is deliberately durable.

## What this would and would not establish

Success would establish the selected finite acquire–verify–use–contribute loop
through installed public interfaces, with receiver-local custody and checking
after sender shutdown. It would not establish novel mathematics, usefulness
relative to a library baseline, large-scale retrieval, permanent availability,
independent hosts, malicious local-source isolation or sustained/exponential
growth. Those remain explicit v1 research and qualification work.

A candidate/transport-only pass is not substituted for the full loop. A failed
authoring attempt, unsupported declaration, resource refusal or interrupted
stage remains part of the evidence and cost record; it is not erased by a later
separately allocated repair.
