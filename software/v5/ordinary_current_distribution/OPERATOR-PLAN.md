# Make the current reciprocal workflow usable

Source-only recommendation, 2026-10-28. This plan does not select execution,
change the product, or qualify a release. All work remains local and unpublished.
The assigned edit is this file only; root owns adoption, implementation selection
and execution.

The next useful intervention is a small successor to the offline operator kit.
It should turn explicit user choices and saved public reports into the current
product's existing inputs. The public API can already receive a theory, check a
dependent extension, publish it and receive the return. Its old preparation kit
cannot express that loop. Another scaffolded mathematics episode would not close
this practical gap.

These are interface-tooling gaps, not evidence that the mathematical protocol
requires replacement. There are still substantive product limits: exact-type
search is not semantic equivalence search; rich cold grounding costs resources;
an authoring frontier does not restore arbitrary notation, instances or executable
metadata. Tooling must describe those limits instead of promising to erase them.

## Smallest practical route

Use one selected package, one approved Python/Lean runtime pair, one owner state
and explicit finite budgets. Keep local source approval and all mathematical
decisions with the agent/operator. No mandatory task list, global research agenda,
workflow scheduler or new trust mechanism is needed.

1. Initialize an owner and retain its successful public report. If the chosen
   mathematics needs a library beyond the basis, independently intake an explicit
   inert bundle. Keep that checked library report as an optional authoring ancestor.
2. Ask a local formal question, or choose existing formal feature filters. For a
   formal type, run the shipped `#ordinary_type_query` command in an approved
   local Lean project, then bind its saved type through the selected checked
   context using the current query entry.
3. Find through explicitly selected providers; choose a returned row. Preview
   its type and inspect needed definitions using the existing operations.
4. Receive the exact selected target with explicit closure/network limits. Only
   a successful independent admission supplies the next checked context.
5. Write ordinary Lean source using the acquired interfaces. Prepare a contribution
   with the checked parent, deliberately selected acquired target triples and
   output names. Optionally choose an approved project and checked ancestor to
   avoid reconstructing installed library declarations during authoring.
6. Publish chosen endpoints from the successful contribution. Serve the existing
   custody/index under an explicit finite lease when another agent needs it.
   The next contribution or receive can use that contribution's checked root.

An agent chooses its investigation and writes its source. Short API instructions
should explain when each operation is useful and where the next inputs come from;
the network need not prescribe proof search. Starting with basis-only work is
valid, but must not be presented as support for arbitrary installed libraries.

## Exact successor scope

Create a fresh sibling such as `ordinary_current_operator_kit/`; preserve the
used old kit and all source/evidence bytes. Reuse its strict bounded JSON/path
handling and inert output format. Keep the implementation in a small preparer,
explicit selected-package adapter/map, examples and one walkthrough. Do not add
a persistent registry, run manager or new schema negotiation layer.

**Package selection.** Recognize exactly the current direct auxiliary sources
and generated-role set. Generated native pins can differ between explicitly
approved builds; unknown direct source bytes or role sets must fail. The adapter
checks the externally selected PROFILE and known interface bytes, not native
correctness, publisher identity, local-project safety or installation approval.
Never introduce a permissive unknown-layout fallback.

**Checked contribution reports.** Accept only the successful public owner wrapper
for `operation="contribute"`, selected PROFILE and exact selected owner paths/ID,
without final-budget or closure errors. Require
`result.status="CHECKED_CONTRIBUTION_WITH_DURABLE_PUBLICATION_BYTES"`, an accepted
admission, and equality of `result.local_root` and `result.admission.local_root`.
Validate the actual implementation's accepted admission status and structured
target bounds; the retained successful fixture has `admission.status="CHECKED"`.
Do not treat an unwrapped `contribution/RESULT.json`, successful process exit,
partial accepted state or a source-only report as a completed owner operation.

**Contribution preparation.** Add `contribute` to owner/stateful dispatch. Require
a selected parent report, explicit approval of the local source, source
`{path, sha256}`, structured output names and deliberate acquired-target selections
from successful same-owner receive/contribution reports. Allow `[]` for work that
needs no acquired target. Read source as bounded UTF-8 bytes, not JSON. Prefer a
byte-identical `Body.lean` copy inside the fresh preparation output so the receipt
pins the source actually passed to the product; preserve the existing total output
bound. Limit source to 1 MiB and target/name inputs to 65,536 bytes each, matching
the public owner. Do not derive source paths from reports.

Optional project authoring uses an explicitly selected, hash-bound descriptor
with existing schema and explicit local execution approval. An optional ancestor
report supplies `--authoring-frontier-root` only alongside that descriptor.
Do not forward `--approve-local-project` to `contribute`: that CLI flag belongs to
`produce-baseline`. The preparer's approval choice is local UX, not a new owner
flag. The product alone verifies the ancestor prefix relationship and performs
the mandatory final check against the actual parent. Report consistency does not
prove that an arbitrary target is in that parent or that local/project meanings
agree.

**Publication.** Preserve the producer/intake route and add an explicit alternative:
`accepted_report` plus `target_indices`. A contribution supplies `result.targets`;
a received target supplies the singleton `[result.target]`. Derive the context
from that same accepted report. Copy exact `{name, export_id, unit_id}` tuples;
validate bounds and duplicates. Recompute identity where the report supplies its
semantic identity; do not invent a missing field in receive reports. The product
checks target membership and exact identity against actual owner state on publish.
Do not silently pick targets or substitute a later root.

**Direct intake.** Keep the producer-assisted convenience mode. Add a mutually
exclusive mode with selected parent, explicit local bundle directory and exact
manifest reference. Validate the documented bounded manifest shape and pass the
chosen original path/hash to the owner; do not require a producer report or the
literal basename `manifest.json`. Inert manifests are not acceptance evidence.
No library discovery, batch selection, retained-prefix generation or source
execution happens in this helper. This removes the dependency on bespoke
research selectors without promising automatic library capture.

**Query handoff.** Add `prepare-query`, emitted as entry `query` with no positional
operation. Require a pinned native-type JSON, explicit same-owner checked context
report and custody limits. Use existing `--native-type`, `--context-root`, owner
paths and fresh `--output`; `run.py` supplies runtime/profile/allocation flags.
The result has top-level `ok`, `operation="prepare-query"`, `specs`, PROFILE and
context selection, unlike the nested peer/owner report shape. Give it a separate
validator. Let `find` take exactly one of explicit `specs` or a successful selected
query report, copying its bounded `specs`. Do not generate a query after
`UNMAPPED_REFERENCES`, closure uncertainty or a failed final publication.

Document the existing prior step using `OwnerQueryCommand` in approved local
Lean code and selected helper paths. It elaborates a proof-free type. The offline
kit does not run Lean or pretend JSON binding replaces elaboration. Manual binding
mode can remain documented direct CLI usage rather than a second new kit mode.
Context mode can perform normal owner recovery, so the later product call is not
a promise of read-only state access; preparation itself remains state-free.

**Existing optional policy fields.** Add only the current consumers' exact shapes:

- Find: optional `candidate_mode` equal to `atomic-v1` or `sparse-v2`.
- Index: optional `access_pairs`, containing 1–8 sorted distinct atomic-feature
  pairs and explicit row/logical-byte limits. Use identical configuration on
  reopen; adding it is not an automatic old-index migration.
- Receive: optional `acquisition_sources`, `attempt_timeout_ms` and
  `finalization_reserve_ms` as an all-or-none group; 1–8 distinct selected contact
  labels and times 1–60,000 ms. Keep existing closure and aggregate limits.

The existing receive cap already allows 1,024 units; do not enlarge it for the
37-unit fixture. Describe current fair bounded rounds accurately. Incomplete
search, empty results and sparse sequential fallback do not imply global absence,
unbounded recall or a guaranteed faster search. There is no automatic legacy retry.

## Choices and report-to-input transformations

| Operator choice | Public data copied | Next input |
|---|---|---|
| Which existing checked parent to extend | Init basis root, completed intake root, receive admission root or contribution admission root | Exact `parent_root` |
| Which vocabulary defines the question | Deliberately selected checked context plus explicit native type | Query context root; product resolves symbol identities |
| Which formal search to run | Successful query report's `specs`, or explicit feature specs | Find config with chosen contacts and budgets |
| Which candidate to inspect/acquire | Exact `find.result.matches[i]` provider/snapshot/record | Preview or receive `selection` |
| Which acquired results the source uses | Selected accepted `target` or entries of `targets` | Acquired-target triples, with no guessed name-to-ID conversion |
| Which installed library bounds authoring | Explicit checked ancestor report and approved project descriptor | Optional authoring frontier; product checks ancestry |
| Which new results to advertise | Selected accepted contribution targets and its checked root | Publish config |
| Which received result to retain as a provider | Accepted receive target and its checked root | Publish config; existing custody supplies bytes |
| Whether/how long to provide access | Existing index, explicit contacts/TLS, custody disclosure and finite lease | Serve config |

All report references are explicit bounded files with selected SHA-256 values.
They are untrusted convenience data. Never follow paths inside them, infer the
latest root, read protected catalogs/custody during preparation or execute a
report-provided command. Final product validation remains indispensable.

## Validation and completion boundary

Use a small source-reviewed native-free suite. Reuse saved successful and failed
reports as data, copying only bounded public fixtures where needed. Do not reopen
owner stores, repeat grounding, run Lean or start services to test this helper.

1. Positive transition checks: receive to contribution; contribution to next
   parent; contribution/receive to publish; query to find; direct-manifest intake;
   sparse fields and complete multi-source policy. Assert exact produced flags,
   IDs and bytes against existing public consumers, including no query positional
   operation and no contribute-only misuse of `--approve-local-project`.
2. Meaningful refusals: wrong owner/PROFILE, contribution/admission root mismatch,
   failed or unwrapped report, closure/budget errors, absent query references,
   out-of-range/duplicate target choice, partial source-policy fields, unknown
   package layout, changed pinned source/manifest, duplicate JSON and malformed
   paths. Refuse before output creation for validation errors.
3. Preservation checks: no overwrite; reports unchanged; raw source copied
   byte-for-byte; receipt pins generated files; no product imports, subprocess,
   sockets or protected-state access. Partial filesystem failure remains visible.
4. Independently review the exact final compatibility map and generated argument
   shapes. Only root may select a later changed-boundary product call if review
   leaves a concrete unresolved integration question. Existing completed native
   mathematics is not a reason for another full campaign.

The completion claim for this step is an executable input-preparation route and
clear agent/operator instructions for already implemented mathematics. It is not
causal evidence of faster discovery, independent-host deployment, source safety,
worldwide release readiness or completion of v5. The reciprocal theory evidence
supports transferable, extendable mathematics; discovery benefit still requires
the separately planned strong-baseline argument/evidence. Keep those objectives
distinct so operator usability work remains bounded and the next architectural
decision returns to the highest-payoff growth question.
