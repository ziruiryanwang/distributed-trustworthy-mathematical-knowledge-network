# Contribute new work from a project using commons mathematics

This v5 development successor connects two existing operations: export checked
commons mathematics as a normal Lean module, then use that module in a new
project contribution. The one-helper package overlay, four pure import controls
and actual public new-proof return all pass independent audit. It is not a final
public release or a growth-speedup claim.

The actual project proved `CommonsReturnExample.mapFour`, transporting four
function iterations across a map satisfying a commuting-step hypothesis. Its
proof uses the acquired theorem at two independent universes, preserves exact
parent identities, and introduces no scratch assumptions. The existing receiver
checked and retained the new theorem; the already-paid module was not rebuilt.
The whole run cost 23.30 seconds elapsed / 10.95 known inclusive CPU seconds,
with all 16 selected earlier artifacts preserved. The result is local return
interoperability, not publication to a peer or evidence of net useful growth.

## Workflow

1. Obtain and independently accept the selected mathematics in your local owner.
2. If your approved ordinary Lean project does not already provide it, use
   [export-module](../ordinary_module_package/README.md) to create a local
   proof-bearing module. Retain its manifest and all five artifact parts.
3. Write new declarations in the project environment using the exported names.
4. Use the existing `owner.py contribute` command with explicit acquired targets,
   parent root, output names, and a pinned trusted-project configuration.

The source body is your new work, not a copy of the imported theorem. Imported
theorems cannot be selected as newly authored current-module outputs. The adapter
exports the new proof as inert evidence; the independent receiver still checks
it against the exact locally warranted parent. Importing a compiled module does
not by itself admit any mathematics to the commons.

## Direct bridge imports

The earlier project adapter refused every generated bridge name because each
is 75 characters long. This successor admits exactly `DMKNBridge_` followed by
64 lowercase hexadecimal characters **for imports only**. Other module-name
limits, output names, paths, field counts and checking rules are unchanged.
The spelling is not a content-authentication or trust check.

Supply this shape with absolute owner-approved paths and the literal module name
returned by your export (the placeholder below is not a valid configuration):

```json
{
  "schema": "DMKN_ORDINARY_TRUSTED_PROJECT_AUTHORING_V1",
  "module_name": "NewWork.Contribution",
  "project_cwd": "E:/MyLeanProject",
  "project_search_paths": ["E:/MyCommonsExport/modules"],
  "imports": [
    {"module": "DMKNBridge_<64-lowercase-hex-from-export>", "meta": false}
  ]
}
```

Add `--project-authoring <absolute-config.json>` and
`--project-authoring-sha256 <exact-SHA-256>` to the ordinary contribution command.
See the [project adapter](../ordinary_project_package/README.md) for all existing
arguments and trust boundaries. Use the export's exact supported Lean runtime;
do not switch toolchains merely because their printed versions look similar.
The command does not rewrite your project, run Lake, fetch dependencies or
create a new owner. Keep contribution output outside protected input/state paths.

## Cost and safety

Reuse an already needed export. Creating a full proof-bearing bridge solely for
one contribution can cost more than the original scratch-authoring route. The
first export still checks its selected proof closure; this change neither removes
that cost nor introduces certificates or peer-binary trust.

Project code, macros and plugins execute with owner approval. Windows process
budgets are not a hostile-code sandbox. Acquire inert peer evidence through
independent checking; do not execute downloaded project configurations or modules
as a substitute. A generated import name grants no permission to load peer code.
