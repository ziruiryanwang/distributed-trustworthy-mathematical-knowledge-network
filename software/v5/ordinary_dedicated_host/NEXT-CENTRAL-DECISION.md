# Next change: continue checked work across auxiliary package updates

2026-10-28. Source-based recommendation to root; no implementation, execution,
state access or package adoption is selected by this note.

**Let the existing offline kit extract mathematical selections from explicitly
selected prior-package reports.** Treat them only as untrusted convenience inputs;
preserve their original PROFILE and leave the current product authoritative.
Keep the current strict mode as the default. This is a small continuation
improvement, not a compatibility certificate or a claim of faster research.

## Why this comes next

The recent observation investigation produced an extendable theory from ordinary
Lean source, followed by independent checking and return. It did not use the
optional index. That supports concept/theory development and transfer; it does
not establish an index advantage, autonomous novelty or net growth acceleration.
The dedicated-host work now addresses a different real role: serving retained
mathematics without becoming a mathematical owner. Its local outcome does not
change the growth inference.

There is a directly evidenced usability obstruction in the current continuation
path. `ordinary_current_distribution/ADOPTION.md`, under “Preserve compatibility
with existing work,” tells users to retain the earlier package for its reports.
Even exporter PE timestamps changed one package PROFILE while its executable
code and receiver stayed the same. Query and host helpers also change PROFILE.

The current kit's `accepted_report` requires exact current PROFILE at
`operator/prepare.py:309`. Its `contribute` branch derives both the parent root
and acquired targets only through such reports. `receive`, `intake-baseline` and
exact-type query preparation similarly require a parent report. Consequently a
user's established work cannot naturally flow through the new helper merely
because an auxiliary tool improved. The low-level commands can select the same
mathematics directly; this is a frontend obstruction, not lost mathematical state.
The already implemented symbol-query route accepts an explicit `context_root`,
providing a narrow precedent for the repair.

## One bounded software change

Add one optional input policy to a fresh successor of the kit, for example
`selection_report_policy: "prior-profile-extract-only-v1"`. Absence retains today's
strict current-PROFILE rule. Allow it only on actions consuming parent/acquired/
frontier selection reports: contribute, receive, intake-baseline and query
preparation. It must not relax find, preview, publication or producer reports.

With explicit selection-only policy, preserve the pinned input hash, existing
operation/result schema, success/cleanup shape, exact selected-state path/store
binding, name/target limits and duplicate checks. Require each original PROFILE
to be a well-formed exact identity, but do not require it to equal today's PROFILE.
Extract only the existing root or selected `{name, export_id, unit_id}` rows.
Do not reinterpret any old execution as having run under the new package.

Retain each source report's pin, original PROFILE and extracted root/target rows
in the preparation receipt, together with a clear selection-only classification.
The helper must not claim that state exists, mathematics was accepted by today's
product, or package compatibility was established. Current input-size limits
bound these records. Keep all other report helpers strict; route this one policy
only through the existing accepted-state selection parser, with an explicit
scope check at each caller. Do not modify native code, database or trust rules.

A concrete workflow is: retain the existing owner and prior reports; select a
new package; set the extraction-only policy; develop a new Lean module; prepare
and run the normal contribution using the same parent/acquired report references;
publish its newly generated current-package result. No long identity needs to be
copied manually. A package with an incompatible mathematical implementation still
refuses the existing owner. Reports from relocated/different selected state still
refuse: this is auxiliary-update continuation, not state migration.

This fixes accepted-state continuation in the current receive/develop/return
loop. Arbitrary old schemas, old-publication rewrapping, automatic discovery of
“latest” state and any source-profile equivalence claim are outside this change.

## Why extraction preserves the current trust boundary

The helper is already inert. The product, not its input report, is mathematical
authority. In the current selected backend:

- `owner.py:460-464` checks the actual owner's adoption/store/implementation
  binding before opening it.
- `ordinary_demand_frontier/ordinary_contribution.py:432` retrieves the selected
  parent from that owner's catalog. An optional frontier must be a same-owner
  compatible prefix (`437-442`).
- `_acquired` checks export identity against semantic ID, unit and name
  (`162-178`); `request_targets` checks each selected name/identity against the
  actual parent binding map (`197-207`).
- Evidence reads check locators, exact units and declarations (`462-480`).
  New units still undergo existing preflight and admission (`593-602`).

Thus the proposed change supplies existing requests, not new warrants. Beyond
exact root/name/unit/export selection, the product requires its installation,
actual owner/store/implementation, custody, evidence and ordinary admission checks.
These cannot be replaced by the old report's claims. A missing root, target absent
from the root, or mismatched unit cannot become accepted through extraction.
Trace unchanged enforcement for each exposed action before implementation; do not
infer every operation's safety solely from the contribution argument above.

## Payoff and alternatives

An equally capable Lean/library baseline can continue its retained work after an
unrelated command-line helper changes. It does not require old machine-readable
success wrappers to recreate an import. Removing our extra obstacle is warranted
without claiming that the commons thereby outperforms that baseline.

The cost is a small input-policy extension and documentation. The benefit is avoiding
package pinball, hand-written low-level invocations and pressure to repeat checked
work after auxiliary upgrades. It does not reduce proof complexity or global
index work. Remaining verbose configuration is real, but a wizard or new mutable
workspace registry would add policy and state before this simpler gap is closed.

An explicit `parent_root`/`acquired_targets` alternative would also preserve the
backend trust boundary, and the symbol-query frontend already supports an exact
root. It is less useful here: it adds several input alternatives and makes users
manually copy precisely the selections already present in their retained report.
Extraction is preferable provided it retains the strict state checks, is clearly
opted into, and cannot leak into report uses with a different authority boundary.

Do not select another ranker, certificate strategy or core semantic change now:
the recent episode supplies no failing relevance case or checking-cost evidence
that would discriminate those alternatives. The host reservation/lease failures
deserve accurate budget guidance; they do not yet justify a new service protocol.
The unresolved scientific question remains when affordable unknown-library
discovery and transfer outperform an equally optimized local library, including
failed search and service costs. This change does not answer it or lower that bar.

## Smallest decision-changing work and stop condition

Implement only the inert selection policy, document one before/after
continuation request, and review unchanged product enforcement. Focused native-free
controls should check unchanged emitted roots/rows, retained source PROFILE/pins,
default prior-PROFILE refusal, explicit extraction success, malformed identities,
state mismatch, rejected wrong operation/result shape, duplicate/conflicting
targets, project/frontier requirements, and retained-input integrity. Verify the
policy cannot relax find/preview/publication/producer report rules. A well-shaped
but false report can at most select inputs; only the product establishes whether
those identities belong to the selected owner's mathematical state.

No fresh theorem, grounding, proof replay, service run or efficacy benchmark is
needed to establish this input-boundary repair. Stop once retained reports can
prepare their identical root/target selections under today's package, with truthful
origin disclosure, without modifying old bytes or weakening the product checks.
Then return to an actual unfamiliar-library need rather than manufacture a search
episode. Do not expand this patch into a universal compatibility or migration layer.
