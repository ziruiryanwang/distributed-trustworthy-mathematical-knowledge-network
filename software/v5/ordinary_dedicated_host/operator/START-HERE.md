# Prepare a checked mathematical exchange

This advisory-query successor prepares inputs for its selected Windows ordinary-library package. It
does not run the product, search, compile Lean, check mathematics or open an owner
database. Use the approved Python 3.14.6 and Lean 4.34.0 runtimes. The selected
package and its PROFILE hash are explicit arguments, not defaults in this kit.
Source/control review and actual test disposition are recorded in the parent
advisory-query directory. Predecessor test results do not qualify these changes.

The practical loop is: initialize, optionally ground a library, search, inspect,
receive, write and check a contribution, publish, and continue from its checked
root. You choose the mathematics. This helper removes copying exact identities
and command flags by hand; it does not choose an investigation.

## Select and prepare one operation

Copy one entry under `requests` in [examples.json](examples.json) into a fresh
request file. Fill required nulls with explicit values. Null TLS/CA fields in
loopback examples are intentional. Approvals start false; select true only for
local source/project execution you approve. These are request choices, not a
request to obtain another confirmation for previously approved work.

Save UTF-8 JSON without a BOM. PowerShell 5's default text encoding is unsuitable.
For a request assembled as a PowerShell object, a fresh-file write is:

```powershell
$kitRequestFile = 'C:\commons-work\request-01.json'
if (Test-Path -LiteralPath $kitRequestFile) { throw 'Choose a fresh filename.' }
[IO.File]::WriteAllText($kitRequestFile, ($kitRequest | ConvertTo-Json -Depth 64), [Text.UTF8Encoding]::new($false))
```

Choose an approved package and use its externally approved PROFILE SHA-256.
Hash agreement selects bytes; it does not authenticate a publisher or establish
that installation/native support is safe. Replace these illustrative paths and
the hash before running:

```powershell
& 'C:\tools\Python314\python.exe' -I -S -B `
  'C:\commons\operator-kit\prepare_selected.py' `
  --package 'C:\commons\package' --profile-sha256 APPROVED_PROFILE_SHA256 `
  --request 'C:\commons-work\request-01.json' `
  --output 'C:\commons-work\prepared-01'
```

The adapter recognizes the exact current 46 direct source roles and 72 generated
roles. A separately approved build may have different generated bytes and PROFILE;
unrecognized direct sources/roles are refused. It does not load product code or
verify native artifacts. Do not bypass refusal by editing pins or using the
preparer directly. Its `PROFILE=None` is deliberate until selected by the adapter.
Saved reports must match that exact PROFILE. Even a rebuild with the same
mathematical implementation can have a different PROFILE: use the earlier
explicitly approved package for its earlier reports, or obtain reports from
selected operations under the new package. Never edit reports to relabel them.
The new `prepare-symbol-query` action also permits an explicitly selected
`context_root` instead of a parent report, as the existing query CLI does.
The product validates that root's recorded metadata in the actual owner; the helper checks only its
identity syntax. This option does not relax other actions' report/PROFILE rules.

Use absolute ordinary local paths. The preparation directory must be fresh, have
an existing parent, and be separate from the kit/package, inputs, owner state,
project directories and operation outputs. The helper writes only that directory.
No overwrite, automatic retry, cleanup, service renewal or recovery is performed.
Preserve partial output after an operating-system failure.

Success produces `arguments.json`, `RECEIPT.json` and the selected input files.
The receipt pins their exact bytes and all selected source/report inputs. Source
and native-type files are copied byte-for-byte. Review the arguments and files
before launch. Keep them unchanged until the product reads them.

## Run the prepared operation

The package's existing bounded launcher executes exactly one operation. Its
`LAUNCHER.md` defines resource limits, recovery rules and supported flags.

```powershell
$kitPython = 'C:\tools\Python314\python.exe'
$kitPackage = 'C:\commons\package'
$kitPrepared = 'C:\commons-work\prepared-01'
$kitCall = Get-Content -Raw -LiteralPath "$kitPrepared\arguments.json" | ConvertFrom-Json
$kitTokens = [string[]]$kitCall.arguments
& $kitPython -I -S -B "$kitPackage\run.py" `
  --profile-sha256 $kitCall.profile_sha256 `
  --python-runtime 'C:\tools\Python314' --lean-runtime 'C:\tools\lean-4.34.0-windows' `
  --diagnostics 'C:\commons-work\diagnostics-01' `
  --wall-seconds 180 --cpu-seconds 120 --memory-mib 1280 `
  --active-processes 6 --stdout-bytes 8388608 --stderr-bytes 1048576 `
  $kitCall.entry -- @kitTokens
```

Numbers above are illustrative ceilings, not measured capacity requirements.
Cold library grounding can require a larger deliberately chosen allowance. Service
limits need room for setup, lease and cleanup. A successful launcher exit says
the process completed; read the operation's report to learn whether mathematics
was accepted. Resource containment does not make arbitrary source execution safe.

## Use reports as explicit handoff inputs

Select the actual report file and compute its hash:

```powershell
(Get-FileHash -Algorithm SHA256 -LiteralPath 'C:\commons-work\diagnostics-01\child\stdout.txt').Hash.ToLowerInvariant()
```

Put the path and digest in `{ "path": "...", "sha256": "..." }`. Report hashes
select data; reports do not establish mathematical authority. The product checks
the actual state and targets when it runs. Paths inside a report are never followed.

| Operation | Report to retain | Next use |
|---|---|---|
| Init | Launcher `child/stdout.txt` owner wrapper | Parent for intake, receive, query or contribution |
| Intake | Launcher `child/stdout.txt` completed owner wrapper | Checked parent and optional authoring ancestor |
| Query | Operation `RESULT.json` or complete child stdout | `find.query_report` |
| Find | Peer operation `RESULT.json` | Deliberately chosen `match_index` for preview/receive |
| Preview | Peer operation `RESULT.json` | Inspect a chosen type binding or request authoring offers |
| Receive | Peer operation `RESULT.json` | Checked parent, acquired singleton target, or re-publication |
| Contribute | Launcher `child/stdout.txt` complete owner wrapper | Checked parent, selected acquired targets, or publication |

Do not substitute launcher `RUN.json`, unwrapped contribution `RESULT.json`,
producer metadata, partial stdout or an unrelated installation's report. Init
and intake have no operation output directory; do not add `--output` to them.
Use the complete reports with successful final closure, not just an earlier
accepted-state field inside a failed operation.

## Search and learn unfamiliar mathematics

To find results mentioning a concept you know, use `prepare-symbol-query` with
`symbol_names`, for example `["FiniteMapRefinement.Context"]`. Choose exactly one
of `parent_report` (successful, same owner and PROFILE) or `context_root` (explicit
64-hex recorded-context selection). This action's `state` contains exactly
`catalog` and `store_id`; omit `custody` and `custody_limits`, which are rejected.
A fresh operation output is required. Other stateful actions still require their
existing custody selection and limits. No theorem name, complete target type, symbol hash,
Lean query source or native elaboration is needed.

There are one to eight names, with conjunction semantics: results must mention
every selected symbol in their visible types. Shorthand is deliberately limited
to fully qualified dotted ASCII components: an identifier beginning with a letter
or underscore and continuing with letters/digits/underscore/apostrophe, or an
all-digit component. Digits remain string components (`"A.12"` is not a guessed
numeric Lean name). Empty components, whitespace, escape/quoted forms, backticks,
`_root_` and open-namespace/alias resolution are unsupported. Instead of
`symbol_names`, `structured_names` accepts exact names in the existing array
format, including actual numeric components. Do not supply both modes. Unknown
names in the selected context produce no usable query output.

Preparation writes canonical `symbol-names.json` and forwards `--symbol-names`
to the existing bounded query entry. Its successful `prepare-symbol-query` report
has `query_kind="symbol-neighborhood"`; copy that report into `find.query_report`
in place of `specs`. The helper checks its kind, profile, context and successful
owner closure, with custody `NOT_OPENED`, snapshot integrity `NOT_CHECKED` and
context readiness `NOT_ASSERTED`. The product supplies the exact recorded-context
symbol IDs while retaining full metadata validation. It does not read retained
proof snapshots for this advisory search or promise that they remain loadable;
actual mathematical use still performs its normal integrity checks. These are
search inputs, not mathematical acceptance or proof that another project's
same printed names have the same meanings. The output does not claim an exact
declared-type key. Optional kind/head restrictions remain explicit existing
feature-query choices; this name mode itself emits only symbol conjunctions.

For a concrete local sequence: choose the recorded root and a familiar fully
qualified name, prepare the symbol query, run its emitted arguments through the
selected launcher, then use the exact successful query report in a separately
prepared `find` request with explicit providers and budgets. Any missing name
prevents the query output. The report's `input_pins` contains only the exact name
input hash; there is no custody-limit input. Old query reports retain their old
PROFILE and closure claims and cannot be relabeled for this successor.

For direct feature search, use the `find` example and choose supported specs:
`type-symbol`, `object-kind`, `declaration-kind` or `declared-type-key`. Printed
Lean names do not determine portable symbol IDs.

For a formal type, first use the shipped helper in approved local Lean code:

```lean
import OwnerQueryCommand
universe u
variable {A : Type u} (f : A -> A)
#ordinary_type_query [u] "C:/commons-work/fresh-type.json" :
  forall x, f (f x) = f x
```

Use the selected package's `authoring/helpers` in the approved local Lean search
path. This is ordinary trusted local elaboration: no proof or theorem name is
required. The kit does not execute this step. Use `prepare-query` with that exact
saved JSON and a selected checked local parent. The existing query entry resolves
its referenced names to symbol identities in that context. Missing names are an
explicit failure; they are not guessed or fetched automatically.

After successful query preparation, replace `specs` in a find request with
`"query_report": {"path": "...", "sha256": "..."}`. Supply exactly one mode.
The kit emits the query entry with no positional operation, as its CLI requires.
The later query operation opens the selected owner and can perform its normal
recovery; offline preparation itself opens no owner state.

Choose a find row, preview its formal type and inspect needed definitions. Search
and preview are not acceptance. Receive the selected target with an explicit
`selected-unit-only` or `bounded-closure` policy. Only its successful independent
admission supplies a checked target. Exact-type lookup is syntactic; an empty or
incomplete search does not establish mathematical absence or global completeness.

## Contribute and publish

The `contribute` request contains:

- `parent_report`: the exact checked context to extend, from this owner/PROFILE.
- `source`: a pinned UTF-8 source-body file, at most 1 MiB, with
  `approve_local_source=true`. It is copied unchanged into prepared `Body.lean`.
- `acquired`: zero to eight report selections, each with `report` and
  `target_indices`. Receive reports expose one target at index 0; contribution
  reports expose their ordered target list. Use `[]` when no acquired target is
  needed. The combined limit is 32 distinct target names.
- `output_names`: one to 32 structured Lean names. For example the name `A.r`
  is `[[0,{"$bytes":[65]}],[0,{"$bytes":[114]}]]`; the outer list contains all
  chosen names. Do not reuse an acquired name as a new output name.
- Your state, custody limits and fresh operation output directory.

Ordinary source can define new concepts and prove consequences using acquired
interfaces. The helper does not prove those consequences or infer which imports
the source should use. The product verifies selected targets against the actual
parent and checks the new declarations before acceptance.

For an installed local library, use `contribute-with-frontier`. Its additional
project descriptor has existing schema:

```json
{
  "schema": "DMKN_ORDINARY_TRUSTED_PROJECT_AUTHORING_V1",
  "module_name": "MyAgent.Contribution",
  "project_cwd": "C:\\my-lean-project",
  "project_search_paths": ["C:\\my-lean-project\\.lake\\build\\lib\\lean"],
  "imports": [{"module": "MyLibrary", "meta": false}]
}
```

Supply its exact path/hash and `approve_local_project=true`; include all approved
local search paths needed by the chosen imports. The descriptor is copied exactly.
Its approval does not approve remote source or authenticate all local dependencies.
Choose `authoring_frontier_report` from a checked ancestor in this owner. The
product verifies its plan is a prefix of the actual parent; it only reconstructs
demanded interfaces above that boundary and still checks the final contribution
against the actual parent. Missing compiled metadata or local meaning mismatches
can fail. No notation, instance or executable-reuse guarantee follows.

To use project authoring without a frontier, omit `authoring_frontier_report`.
To use plain authoring, omit all three project/frontier fields. The approval
boolean is consumed by the helper: it does **not** emit `--approve-local-project`
for contribute. That existing product flag is reserved for produce-baseline.

After success, use `publish-accepted` with the complete contribution wrapper and
selected target indices. The helper derives targets and checked context from the
same report. A successful receive can be re-published using index 0. Publication
checks actual retained bytes and state; it does not accept mathematics anew. The
contribution report can also be the parent of the next contribution or receive.

## Grounding and optional provider policies

For an inert library bundle, `intake-explicit-manifest` takes its explicit local
directory and separately selected manifest path/hash. The manifest need not be
called `manifest.json`; no producer report is required. The product reads the
bundle and independently checks it. The old producer-assisted intake/publication
requests remain available. Producing a bundle from a trusted local project requires
explicit project approval; an inert bundle or manifest alone is never acceptance.

The kit does not automatically discover a library, construct retained-prefix
manifests or capture arbitrary projects. Use the existing public producer/intake
route or a deliberately supplied exact bundle.

Current optional fields are passed only after validation:

- Add `candidate_mode: "sparse-v2"` to find when choosing sparse access;
  `atomic-v1` remains the default. Current search uses fair bounded rounds, but
  bounded work and fair scheduling do not guarantee complete or fast discovery.
- An index may include `access_pairs: {"pairs": [["feature1", "feature2"]],
  "limits": {"max_rows": 4096, "max_logical_bytes": 1048576}}`. Replace feature
  placeholders with exact 64-hex atomic feature IDs. Each pair and the list must
  be sorted and distinct; at most eight pairs. Choose them for a fresh index and
  repeat identical configuration on reopening. This is not an index migration.
- Receive may include all three of `acquisition_sources: ["peer-a", "peer-b"]`,
  `attempt_timeout_ms: 1000`, `finalization_reserve_ms: 3000`. Labels must be
  distinct existing selected contacts, at most eight. Aggregate operation limits
  are unchanged; these example times are not reliability promises.

Serve only an existing index with explicit whole-custody disclosure and a finite
lease. Loopback plaintext is supported; remote contacts require selected TLS.
Do not expose this local unpublished project externally without user direction.

This kit improves operation of the implemented reciprocal library. It is not
evidence of discovery acceleration, security review, independent hosting or
completion of the final deployable v5.
