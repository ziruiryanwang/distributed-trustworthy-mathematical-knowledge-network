# Ordinary complete-closure verification

This optional local owner checks a small complete mathematical dependency DAG
using the adopted native checker. It does not generate or verify a cryptographic
receipt. It is separate from the I/A/mixed acceptance APIs.

For a small DAG, native checking may be cheaper than obtaining a succinct
certificate. It still downloads and checks the complete supplied proof closure,
so it is **not** the ancestry-independent route required for large developments.
The existing finite wire/member limits remain; exceeding them is an unsupported
or resource-incomplete operation, not evidence that the mathematics is false.

## Acceptance argument

The owner submits no assumed claims or certified frontiers. The checker verifies
each local module extension and requires every parent to be an earlier checked
exact journal. By induction, all selected members are valid relative to the
adopted foundation and checker. The graph rules additionally enforce exact
rank, acyclic dependency order and complete support of the selected targets.

The owner binds the actual same-call result to the complete input, selected
targets, adopted executable and exact member commitment. Only a clean, bounded
invocation can create a live `VerifiedNativeMember`. Structural binding alone,
file hashes, saved reports and the aggregate header are not mathematical authority.

## Use

An owner-controlled caller supplies:

- The adopted supervisor manifest, native executable and exact source/runtime
  pins. These are local trusted configuration, not choices made by a peer.
- One original absolute monotonic deadline and finite input/worker/controller
  allowances. A parent operation must reserve this suballocation once.
- Immutable witness bytes in dependency order and exact 184-byte target journals.
- A fresh operation directory disjoint from inputs and installation.

`check(...)` performs one invocation and returns opaque same-owner tokens.
`describe(token)` returns a copy of its bound journal and summary.
`members()` returns the live inventory. `close()` revokes all tokens.
Entered failures revoke the owner; there is no implicit retry or budget renewal.
`report()` is accounting only and cannot restore authority.

The tokens cannot be passed as I/A/mixed handles. Semantic-context and source-
authoring integration are not exposed by this component. Reports and exported
witnesses remain ordinary untrusted data at a new recipient.

## Trust and cost

The local Python owner, installation and operating system are trusted. Windows
Jobs enforce resource supervision; they are not a hostile-code sandbox.
The native checker has the adopted restricted Lean-related mathematical profile,
not an assertion of support for every Lean library.

A verification-component timing is not a full read/use comparison. Both native
and certified routes may reuse already-acquired semantics and legitimate warm
caches. Certificate production, service costs and failures remain relevant to
any complete growth claim. Neither this option nor a receipt guarantees useful
new mathematics or positive economic benefit on every workload.

## Local validation checkpoint (2026-10-20)

Nineteen focused inert boundary controls passed. A real retained three-module
closure then reached the exact requested projection journal through one native
invocation, with zero assumptions and three live members; closing the owner
revoked them. Its enclosing operation used 1.3125 known CPU seconds and
1.5337696 wall seconds. This is not a matched full-workflow comparison.

The first actual input was correctly refused because its prepared base still
carried a zero-image placeholder. The separately recorded successor binds only
that metadata field to the adopted relation and checks all mathematical content
afresh. The failure remains preserved and charged. No production checker or
acceptance rule was changed to obtain the successful result.
