## One small real fixture family: three outcomes, one shared setup

Use a fresh ordinary owner with the existing selected basis. Create only:

- Root F: accepted transparent `Base.c : Nat := Nat.zero`.
- Root P extending F: accepted `Above.d : Nat := Nat.succ Base.c`.

Use core constructors explicitly, avoiding `+`, numerals and extra Std lemmas.
Select F as the authoring frontier, P as the protected contribution parent, and
the exact accepted Above.d target triple. The approved frontend supplies Base.c
but not Above.d; reconstruction must therefore actually use received Above.d.
Produce each required tiny frontend through the existing bounded helper/build
mechanisms, once. Do not borrow the conditional eleven-record kernel fixture as
if it were a complete protected owner, and do not repeat its sixteen controls.

The positive and semantic-negative cases form the paired test; one missing-name
case tests the explicit fail-closed branch. Each uses a fresh output/native
process and its separately fixed finite allowance. Serialize the shared owner.
Both negative cases select original P, not the positive successor root.

Record actual callback/file acquisition for frontier evidence separately from
the protected snapshot plan: **zero Base.c/ancestor portable-evidence fetches**
is the goal, not zero snapshot validation or zero approved runtime import bytes.
Use a pass-through trace/guard on the actual evidence fetch boundary. Count any
target reads, failed work and setup; do not omit them from reported cost.

Check clean outer/native closure, exact selected parent and target bindings,
candidate theorem/proof correspondence, accepted-prefix preservation on refusals,
and unchanged receiver INSTALLATION/implementation identity. These are event
checks for three cases, not a new kernel assurance campaign. Preserve all failed
inputs and outputs. A result false under P being accepted, an ancestor evidence
fetch, or an implicit retry falsifies the proposed boundary.

First finish independent review of the four Python and two Lean successor diffs.
Run the native-free suite only after root selects it. If it passes, root may
select the four-module auxiliary build, exact package overlay and this one fixture
family. Any failure triggers a specific decision, not an automatic rerun. Real
finite-map refinement is later useful workflow evidence, not a substitute for
the deliberately false-under-parent discriminator.

Do not promise the runtime/closure cost from source inspection. The remaining
question is whether this small optional route works cheaply and preserves the
existing final acceptance boundary; public deployability or growth acceleration
does not follow from these controls alone.
