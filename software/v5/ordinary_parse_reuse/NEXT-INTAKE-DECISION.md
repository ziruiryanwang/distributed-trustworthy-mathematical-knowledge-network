# Next strict rich-library intake: conditional proceed, not another parser project

2026-10-26. `practical_library_route`. Source/saved-data decision only. No
experiment, product import, owner opening, selector modification, cap change,
package or Git operation was performed for this note. Root owns all later
selection and actual-outcome adoption.

## Recommendation

**Proceed once with the existing public initialization and three-batch intake
after the focused controls, independent review and fresh file-only package have
actually passed their gates. Hold execution until those concrete prerequisites
and the new package identities are bound.** Keep the existing proposed limits.
Do not preemptively widen parsing reuse into custody/catalog, replace the parser,
add a profiler or run a second synthetic benchmark.

The original 13-pass multiplication was an avoidable known obstacle, addressed
by the selected internal change. Eight passes remain substantial, and successful
completion under the limits is not established. But no remaining deterministic
size/count/refusal is known from this source screen. The next consequential
unknown is real native compatibility and whole-path cost for an authentic rich
closure, not whether the same internal parse can be reused another way. One
finite public outcome has higher expected decision value than a wider speculative
cache interface or another tiny native-free count test.

This is not permission for a run or a prediction that it will pass. A first
finite refusal is a useful discriminant only if its phase, confirmed prefix,
cost and state uncertainty are preserved and determine the next decision.

## What unchanged budgets require

Keep the existing proposed allocations:

| Stage | Public launcher wall / CPU / MiB / processes | Outer wall / CPU / MiB / processes |
|---|---|---|
| Initialize | 90 / 60 / 1280 / 3 | 120 / 90 / 1536 / 4 |
| Three-batch intake | 360 / 300 / 1536 / 3 | 420 / 330 / 1792 / 4 |

Public streams remain 1 MiB each; outer stdout 4 MiB / stderr 1 MiB. Each actual
batch still has `CallLimits(cpu_seconds=60, output_bytes=64MiB)` and the unchanged
native heartbeat/depth bounds. Memory is aggregate Job private commitment, not
an additive grant per process. The whole intake has one deadline; no per-batch
wall renewal. Native allowance reserves 24 wall seconds and one CPU second
from the remaining allocation for cleanup/bookkeeping.

Important correction to the older INTAKE-PLAN wording: `capacity(3)` checks
aggregate grant headroom upfront, but `reserved_cpu` is incremented by 60 in
`operation()` only as each batch is attempted. It is not charged 180 before
the first batch. Reservations are nevertheless nonrefundable; full success
charges 180, while a failed prefix retains the reservations actually made.

Let `C_start` include the public owner's support/opening work before its intake
budget, and `C_ctl` the subsequent whole intake process CPU. The source creates
an integer CPU budget by subtracting startup work and one second from 300.
A full success must therefore satisfy approximately, and strictly under the
actual integer/check arithmetic,

```text
C_ctl + 180 < 300 - C_start - 1.
```

`C_ctl` includes all eight portable passes and controller preparation inside the
batch grants. This conservative reservation accounting intentionally counts
batch controller cost as live parent cost while keeping each full grant reserved.
For every batch, its own controller work plus accounted native CPU must also
fit the separate 60-second grant. Outer 330 CPU does not loosen either condition.

If one models a full-closure reader-equivalent pass by a representative cost
`R` and all other controller work by `O`, the necessary whole-path condition is
`8R + O + C_start + 1 < 120`; hence even the optimistic `O=C_start=0` threshold
is less than 15 CPU seconds per full-closure pass. Actual passes need not cost
identically, so this is a sensitivity model, not a measurement. Each large
batch additionally has five reads, actual storage work and native work sharing
60 seconds. No source argument supplied here proves either inequality holds.

These explicit inequalities explain both why the selected reduction matters
and why pass/fail must be observed honestly. They do not justify automatic cap
increases or a disguised extra experiment. If other source evidence establishes
a deterministic refusal before launch, retain the hold instead of running it.

## Outcome-driven stopping rule

Run no more than the separately selected first initialization and first intake.
Do not add status operations unless retained evidence leaves a material ambiguity.

- A clean completed intake resolves representative grounding and supplies the
  concrete selected base for a later useful ordinary authoring decision. It does
  not prove growth acceleration, all-Std compatibility or final v5 readiness.
- A native semantic/reconstruction refusal identifies a core interoperability
  problem. Preserve its exact first failure and any confirmed prefix.
- A controller/time/memory/output refusal identifies the limiting phase under
  these allocations. Do not infer mathematical invalidity or blame RAM without
  evidence. Choose the next smaller source intervention or a documented operating
  envelope from that outcome; do not automatically enlarge limits or retry.
- Uncertain cleanup/commit state remains uncertain and preserved. No database
  editing, lock removal, rollback claim or hidden continuation is authorized.

The recommendation advances authentic library usability while bounding its cost.
It does not convert a conditional experiment into completion of the user's goal.
