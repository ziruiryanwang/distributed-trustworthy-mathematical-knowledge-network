## Why the intake addresses a real obstruction

`CORE-NEXT-DECISION.md` identifies a recipient who wants unfamiliar finite-map
work without executing its foreign producer's project. Small concept episodes
already show checked creative continuation on prepared bases. They do not show
that realistic dependencies can be independently grounded at acceptable cost.

The retained closure is genuine Std mathematics: 2,651 units and 44,912,843
portable bytes, selected by `Std.HashMap.isEmpty_insert`. Its semantic frontier
has 265 units, so the 32-group no-project reconstruction route is not an adequate
authoring route here. The separate approved-project path avoids reconstructing
that imported frontier without replacing independent checking.

Thus a successful rich intake would close an actual missing premise for this
workflow: a warranted, compatible specialty base on which unfamiliar small
extensions can be checked. It would not itself create a theory, demonstrate warm
use or establish a growth advantage. Treating intake alone as the payoff would
leave the user's creative-development requirement unanswered.

This premise is necessary only for the strict recipient workflow. A user who is
content to approve and use the ordinary package can already do so. That remains
the simpler route when strict independent acquisition is too expensive; no claim
that every ordinary Lean user needs this bootstrap is justified.

## What reusable delta means here

The contribution writes its new unit evidence and previews and returns exact
target rows. Existing direct `peer publish` can index selected rows at the returned
checked root; the reuse workflow already maps `result.targets` and
`result.admission.local_root` to that API. Publication, finite serving and another
owner's acceptance are separate operations, not implicit effects of contribution.

For another owner with an independently grounded compatible rich parent, existing
parent-relative peer receiving can check missing delta units. Do not promise a
cold basis-only recipient the same small delta cost. In particular, the current
selected-export companion closes to the fixed basis and caps the total at 1,024
units: it cannot export the full 2,651-unit ancestor closure just because a new
part is small. A particular contribution might need a smaller subset; the actual
closure, not delta size, decides. Retain the complete restored baseline bundle
for explicit bulk intake; do not select a new export adapter without an actual need.

The immediate capability stops at a locally checked, durable, publishable delta.
An actual receiver/return demonstration is not automatically included. Existing
publication/custody/receiving evidence supports unchanged mechanisms, while the
rich-parent composition remains a distinct unexecuted claim.

## Smallest subsequent evidence and stop rule

After actual rich intake is adopted, a separately selected investigator-led
contribution can test the remaining changed premise once: does approved ordinary
finite-map authoring above that real parent produce a genuinely new checked,
retained extension without reconstructing the large imported frontier? Inspect
the actual dependency bindings and new declaration bodies, not merely success
strings. Retain original source, failures, exact parent/output identities and
whole-operation costs. Keep ordinary contribution limits unchanged: 32 new whole
units, 4 MiB evidence/candidate and 131,072 nodes, among the existing bounds.

Do not commission an invented neighboring-lemma exercise solely to claim growth.
Require an investigator-stated use for the new interface/law before selecting
runtime. If the selected closure cannot support that work, localize the missing
names or limit and compare the approved-package alternative; do not automatically
bootstrap more Std, raise caps or design a new authoring system. If strict intake
itself is impractical, stop that route and state its operating restriction.

Full-cost acquisition and parse-reuse affordability are owned by
`ordinary_std_intake/INTAKE-COST-SCREEN.md` and the separate current cost review;
this note adds no duplicate benchmark or amortization claim. One warm success
would establish the stated capability, not causal discovery acceleration,
universal library compatibility or final-v5 completion. The existing PAgE design
owns the causal discovery question.
