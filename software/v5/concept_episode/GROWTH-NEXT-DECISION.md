## Decision

**After the small inspect facade, make the existing public operations into one
usable ordinary-project investigator workflow. Do not build another concept
generator, generic inert frontend importer, theory registry or package network.**
The missing product capability is the join between discovering exact mathematics
and continuing it in a usable local authoring environment. Native Lean already
supplies the creative language and frontend; our network should not replace them.

For an already available, explicitly approved native project, the existing SDK
operations suffice in principle. Their exact target rows permit the comparison
below. **No evidence establishes manual ID comparison as a costly bottleneck;
do not implement another wrapper now.** Document the precise composition without
a new mathematical format or native checker. Do not rerun A/B to prove that the
same production and intake primitives still work.

There is a separate unresolved capability: a discovered theorem does **not**
currently locate its ordinary source package. Do not pretend documentation closes
that gap. Initially use independently obtained ordinary repository/package hints;
automatic source resolution is optional future work, not an authority for truth.
An automated theory-to-project resolver would need an explicit new metadata seam;
no such implementation is selected or justified merely by having an idea for it.

## The smallest exact crosswalk

The current ordinary discovery record contains a semantic namespace, ExportID,
preview hash/size/features and an exact unit/name locator. It contains no native
repository revision, module name, source path or project content manifest
(`ordinary_export_adapter.py:194-199`, selected native-src01 package).
The baseline producer returns exact target rows and an inert bundle manifest.
Its `project-selection.json` binds selected paths/modules, explicitly **not** every
transitive binary (`baseline_production.py` module contract and lines 290-321).

Consequently, the following composition is possible without inventing authority:

1. An investigator uses `find`, `preview`, then optional `inspect` to select a
   formal connection. Those steps establish identity-bound information, not truth.
2. The investigator independently selects a compatible ordinary project obtained
   through approved package/repository practices. Record exact revision/dependency
   selection for reproducibility; separately approve its executable environment.
   A peer hint never grants execution approval or makes a package safe.
3. If correspondence to a discovered target is needed, use `produce-baseline`
   on that approved compiled project and the actual selected structured names.
   Compare each resulting `(semantic_id,name,unit_id,export_id)` with the selected
   exact target, using the validated bundle rather than an untrusted status string.
   Missing/mismatched outputs are unresolved or different mathematics, not aliases.
4. Independent `intake-baseline` establishes mathematical acceptance of selected
   inert outputs. Neither production nor exact identity matching does so alone.
   A result warrants only its exact checked closure under the receiver policy.
5. Investigate locally with the approved native project; choose a new definition,
   model, countermodel, generalization or bridge without a supplied endpoint.
   Export and independently check the resulting contribution through the same
   existing route. Publish useful intermediate declarations as well as endpoints.

This does not require pre-adopting every source input in the local accepted store
before beginning exploratory work. The final exported closure still must undergo
the required independent checks; possibly false drafts remain drafts. Conversely,
successful output checking cannot retroactively undo harmful native execution.

Exact correspondence here is narrower than arbitrary project equivalence.
Different proof bodies/representations can produce different identities while
proving equivalent statements. Refusal is correct for an exact-target crosswalk;
establishing a different connection requires actual checked mathematics.
Continued project identity requires unchanged approved artifacts or fresh checks,
not reusing a past report after silently changing the project.

## Why this supports theories rather than a theorem warehouse

A useful handoff should expose ordinary named definitions, assumptions, relevant
models/countermodels and connection theorems. These are selectable Lean declarations,
not mandatory new network object kinds. Exposing only final propositions can hide
the representation or reusable bridge that made the development useful.

Theory revision is branching, not an overwrite of one canonical vocabulary.
Changed laws/definitions obtain new immutable identities; an investigator may
prove implication, equivalence, transport or a counterexample relating versions.
An older useful branch stays usable. No popularity vote merges incompatible
definitions, and no human intention enters mathematical acceptance.

Bridge modules may depend on two independently maintained theories without either
upstream accepting the bridge. Known-symbol discovery can reveal such connections
when both symbols occur in their exposed types. This is a concrete reuse channel,
not a completeness guarantee: implicit/body-only connections can remain invisible,
and very popular symbols still require selective corpus/query strategies.

Models and countermodels are substantive positive knowledge. Nonemptiness can
refute a particular vacuity concern; it is not a universal admission condition.
An abstraction may organize a useful infinite family even when adding its
definitions does not enlarge ideal deductive closure. Its value is the new usable
interface and warranted finite-agent capability, not a larger raw theorem count.

## Follow-up decision: implement an advisory authoring-offer association

2026-10-24, root-requested source/theory challenge. **Yes: this is now central
enough to implement narrowly after inspect.** Indefinitely requiring an externally
supplied project leaves the recommended native authoring route disconnected from
network discovery. That is an actual missing operation, not evidence that manual
ID comparison is expensive. Documentation remains useful but cannot create this
missing information. This supersedes deferral as the next architectural choice;
root must still select/review exact source scope before implementation/runtime.

Use a **separate advisory lookup keyed by `(semantic_id, ExportID)`**, not another
mathematical object kind or a mutation of committed theorem previews. A provider
may return several independently replaceable authoring offers for the same export.
The exact mathematical index and acceptance namespace need not change: query the
advisory route only after selecting an actual export. A provider with no offers
returns empty/unsupported, not a conclusion that no source or mathematics exists.

Minimum offer data: the queried key; HTTPS repository locator; full immutable
commit identifier with its Git object format; normalized repository-relative
project directory; structured Lean module and declaration names; asserted Lean
toolchain. These are **provider claims**, not a content-to-semantics certificate.
Use a digest of canonical offer bytes for deduplication, never as proof that the
repository builds or matches the accepted export. A branch/tag alone is inadequate
to identify a reproducible revision. Dependency resolution can remain incomplete;
do not expose `compatible:true` or imply a commit pins all transitive artifacts.

Minimal operations: (1) an operator selects a bounded immutable local offer map,
optionally authored using existing producer target rows; (2) existing provider
serving exposes a read-only, finite exact-key lookup; (3) a state-free peer client
retrieves those claims under its original aggregate network budget. No new global
registry, network write API, package downloader, custody database or Git hosting
service is required. Reuse existing JSON validation, contact selection, quotas,
reservation/failure accounting and clean shutdown. A bounded sidecar map suffices
for the first implementation; huge-network completeness is not asserted.

Suggested first profile: at most eight offers and 32 KiB per reply, explicit
truncation when the selected provider has more, no retry or referral chasing.
Return the queried key and `UNVERIFIED_AUTHORING_ASSOCIATIONS`; truth, source
availability and usable imports remain unestablished. Require noncredentialed
HTTPS repository locators without userinfo/query/fragment, bounded strings and
normalized relative directories. Never interpolate these values into a shell.
The receiver must explicitly select any later repository access and executable
environment. Source availability checks/downloads are **not** this operation.

Wrong/stale offers do not authorize a premise. Their lookup has the original
finite budget; following them may waste separately approved effort and time.
Exact native-project correspondence still follows the existing production and
validated-target comparison; mathematical acceptance still follows independent
intake. Execution security is a distinct approval/isolation boundary. A source
offer cannot repair that boundary merely by linking a genuinely checked theorem.

Ordinary Git hosting and mirrors remain interchangeable source distribution
choices. No provider's hint is indispensable; source holders can advertise the
same commit independently, and users can still supply manual routes. This removes
a concrete private-orchestration dependency without inventing a new package system.
It does not yet prove replicas exist or continue serving after an origin vanishes.

The smallest decisive controls are exact query/reply binding, malformed/oversized
offer rejection, bounded truncation/failure accounting, and proof that lookup never
opens owner state, invokes Git/Lean, downloads a repository or claims acceptance.
One retained concept target plus synthetic inert offer metadata can exercise the
new seam; no repeated theory episode or actual external publication is needed.
