# Build the ordinary Lean-first commons from source

This is a **source-build candidate**, not a completed v5 release. Its new
composition has not yet been compiled or run. It preserves the reviewed ordinary
checking, method-use and contribution components; it does not establish new
mathematical acceptance, useful growth, global deployment or hostile-code safety.

## One build command

Use complete supported **Windows x86-64 Python 3.14.6 and Lean 4.34.0**
distributions, including Lean's native compiler tools. Select the repository
source checkout explicitly. Its mapped source/assets and the builder are enough;
no experiment tree, old installation, owner database, retained executable or
private operation-selection file is an input.

For example, from PowerShell with an existing output parent and a fresh destination:

```powershell
& 'C:\tools\Python314\python.exe' -I -S -B `
  'C:\commons-source\software\v5\ordinary_native_distribution\build.py' `
  --source-root 'C:\commons-source' `
  --python-runtime 'C:\tools\Python314' `
  --lean-runtime 'C:\tools\lean-4.34.0-windows' `
  --output 'C:\commons-builds\native-01' `
  --wall-seconds 600 --cpu-seconds 600 --memory-mib 2048
```

The allowances are explicit example choices, not measured requirements or a
promise of success. Valid ranges remain 120–3600 wall seconds, 100–3600 aggregate
CPU seconds and 256–8192 MiB. There is no automatic download, retry or allowance
increase. Failure preserves partial outputs and logs; a later attempt needs a
fresh destination and deliberate selection, not state repair or continuation.

Successful output would have this layout:

```text
native-01/
  package/                  141 payloads plus the generated PROFILE.json
  _build/
    inputs/                 exact selected repository-source snapshot
    base/                   freshly built receiver and authoring support
    extractor-source/       seven native compilation sources
    extractor-objects/      fresh objects and two separately linked programs
    query-source/           current context-query command source
    query-objects/          newly generated command companions
    BUILD-RESULT.json       actual hashes, identities and charged build costs
```

Only `package/` and the explicitly selected external runtime distributions are
runtime inputs. `_build/`, the repository checkout and its absolute paths are not
needed to run that package. The receipt retains build paths for diagnosis; the
package profile uses logical names and actual generated byte identities.

## Exact build composition

This recipe derives from `ordinary_preview_package/build.py`. It keeps the
existing eight receiver modules, thirteen authoring modules and their five
companions, the context-query module, and the missing-import exporter. The only
additional native program is the existing `BaselineExporter.lean`.

The native lane compiles the five shared modules once: OriginalExpr, OriginalDecl,
CheckedExtension, BootstrapSupport and the existing legacy view of OrdinaryExport.
Each executable links those fresh shared objects plus **only its own** program
object. MissingImportExporter and BaselineExporter are never linked together;
both define an entry point. No old object files or fixed historical executable
hash are reused. Source/runtime pins and the original transformations stay exact.

The runtime package selects the reviewed native-first `owner.py` and `profile.py`,
adds the four existing baseline Python roles and source-built BaselineExporter,
and retains the other selected preview roles. Parked original-reference matcher,
registration and source-authoring modules, unused baseline programs, and the
optional LP file backend are not added.

The exact census is 28 installation payloads, 111 profiled auxiliary roles and
two documents (`README.md` and `PRODUCER.md`): **141 payloads**. Documentation is
copied and recorded in the build receipt, but is not an executable profile role.
The extra `PROFILE.json` is committed last. Its actual hashes, installation
manifest and implementation identity are generated from this build, not copied
from a previous run. Different build bytes may yield different identities.

The source map names 78 source/assets plus this builder and its map. It contains
60 direct-copy targets; the remaining 81 payloads are eight receiver modules,
65 authoring companions, five query companions, two executables and the installed
manifest. The base builder's 47 inputs and existing named runtime pins are
retained. These pins are not a complete hermetic compiler/system census.

## Using the resulting package

Keep the printed/retained actual profile hash and pass it, the explicit runtime
roots and finite operation limits to the public commands. Each invocation uses
the selected Python with `-I -S -B`. `owner.py --help`, `peer.py --help` and
`query.py --help` describe their arguments. An operator approves the selected
package and runtime; possession of a hash alone does not authenticate its author.

The supported architectural workflow is:

1. Work in a locally approved compatible ordinary Lean project. A reusable method,
   its definitions and a useful consumer adaptation are ordinary named declarations;
   no special method language or network-wide research agenda is required.
2. Use `produce-baseline` to export explicit completed target names from an approved
   local compiled project, or reuse an existing exact bundle. The producer does not
   need mathematical owner state, original-reference registration or a cryptographic
   certificate. The packaged `PRODUCER.md` records its exact input contract; its older
   source-stage wording describes that component's history, not this build's result.
3. A recipient initializes its own explicit owner policy and uses `intake-baseline`
   to check the selected inert bundle above its own parent. Producer reports and
   compiled project files are not receiving-side mathematical authority.
4. Use supported checked declarations through `export-module` and ordinary Lean
   application, or use already approved native packages when their rich frontend
   API is needed. Discharge actual premises. Return newly proved work through
   `contribute`; `extract-project`/`complete` can supply supported genuinely missing
   proof data. Existing peer/query commands separately expose, find and acquire
   selected records under their unchanged contracts.

This is the existing workflow, not a new end-to-end execution claim for this
source composition. Selected declarations do not reproduce original notation,
typeclass registrations, tactics or executable package behavior. Approval to run
a project and independent mathematical acceptance remain separate decisions.
Do not execute an unknown producer's code merely because its output will later be
checked. Process limits are not a security sandbox, and final proof checking
cannot undo tampering with the checker or protected state.

## Resource and state boundaries

The unchanged controller derives decreasing child grants from one original
allowance. Native compilation is sequential. Inclusive child Job CPU is charged
once; nested compiler CPU is not added again. Missing final CPU measurement
charges the full grant and stops. Clean closure is required. Existing controller
and supervisor reservations are retained; unused reservations are not renewed
budgets. An enclosing owner Job is still needed for hard limits on the cooperative
outer controller. No total disk-quota or hostile-source isolation claim is added.

Old installations, accepted roots and module anchors are untouched. Newly built
support can have a different identity even when semantics are unchanged. Do not
silently migrate an old anchor or reuse incompatible owner state by substituting
the new profile hash. Start with a deliberate supported state/compatibility choice.
