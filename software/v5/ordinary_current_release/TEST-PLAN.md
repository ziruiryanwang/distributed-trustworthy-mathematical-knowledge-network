# Changed-boundary evidence plan

Source-only plan. Root selects exact sources, fresh outputs and finite allowance
after implementation review. No execution is authorized by this document.

## What needs checking

The compiler algorithms, checker and binding optimization have evidence already.
Do not repeat their campaigns. This change introduces release selection and
distribution composition, plus one compatible source pin in an offline exporter.

1. Independently compare all 154 prebuilt bytes with the manifest; direct-copy
   sources match all 72 roles; exact compilation roles account for all others.
   Check fixed lower-builder closure, unchanged lanes/transforms/runtime pins,
   and explain every difference from its old map.
2. Produce source and prebuilt archives once; independently stream exact ZIP
   members, compare hash/length and metadata, and verify one fresh extraction of
   each. Exact source closure includes every runtime-imported helper and every
   current documented command, without executing historical overlay chains.
3. Test small invalid fixtures for a changed source/payload, unexpected path,
   aliased member, redirected file, malformed manifest and existing destination.
   Use tiny fixtures or direct structural validation; no duplicate full package.
4. In the relocated source, run the current offline preparer against the relocated
   prebuilt package and a retained valid request. Assert expected config outputs
   and unknown-interface refusal. No native program or protected state is opened.
5. Verify the offline export companion loads the new binder in a narrow inert
   fixture. Existing exported envelope semantics are unchanged; no acceptance
   claim or large library export follows. Prefer existing valid retained fixture.
6. The new direct source build needs one clean build only if the source-only
   compiler-lane argument and public source route are ready. Fresh generated
   PROFILE/INSTALLATION must be derived from actual outputs, not assumed to match
   prebuilt identities. Relocated public preparation/loading then checks the new
   package, not a second mathematical or growth campaign.

## Scope and resources

The first suite is file-only/inert and uses the existing Run-V5-Check supervisor.
Original input/package/source bytes are pinned and reread, outputs are fresh and
disjoint, and all failures/partial artifacts are retained. Choose the actual
finite envelope after source review; do not add retries or new allowances inside
the suite. Native build has a separate explicit finite selection if adopted.

Passing these gates establishes a usable selected distribution path. It does not
establish independent-host operation, global search completeness, growth speedup,
new trust in executable inputs, a license or completed deployable v5.

## Implemented first gate

`test_release.py` packs the source and exact prebuilt once each. Each pack writes
one ZIP and makes its sole fresh extraction from the inspected ZIP. The harness
independently streams ZIP members and imports each relocated verifier, checking
helper resolution without reliance on the original repository. New support bytes
must match the enclosing supervisor's reviewed source snapshots before any
relocated code loads; canonical originals and snapshots are rechecked afterward.

Six exact-code file refusals cover existing output, wrong manifest hash, changed
same-length payload, extra empty directory, hard-linked payload and case-altered
ZIP member. Four profile-layout refusals cover unknown binder identity, extra
role, Boolean native length and unknown schema. A final wrong-PROFILE refusal
must occur before output creation. Native identity variation is allowed only by
the inert interface selector; it is explicitly not approval of those artifacts.

Actual relocated preparation writes an `init` argument list only. The exact
arguments, selected profile, limits, output pins and saved receipt are verified;
future catalog/custody directories must remain absent. The relocated export
companion loads its genuine selected codecs and new binder, with no custody,
database or native worker. This checks compatibility, not a new export campaign.
Both distributions are reverified after use. No public query is repeated here.

Proposed one `current-release-controls01` allocation: outer Run-V5-Check
180 wall / 90 inclusive CPU seconds / 768 MiB / one active process, 2-MiB stdout
and 1-MiB stderr. Harness 150 wall / 75 own CPU, existing file helper operations
60 wall / 30 own CPU each, all subordinate to the original outer allowance.
There are no subprocesses, network listeners or owner/native operations.
Expected disk is one source and one prebuilt ZIP plus their sole extractions,
small snapshots/fixtures/reports, not a new runtime or mathematical corpus.

`select_release.py` prepares but never launches that selection. It pins every
current source/companion/new support input, the exact 154-file package, the two
foundation data files outside the snapshot source scope and selected Python
runtime components. Final source hashes and actual selection hash belong in the
root execution record after independent review; this remains a plan until then.
