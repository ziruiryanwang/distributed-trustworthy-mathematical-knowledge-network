## Mutation and serialization

The plan correctly discloses that this is **not a read-only database open**.
Catalog opening takes the owner lock, validates adoption/activation, sets SQLite
pragmas and changes every abandoned `RESERVED` operation row to `INTERRUPTED`.
Opening can also recover a journal. Custody opening sets its own pragmas and
validates stored counters/configuration. Neither exact database byte preservation
nor transactional rollback of an interrupted launch is promised.

One important operational detail: the owner opens custody **before** acquiring
the catalog lock. Consequently the catalog lock alone is not evidence that all
custody users are serialized. Root must hold off every known operation/service
using either selected state directory throughout this single status call. Do not
delete a lock/journal, force a reopen, or retry automatically if it refuses.
The selected clean historical state and existing user authorization for local
v5 development make normal recovery within this existing owner API in scope;
there is no justification for private database edits.

Both owner objects have explicit closure paths; close failure changes owner
`ok` to false. The launcher separately preserves supervision and reports unknown
outcomes rather than interpreting failure as rollback. Acceptance of this gate
needs the owner result **and** inner/outer clean closure, not exit code alone.
