## User workflow and payoff

A new operator can build/use the current package, but its full public workflow
requires config shapes and exact report fields currently discoverable mainly by
reading code. Copying structured names, local roots, unit/export identities and
provider records by hand is a predictable failure point. A small offline adapter
and complete walkthrough can remove this obstacle without inventing mathematical
authority or repeating already completed native experiments.

## Mandatory interface boundaries

Use Python standard library only. Preparation consumes explicit operator choices,
bounded JSON inputs and exact documented public reports; outputs only fresh
configuration files, their SHA-256 identities and structured argument data. It
must never execute commands, download/build a project, bind a socket, open owner
catalog/custody, alter a report, or choose the latest local root. No shell strings
with interpolated report content; structured arguments or clearly reviewed manual
commands only. Reports are untrusted data, not execution instructions or a warrant.
The actual product independently validates state/target identities on use.

Reject duplicate JSON keys, nonfinite values, unresolved placeholders, wrong
report operations/statuses, malformed identifiers and out-of-range row selections.
Enforce explicit finite input/file/list limits and never overwrite an existing
output or follow redirected paths. Preserve all partial outputs after failure;
no recursive deletion, automatic retry, service renewal or recovery.

The walkthrough must specify real public flag syntax and every input's source,
including `init` output capture, manual query/known-symbol selection, find result
selection, preview, receive policy, optional approved ordinary-source work, inert
bundle intake, publication and finite loopback serving. Do not require a fresh
mathematical example or pretend all authoring paths are automatically supported.
Source execution/TLS approval, serving all custody, chosen policy limits and exact
root/provider decisions remain explicit. Loopback is not remote deployment.

The kit should be small: support concrete common handoffs, not a new workflow
engine, schema registry, identity mechanism, trust mode or project generator.
Prefer existing typed output fields; refusal is better than guessing missing
bindings. Example policy ceilings are examples, not measured required capacity.
