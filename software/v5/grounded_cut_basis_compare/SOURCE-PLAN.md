## Shared-state invariant checked in source

Let P be the freshly committed native prerequisite root and B its basis root.
Setup checks both target names absent from the exact context of P. Every
alternative receives the same original full claims and selects P by exact root
identity, never by a mutable newest-root pointer or another lane's result.

- `PortableCatalog.context(P)` walks the selected immutable parent chain and
  validates committed operations/artifact identities. It does not merge sibling
  branches. New native roots have explicit parents.
- Both cut bootstrap functions take the actual locked native catalog, capture
  its selected context and create a distinct cut catalog. They do not reserve,
  commit or rewrite native mathematical roots. Their derivation cost is paid
  separately for each cut support and is never inferred from a saved descriptor.
- SourceAnchor checks native eligibility and retains a real source owner lock
  throughout a cut event. RESTORED additionally hashes the exact fixed basis.
  The native source remains physically at its fresh setup location; it is not
  cloned, relocated, reconstructed from a JSON report or treated as peer evidence.
- `PortableCatalog._open` does execute recovery-oriented `UPDATE operations ...
  WHERE state='RESERVED'`. Thus the invariant is immutable selected committed
  mathematical rows/artifacts and exact marker/activation, not immutable whole
  SQLite file bytes. Clean setup closure and no pending operation are required.
  Unexpected recovery, withdrawal or ambiguous state aborts the comparison.
- Run NATIVE last, with no concurrent cut/native handles. Sequential admission
  extends P to N1 then N2. Batch admission selects P again and creates NB as a
  sibling branch; it does not reuse N1/N2 as its mathematical parent. The public
  planner independently rechecks target absence/reuse against P.
- OLD/RESTORED loaders intentionally use overlapping module names and forbid
  preloaded graphs. Separate isolated processes are required; no module cache
  surgery, custom rewritten import graph or cross-support in-memory object.

## Custody isolation

Native admission's `_stage` persists and reads back inputs even when a selected
parent is unchanged. Sharing a custody backend after another lane added targets
would give later lanes a warm-persistence advantage. Each alternative therefore
needs a fresh custody backend containing exactly the34prerequisites before its
contribution interval, with neither target. Populate through actual public inert
custody API, not SQLite copying or direct row insertion. The setup backend is
separate. All redundant benchmark-isolation population is charged in the total
experiment bill; standalone attribution must explicitly distinguish this overhead
from the one prerequisite-custody setup a real user would need.

## Explicit full-cost accounting

There are three different reports, never interchangeable:

1. **Warm continuation:** the complete two cut events, ordinary sequential
   events, or ordinary batch event. Actual operation-local loading, planning,
   selected semantics, persistence, commit and handle closure are inside these
   intervals. It assumes that the prerequisite context and route support already
   exist; it is not an initial-use price.
2. **Standalone attributable use:** reconstruct a common fresh native setup
   followed by one fresh route process, from the observed phase costs below.
   These are mutually exclusive attributions of one experiment, not four cold
   executions, a prediction of an optimized single-process run, or costs that
   should be added together. Ordinary users may amortize more by staying in a
   process; this comparison does not establish that alternative's cost.
3. **Actual experiment bill:** the enclosing outer Job CPU and wall time, plus
   its separately reported wrapper CPU. The sum of four inclusive stage Jobs
   plus coordinator CPU is only a pre-final-report subtotal. Coordinator startup,
   final accounting/output and process exit remain in the outer Job. Nested
   worker CPU must never be added to either inclusive Job total again.

Every stage has an exact, nonoverlapping phase census, base/source loading and
the residual needed to reconcile its live Job CPU and supervised elapsed time:

```text
stage inclusive Job CPU = base/source load + all measured phases + signed residual
stage supervised wall  = base/source load + all measured phases + signed residual
```

The residual retains interpreter startup before the driver's BOOT sample,
uninstrumented controller/output work, helper overhead outside worker accounts,
process exit and closure. Tiny negative CPU discrepancies up to0.1seconds or
wall discrepancies up to1microsecond are retained explicitly, not hidden as
negative-cost work; attribution uses a nonnegative conservative charge and
reports the extra rounding charge. Larger discrepancies refuse accounting.
Each event's CPU decomposition and the stage's known worker sum are checked.
The stage supervisor's own CPU is separately identified as a **subset of the
coordinator's CPU**, not another child charge. Peak Job private commit is retained.

| Component | Standalone attribution | Actual bill |
|---|---|---|
| Common source/base loading; genuine native basis and34prerequisites | Same one measured setup for every alternative | Charged once |
| Route source/base and full selected input validation | Charged to its route | Every stage charged |
| OLD/RESTORED support load and real cut derivation | Charged only to that cut route | Both charged |
| Its complete contribution interval(s) | Charged to its route; native batch does not pay sequential contributions | All four alternatives charged |
| Four additional prerequisite custody populations | Excluded: common native setup already funds one actual prerequisite custody | All four charged as benchmark isolation |
| Fixture graph/support/handoff preparation and explicit post/pre-audits | Separately visible benchmark-only phases | All charged |
| Startup, report/tail residual and enclosing stage supervision | Entire observed pool exposed; attribution range and full-pool charge reported | Entire actual cost retained |

The shared NATIVE process serves both sequential and batched branches. Exact
allocation of its lifecycle residual and supervision between those hypothetical
standalone users is not observed. The report therefore exposes both the measured
required component total and the total obtained by allocating the full available
setup/route residual and supervision pool. Its range is a range of **allocations
of observed overhead**, not a probabilistic interval or upper/lower guarantee on
a different execution. Explicit sibling mathematical work is excluded, never
charged only to native. No unique full-cost winner may be inferred merely by
choosing different residual allocations or from overlapping ranges. The same
transparent residual treatment applies to both cut routes.

Required retention is not a free post-processing step: actual native setup,
cut derivation and contribution intervals include their persistent writes and
handle closure. Common setup already creates the34-unit custody; each standalone
route is assigned that custody once. Actual benchmark isolation creates four
additional equivalent custody stores and pays all of them in the real bill.

total database allocation, disk I/O, native artifacts, or future storage costs.
No retention horizon, future repair cost, network traffic, initial software
installation/download cost or lifetime growth benefit is measured. Those remain
separate deployment costs, not zero-valued observations.
