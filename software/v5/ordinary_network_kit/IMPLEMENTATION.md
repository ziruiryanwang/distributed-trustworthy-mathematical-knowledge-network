## Actual user workflow

An investigator can prepare a directory query, inspect its actual candidate
report, explicitly approve contacts for a new operation, and prepare preview or
receive. A provider can prepare an optional pair-enabled index configuration.
This closes the old kit's rejected-layout/config/report seams; it introduces no
new search algorithm, contact authority, mathematical rule or agent planner.

## Exact changes

`prepare.py` is a fresh successor of the frozen operator preparer. Unchanged
operations retain their existing request/config forms and starter query subset:
portable type symbols, object/declaration kinds, and exact declared-type keys.
Structural-head queries remain available through direct product configuration,
not this deliberately conservative helper.

- `find`: optional strict `candidate_mode` accepts only `atomic-v1` or
  `sparse-v2`. Absence stays absent, so the product's atomic default is unchanged.
- `index`: optional `access_pairs` is forwarded unchanged. Null mirrors the
  product's disabled default. Enabled values require 1..8 sorted unique pairs,
  distinct ordered 64-hex atoms, strict integer quotas and the 4096-byte cap.
  The product still decides fresh creation, exact reopening and capacity.
- `directory-find`: validates the existing explicit contacts/directories,
  1..8 route subsets, distinct normalized routes, at most 32 directory-route
  combinations, directory caps, nested search/mode and static owner egress.
- `directory-serve`: validates 1..2048 distinct route registrations with
  1..16 distinct four-field IPv4 hints each, and the same finite service/TLS
  settings used by ordinary serve. Hints cannot carry CA files. Existing 1 MiB
  request/4 MiB prepared-output bounds remain conservative additional limits.
- Preview/receive's existing `find_report` key accepts either an actual `find`
  or `directory-find` report. Its original pinned bytes are not rewritten.
  Top-level and result operation identities must agree; the existing successful
  profile, cleanup, candidate record, snapshot and portable locator checks stay.
  The selected provider label must occur in the new request's explicit contacts.
  Learned directory contacts are never read, promoted or dialed by this helper.

The small validators factor the predecessor's search-spec, limit and finite
service checks; no schema registry or execution framework was added. Input
path/hardlink/reparse checks, exact report pins, aggregate input bounds, fresh
exclusive output, state separation and partial-output retention are preserved.
No owner database is read. No current context or acceptance is fabricated.

`prepare_selected.py` still loads only its exact local inert preparer, with no
product imports. It verifies the exact local compatibility-map hash, selected
PROFILE hash, known role census and actual noncompiled source bytes before
preparation. The new map has exactly 45 fixed noncompiled roles and the same
72 native-role names from the predecessor. Only `contact-sparse-v2` is recognized;
old variants remain supported by their untouched old kit.

The known map is derived from the exact assembled sparse PROFILE
`97f93cc66f77ebcecd7a3a341baaaf4725236a8dec5fb9cee3c3e67d478f2834`.
Native artifact hashes may differ in an independently selected fresh build,
but arbitrary auxiliary layouts are rejected. This is interface compatibility,
**not** package authentication, executable safety or mathematical approval.
The product loader/operator retains those responsibilities.
