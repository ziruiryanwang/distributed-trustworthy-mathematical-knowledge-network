## Current public capability

**The current software can develop and return new mathematical concepts using
received inert mathematics, without mandatory certificates or adoption of the
producer's executable project.** This is an implemented bounded capability,
not a claim that every Lean frontend feature or every remote theory is usable.

The current `ordinary_reply_capacity/source-map.json` selects
`ordinary_demand_frontier/ordinary_contribution.py` and its native helpers.
Its public `contribute` route authenticates the acquired targets against the
selected local checked context, retrieves their exact retained evidence, and
builds a demand-scoped authoring request. An approved recipient project may
supply its existing frontend and a checked-ancestor frontier. This can be the
recipient's ordinary Std project; it need not be the producer's source tree.

`OwnerConstruction.lean:196-293` supplies demanded definitions and atomic groups
with their computational content, and exact theorem signatures as scratch
assumptions. That scratch environment is candidate construction only. Complete
new proofs are exported, bound to the actual recipient interpretations, and
independently checked by `ordinary_contribution.py:577-607` through the normal
owner preflight/admission path. An existing frontend's printed names or scratch
success cannot replace final checking. New definitions are allowed; this is not
restricted to theorem instantiation.

The already adopted `ordinary_finite_map_refinement/FRESH-RECIPIENT-REVIEW.md`
records the decisive composition: B independently received 37 inert units above
its own Std context, developed a dependent consequence after A stopped serving,
and returned one newly checked theorem to A. Its actual proof depended on the
received contextual-equivalence theorem. `ordinary_observation_growth/OUTCOME.md`
separately records export, checking and publication of further concept/theory
work, using the existing ordinary producer route when the smaller contribution
envelope was unsuitable. These are capability results, not speedup estimates.

Thus another reference loader, rich-authoring backend or synthetic theory round
is not the missing growth integration. Missing frontend metadata and conflicting
exact interpretations remain real, disclosed refusal boundaries. The existing
ordinary-project/producer alternatives and checked receiver interpretations
should be preserved rather than promising automatic reconstruction of all Lean
notation, instances, plugins or arbitrary coexisting package versions.

## One unresolved central condition: selective unfamiliar-vocabulary exposure

**The shipped formal-search API does not perform structural analogy or general
pattern search across independently named concepts.** This is a concrete source
fact, not a criticism of its supported exact search.

- Current `peer_api.py` is mapped to `ordinary_multi_source/peer_api.py`.
  `find` at lines 493-529 compiles the selected feature conjunction through the
  exact adapter. Additional providers and sparse access do not change that
  feature language.
- `ordinary_formal_query/discovery/ordinary_export_adapter.py:60-91` accepts
  kind, exact symbol, exact declared-type-key and head features. Constant and
  projection heads retain exact portable symbol IDs. It has no wildcard,
  symbol-variable or renaming-invariant law-pattern feature.
- `ordinary_formal_query/formal_query.py:18-27,122-170` intentionally preserves
  exact global symbol/level identities and performs no reduction or
  substitution. `prepare-query` is exact-type-key preparation, not a Loogle
  query disguised by the word "formal". Binder-label erasure does not erase
  independently defined global vocabulary.
- The kit's guide and request catalog supply these exact routes. Loogle was
  inspected as an optional ordinary external tool in `PREEXPORT-TOOLS.md`;
  it is not a bundled or selected pattern-search provider in this kit.

The already proved obstruction in `CREATIVE-GROWTH-MECHANISM.md` therefore still
applies: a query requiring a known nonfoundation symbol cannot return a law
whose explicit type uses only different nonfoundation symbols. Common equality
or declaration-kind features relax this exclusion but can leave a huge posting
set. Faster name resolution does not remove that relevance/selectivity boundary.

The required condition for a useful cross-vocabulary route is that relevant
unfamiliar laws reach an investigator within a selected corpus and affordable
search/inspection budget **before** the investigator has written the bridge.
It need not solve arbitrary mathematical equivalence. The existing conditional
growth argument depends on affordable exposure and adaptation; it does not prove
that the exact feature API supplies this condition on a huge diverse corpus.

## Interpretation and the next implementation decision

An analogy result must remain advisory. A mapping between unfamiliar symbols is
neither an identity override nor a proof. Subsequent use requires an ordinary
checked instantiation, representation map/transport theorem, common abstraction
with checked instances, or another explicit mathematical argument. Existing
contribution/producer and recipient checking routes can carry those declarations.
No automatic formal name translation or bridge synthesizer is required for
soundness, and none is established by the current search API. Name collisions
and incompatible realizations can prevent joint import; separate roots provide
coexistence, not an automatic merge (REALIZATION-IDENTITY-COMPATIBILITY).

The earlier source discriminator already found a meaningful Repair/Nat.mod_mod
law pair and suitable Loogle pattern expressibility, with explicit higher-order
matching and provider-coverage caveats. Do not repeat that investigation or claim
its proposed pattern was actually served. It ruled out a claim that we must
invent a new matcher merely to express the pattern.

For an implementation advancing this particular growth gap, root's next choice
should compare **one usable existing formal-pattern provider/handoff** with
**a bounded advisory structural feature over the existing inert previews**.
The comparison must settle corpus coverage, supported query semantics and bucket
selectivity, not rerun concept creation. The latter is justified only if an
identified coverage/selectivity need is cheaper to serve that way than through
the ordinary maintained tool. It would require an explicit feature revision and
indexing cost; exact old snapshots cannot acquire the new feature by relabeling.

No such provider or feature is selected by this audit. This is the one remaining
growth condition identified here; cold verification and warm cut mechanisms are
being handled separately and are not reopened. The full v5 goal remains active.
