## Consequential question

Can the new single-query/two-source-posting feature distinguish a locally known
schedule-equivalence conclusion from repeated-schedule nonmatches, without
requiring the remote theorem's hidden premise telescope, while preserving the
existing exact-type and positive-membership boundaries?

The control answers only this bounded metadata question. It cannot establish
the theorem's applicability, prove its premises, show semantic completeness,
demonstrate a runtime advantage, or justify useful mathematical growth. Tiny
synthetic previews are deliberately unproved and never enter mathematical
acceptance. Actual candidate membership uses the real parsers and SQLite index,
not fabricated success responses.

## Nine focused groups

1. **Retained theorem and independent conclusion.** Construct
   `forall alpha rs ss x, run rs x = run ss x` using already known TheoryA symbol
   bindings before parsing the remote theorem. Its explicit context count is
   four, not the remote theorem's ten leading parameters. The source's conditional
   theorem emits both partitions; a one-edge unproved reflexive distractor emits
   only `equal`. The ordinary non-exact feature sets agree, the exact whole-type
   key does not identify the target, and the one `separate` feature discriminates.
   The edited node25 remains used in two premise domains; no orphan is introduced.
2. **Equal substitution and duplicate leaf nodes.** Distinct remote parameters
   may instantiate to the same query term. Two separately numbered equal leaves
   must produce `equal`, which the unconstrained source includes. An explicit
   zero context count does not strip all binders automatically.
3. **Different internal DAG sharing.** One compound endpoint shares a child;
   the other contains two separate copies of that child. Fixture indices prove
   the different sharing before the actual query helper must return `equal`.
   The fixture's explicit backreference constructor is not a key implementation.
4. **Missing and early-variable endpoints.** Missing paths and variables met
   before the full path is traversed produce `separate` query partitions and
   unconstrained two-key source postings. Two absent endpoints are not equal.
5. **Exact structural quotient.** Alpha-renamed endpoint binder labels agree;
   different universe instances and different portable symbols do not. No
   reduction, inferred semantic equivalence or endpoint theorem is substituted.
6. **Strict refusals.** Boolean, negative, noninteger and excessive context
   counts; counts beyond the query telescope; malformed scope; insufficient
   type-node limit; wrong feature profile, value and extra fields must refuse.
   A refused incomplete key computation must not become a `separate` answer.
7. **Complete feature capacity and declaration kind.** A theorem with 122
   distinct constants reaches exactly 128 features. Adding one more refuses
   rather than silently omitting a correlation feature. A definition gets no
   correlation keys and retains its 127 ordinary features with 123 constants.
8. **Namespace and record binding.** Old/new namespace IDs differ; substituting
   the old namespace refuses. Removing one advertised correlation feature fails
   exact record/preview resolution. The unchanged exact-type helper still
   produces its normal `declared-type-key` specification.
9. **Actual index path.** Admit only the two previews into a fresh bounded
   SQLite metadata store. Query the ordinary kind/run-symbol conjunction, then
   add the correlation feature. Verify actual summaries and positive candidate
   proofs through the production helpers. Require two versus one returned and
   scanned metadata records, within at most two nonempty partitions per query.
   Both results continue to disclaim mathematical acceptance, global completeness
   and verified scan coverage. The temporary store is closed in `finally`.

The two-versus-one observation is a mechanical discrimination check, not a
performance benchmark. The repeated-parameter decoy is not claimed to be a new
checked mathematical result. There is no global recall or growth inference.

## Durable output contract

The current suite deliberately does not print a success JSON object. The root
integration driver reads the saved report instead:

- `RESULT.json`: `status` (`PASS` only after all groups and final input checks),
  `failure`, `groups` (objects with `case`, `status`, `detail`), elapsed/process
  CPU times, exact module `source_map`, retained evidence hash, scope and
  `mathematical_acceptance: false`.
- `RESULT.json.query_fixture`: `native: "query-native.json"`,
  `bindings: "query-bindings.json"`, `context_count: 4`.
- `query-native.json` and `query-bindings.json`: exact canonical bytes without a
  report newline, generated from the independently declared raw-distinct goal.
  The integration driver may use these as inert inputs to the real public query
  CLI; this suite never starts that CLI.
- `FIXTURES.json`: bounded saved synthetic query/preview bytes and their hashes.
- `index/`: fresh metadata-only SQLite state. It is retained for audit, not
  deleted or promoted into an owner's accepted mathematical library.

Every output file is created exclusively; a failure remains a failure and is
not overwritten by a retry. Source review must precede a selected execution.
Manual/context CLI plumbing, launcher option forwarding, file-only packaging
and inert operator-kit recognition belong to the separately reviewed integration
driver; this focused suite alone does not qualify those public paths.
