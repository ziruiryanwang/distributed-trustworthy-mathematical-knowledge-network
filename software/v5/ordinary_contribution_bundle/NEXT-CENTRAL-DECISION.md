## Recommendation

**Make affordable repeated ordinary admission the next scalability decision,
but do not yet select a persistent catalog index, session, cut integration or
new native campaign.** The concrete narrow candidate is reuse of one private,
same-operation parent-context view. It removes duplicated controller work while
leaving the actual ordinary parent and checking relation unchanged. Its priority
over other work depends on the cost threshold below; source loops alone do not
establish that controller metadata dominates useful production.

The public handoff closes an identified user action. It does not make another
convenience the default next step. No higher-payoff *observed missing workflow*
is established by this source trace. Preserve the existing shared-carrier search,
ordinary project authoring, new-definition/consequence and independent-recipient
routes; their previous findings need no repeated demonstration.

## Exact remaining work

For native-bootstrap owners and a newly admitted batch, both `contribute` and
`complete` reconstruct the same parent **five times**, before any extension commit:

1. Contribution request setup (`ordinary_demand_frontier/ordinary_contribution.py:432`)
   or completion planning (`ordinary_library_package/completion_api.py:87`).
2. Public preflight (`ordinary_parse_reuse/ordinary_admission.py:534`).
3. Admission's independent replan (`ordinary_admission.py:583`).
4. Admission's execution context (`ordinary_admission.py:604`).
5. Catalog extension reservation (`ordinary_lean/portable_catalog.py:607`).

A distinct authoring frontier adds its own context; legacy import can add open-time
validation. Five is the ordinary successful path above, not a universal call count.
The replan is a real trust boundary: accepting the caller's preflight object is
not a legitimate shortcut. Only privately derived state under the actual owner
lock could be shared while independent raw-unit/binding validation remains.

`portable_catalog.context:530-549` walks only the selected ancestor chain, reads
every root record, validates it and builds the whole binding map/module plan.
`_context_rows:492-528` scans every binding and copies module metadata;
`_validate_record:390-490` checks committed origin, support and snapshot bindings.
This scans the selected chain, not unrelated branches. Let L be selected roots,
M their metadata/name bytes and A retained snapshot bytes. One context's
metadata work P is at least proportional to L+M; an exact-name dictionary lookup
inside later code does not remove the cost of constructing that dictionary.

`_artifact:319-332` caches verified `(path,size,hash)` per open catalog, initialized
empty at `_open:174`. Thus the five calls do **not** hash A five times; they repeat
metadata work, while a fresh owner process pays selected snapshot hashing again.
The native worker still restores the full selected module chain and enumerates
all parent constants (`ordinary_kernel_admission/OrdinaryWorkflowWorker.lean:198-227`).
Saved chunks contain checked new records, not reproofs of all previous theorems.
Do not describe restoration/hash/name work as repeated kernel theorem proving.

Existing reuse was checked: `_verified_artifacts` already covers snapshot hashes;
`ordinary_parse_reuse/_plan_with_parsed` and `_prepared_extension` already reuse
private same-call parsed units/immutable native projections, but deliberately do
not cache contexts. No context-view cache was found in the selected sources.
Use that established ownership pattern if extending reuse; do not add a public
cache parameter or retain the mutable dict returned by `catalog.context` blindly.

For sequential ever-growing parents, summing P(L_k,M_k) can be quadratic in the
number of additions even though each snapshot is a delta. Same-operation reuse
changes roughly `5P` to `P`; it does not change that lifetime order, remove A,
reduce native environment size or make a large necessary context fit memory.

## Decision threshold and next action

Let T be full CPU cost of a naturally needed contribution/completion, including
failed attempts and outer work; let C be the five repeated metadata passes,
excluding the first snapshot hash. At comparable pass costs, private reuse can
save at most about `0.8 C`, before its own checks/copies. **Use C >= 0.25 T as a
proposed screening threshold** for a target >=20% whole-operation saving. This is
a prospective engineering choice, not measured evidence or an adopted budget.
Also consider a real controller-memory/allowance failure attributable to map
reconstruction; a worker-memory failure needs a different decision.

On the next independently needed ordinary operation, obtain phase attribution
once under its existing finite envelope, with batching and the smallest practical
eligible parent already applied. Do not reproduce mathematics merely to benchmark
the explicit loops. Existing contribution02 reports 4.84375 controller CPU seconds,
5.390625 worker CPU, and an audited 11.015625 known total including outer work
(`ordinary_finite_map_refinement/CONTRIBUTION02-OUTCOME`, pinned wrapper 06534e76).
Controller context cost is at most 44% of that total; its actual share is unreported.
This does not establish the 25% screen, and that real run also had a distinct
frontier. Existing evidence therefore does not authorize a new timing experiment.

If the threshold is met, select a small source design for one private view bound
to exact catalog/implementation/root and original limits/policy under the held lock.
Retain activation/withdrawal checks at every boundary; independently validate raw units,
expose no mutable caller cache, and discard the view on close/support change.
Compare benefit against the existing batch in one changed-boundary validation;
no new warrant kind, persisted cache or native checker is required for that scope.
Changing admission/catalog source still changes its checked implementation identity.
Price honest integration and retained-owner compatibility/re-admission; do not
silently relabel existing roots to make a small controller saving look free.
If C is below threshold, **do not implement the metadata optimization** merely
because five calls exist. If necessary parent hashing/native restoration instead
dominates repeated durable work after honest batching/small parents, reopen the
already-reviewed grounded-cut full-cost comparison only for its actual supported
workload and with mixed-definition re-entry charged. Otherwise keep current routes
and spend effort on an independently identified practical growth/deployment gap.
