## Bounds and failure meaning

Root chooses explicit wall/CPU/memory arguments within the recipe's finite
ceilings. Compilation receives only remaining original wall and CPU allowance,
less the existing 24-second/one-CPU-second cleanup/bookkeeping reserve. Insufficient
remainder refuses before launching; the original parent deadline never changes.
Observation and any known child CPU survive clean-result rejection. Actual child
CPU is charged before final assembly. The existing supervisor
bounds each stdout/stderr stream at 1 MiB and limits the inner tree to four active
processes. Its sampled log limits are not hard filesystem quotas. The outer Job
must contain the parent as well; cooperative parent checks are not a sandbox.

Each source is at most 2 MiB, all source copies at most 16 MiB, each generated
object at most 64 MiB, and assembled payloads at most 512 MiB. Generated-file
bounds are checked before assembly acceptance, not enforced by a new disk quota.
The approved fixed compiler/source plus finite time/memory bounds are additional
operational premises. Existing source verification is reused; no base recompilation,
Lean experiment, proof campaign, fallback compiler or retry is selected.

Failure preserves copied inputs, partial outputs and supervised diagnostics. A
manifest may exist if final loader compatibility fails; its existence is not a
successful build or permission to use the candidate. Adoption requires the actual
zero/clean outer result, final build report and independent saved-output audit.
Nothing here establishes a checked theorem, runtime speedup, useful growth or
final-v5 deployability. The separate actual native evidence plan remains open.
