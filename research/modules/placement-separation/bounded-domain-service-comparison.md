# Bounded provider domains and publication windows: service comparison

Date: 2026-09-20. Author: `bounded_domains_author`. Status: **HELD repaired complete source for independent resource and service rereviews; UNSELECTED comparison**. Concept/specification and finite arithmetic only. No implementation, executable model, native extraction, Lean execution or benchmark. ## Decision in brief

The existing independent-provider admission path can bound the full-current-catalog rebuild term without a new protocol, **if actual complete domains, closure resources, per-provider-key routing and the same reader/publication service all fit**. It is not sufficient merely to cap selected targets, manufacture provider identities or wait for a convenient batch. The bound is on each build's complete actual input, not on the number of labels assigned to a shard.

This comparison derives a finite sufficient region and three independent defeating families: a bounded selected domain with an unbounded-with-prefix native dependency closure; lost provider-level common-key sharing; and indistinguishable providers under a fixed unfamiliar-reader probe budget. Publication windows change the feasible region only where the original offer permits their delays and incident degradation. No positive operating point or general scalable-growth theorem is established.

The decision is **retain the existing bounded-provider route as a conditional deployment option, but do not accept it as the demonstrated answer to the joint-service bottleneck**. Identify the failed axis first: current-domain rebuild isolation, the qualified-provider native/index-role coupling, or information-poor cross-provider discovery. Evaluate applicable existing alternatives, including selected I direct-contact candidate brokers, before concluding that a new mechanism is needed. Those are different problems; this note specifies no replacement mechanism.

## What must be bounded for the catalog argument

For every provider p and catalog attempt b, retain the catalog's complete tuple

`(e_pb, n_pb, i_pb, p_pb, bytes_pb, inputGenerations_pb)`.

Here e counts **all actually traversed** current/excluded/historical/tombstone inventory records; n counts coherent current locator rows; i counts token/posting visits; p counts physical index-node visits; bytes includes actual repeated reads and preparation/sorting/set-comparison work. The whole current relation is established in both inclusion directions. Complete native closure, reconstruction RAM, actual maps and per-member support dependencies are additional dimensions, not encoded into n.

Use distinct caps `K_e, K_n, K_i, K_p, K_bytes`, plus actual resident slot/payload/scratch and retained-generation bounds. The simple record-visit notation K below means **K_e**, not a target cap. It is legal to have n <= 20 while e is much larger because historical records remain traversed, or while a physical posting layout has many pages. Conversely, a valid exact current layout can omit retired records from current traversal while retaining their separately owned bytes; their retirement must actually have occurred, and those bytes still count until reclaimed. This source provides no automatic history compactor.

A selected-target cap k bounds only the selected contribution to n when the number of selected exact descriptor/replay alternatives per target is separately bounded. All coherent current nonselected locator rows also enter n and must be bounded explicitly; historical/excluded records additionally traversed enter e. K_n therefore remains an independently supplied complete current-row cap. With one completed selected feature descriptor per selected target, 32k bounds only the number of **distinct logical selected descriptor/token postings**, not i. Expected-token enumeration, actual-relation enumeration, both-inclusion checks and sorting/comparison can visit the same logical posting more than once without revisiting any physical page. K_i, K_p and K_bytes remain separate complete actual-work bounds. None of these cardinalities bounds native support. Even a final catalog that fits may fail during two-sort-buffer preparation beside old readers, old layouts and current native reconstruction.

For one finite realized chosen plan, partition **actual catalog attempts** at provider p into four disjoint classes: Z_p successful initial builds; A_p successful arrival-associated builds; I_p successful other builds; and F_p failed/abandoned attempts, regardless of their initial/arrival/other purpose. An admitted but unstarted preparation belongs to none of these actual classes and retains its separate reservation. Each successful build has exactly one class; an arrival coinciding with initial preparation cannot credit the same build to both Z_p and A_p. A still-running attempt at the observation cut prevents this terminal-attempt equality unless it is explicitly included as a further charged class; the displayed finite plan assumes every attempted build has completed or been lawfully stopped. Then

`B = sum_p (Z_p + A_p + I_p + F_p)`

counts every actual build attempt under that terminal finite plan exactly once. Work already spent on a stale attempt is not credited back. Each attempt enumerates at most K records if its actual complete input bound holds, hence

`Visits_inventory <= K * B`.

Additionally require an injective association from successful arrival-associated builds to actual distinct nonempty publication commits. Each associated commit consumes at least one fresh unique assigned locator arrival not credited to any other associated commit. Several commits may be coalesced before one build, and a failed attempt receives no successful-arrival credit. With N assigned locator arrivals across providers, this explicit injection gives `sum_p A_p <= N`. Rebuilding twice after one arrival must classify the extra successful build as other work I_p; merely naming it another arrival rebuild does not establish the bound. Thus

`Visits_inventory <= K * (sum_p Z_p + N + sum_p I_p + sum_p F_p)`.

This is the promised **O(NK) arrival-enumeration branch** only when initial, other-invalidating and failed-attempt counts together are O(N), with the constants and finite horizon supplied. It is an upper bound on record visits for this declared bounded algorithm, not a universal runtime claim, not a count of unique mathematical results and not a bound on all maintenance. Replicating one new mathematical target to a fixed a providers gives up to a assigned entries only under the stated one-entry-per-placement premise; use the actual total N otherwise. An incident affecting every provider, frequent pure R rewrites or growing history can defeat the needed bounds.

Slot sorting adds at most `sum_b n_pb*ceil(log2(max(1,n_pb)))` comparisons, duplicate checks add `sum_b max(0,n_pb-1)`, and actual member occurrences V add at most `V*(ceil(log2(K_n+1))+1)` locator comparisons. Actual posting-set checks and byte reads are not paid by these comparisons. Every support dependency visit remains in D. Neither V nor D is bounded by K alone, and nothing here supplies positive primitive work/elapsed bounds.

For contrast, one growing provider retaining every prior selected locator and completing a full build after each of N additions enumerates at least `N*e0 + N*(N+1)/2` current records. That reviewed lower bound and this bounded-domain upper bound concern different actual placements and input sizes under a common service offer; their difference does not cancel the new providers' native/routing/discovery costs.

## Publication windows: admission conditions, not a free freeze

Consider one actual provider-local arrival cohort. Its local policy may defer a discretionary public index commit until a window boundary, only if the same offered contribution-to-FIND and contribution-to-covered-route deadlines permit that wait. Native acceptance itself is not postponed into a false “already published” status. Pending admitted bytes, pins, proposals and candidate history are counted throughout the delay. A maximum waiting window W does not promise a batch of size b: sparse arrivals may force a singleton commit to meet its deadline.

Name arrival a, actual readiness time r_a after required native/custody/public-authority preparation, chosen commit c_a, and offered absolute deadlines `d_FIND(a)` and `d_cover(a)`. A sufficient concrete calendar must place native acquisition/checking and all dependencies before r_a, have `r_a <= c_a <= r_a + W`, complete current FIND service by d_FIND, and finish every required actual route/support prefix by d_cover. If the offer measures delay from external arrival rather than readiness, the native preparation prefix remains in the deadline; re-labeling arrival as ready cannot shorten observed latency.

After c_a, let the exact supplied critical-path bounds through current catalog preparation, actual support scans/authorization and needed route commits be L_cat, L_auth,g and L_route,g, including resource blocking and old-effect settlement. One sufficient selected schedule requires current C/R/guard stability through every current authorization it relies on, and

`c_a + L_cat + L_auth,g < nextRelevantInvalidation`

for those authorizations, with their actual route commits before each original-occurrence safe lease deadline and the offered coverage deadline. The precise path may overlap legitimate work; a fully serialized sum is a conservative certificate, not an optimality claim. A build is charged once as work but its complete predecessor latency applies to each dependent group. Existing independently valid old-mode or SG summaries retain their own contracts; a comparison cannot force them to rebuild just to favor the new assignment.

Only discretionary arrivals/layout choices may be held back. Support invalidation, disclosure withdrawal, unsafe recovery fences and genuine incidents take effect immediately. An owner cannot create an allegedly stable window by delaying a known authoritative change. A shared native incident can invalidate many small domains at once. The finite incident allowance must fund actual failed builds, both required incident scans, rechecking and aftercare without letting a full queue suppress invalidation.

If service explicitly allows b arrivals to accumulate and n=bq arrivals really arrive within their per-arrival deadlines, q builds can replace n builds. If the earliest arrival's deadline expires before b arrive, the proposed b-sized schedule is infeasible; its small rebuild total is not equal service. A legitimate periodic window can instead commit its actual nonempty cohort, bounded by the offered wait, and report the realized smaller batch. No synchronized network clock or agreement on everybody's windows is required.

There is a second limit even after bounded partitioning. Fix one affected provider whose current catalog build and post-READY authorization have exact residual durations 60 and 15, and whose relevant current commits occur every 70 duration units before an actual lease expires at 600, as in the reviewed envelope. If that provider still contains the affected entries and cannot lawfully defer commits, merely adding other small providers changes none of this critical path. A real smaller complete domain could shorten the path only with supplied new duration bounds, paid assignment and unchanged service. Windows cannot defeat forced incidents, an immutable original deadline, or a nonexistent executor slot.

## Complete native closure: the hidden cross-domain dependence

Let X_p be the exact finite native/checking material that qualified provider p must retain and protect for its chosen targets/replays under the installed foundation/assessment contract. Let size(x) be actual charged retained bytes of an independently materialized required object/unit, with the counted units occupying pairwise-disjoint charged byte allocations within each independent materialization. Where p independently stores these exact bytes without cross-provider physical sharing, its closure payload is at least `sum_(x in X_p) size(x)`; the relevant aggregate is

`S_native = sum_x m(x)*size(x)`,

where m(x) counts the actually independent retained allocations requiring x. Global mathematical uniqueness would instead count x once and cannot pay for m(x) disks. Actual physical compression/deduplication, alternate lawful representations or shared custody ownership require their own proved/supplied accounting and may change this relation; no universal positive bytes-per-theorem law is asserted.

The complete checker/core setup, replay-context compatibility, current assessments and reconstruction peak must be supplied separately. Holding canonical bytes twice does not imply doing every check twice, but permission to reuse a compatible existing assessment is governed by its exact actual contract. This catalog adds no cross-provider or cross-group native-assessment cache. A provider checking one new root can still need the whole large context in RAM; selected-target count alone cannot bound it.

**Finite chain counterfamily.** Fix N=mk exact targets t1,...,tN with the following actual selected evidence dependency property: replay tj requires distinct positive-size retained units x1,...,xj, each occupying s bytes in the chosen independently materialized representation. No alternate replay is substituted. Partition the selected targets into m consecutive domains of k targets each, on independently retaining providers with no shared physical allocation. Provider i retains the closure through x_(ik). Therefore

`S_native >= s*k*sum_(i=1..m) i = s*k*m*(m+1)/2`

`= s*(N*N/(2*k) + N/2)`.

The last provider alone requires at least sN bytes although it selects only k targets. With k=1 this is `s*N*(N+1)/2`; with one provider the union is sN. For a finite host payload cap C, a prefix with sN>C cannot fit that last provider under these explicit representation/closure premises. All prefixes considered must be actual finite admissible inputs until that boundary; this is not an assertion that arbitrary Lean developments realize the dependency pattern or that no redesigned evidence representation can improve it.

This counterfamily defeats the inference “small current FIND means small qualified node.” If newly introduced providers begin without the required units, their missing-byte acquisition and the actual exporters' service add corresponding transfers, counting any real prepositioned cache/past acquisition as paid history instead of assuming emptiness or warmth whichever is convenient. Repeated support inspection can add further work: for actual ad-member anchor occurrence a at p let d(p,a) be its complete current dependency visits; total D is the sum over **every** actual scan occurrence, including failed and repeated ones. The catalog does not divide D by closure overlap.

**Bounded-overlap contrasting family.** Under separately supplied native compatibility, suppose each domain's exact required closure is one fixed core of C0 bytes plus disjoint selected increments of at most d bytes/target, with at most k targets/domain and no growing cross-domain chain. For m independently retained domains and N assigned targets, closure payload has the supplied upper envelope `m*C0 + N*d`. If m grows proportionally to N/k, this payload is O(N) for fixed k,C0,d, but cold checking, RAM, metadata and serving still need their own bounds. The comparison is between explicit dependency families, not a claim that mathematical locality guarantees the favorable one. A local heuristic can seek low overlap/short closures and be evaluated for its actual results without entering truth acceptance.

**Same-host qualification.** Several separately authenticated provider domains may share a genuinely owner-controlled immutable native arena. Then the shared payload union can be charged once, plus all actual ownership/pin/reference/assessment metadata, separate index/routing state and overlapping working sets. No independent-failure credit follows. Unsharing or migrating a domain later requires the actual bytes and pins. Shared hardware keeps a single aggregate CPU, RAM, I/O, disk and network ledger; it can reduce duplicated payload yet still fail the deadline/calendar or physical peak. A declaration that ten identities each have eight GiB of capacity does not create eighty GiB on an eight-GiB host.

**Already selected role-separation alternative.** I's direct-contact candidate broker need not retain/check every indexed native closure. The chain counterfamily therefore constrains the qualified-provider deployment just specified, not every selected V6 search role. Before proposing another broker mechanism, compare existing I against the same offer: known broker contact, bounded claimed-token conjunction/optional exact-target search rather than G native pattern filtering, actual metadata ingest/source-self mutations and snapshots, exact evidence-source custody/serving, false/stale-lead work, and receiver acquisition/pattern/native checking/application all remain paid. Copied pattern digests are not pattern bodies; I does not automatically reproduce the 25-domain versus one-50-entry G pattern-query case below. A broker copy is not an extra qualified evidence copy. Required old custody cannot be deleted for the claimed saving. If the offer requires initially unfamiliar routed discovery of the broker, I does not supply that service; substituting a known contact weakens the offer, while BROKER_ROUTE remains unselected. This source designs no new broker and claims no free transfer of this catalog's qualified-provider support semantics to I.

## Provider-key amplification and concentrated holders

At one fixed F/E, let T_p be the exact currently selected descriptors at provider p, and U_p the union of their emitted keys. Define `a(k) = number of providers whose selected current relation includes k`. Then

`sum_p |U_p| = sum_k a(k)`.

With exactly r selected depth-zero row copies per provider/key and no extra/partial rows, selected route stock is `R = r*sum_k a(k)`. A one-provider index over the same descriptors needs `r*|union_p U_p|` such rows. The difference is exactly `r*sum_k (a(k)-1)` over present keys in this restricted incidence. Ads at distinct providers cannot borrow the same provider-bound row. Extra copies, groups, deep markers, history and uncertainty add their actual state/work.

This loss of sharing is small when partitioned domains mostly use disjoint tokens, but maximal common keys give a simple necessary amplification. If all P domains emit the same h common keys and otherwise disjoint u keys/domain, the one-provider selected row count is `r*(h+P*u)` and the partitioned count is `r*P*(h+u)`, a difference of `r*h*(P-1)`. This is a stock/count identity, not a runtime ratio. Multiple targets sharing a token within one provider still share one row; there is no per-theorem ad multiplication inside that domain.

Use a concrete inherited capacity boundary: one common key at 4097 independent providers requires 4097 provider ads in its depth-zero cell if all stay there, whereas the F cell cap is 4096 ads at a holder. An offer requiring all those providers' four selected copies at the same four depth-zero holders cannot fit that exact incidence. There is no inference that **all** possible assignments among 16 holders fail; capacity and actual incidence are checked per holder. The selected deep-cell/ancestor-marker mechanism can provide another path if separately funded, with changed lookup/copy/path calendars and real willing capacity. It is not free flat storage obtained by adding a provider.

Even before stock saturation, hot common tokens concentrate lookup/ROUTE_LIST/marker work at their actual nearest-holder sets. Source/provider capacity elsewhere cannot fund those holders. Group consolidation changes per-group operation overhead, not the rP signed row copies for one key, selected byte-time or full provider enumeration. Distinct provider identities may create more groups/lane records at the same holder; shared hosts do not eliminate them. No ideal uniform-placement average is a hard per-holder capacity theorem.

Retained bounded providers are not retired providers. Sealing a domain against discretionary new additions may stabilize C but preserves its proof custody, public service, applicable scans/incidents, route leases, marker renewal, query demand and funding boundary. For a fixed finite observation horizon, aggregate work includes every sealed incumbent. More domains reduce per-domain update size while increasing the population of independent standing obligations; whether actual group consolidation offsets any of that is an exact incidence/cost question.

## Query fanout: a bound on local work is not a bound on useful discovery

The common service cohort includes unfamiliar readers, not only already known direct contacts. Keep each query's formal expression, selected predicate, acquisition/application obligation and original total query budget. ROUTE1/STRUCT2 need no global ledger: paid lookup reaches candidate providers, each actual FIND tests its own exact postings, and the client independently checks a selected application. The resulting discovery is conditional and scoped; no component certifies global absence or completion under arbitrary ongoing growth.

G's initial interactive attempt permits at most 24 provider FIND pages, 16 route-cell lookups, four peers concurrently, two local CPU-seconds and ten wall-seconds, with its other byte/type limits. These are ceilings, not guarantees. At least one actual paid FIND page is needed to inspect a previously unqueried provider's hidden candidate relation in the simple case below. Four concurrency slots do not imply four total providers; likewise 24 pages do not mean 24 completed provider scans or 24 successful candidates.

**Indistinguishable-provider counterfamily.** Suppose P actually reachable eligible providers all advertise the same query token and their available unqueried metadata disclose no feature correlated with which contains a designated usable result. Exactly one provider contains that result. The same finite query cohort requires finding that result (or a fixed success probability), with at most q distinct provider probes; all nonwinning probes can return identical negative candidate observations. With the winning provider uniform and independent of the client's probe order/randomization, success probability is at most `min(1,q/P)`. This follows by conditioning on each previously unqueried provider: without new distinguishing information, the q probed identities cover at most q of P equally likely placements. For a deterministic algorithm a placement outside its probed prefix defeats certain success when q<P. This is not a lower bound against richer informative metadata or a different prior.

For a concrete G-policy case, take P=25 domains, each containing two current descriptors carrying the routed token: a decoy ad anchor and a nonanchor entry. Stipulate one admissible common query pattern under which all decoy anchors and 24 nonanchor entries mismatch; the remaining nonanchor entry passes and permits the designated checked application. Ads reveal only the decoy anchor, so directly acquiring that anchor does not reveal the hidden useful result. The exact feature/pattern incidence, bytes and native application are supplied hypothetical premises, not a generated Lean corpus. The client's chosen G attempt obtains unknown candidates through FIND; a different candidate-revealing query/import policy needs its own finite cost and comparison rather than a free shortcut.

Assume each split provider's two inspections fit one FIND page and the complete paid route/native/calendar work otherwise fits. The 24-page initial cap cannot guarantee visiting the winning provider. On one original provider the same 50 descriptors require only two pages under the at-most-32-pattern-probes-per-page bound **if actual bytes, node-pair work, CPU and service supply impose no earlier stops**; only the one matching descriptor is returned, well within the 32-type client cap. No two-second page maximum is treated as a supplied fast completion time. This is a finite same-query case where redistribution loses a page-budget guarantee despite correct routing, not a claim that a large provider always has useful discrimination. An exact-ID query, helpful learned prior or a different evidence-acquisition policy changes a stated premise.

More funding, preserved useful contacts, genuinely informative query tokens, or empirically successful local ranking can make the independent-domain path adequate for an actual cohort. Those are valid possible premises and heuristic techniques, not native truth authorities. Their cost and failures remain measured/specified against the same cohort; substituting known contacts, shrinking the query pool or lowering success/deadline requirements is a changed service, not an efficiency result. Replicating useful descriptors across domains may help recall but raises actual native/route/stock duties under the current qualified-provider role.

## Joint conditional certificate and decision rule

For each compared policy v and actual resource owner/host o, partition its finite work into: incumbent continuation; actual domain admission/migration; complete native/custody/use; posting/C/R construction; catalog builds; actual map/member/dependency scans; routing/query service; and funded cleanup/aftercare. Count each work event once in one class. At every prefix require

`spent_o + sum(disjoint remaining promised-job reserves_o) <= actual grant_o`.

Use actual complete vector bounds, not a scalar average. Stock requires the actual base allocations plus admitted positive overlap below every relevant cap, with zero forecast release credit. A later measured generation-fenced release can define a new base but cannot be deducted again. Include same-host shared arenas exactly once where physically shared and all real references/maps/working buffers separately. No remote CLOSED/EXPIRED response proves foreign physical reclamation.

Then require one concrete service calendar satisfying all incumbent/arrival publication, currentness, useful-query and lease deadlines at every provider, holder, exporter and reader. Primitive bounds include foreign queue/service/delivery and unresolved outcomes. Unknown original lease-clock continuity gives no continuity certificate. Actual query-path/willingness and native eligibility are supplied assumptions, not consequences of the equations. Bound build failures/other invalidations and provide lawful stopping/aftercare for every promised branch; a safe refusal is not a successful contribution in the fixed offer.

Under these premises, finite composition is straightforward: independent providers apply the existing custody/native/publication/routing guards to their own complete domains; actual host ledgers aggregate shared physical resources; exact anchor checking prevents cross-provider identity from changing mathematical acceptance; current catalogs preserve their per-member support predicates; and the supplied calendar discharges each finite offered service obligation. No global acceptance vote, central server, global current-state oracle or network task coordinator is needed. This establishes a **conditional sufficient finite plan**, not that the premises have been realized, nor a claim of perpetual useful supply or discovery.

Use this decision table to avoid endlessly adding mechanisms that solve the wrong bottleneck:

| Observed/proved failure in the same offer | Consequence | Minimal next question; no mechanism selected here |
|---|---|---|
| Full complete rebuilds dominate, but closure/route/query service and actual bounded-provider supply fit | Existing independent domains and lawful windows can be sufficient; no missing wire operation follows | Supply a complete operating case and qualify it later under execution authority |
| A coherent provider must retain one namespace/service but its complete build path cannot meet currentness deadlines | Same-identity slot labels and delayed mandatory incidents do not fix it | Is a paid exact change-specific/current-projection mechanism justified under unchanged guards? |
| Small qualified domains repeat a growing native closure or cannot reconstruct it | The qualified-provider coupling is a material capacity barrier, not a requirement on all V6 search roles | First test already selected I direct-contact candidate brokers under the same offer and complete costs; only a remaining service gap warrants a distinct mechanism study |
| Common-key duplication/hot holders exceed supply | Local catalog bounds do not supply routing capacity | Is changed actual placement, supplied deep service, or a different candidate-discovery representation warranted? |
| Uninformative provider fanout exceeds the unchanged reader budget | More providers can degrade useful reciprocal reuse | Can informative bounded retrieval/ranking improve the fixed query cohort, with explicit heuristic error and cost? |
| Target cap fits but history/posting/generation caps or retained incumbent work do not | The assumed O(NK) branch was not established or is not the full bill | Bound the actual traversed/retained state and continuing service, not merely selected outputs |

These questions can require distinct future studies; their existence does not authorize new protocol design in this note. Do not reject a policy merely because a conservative upper envelope fails if a better actual bounded schedule may exist. Conversely, an exact stock, information or duration countercase is not repaired by displaying a smaller unrelated upper bound.

## Research result and handoff

The useful new result is a precise separation: bounded **complete** provider domains can linearize the declared arrival-driven full-enumeration term, but the current full-native index role and provider-level token sharing move independently. The chain family gives a finite closure-replication defeat, the common-key identity gives an exact routing amplification term, and the fixed-query counterfamily gives an information constraint. They exclude a general scalability conclusion from bounded-domain labels, even in an honest network.
