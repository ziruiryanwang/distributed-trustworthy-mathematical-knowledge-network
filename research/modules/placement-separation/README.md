# Module: separate placement authority from logical index runs

Date: 2026-09-20. Author: `placement_scope_separation`; integration owner: root. Status: **UNSELECTED investigative design candidate**, awaiting independent review. No protocol identifiers are allocated. No implementation, executable model, extraction, native execution or benchmark is authorized or reported.

## Question and scope

Can a producer compact its local immutable mathematical index runs without migrating unchanged remote advertisements merely because the logical run identifiers changed?

The selected F/G/H/O design ties holder-group ownership to an immutable FeatureScope. This creates real old-group DROP/new-group PUT work during scope consolidation even when the same public targets, feature tokens, signed anchors and provider service survive. The [architectural contract](architectural-contract.md) investigates a stable, separately typed placement authority with explicitly versioned finite producer support. It preserves independent native checking and does not introduce a central server, global ledger, research task list or human-intention acceptance rule.

This is not a correction applied to frozen F/G/H/N/O/P or to the current-mode continuation investigation. The selected design remains [CURRENT-DESIGN](../../../CURRENT-DESIGN.md). Existing groups keep their exact old meanings. The candidate is useful only if its explicit support/authority/lifecycle contracts close and its shifted costs beat the alternatives under relevant workloads.

| Ownership | Stable placement authority is distinct from immutable logical runs; one provider/key owner, versioned borrower resolution | Proposed local state; new negotiated group semantics still required |
| Compaction | Preserve exact selected semantic map and publication bindings before claiming zero remote mutations | Conditional preservation argument, not an execution or cost measurement |
| Resources | Count local compaction, eligibility work, leases, transitions, retained histories and genuine new keys | Formulas and countercases; no supplied operating calendar |
| Compatibility | Never reinterpret operation 20, FULL_FEATURE or old ScopeIDs | New mode/open/result/status and mixed-profile consumer contracts remain unallocated and incomplete |

Main countercases are withdrawn anchors with unchanged remote member roots, stale borrower coverage, version/generation ABA, budget-exhausted compaction, namespace proliferation, capacity-driven repartitioning and old-group migration with lost outcomes. The architecture explicitly retains all of those obligations.
