Date: 2026-09-20. Author: `shared_support_catalog_author`. Status: **HELD complete source for two independent reviews; UNSELECTED**. This is paper specification and arithmetic, not implementation, an executable model, Lean execution, extraction or a benchmark. No predecessor or wire binding changes.

## Decision this envelope supports

Removing linear anchor search does not establish that the complete service fits. A candidate must jointly pay for initial conversion, recurring routing, complete current-index preparation, every actual support inspection, native/custody/query work, retained physical generations and deadline-compatible service at each owner.

This note derives three decision boundaries: a maximum funded build/member-service allowance for a declared finite plan; a guard-validity/deadline threshold that aggregate daily totals cannot discharge; and necessary adoption/enumeration limits for particular recipes. It does not invent favorable implementation constants to declare either RETAIN or SG operable. Both may use the reviewed provider-local catalog; independently justified old scoped algorithms remain competitors.

## Resources belong to actual owners

Let o range over the source, each distinct holder, native custodians/exporters, query consumers and any shared physical hosts. Resources are vectors: calls, CPU, I/O, traffic and paid byte-time; stock constraints additionally include actual RAM, disk, metadata, record counts, executor/batch slots and counter headroom. Roles sharing hardware or a parent grant share its ledger. Source spare CPU does not fund a holder or a querying agent.

For sensitivity only, `J-B` denotes a **new separately supplied** source grant with the same numeric ceilings as P's B: 196,608 calls, 28,800 CPU-seconds, 8 GiB traffic and 32 GiB I/O per admitted day; 1 GiB metadata, 8 GiB RAM and 16 GiB disk. Admitting J480 under these numbers still requires actual matching state, enlarged applicable count limits and all external supplies. Default F source counts may already exclude the dispersed case. Neither P's representation/service assumptions nor Q's 508 uncommitted calls or 64 MiB witness headroom is transferable funding for J480. No remaining Q allowance is used here.

Before comparison each owner supplies this finite ledger:

|---|---|
| Native/custody/use | Actual unique evidence/checking material, reconstruction RAM, dependency/assessment records, custody scopes/pins, export references, staged replies, checked-application work and candidate inspection/publication work |
| Complete current publication inputs | C manifest/dispositions; complete PublicIndexDescriptor, StructuralDescriptor and exact replay-link bytes; extraction/token records; actual FIND postings and physical index nodes, selection overlays/tombstones and required historical inputs |

| Per-use support | Actual group map/history/ad bytes, per-member exact anchor/token/scope bindings, complete current dependency visits and repeated read bytes, summaries/borrowers and final current guards |
| Routing and transfer | Every source/holder row/group generation including empty/partial/uncertain state, owners, actual encoded mutations, markers/paths, leases, queued calls, invocation outcomes/delivery, retained maps/snapshots and cleanup cursors |
| Continuing service | Renewal occurrences, discovery/query/native service, admitted repairs/revalidation, incumbent jobs, stopping/aftercare and the next funded decision boundary |

The complete structural input byte count is the actual allocation union of those manifests, descriptors, replay links, extraction records and layout/posting pages; it is **not** `480 * sizeof(locator)`. An input retained elsewhere still needs an actual readable location, pin and service bound. For scale only, 480 maximum-4096-byte StructuralDescriptor records use at most 1.875 MiB for that record class alone. This excludes public descriptors, replay/support records, posting structures, keys/ads, native closures, input history and transient buffers. It is not a catalog or metadata bound.

Define `Alloc_o(t)` as the set of distinct actually charged allocation generations at owner o. Count each physical allocation once per resource axis, including aliases' real reference metadata; count separate replicas separately. Catalog inputs may share native or index bytes, but equality of hashes does not establish shared allocation or release authority. Repeated read bytes are work even where unique physical storage is shared. Metadata may constrain a subset of disk/RAM simultaneously; satisfying its cap does not satisfy the full resident cap.

For example, a build peak includes current/old pinned inputs, two `n*w` resident slot buffers, payload residency, posting-set scratch, concurrent group maps/summaries, native checker/runtime residency and every other live generation. If unchanged inputs share one arena, do not count phantom duplicate bytes; if old readers keep separate layouts, do not erase them. Payload/pointer offsets bind exact generations. Required current-data service may outlive a catalog but must retain its own owners.

## One finite operation calendar, not independent favorable totals

For policy v, list actual planned events in precedence order: native/custody preparation; chosen old-mode retention or SG adoption; each C/R/guard commit; catalog build attempts and their bound input generations; actual group-scan attempts; authorizations, dispatches, settlements and renewal commits; query/application jobs; and actual local release barriers. Give every job an owner, disjoint work allocation, peak stock, complete duration bound, input guards, permitted outcomes and deadline. A scenario may contain finite branches; admission covers every promised branch's applicable bounds, not a favorable guessed outcome.

Record the intervals in which each catalog's C/R/V remains current. A build attempt is counted whether READY or abandoned. An unrelated renewal with coherent unchanged guards can reuse/rebind its summary: **two renewal passes do not imply two builds or two full scans**. Conversely, a layout commit invalidates this catalog-dependent recipe even with exact RepEq. Delaying offered C publication to avoid rebuilds changes publication service unless the original offer permits that batching. Queue saturation stops new promises but never authoritative invalidation.

For scan attempt j, use its actual reconciled map size m_j, complete dependency visits d_j and all repeated bytes. Set

`V_v = sum_j m_j`, `D_v = sum_j d_j`.

These include discarded/incident attempts and possible prior PUT outcomes. There is no division by replica count, shared theorem count or number of groups. Missing native assessments require separately admitted native work or nondecision. Incidents retain classification of the actual postsettlement map and a second complete scan of the actual cleanup result; the exhaustive supported/removal premise cannot hide UNKNOWN residual members. The same catalog can prepare both scans only while all its dependencies remain valid.

One nonoverlapping work account at each o is

`W_v,o <= F_v,o + sum_(b in Builds_v) B_b,o + sum_(j in Scans_v) S_j,o`.

All terms on the right are supplied conservative vectors, not measurements. F includes paid preparation of this plan, initial adoption, ordinary/incidental route calls, complete native/custody/query/candidate jobs, required revalidation, C/R construction, incident cleanup, old-effect settlement, summaries reused without full scans, histories and aftercare. B includes the complete catalog preparation/commit/retirement portion assigned to that build, with physical posting validation and bytes. S includes actual map/history inspection, signatures, exact member/scope/token/lookup work, D_v dependency work, and scan-summary/guard publication. A cost assigned to B or S is removed from F; cleanup scans cannot also be counted inside a generic incident allowance. A build's aftercare may be split into its own suffix only by transferring that disjoint reservation.

All owners, not merely the source, must have bounds. A routing holder normally has row/map/control work rather than the source's native support scan; native readers/custodians have their own actual service. Shared owner/host ledgers aggregate those distinct roles once.

## Finite sufficient admission certificate

At every owner, grant and actual prefix require

`spent + sum(disjoint unspent reserves for every promised remaining job) <= grant`.

A consumed prefix moves from unspent to spent; uncertain calls remain conservatively charged. A new catalog or changed stock observation creates no grant. Incumbent native/custody/use and finite aftercare are reserved before optional conversion/builds. At a measured stock cut b require, for each resource axis and every planned peak,

`stock_o(b) + admitted positive overlap_o(after b through peak) <= cap_o`.

Before actual release all forecast release credits are zero. An actual generation-fenced local release can define a new measured base; it neither subtracts the same release twice nor resets spend, unresolved effects or other references. The source cannot infer foreign physical reclamation from CLOSED/EXPIRED responses. Per-holder actual enforcement and supplied capacity remain indispensable.

Use a concrete executor/service calendar. The conservative recipe may serialize its own jobs, inserting incumbent reservations and nonpreemptible blocking. A remote path's complete elapsed bound includes holder queue/admission, processing, delivery and required settlement; simultaneous source and holder work is counted on their own resources, not twice as elapsed time when genuinely overlapped. No source slot entitles it to a foreign slot.

For each actual holder lease observation retain the original invocation occurrence, original effectful dispatch or proven-earlier timestamp s0, exact response, and continuous monotonic origin. Under holder/source relative-rate upper bound `1+rho`, use

`safeDeadline = s0 + remainingAtOriginalCommit/(1+rho)`.

Subtract the current source time to obtain margin. A replay's later send time, requested future lease or hoped-for future success cannot refresh it. For later rounds either use the actual new occurrence-bound observation before readmitting successors, or supply an explicit minimum resulting lease/response contract sufficient for that planned branch. An upper 48-holder-hour limit is not a minimum lease. Unknown continuity/deadline gives no no-gap certificate.

The critical path to each promised holder-row renewal includes its old effect settlement (OPEN included), any shared build, actual map/dependency passes, authorized cleanup and final renewal. The strict SG lane allows no competing effectful observation to bypass uncertainty. A prior action that removes a promised survivor defeats continuity from the original cut even if it settles promptly. Build latency is paid once as work but precedes every dependent group's deadline; it is never divided by cohort size.

Given complete valid input branches, faithful guards, actual resource/slot supplies, admitted native/use jobs and the above prefix/deadline checks, induction over the finite planned transitions gives their conditional service and accounting result. This is a sufficient certificate for that plan, not optimal scheduling, perpetual supply, or a guarantee of useful discovery. Rejecting a conservative bound does not prove every implementation or alternative schedule infeasible. Missing a service premise exposes the actual partial state and failed promise rather than retroactively declaring successful operation.

## Budget thresholds with explicit denominators

For one declared policy, owner and work axis d, let `A_d` be its actual current unspent grant after already-spent authority and disjoint incumbent obligations represented outside this equation. Let `F_d` cover all remaining fixed jobs above, excluding precisely the build and scan classes shown next. Suppose a finite regime supplies:

- J attempted builds, each with complete allowance `beta_d > 0`, including declared abandoned-attempt/aftercare bounds;
- V member occurrences, each with allowance `mu_d` for its exact per-member structural/scope/native-dependency work;
- `P_d` for all scan work not charged per member, including group maps, summaries/guards and empty-group jobs.

Then a sufficient reservation test is

`F_d + J*beta_d + P_d + V*mu_d <= A_d`.

For fixed nonnegative remainder it yields

`J_max,d = floor((A_d-F_d-P_d-V*mu_d)/beta_d)`

and, if V>0,

`mu_max,d = (A_d-F_d-P_d-J*beta_d)/V`.

Take the intersection over owners and axes, plus stock and calendars. A negative numerator rejects the plan; a zero build cost needs its direct inequality, not division by zero. Nonuniform jobs use their actual sums rather than this uniform envelope. These are maxima of a **declared sufficient reservation**, not necessary optimal capacities; upper costs exceeding them do not prove actual nonfit. They nevertheless identify what a design refinement must change: complete build cost/frequency, repeated member/dependency work, or independently supplied resources, not just locator comparisons.

For k actual mandatory complete J480 sweeps without changed membership, V=`61440*k`. If all 32 keys of target t use the same exact anchor with complete dependency inspection d_t on each occurrence, then

`D_v = 128*k*sum_(t=1..480) d_t`.

The factor 128 is 32 actual keys times four actual copies; fewer groups does not remove it. This is not 128 fresh native proof checks: d_t is the existing contract's complete current support/assessment inspection, with rechecking separate when needed. Early existing-summary reuse can eliminate a sweep and thereby lower k; renewal count does not define k.

For a newly supplied 28,800-CPU-second J-B source cap and k >= 1, the per-member allowance threshold is explicitly

`mu_CPU <= (28800 - spent/reserved-other - F_CPU - P_CPU - J*beta_CPU)/(61440*k)`.

Every subtracted term has disjoint ownership. Even setting every other term to zero gives only 0.46875/k CPU-seconds per member occurrence. That number is a loose arithmetic ceiling, not a supplied implementation cost or available headroom. With real nonzero useful/native/custody duties the allowable value is smaller. Conversely, if an independently established **actual lower bound** is d_min dependency visits/member and ell_d work units/visit, then `61440*k*d_min*ell_d` is a necessary work lower bound on this chosen scan recipe. If it alone exceeds the grant, that recipe cannot fit; no such positive cost lower bound is fabricated here.

## Churn has both work and valid-window thresholds

A bound on J alone is insufficient. For catalog epoch r let c_r be its actual start cut and c_(r+1) the next relevant C/R/V change. Under the conservative chosen serial order, let `a_(r,g)^+` bound time from c_r through complete preparation, incumbent blocking and all predecessors needed to publish/authorize group g's current summary. Let `z_(r,g)^+` additionally bound the path through its actual holder renewal commit. A sufficient condition for this use is

`c_r + a_(r,g)^+ < c_(r+1)` and `c_r + z_(r,g)^+ < safeDeadline_g`,

with all other group/owner guards stable at authorization. There must actually be a supplied start slot at c_r; otherwise include the wait. A later incident after authorization may allow an already authorized renewal to commit, but cannot restore a current source-support assertion. The stated service must specify how long those assertions may remain degraded.

For a periodic supplied stable window Delta, a single group's simplified path is build b plus scan/authorization s and renewal completion r. The sufficient threshold is `Delta > b^+ + s^+` and `remainingSafeMargin > b^+ + s^+ + r^+`; multiple groups replace s/r by their actual prefixes. This is separate from `J <= J_max`. Failure using upper bounds only rejects this sufficient certificate. A genuine failure proof instead needs exact/lower duration and actual expiry premises, as below.

**Supplied finite defeating case.** This timing case is separate from a realized J480 corpus. A continuing supported survivor group has an actual lease expiring at source time 600, equal continuous source/holder clocks and a coherent original invocation basis giving that same conservative bound. For example, original dispatch/commit at -600 with 1200 holder-seconds remaining gives deadline 600. At time 0 there is no independently valid summary or already authorized in-flight renewal usable after the change. Relevant actual selected-entry C commits occur at times 0,70,140,...,560; they invalidate this catalog-dependent policy without invalidating the designated survivor's native support. All changed entries have separately supplied native/custody publication prerequisites and bounded finite state; the case assumes no unpriced extra row or scope allocation.

For this case stipulate **exact**, not merely maximum, durations: each full current build takes 60 seconds; the vulnerable group's actual full scan/authorization takes 15; its holder renewal commit path takes 5. The 15 seconds is residual required scan/authorization after the current catalog becomes READY, with no earlier credited precomputation in this supplied recipe; it is not a lower bound on a differently staged algorithm. Primitive queues are otherwise available and there are no old unresolved effects. Every early 70-second window ends before the required 75-second summary/authorization point. A newly captured cut cannot use the preceding cut's partial scan. The last cut at 560 cannot authorize before 635; even a hypothetical still-active renewal could commit no earlier than 640. In reality the actual old lease expires at 600, so that renewal cannot preserve its continuity and an expired-group renewal is refused under the inherited rule.

The eight interrupted prefixes can each be stopped at the next invalidation after 70 seconds; a final full hypothetical path has 80 seconds. Thus the attempted-path allowance can be at most `8*70+80=640` CPU-seconds under an additionally supplied at-most-one-CPU-second per elapsed-second bound, well below a 700-second residual allowance. Real incumbent native/custody/query/publication jobs must separately fit the rest of the source grant and reserved slots; they are not removed by this comparison. Ample charged stock and holder capacity do not fix the absent 75-second stable authorization window. Continuing noncritical use jobs can succeed while this promised row continuity fails. This is a failure of this exact supplied recipe/service case, not a claim that every correct scanner needs 75 seconds. Deferring the C commits, using another qualified summary policy or reducing the critical path changes an explicit decision variable.

**Growing-current-domain enumeration.** A second necessary recipe boundary concerns actual traversal rather than timing. Start with e0 distinct selected current catalog locator rows. Each of n arrivals must add at least one distinct new selected current locator row, and all preceding rows must remain selected/current through the later named builds: no pruning, coalescing or replacement removes them. Distinct retained submissions or replay objects alone do not establish this growth premise. Consider only finite admissible prefixes within the actual count/byte/resource caps, not an unbounded fixed-cap provider. If the service offer requires a fresh completed whole-current catalog after **each** commit before the next, preparation enumerates at least

`sum_(j=1..n) (e0+j) = n*e0 + n*(n+1)/2`

current records, before history, postings, member work or initial preparation. This is an actual record-visit lower bound for the declared full-enumeration recipe, not a runtime bound for all algorithms. With fixed batch size b and n=bq, the corresponding visits are at least `q*e0 + b*q*(q+1)/2`; batching changes delay and reduces the coefficient but stays quadratic in n for fixed b. If the offer permits skipping superseded cuts, this per-commit premise is absent and the lower bound does not apply. Converting visits to CPU/I/O requires actual positive per-visit cost bounds. Incremental or exact projected catalogs would be separate mechanisms, not assumed solutions here.

## Consequential conclusions and remaining inputs

The jointly admissible region for each policy is the intersection of the complete work inequalities, every owner's positive peak-stock constraints, current guard-valid windows, actual lane/outcome histories, and every promised service deadline. It is not defined by locator count or final group count alone.

- Under the specified dispersed adoption strategy and a single J-B call grant, the region is empty before useful service is added. Dense SG's renewal reduction remains conditional on financing conversion and holder-local peaks.
- Whole-current catalogs remove a structural-search amplification term but leave 61,440 member occurrences per full J480 sweep, actual D_v and complete current-index preparation. Both modes can use the catalog; no SG-only credit or deferred twenty-entry projection is imported.
- `J_max` and `mu_max` expose a measurable design target without claiming it has been achieved. The exact C-churn case proves that fitting a daily resource total is not sufficient for timely current authorization. Per-commit whole-domain enumeration can also become the next growth barrier.
- RETAIN can avoid optional conversion and may preserve independently valid scoped summaries. SG can save dense recurring calls and avoid NORMALIZE owner transfers, but neither benefit supplies proof custody, native reconstruction or checked reuse.

The unresolved quantities that can change this decision are now specific: complete current descriptor/posting/pin bytes and residency; per-member actual dependency/byte work; complete build duration/work under that residency; actual allowed C/R/incident windows and query/publication delays; full adoption/aftercare per-owner vectors; and independent holder/native/query supply. Supplying only a fast locator benchmark or a favorable final-state byte count would leave the decisive tests unevaluated.

No positive whole-service qualification or sustained useful-growth result is established. This bounded envelope permits a later independently supplied operating case to pass or fail explicit tests; it does not select SG/catalog, allocate symbols, authorize implementation, or revise P/Q.
