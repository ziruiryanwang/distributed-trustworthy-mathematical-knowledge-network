## Exact feature derivation

Let B and A be closed exact carrier expressions under one adopted foundation. In this fixture each has a small, completely inspected informative raw head, denoted b and a. Let f, op_B and op_A be exact rigid external references. Displayed notation below abbreviates their fully explicit native expressions; it does not authorize source-name, coercion or typeclass resolution.

The initially unknown corpus supplies these specialized actual effective declaration types:

- `f : B → A`;
- `h : ∀ x y : B, Eq A (f (op_B x y)) (op_A (f x) (f y))`;
- `r : ∀ x y : B, Eq A (f x) (f y) → Eq B x y`.

Each source is an eligible retained STRUCT2 target with its ordinary exact selected evidence. All three types have only the displayed binders, no hidden earlier uninstantiated parameters, and small enough syntax to finish the required inspections. Their native declarations, not their display spellings, are the fixture.

| Target | Raw selected domain heads | Exact reason tag 5 survives |
|---|---|---|
| f | B | Lane 2 emits `[4,b,a]` then `[5,b]`; both fit its eight-token reservation. |
| h | y:B, x:B | Terminal EqRef is excluded from informative output heads, so no input/output pair is generated. The first informative domain generates `[5,b]`; repetition coalesces. |
| r | final equality premise, y:B, x:B | The final domain's EqRef is not informative; subsequent B domains generate `[5,b]`, again within lane 2. |

Hence the client can compute the same token `Hash(ExtractorID,[5,b])` from its local B alone and submit existing mode-6 BINDER_DOMAIN with that single required token. The hash notation here abbreviates STRUCT2's exact domain-separated token encoding, not a new encoding.

The necessary initial query has `PatternOption=[0]`. Token membership alone is enough to nominate all three kinds of declaration. A descriptor nominates a target and replay, not its native type. The client must obtain actual type-bearing objects through existing authorized source scopes, and all accompanying bytes count. In particular, a definition object can carry its body; a “type probe” is not an invented free header endpoint.

For associativity, the image-side desired equality has informative operand heads `Head(op_A)` on both sides. Existing APPLY_RESULT lifting can request `[2,0,Head(op_A),Head(op_A)]`. The actual A-associativity theorem emits that pair first in the reserved conclusion lane for this small fixture. No JudgmentID of that theorem is needed to produce the query.

## Minimal supported paper retrieval path

Choose one already permitted known-contact provider and a finite public snapshot containing the explicit f/h/r above and the A-associativity theorem, with no other matching rows. The existing known-contact start is a supplied finite service condition, not a central server requirement. Descriptor-ID order is immaterial because every matching row fits the page and type-probe envelope; the algorithm need not know which identifiers will be returned.

1. From B, issue the token-only domain query. The three matching descriptors are returned in ordinary descriptor-ID order.
2. Probe their actual type-bearing objects in that order. Syntax can pair the exact repeated f reference in h/r with the f candidate and recover A/op_A. These are inert nominations until their actual complete selected evidence, typing and current-use guards are checked.
3. Form the one A-side associativity view from the nominated syntax. Issue its ordinary relation-pair query, which returns the A theorem.
4. Obtain and independently check the exact f/h/r/theorem evidence and arguments; build the preservation/congruence/associativity/reflection proof already described by BRIDGE1. No metadata match proves either preservation or reflection.

This trace requires two successful provider pages and four type probes, one image view, plus every actual acquisition/checking cost. Those count under, rather than in addition to, the proposed eight-page/sixteen-probe/two-view ceilings and shared parent resources. A protocol continuation, failed source contact or discovery step also consumes its actual admitted resource allowance. The trace assumes small supplied objects and enough admitted resources; it does not establish real performance or promise that every target is cheap.

## Concrete failure cases and required limitations

### FE-001: a B-domain pattern excludes reflection

STRUCT2 stores only its last inspected domain as a complete binder-domain pattern. For r above that domain is `Eq A (f x) (f y)`, not B. A BINDER_DOMAIN query with the concrete B pattern may therefore exclude r even though r carries the requested `[5,b]` token. The smallest repair is `PatternOption=[0]` for this discovery lane; there is no need to change STRUCT2 or fabricate a pattern for every domain.

### FE-002: a familiar wrapper can hide the entire route

Replace only r's displayed type by `Function.Injective f`, where the ordinary definition has the same mathematical meaning. Its native declaration type now has that exact wrapper head and no syntactically exposed B binder. STRUCT2 does not delta-unfold it, so it need not emit `[5,b]`. f and h can be discovered while the independently sufficient reflection evidence remains outside the initial lane. Assuming that the English word “injective,” a source class registration or a familiar constant name repairs the miss would invent an unsupported index.

The same limitation applies to a B domain presented as a distinct alias or a beta-headed expression. Tag 5 uses informative **raw** domain heads. Normalizing the last-domain focus does not authorize a new tag-5 emission rule for all domains. “Closed B” alone is therefore insufficient: the admitted initial fragment must require the relevant explicit raw heads or accept an unsupported/missed case.

### FE-003: generic Lean interfaces are not specialized native fixtures

A generic homomorphism theorem may bind a carrier variable α and dictionaries, with x/y domains α rather than the local exact B. Those parameter heads are not b. A theorem stated with `Function.Injective`, coercions or structure projections can have a different native shape from the explicit fixture. Source implicitness is not a network instantiation service: Native2 does not import remote elaborator extensions, source instance registrations or binder annotations as authority.

An optional bounded local proposal engine may guess actual universe/parameter/dictionary terms and inspect known definitions, but must charge that work, retain unresolved arguments and ultimately check them. The initial supported example must not quietly assume this general elaboration has already happened.

### FE-004: finite candidate coverage must be a stated premise

More than sixteen matching type candidates can place h or r outside the inspected prefix, even when all objects are true, available and correctly indexed. A long telescope can put B outside the last sixteen inspected domains. Rich types can exhaust visits or token lanes. More pages do not by themselves repair a type-probe limit. These are normal bounded misses, not evidence that no bridge exists.

The successful finite fixture avoids these misses by defining the whole matching scope small enough to inspect, not by placing known answer IDs first or granting the client a hidden list of useful declarations. A performance evaluation must include crowding, wrapper and cold-closure losses in its denominator.

## Soundness and evidence boundary

Speculative view generation can remain entirely syntactic, including construction of a query containing exact unqualified A/op_A references learned from an acquired type object. Such syntax carries no theorem acceptance, checked map state, authority to execute remote code, or assertion that those references are compatible with the receiver. Query syntax and source disclosures still obey the actual local policy and resource limits.

Only the existing complete-evidence and exact application path can establish a reusable result. The conditional mathematical argument requires all four actual ingredients: a typed map, operation preservation, a checked A-side equality and equality reflection. A constant map with preservation into a singleton does not generally supply reflection. Dropping r would turn the proposed return path into an unsound one even when every retrieved A theorem is valid.

### FE-005: explicit judgment telescope versus Pi syntax — repaired and closed

The helper-recognition algorithm's step 1 says “Strip only the exact stated Pi sequence.” However, STRUCT2's indexed judgment type is its **ordered context telescope followed by its conclusion**. A semantic h/r judgment can place every displayed binder in that explicit context, leaving only an Eq conclusion and no leading Pi nodes at all. A literal Pi-only implementation would reject these ordinary supported semantic declaration forms.

A minimal r counterexample has explicit context `[(x,B),(y,B),(p,Eq A (f x) (f y))]` and conclusion `Eq B x y`, with no leading Pi in that conclusion. In the conclusion's actual de Bruijn scope, x is index 2, y is index 1 and p is index 0; in p's domain, x is index 1 and y is index 0. These positions cannot be replaced by display-name matching or by treating the conclusion as a closed expression. Its effective type is exactly the required r signature, yet a literal attempt to peel three Pi nodes from its stored conclusion fails immediately.

Required repair: define helper/image-theorem matching over the effective declaration type obtained from the exact ordered judgment context followed by any permitted leading Pis in the conclusion. Preserve dependent order and correct de Bruijn scope; do not assume stored source binder labels or copy a potentially large implicit Pi expression. The combined effective binder sequence must have exactly the selected signature, with no extra assumptions. Definitions/opaque candidates use their actual declared type. Phase D's image-result matcher needs the same effective-type convention.

Closure criterion: the repaired proposal explicitly applies that effective-type convention to both helper recognition and phase D, rejects additional combined telescope binders, and retains scope-correct comparison/instantiation. This does not add a new mathematical feature or richer supported fragment. It makes the selected template refer to the actual already selected representation. The author and integration owner were notified before the initial audit was saved.
