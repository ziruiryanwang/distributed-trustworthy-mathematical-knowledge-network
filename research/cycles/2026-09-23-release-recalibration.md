## Selected next milestone after replica return: real network capability

The implementation-ready proposed follow-through is now in
[Remote transport v1](../../spec/REMOTE-TRANSPORT-V1.md), an explicit addendum to
the historical network concept rather than a claim of implementation. It needs
independent review before a successor source cut changes.

The selected source has these code-enforced boundaries, confirmed read-only:

- `manage.py:70` constructs every endpoint with host `127.0.0.1`.
- `py/node.py:72` rejects any other host with `CONFIG_PEER_LOOPBACK`.
- `py/peer_service.py:116,121` fixes the connection address and HTTP Host.
- `py/peer_service.py:235,241,247` fixes recorded host, listener and readiness.
- `py/peer_service.py:264,269` rejects other source addresses and Host values.

Removing one check cannot produce a correct remote implementation: all public
configuration, workers, server authority, request construction, receipts and
support statements must describe the same profile. No change to those files
or network execution is authorized by this read-only checkpoint.

**Recommend one minimal owner-configured remote profile**, not a DHT, universal
peer discovery, global identity system or public listener by default. Its
preimplementation contract should fix the following distinctions:

1. **Endpoint authority.** The local owner selects each alias's exact destination,
   port and transport profile; remote catalog data cannot redirect a connection.
   Start with an explicit literal-address profile to avoid introducing DNS and
   rebinding semantics. Refuse redirects and ambient proxy substitution. Make
   nonloopback listening an explicit owner choice, with loopback the default;
   do not turn `0.0.0.0` into an implicit convenience setting.
2. **Endpoint authentication.** Use a narrowly specified authenticated transport,
   for example TLS with an owner-pinned certificate, or an explicitly selected
   and tested authenticated-tunnel adapter. Decide pin provisioning, mismatch,
   rotation and failure behavior before implementation. A source IP/HTTP Host
   check is not cryptographic peer authentication. Operational endpoint keys
   need not identify human authors and confer no mathematical authority.
3. **Content and proof authority.** Authentication binds a session to the selected
   endpoint, not truth, completeness or currentness of its catalog. Preserve
   exact page/bundle/content checks, receiver-side metadata rederivation and
   fresh local Lean admission. A malicious authenticated endpoint can omit data,
   stall or serve unacceptable candidates; it still cannot supply acceptance.
4. **Bounded operation.** Include connection/authentication handshakes in finite
   wall/CPU/byte/concurrency allowances, refusal and pending-state accounting.
   Keep service exposure read-only, with no peer-triggered local source execution,
   private-state route or configuration mutation. State conditional availability;
   do not promise Internet DoS resistance from one bounded synchronous listener.

**Falsifiable local gate, possible without external binding:** configuration
round-trip/refusal tests for remote destinations; synthetic/fake sockets proving
the chosen destination, Host and listen address are honored rather than replaced
by `127.0.0.1`; separate loopback processes exercising the real authenticated
transport success plus wrong-pin, wrong-authority, truncation, malformed content,
timeout and quota cases; then the genuine D1 custody/acquisition/fresh-admission
path through that same transport implementation. A socket double alone does not
qualify authentication or transfer. Loopback test execution does not establish
NAT, firewall, independent-machine routing or independently operated deployment.
Freeze exact failure/status/state expectations and finite resources first.

After the transport profile has these gates, perform a **fresh-operator, measured
reciprocal continuation on its pinned candidate**. Use public build/configuration,
request-helper, management, custody and status interfaces. Reuse the genuine D1
publication rather than authoring another toy control or replaying the old failure
just to obtain a green label.

Pass only if an independently briefed operator/agent can install/configure from
the candidate instructions, discover/acquire/admit available mathematics, author
and publish a nonvacuous successor, and have another node freshly admit it after
the author's service stops. The successor's canonical proof must actually reach
the acquired result; include its exact target and assumption/foundation checks.
A second useful operation must work on preserved state with honest remaining or
explicitly renewed allowance. Fix a finite wall/resource/intervention budget
before execution; include the full unsuccessful work in the outcome. Source
refusal is allowed if it is terminal, charged and recoverable by the agent;
unknown outcomes, hidden state repairs or manual acceptance are not a pass.

The fresh-operator test is necessary but not sufficient: on loopback-only code
it would establish an operable local product, not the network goal. Conducting
it after remote-capable implementation checks the intended release profile and
avoids polishing an architecture that still lacks its central transport. If these
gates pass, move to the small heterogeneous usefulness/cost comparison; if one
fails, fix its demonstrated central obstacle before expanding mechanisms. No
second physical machine is required for these local milestones; none of their
results can be called independently hosted operation.
