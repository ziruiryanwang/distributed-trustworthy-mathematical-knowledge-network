# Next aggregate investment: preserve useful frontiers before funding them

2026-10-12. Source/theory decision aid; no runtime, new source implementation,
proof funding, cap increase or release acceptance is selected by this note.
Canonical root: `E:\Distributed Trustworthy Mathematical Knowledge Network`.
Existing source, receipts, failed operations and evidence remain unchanged.

## Central conclusion

The immediate question is not whether another two-delta proof would add new
mathematics. It would not: those conclusions already have actual native checking
evidence. The question is whether the system can cheaply advance a **reusable
certified frontier**, so that later contributors need neither all ancestral proof
witnesses nor a separate cryptographic certificate for every intermediate theorem.

There is an additional investment hazard in the current implementation:

> An aggregate receipt produced under guest image A cannot currently serve as
> an aggregate frontier under an optimized successor image A'. Stabilizing the
> mathematical member identities does not stabilize receipt compatibility.

Therefore separate three decisions:

1. One bounded execution screen can answer whether the selected representation
   improvement fits the unchanged guest envelope. It need not fund a proof.
2. A finite capability qualification can establish the genuine aggregate import
   boundary. Its purpose and cost are research/release assurance, not a claimed
   profitable production investment.
3. Repeated operational sealing needs a defensible complete-route benefit and
   service-capacity argument, including how the resulting receipt survives normal
   implementation upgrades. Popularity alone supplies neither argument.

The cheapest next screen remains the independently reviewed bounded-parse
successor, after its actual native/build gates. Before investing heavily in its
first successful seal, make an explicit choice between retaining that image as
a supported frontier producer and implementing the small, reviewed multi-image
compatibility boundary below. No compact binary codec or deeper checker rewrite
should be developed in parallel merely because it might help.

## The exact image-compatibility obstacle

This is a read-only finding in the actual selected source interfaces, not a
hypothetical weakness in cryptographic hashing.

| Existing boundary | Current rule | Consequence for an old A receipt under child A' |
|---|---|---|
| `aggregate_claims/header.rs` | H includes A, fixed I, foundation, policy, member root/count, maximum rank and seal height; `bind_image(x)` requires H.A = x | The header already states the exact proving image |
| `aggregate_claims/relation.rs`, aggregate assumption tag 1 | Decode parent H, then `parent.bind_image(output_image)`; pending image is `output_image` | Parent A must equal child output A' |
| `aggregate/main.rs` | Call `env::verify(pending.image(), pending.journal())` for every pending claim | It can already discharge exact image-specific claims; the relation must authorize which images are admissible |
| `aggregate/receipt.rs::verify_pending` | Non-I pending image must equal independently adopted A; exact H and full non-dev application verification | Host preflight also intentionally enforces one A |
| `aggregate_claims/input.py` and member bindings | Aggregate parent headers/openings are decoded under the one `adopted_image` | Encoding/acquisition paths also reject different A values |
| `mixed_claims/packet.py`, `receiver.py`, `imports.py` | Single aggregate image and single aggregate owner/profile; owner-origin/lifetime checks bind it | Public ordinary-delta reuse cannot silently become multi-image |

H is the fixed 192-byte `DMKNA002` header. The outer witness stream is
`DMKNAI02`. The legacy I journal J remains 184 bytes. Membership commits exact J
bytes, not a sender assertion that two similarly named theorems are equivalent.

An optimization changes executable image identity even when it provably
preserves the mathematical relation. The old receipt remains valid **under A**;
it does not turn into an A' receipt. Replacing H.A, copying a success record or
verifying the old receipt under a convenient inferred image would break the
intended trust boundary. Keeping old A supported can preserve that route, but
does not allow a new A' guest to import it under today's same-A rule.

## Safe compatibility: adopt implementations of one mathematical relation

Separate two things that are currently coupled operationally:

- The mathematical meaning: valid exact module warrants under the selected
  foundation, permitted axioms, semantic policy and declaration interpretation.
- A particular implementation image that establishes that meaning through a
  particular receipt scheme, checker and recursive-assumption rule.

A new guest may accept old images only when the adopter has justified that
their conclusions imply the mathematical validity predicate required by the new
guest. Equal header fields are necessary bindings, not evidence of that implication.

Write V(J) for “J denotes a valid module under the selected mathematical policy.”
For a reviewed legacy image a and header H, the needed assurance statement is

    ValidApplicationReceipt(a, H) and H.A = a
      implies every exact J committed by H satisfies V(J).

This is conditional on cryptographic soundness, commitment binding and correct
implementation of the relevant checking/interpretation rules. It is **not** a
new proved checker-to-Lean refinement theorem. If the old relation allowed extra
axioms, interpreted bodies differently or contained an unsound checking path,
matching I/foundation/policy strings cannot repair it. Mathematical semantic
inclusion is the obligation; equality of execution costs or witness languages is
unnecessary when the accepted conclusions remain sound under V.

### Smallest initial mechanism

For one explicitly reviewed new image, compile a finite legacy-image/profile
table into its source. The table identifies exact old images, exact supported
header/commitment formats and fixed mathematical/cryptographic profiles. The new
guest additionally supports its existing self-image case, bound externally as
today by the final receiver.

For each aggregate parent:

1. Decode an exact supported H and validate its mathematical/profile fields.
2. Require H.A to be either the declared child output image or an exact image in
   the compiled reviewed legacy table. This is membership in a locally adopted
   trust set, not a sender's claim that an image is trusted.
3. Construct the pending claim as `(H.A, exact H bytes)`, **not** `(child A, H)`.
4. Keep the same bounded membership, exact-J, graph, rank, used-assumption and
   target-closure checks; preserve child height `1 + max(parent heights)` with
   overflow refusal. Check every new delta under the selected conditional relation.
5. Execute `env::verify(H.A, exact H bytes)` for every unique actual claim and
   require complete recursive assumption resolution in the final application
   receipt. The final recipient still verifies under independently adopted child
   A and requires output H.A = that actual A.

The self-image rule does not require an impossible embedded self-hash. A sender
could put a different output image in its wire, but the final independently
pinned verifier rejects such a claim. The dynamic pending-image API is not
authority to accept any image: the checked relation and final actual-image binding
jointly restrict it.

Conditional soundness follows from the legacy assurance statements, induction
on aggregate seal height for same-image recursive premises, and topological
induction over newly checked deltas. Legacy assurance must include its own
transitive accepted-image dependencies. Each frontier opening inherits V from
its actual verified header; exact premises then establish V for each new member.
Changing image does not justify weakening mathematical ranks or claim equality.
Avoid circular upgrade assurance: an old-image inclusion argument cannot assume
the soundness of the not-yet-justified new image it is meant to justify.

### Minimal API/schema migration, before any code is selected

For old and new images using the same exact H/J/membership formats, the existing
wire already carries every parent image in its H. There is no information-theoretic
need to add a new field or rewrite member identities solely for image compatibility.
The accepted relation and local adoption profile nonetheless change, and the
compiled guest image necessarily changes. An explicit new profile/behavior version
must prevent callers from assuming old one-A APIs support the new relation.

The minimum coherent implementation scope would include:

- A shared exact parent-profile admission rule in the new relation and host
  `verify_pending`, with the same legacy set and same supported format/profile
  semantics. The guest remains decisive even if a host lies; disagreement can
  still produce needless failures and expensive work.
- Input encoding/binding APIs that distinguish **child output image** from
  **admitted parent images**. An unconstrained sender-provided list is not such
  an API. A locally selected immutable profile supplies the table.
- A public verifier-owner map keyed by exact supported image/profile where
  mixed frontiers are exposed. Each actual receipt is checked by that specific
  owner and exact header; multiple receipt claims cannot share authority merely
  because their ModuleIDs match.
- Profile/cache/lifetime identity that includes the exact adopted image set and
  cryptographic/checker policy. Changing that set is an explicit new profile;
  old live handles or stored success flags cannot silently cross it.
- Exact negative controls for unadopted image, old-receipt/new-image substitution,
  same-header-field but inadmissible image, altered membership, missing assumption,
  and profile mutation. A genuine cross-image receipt test is a separate later
  capability allocation, not replaced by these source/synthetic controls.

If a codec, H layout, member commitment meaning, foundation or policy changes,
add explicitly versioned dispatch with a separate semantic interpretation and
inclusion argument. Never make the old decoder permissive to an unknown header.
A deliberate wire-version increment may be useful for negotiation even for a
same-layout behavior change; it is not required to represent an already present
parent image. Old clients may safely refuse unsupported new profiles.

### Static versus externally committed admission policy

A fixed table in an immutable adopted image is the simplest initial option. It
has finite audit scope, no live server dependency and no policy lookup on every
receipt. Adding an allowed image creates a new guest image; cross-image imports
then allow retained expensive receipts to remain useful to that successor.

An external policy could also be safe if the guest and recipient independently
pin an immutable policy commitment and verify membership under it, with exact
format/semantic meaning and update rules. A sender-selected commitment proves
only membership in the sender's chosen list, not authorized checker soundness.
If one generic guest accepts many policy roots, the application claim must bind
the relevant root (or the receiver must otherwise enforce the exact admitted
one); the present header has no separate upgrade-policy-root field. This is a
larger policy/schema design, not an unsigned list file passed to today's APIs.
Signed mutable lists replace some trust with update-key governance and rollback/
revocation obligations. None of these options requires one global registry.

### Security updates are the limit of compatibility

Performance migration can preserve valid old receipts. Soundness revocation is
different: wrapping a receipt made by a buggy checker in a new aggregate cannot
cleanse its false premise. An image that admits the revoked image can itself
certify contaminated descendants, even if its own new-delta checking is correct.

With the present compact H there is no public complete ancestry/taint commitment
that lets a receiver identify every unaffected descendant selectively. A safe
initial response may conservatively withdraw adoption of transitively exposed
images and re-establish affected frontiers from sound evidence. That can reject
some actually valid work; it is preferable to treating wrapping as repair.
Selective revocation would need its own bound, authenticated dependency statement
and assurance design. This note does not invent one or add identity governance.

Thus image stabilization alone is a temporary cost-control tactic, **not** a
sufficient worldwide upgrade architecture. Nor is a permanent accept-all-old-
images table acceptable. Preserve immutable evidence, separate performance
compatibility from security validity, and make local supported profiles explicit.

Independent assurance source challenge agrees that same-profile migration needs
no structural header/wire field change, that the pending image must actually be
changed to the parent's exact A (not merely loosening `bind_image`), and that
already folded assumptions cannot be revoked by a host-only filter. It also
correctly limits priority: no genuine A receipt currently exists, so this remains
an investment/upgrade design decision and must not displace the immediate
bounded-execution cost blocker with an unneeded parallel implementation.

### Conservative revocation without a new mathematical header

Root proposes a useful theory candidate: attach complete reviewed **potential
authority dependencies** to each locally adopted image/profile. The immutable
compiled legacy-image tables induce an implementation-support graph. Its edges
describe what an image *could* accept, not which parents one particular receipt
actually used. The own-image recursive case is handled by the existing seal-height
induction; it is not an inter-version cycle. Require the separately adopted
legacy-image graph to be finite and acyclic for this simplest assurance argument.

Let D(a) be a conservative complete direct dependency set for adopted profile a,
and let Cl(a) be its reflexive transitive closure. Include the relevant I,
foundation/checker and cryptographic-profile dependencies as typed trust nodes,
not only aggregate executable images. For locally known revoked nodes R, admit
an image/profile only if

    Cl(a) intersect R = empty.

This over-approximates taint: it rejects a profile capable of relying on a revoked
predecessor even when this particular receipt never did. It cannot miss such a
dependency **if** D faithfully contains every authority path permitted by the
actual pinned code and profile. A sender's incomplete metadata would invalidate
that premise. The receiver therefore adopts reviewed metadata bound to the exact
image/implementation and its complete support table, not an unauthenticated
receipt annotation. Unknown or unavailable required metadata cannot mean “clear.”

This permits unchanged H: the recipient already pins actual image a, which selects
its independently adopted dependency metadata. After learning a revocation it can
invalidate all transitively exposed profiles, including live imported handles and
persisted checked-cache authority derived under them. Clearing only future host
preflight while retaining those old handles would not enforce the stated rule.
A clean successor profile must exclude exposed predecessors or re-establish needed
mathematics from sound evidence, not rewrap an already accepted old warrant.

The closure concerns **implementation versions and trust profiles**, not every
mathematical theorem or proof ancestor. It may be cached and incrementally
maintained. Its work is not inherently constant: a growing version graph has
storage/update cost and needs explicit adoption bounds. Truncating it under a
budget and treating the result as complete is unsound. A small supported version
window with explicit refusal is an operational choice, not automatic global
compatibility. A metadata server need not be central or mathematically authoritative;
the local code-bound adoption process supplies the trust decision.

The rule restores the appropriate future acceptance boundary **after** complete
relevant revocation information reaches an honest maintained client and it applies
the policy/derived-cache invalidation. It cannot tell a partitioned client about
an undiscovered bug, undo decisions made before the update, or guarantee universal
simultaneous revocation. “Eventual safety” therefore needs eventual communication,
policy update and revalidation assumptions. Previously emitted false results do
not become true merely because their software has been withdrawn.

This is a defensible compatibility/revocation design without mathematical ancestry
replay. Precise receipt-by-receipt exemptions would instead require authenticated
dependency summaries with a new public-claim interpretation, or rechecking from
adequate original evidence. Root's candidate is theoretical and unimplemented;
neither its code binding nor operational update protocol is cleared by this note.

## Smallest missing cost evidence

The existing notes already define the full-cost comparator and sealing inequality.
The practical gaps for this exact aggregate investment are narrower:

1. **A successful complete A execution**, under an adopted actual image, with its
   real segment layout and actual frontier claims. A capped prefix cannot supply
   this. Native success is not a guest cost estimate.
2. **A finite successful-production route and quote**, including segment proving,
   recursion, actual assumption resolution and final verification. A finite attempt
   budget is not a promised successful-seal price. Quote uncertain terms explicitly;
   record actual failed and successful work without double-counting nesting.
3. **One exact proposed packet rewrite**, with before/after wire bytes, receipt
   size/checks, selected member/interface/body costs and residual branch ancestors.
   The current second delta imports both the base and first delta: replacing the
   first alone does not make the base disappear. Compare whole receiving routes.
4. **Matched receiving and service costs**, under stated cold/warm/cache classes,
   and a horizon/demand/custody assumption. Do not reuse the timer-quantized small
   native worker observation as a precise full-route saving.
5. **Useful lifetime of the funded frontier**, including supported image migration,
   retention/repair and security-policy failure. A seal that is discarded at the
   next optimization has a different amortization region from a maintained one.

For a proposed exact rewrite, fixed nonnegative resource weights w and horizon T,
the existing rule is

    sum_i w · (C_before,i - C_after,i)
      > w · (C_new-production + C_new-service(T)).

All C terms in this display are resource vectors with the same units/order;
both sides are scalars priced by the same fixed w. Equivalently, already priced
scalar production/service costs may appear on the right, labeled as such.

CPU, bandwidth, storage occupancy and latency are not inherently interchangeable;
state weights or retain a resource vector. A rigorous sufficient decision uses a
justified lower bound on savings above upper bounds on additional costs. A less
certain forecast can still inform a deliberately funded decision, but is labeled
as such and should expose sensitivity/stop-loss limits. The rule does not require
inventing impossible certainty about independent agents' future research.

For this marginal decision the existing genuine I proof is a sunk shared input,
not a new A charge. For a whole-network or whole-project growth claim its creation
and incurred failures are still costs. Keep this distinction rather than either
charging I again on every consumer or deleting it from the total benefit story.
The equally optimized local library and ordinary checked-library-sharing route
remain comparators: an advantage over forced full ancestry replay is not by itself
an advantage over a well-cached ordinary library.

### The present small workload may have no certificate benefit region

This is a real possible negative outcome, not a missing popularity feature.
Suppose, for the same retained fold/map contribution and local initial cache,
the ordinary shared-library route's **whole marginal acquisition/check cost** is
at most the certified route's receipt acquisition/verification, member opening
and residual interface/body cost. Then each matched use has

    C_ordinary,i - C_certified,i <= 0.

With nonnegative additional production and maintenance costs, no number of such
uses makes a new certificate economically superior. A tiny native-check workload
may already be cheaper than verifying and transporting A. The current evidence
does not establish that inequality in either direction for a real A receipt;
the possibility must remain explicit. Base worker timers, certificate byte size
alone or the fact that the aggregate has two deltas do not decide it.

There are consequently two distinct deliverables:

- **Sealer operability:** the public path creates a genuine aggregate receipt,
  imports a selected member and supports subsequent authoring without sealed
  witness download. The existing small fixture is sufficient to exercise this
  boundary, even if its certificate is economically worse than native checking.
- **An economically useful seal:** for a specified longer or otherwise costly
  uncached closure, the exact certified route has a supported positive full-cost
  margin against ordinary optimized library sharing, and demand/capacity support
  amortizing its creation and continued availability. This does not follow from
  the first deliverable and needs no promise that every fixture benefits.

Count actual costly cache-miss events across **distinct cold library states or
explicitly justified invalidations**, not theorem invocations. Once a library has
checked and retained a module, the ordinary route can use it repeatedly without
replaying its ancestry; the certified route receives the same optimization.
One receipt held in a compatible live/cache profile likewise need not be verified
anew at every application. Restart persistence has its own authenticated cache
and security assumptions; an arbitrary stored success flag is not that cache.
Do not manufacture coldness, disable an ordinary cache or charge every proof
step as a fresh recipient in order to cross an amortization threshold.

Long ancestry motivates a possible positive region because a genuinely cold
recipient can replace substantial selected-witness acquisition/checking by a
compact warrant. It is not yet a lower bound against every possible ordinary
mathematical strategy. A shorter available proof, already cached interface,
local derivation or equally optimized library can change the comparator. Model
and compare specified capabilities/algorithms with the same initial knowledge;
one slow tactic cannot establish an inherent mathematical discovery lower bound.

The relevant useful lifetime is also not “forever because hashes are immutable.”
Actual custodians must retain the receipt, member openings and needed semantic
material; clients must still support its image/policy; cache churn must be modeled.
Approved cross-image reuse can preserve a costly old-A investment across a
performance upgrade, while a soundness revocation may invalidate that expectation.
Amortize only over a stated maintained lifetime and forecast class, with the
associated custody, upgrade and possible replacement costs exposed.

## What the two-delta workload contributes

The mathematical example substantively composes fold/map laws. It is not an empty
identity wrapper. Nevertheless, sealing or rechecking the **same retained two
deltas** creates no new theorem content. It is changed-boundary evidence for an
additional access/reuse capability. Such capability matters if it makes the same
warranted methods usable under budgets that previously excluded them, or saves
full costs on actual uses. That claim requires the complete-route comparison.

Likewise the strict-evaluator operation saving from fusion is a conditional
algorithmic result. An equally optimized baseline may already fuse. Do not count
both reuse of the law and baseline-denied optimization as separate free gains.
See [DELTA-RECIPROCAL-GROWTH](DELTA-RECIPROCAL-GROWTH.md) and
[GROWTH-WORKLOAD](../v5-2026-10-07/GROWTH-WORKLOAD.md) for the established model;
no new philosophy document is needed for this immediate investment decision.

## From this investment to actual reciprocal operation

The operational route remains: agents contribute cheap, complete bounded native
deltas; recipients discover candidate methods, authenticate selected frontiers,
check only the bounded new closure and demanded semantics, then publish their own
extensions. A selective aggregate service advances the certified frontier in
batches when capacity and expected/justified reuse warrant it. This avoids a
mandatory cryptographic application receipt for every intermediate theorem;
every new theorem still requires valid mathematical checking.

The next genuine aggregate boundary demonstration should reuse the current
mathematics and retained base, produce one real A receipt, then let a fresh public
consumer authenticate a selected member **without sealed proof-witness download**,
author an extension, and export that extension with its actual warrant. It is an
integration gate, not another mathematical-discovery claim or a finished v5.

Final deployable reciprocal operation additionally connects this route to
replaceable unknown-ID indexes with explicit coverage and budgets, independently
maintained custody/repair, ordinary client APIs, recoverable owner state, hostile-
input isolation and secure profile updates. Do not make those components wait
for automatic certification of every theorem. Conversely, no receipt optimization
alone supplies useful discovery, continued availability or full-cost growth.
The central deliverable is their working loop; this note selects the smallest
next economic/trust decision rather than redefining that destination.

### Smallest coherent successor design

1. Add one bounded, owner-adopted policy guard, supplied only through trusted
   constructor configuration. It holds an immutable reviewed support-manifest
   digest and complete per-profile potential-authority closures, a stable local
   policy-domain identity, a monotone revoked set and local update generation.
   No remote caller supplies an alternative graph, guard or verification callback.
   Validate completeness, size, types and inter-version acyclicity at adoption;
   unknown dependency metadata refuses.
2. Bind the guard's stable identity and support-manifest digest into the fresh
   owner profile. Retain its originating object/domain just as current sessions
   retain originating owners. Each `_active` checks that the profile's closure
   avoids the guard's current revoked set. Cache this intersection result only
   for the exact manifest/profile and current update generation. The immutable
   profile need not be silently mutated on every revocation update.
3. Apply revocations monotonically through the trusted local owner control path.
   If a closure is denied, permanently close that affected owner and invalidate
   its handles; dependent mixed owners/sessions then fail their existing liveness
   checks and clear their registries. Preserve resource charges and evidence.
   A changed support graph or attempted reinstatement requires explicit new
   adoption/new owners, not deleting a revoked entry from an old live guard.
4. Check the guard at entry **and** the final authority publication/return point,
   including cache hits and post-worker completion. Merely hashing a policy file
   at owner construction leaves already live handles unaffected and is inadequate.
   Replacing the shared guard while old owners retain an unrevoked copy is also
   inadequate: retire the old guard explicitly or update its monotone state.
5. Keep current exact class/origin/pin gates. Several APIs require `type(owner)
   is ReceiptVerifier` or the exact mixed/aggregate class, so an ad hoc subclass
   is not a drop-in fix. Use a fresh coherently selected source successor and
   update its explicit import/pin/profile bindings. Do not modify used sources.

The present model is a trusted **single-owner** controller. Define the local
update linearization point: once that controller applies a revocation, subsequent
authority operations must observe it. A revocation message merely arriving while
a synchronous worker is running is not already an applied update. A queued update
must be applied before later authority promotion when the controller processes it.
If concurrent updates are introduced, final guard-check/handle-publication needs
a shared synchronization or generation protocol; a last check followed by an
unguarded concurrent mutation is not an atomic guarantee. Immediate cancellation
of native workers is a separate resource policy, not necessary to refuse their
now-inadmissible results after clean closure.

### Persistence and minimum later controls

The inspected v5 registries above are process-local. Their saved request, binding,
owner and result files explicitly are **not transferable/persisted acceptance
credentials**; this lane has no API that restores mathematical authority merely
from them. Therefore this change does not presently require migrating a durable
verified-cache database. On restart, construct guarded owners under current local
adoption state and actually verify retained receipts again. A future durable
verified cache needs authenticated binding to exact receipt/profile/support
metadata and current revocation policy; storing an old `verified` flag is not it.
Persisting monotone local revocations across restart also needs owner-controlled
rollback handling; no such update/storage protocol is implemented by this note.

Later focused controls should cover direct and transitive revocation, an unrelated
profile remaining usable, receipt/member cache hits after revocation, existing
mixed selections and in-flight authoring completion refusing after an applied
update, old-guard replacement/rollback, unknown metadata, and retained costs.
Synthetic controls can validate these owner-state transitions, but cannot establish
cryptographic inclusion or correctness of support metadata for real images.
There is no need to repeat a genuine proof campaign merely to test cache revocation.
