# Keep the first useful aggregate image stable; make upgrades explicit

2026-10-12. Root-requested decision proposal grounded in current source. No proof
funding, image adoption, compatibility implementation or runtime is selected here.
This note uses the existing full-route economics and does not rederive rent-or-buy.

## Recommended decision before expensive sealing

**Do not spend on an image that we already intend to replace.** If the bounded-
parse successor completes the unchanged-cap screen and its mathematical and
production boundaries remain independently clear, designate that exact image A0
as the fixed producer/receiver image for the first complete reciprocal v5 path.
Permit one separately budgeted genuine-seal capability operation on A0. Keep A0
unchanged through fresh public receipt/member admission, substantive native-delta
authoring and subsequent public acquisition. Do not start another guest optimizer
in parallel merely because it may be faster.

This is an **image-support decision**, not proof authorization or a declaration
that the small fixture has profitable certificate economics. The capability
operation pays for missing trust-boundary evidence. Repeated operational sealing
still needs the existing complete-route benefit and capacity justification.

If another guest change is already consequential before the first A0 proof starts,
stop and make that decision first. With no genuine A receipt yet, there is no
aggregate certificate investment to preserve by pretending an unsettled image is
stable. Successful execution capsules cannot be moved to a changed image by
renaming or rehashing their binding.

## Why this is the smallest coherent choice now

| Actual source boundary | Current consequence |
|---|---|
| `aggregate_claims/relation.rs` and bounded-parse successor | An aggregate parent H is bound to the child-declared A; its pending claim also uses that A. A0 cannot be imported by child A1 when A0 differs from A1. |
| `aggregate/receipt.rs::verify_pending` | Host accepts fixed I or the independently selected same A, with full application verification. A host-only permissive list cannot change the guest's rule. |
| `aggregate_claims/header.rs` | Exact192-byte H already carries parent A; exact184-byte member J and mathematical ModuleIDs do not need replacement merely because a checker is optimized. |
| `mixed_claims/packet.py`, `receiver.py`, `imports.py` | One aggregate image/owner is bound into each public owner/session. It is not a multi-image import API. Saved success flags are not transferable authority. |
| `aggregate_production/stage_host.rs` | The unused production candidate preserves exact same-I/A checks and capsule bindings. It neither supplies nor needs an upgrade policy to produce its first A0 receipt. |

Keeping A0 installed continues its existing same-A route while sound and available.
It does **not** enable A1 to consume A0, allow one current mixed session to combine
arbitrary A images, or solve worldwide security updates. Those distinct claims
must not be bundled into the word “compatible.”

Adding a legacy table before any A0 receipt exists provides no current reuse.
Adding it to a future A1 can preserve A0 then, because the necessary parent image
is already present in H. Thus there is no mathematical need to rebuild A0 now for
a speculative future implementation version. There is a need to preserve its
exact semantics, dependencies and evidence so a later inclusion review is possible.

## What root should record with the first A0 selection

One concise local adoption/support record, attached to the existing source/image
selection rather than a new global registry, should state:

- Exact actual A0 image, ELF and source/runtime profile; fixed I/foundation/policy;
  H/J/membership formats; cryptographic/verifier assumptions.
- Its current direct potential-authority dependencies: the exact I implementation
  and relevant checker/foundation/cryptographic trust profiles. The own-A0
  recursion is justified by seal-height induction, not an inter-version cycle.
- Scope: retain a working A0 receiver/producer route and needed capsule/receipt/
  member/opening/semantic material through the selected reciprocal milestone.
  One finite capability budget is allowed only by a separate explicit launch.
- Replacement rule: no performance update silently drops this route or relabels
  its receipts. A successor either keeps A0 as a separately supported route or
  receives explicit cross-image adoption as described below.
- Safety override: suspected/established soundness compromise blocks new
  acceptance and funding under the affected profile. Sunk proof expense never
  overrides a mathematical or cryptographic defect.

The milestone scope is sufficient for this R&D decision, not a public retention
promise. Before selling or funding ongoing service, the responsible local operator
must additionally state a finite supported horizon, custody/repair capacity,
update responsibilities and retirement procedure. No anonymous global population
can be assumed to maintain those services simply because the software is shared.

## The successor contract to adopt in principle now

For a genuinely justified later performance upgrade, choose the already analyzed
**finite, compiled predecessor table**, not a mutable sender-provided trust list.
For the first upgrade, A1 may support exactly self-A1 plus reviewed A0, with fixed
I/foundation/policy and the same H/J semantics. Further predecessors require a
separate explicit inclusion decision; never add every historical image by default.

The guest must derive every parent pending claim as `(parent H.A, exact H)` and
actually execute `env::verify(parent H.A, H)`. It must accept that image only from
its compiled reviewed set or its externally bound self case. Host, input builder,
member bindings and public owner/session maps must make the same distinction
between child A1 and permitted parent A0. Final verification remains against
independently adopted A1 and exact child H. This is a coherent fresh source
successor, not changing one conditional or allowing arbitrary callback verifiers.

The inclusion obligation is semantic: every A0-authenticated member must satisfy
the validity predicate required by A1. Equal image-profile strings or matching
foundation names do not establish it. A0 receipts can stay costly-but-useful
premises even if A1's new-delta checker is faster; there is no need to reproduce
their proof construction merely to optimize later work.

This contract selects an upgrade direction, not its implementation today. The
existing [cost decision](NEXT-AGGREGATE-COST-DECISION.md) contains the full soundness
and API argument. The decisive trigger is an actual beneficial guest change with
retained A0 frontier value, or public multi-version deployment—not curiosity about
possible versions before the current end-to-end path exists.

## Security retirement is different from performance retirement

Adopt complete code-bound potential-authority dependency metadata for each
supported profile. If R is the locally applied revoked set, deny a profile a when
its complete transitive trust-dependency closure intersects R. Self-image recursion
is excluded from the inter-version DAG and remains covered by seal-height
induction. A1 that could accept revoked A0 is conservatively withdrawn even if a
particular A1 receipt did not use it. Current H does not prove receipt-specific
absence of that dependency.

This avoids traversing mathematical proof ancestry, but only with complete reviewed
implementation dependencies and correct client enforcement. The current software
does not yet implement that persistent update protocol. Its owner `_active` and
final-promotion gates are the established insertion points; live handles and mixed
selections must be invalidated, and local revocations must survive restart with
rollback handling. Reverification against an accidentally rolled-back policy is
not a fix. Eventual update delivery is an assumption, not a global synchronized
revocation guarantee.

A sound successor excludes exposed predecessors or rechecks the required original
mathematics under sound rules. Rewrapping a possibly false premise is not recovery.
Preserve available original witnesses during development and price their selected
custody if they are promised as a recovery route; do not impose permanent full-
history replication on every participant.

## Funding and immediate sequence

The useful service lifetime of a seal ends at the first unsupported-image boundary,
loss of required custody, or applicable security retirement. Economic forecasts
must use that maintained lifetime, not the immutability of a hash. Uncertain
future upgrades/revocations remain disclosed risks; the existing marginal cost
criterion and equal-cache comparator still apply unchanged.

1. Finish the already selected guest-build correction and adopt its actual result.
2. Assemble once and screen once under the same2^25 cap, using the unchanged
   mathematical input and genuine I receipt.
3. If it completes, explicitly select A0's support record and quote one finite
   aggregate-seal capability allocation. Root may refuse its cost; screen success
   is not automatic funding. If it fails, preserve failure and diagnose before
   another representation change or cap proposal.
4. Keep A0 fixed while connecting the genuine receipt to the complete public
   reciprocal path. Work on independent discovery/custody/client integration can
   continue without another guest image or another copy of the same proof.
5. Implement version compatibility and restart-safe revocation before claiming
   maintained public multi-version deployment, or earlier when an actual valuable
   A0 frontier would otherwise be stranded by a justified upgrade.

This sequencing protects expensive results without diverting the current project
into an unnecessary version-management implementation. It leaves the full global
v5 requirements intact and makes the next irreversible expenditure an explicit
root decision.
