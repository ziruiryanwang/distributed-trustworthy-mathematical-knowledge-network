# Next practical-value decision: make the ordinary owner usable

2026-10-23. Source/theory-only checkpoint by `practical_value_next`.
No code, build, experiment, Git operation or external request was performed.
This recommends a selection; root owns implementation and runtime authority.

## Decision and real workflow

**Next: expose a thin persistent-owner entry point over the existing checked
pipeline, not another invented difficult theorem or certificate experiment.**
A user should install the supported ordinary package, create/open one local
owner, inspect its current accepted context, contribute caller-chosen Lean
declarations using acquired results, close the process and continue later.
Existing discovery/acquisition/publication APIs remain the corresponding peer
seams; the new entry point must not create a second acceptance implementation.

The immediate interface is a small `init` / `status` / `contribute` surface with
an installation/profile loader, exact selected context, caller source file,
output-name list and bounded operation allowance. It must not require research
snapshot layouts, a frozen fixture plan, copying a catalog per contribution,
or knowledge of the previous example's names. Keep peer source execution out
of this interface: only owner-approved source executes; peer evidence is inert.

## Why this is the next issue, from inspected source

`ordinary_contribution.contribute_source` already accepts arbitrary supported
new targets, several acquired methods and a caller-owned source body. It keeps
mathematical admission in `ordinary_admission`; it does not initialize or copy
the owner. The saved actual03 example demonstrates this narrow generic seam,
not mathematical novelty or positive useful-growth margins.

`run_generic_contribution.py` is intentionally a diagnostic launcher: it
requires a snapshot-relative layout, copies an exact retained local store,
loads `selection.json` and asserts fixture-specific method/output facts.
Those conditions preserve experimental evidence but are not a product UX.
Removing them from a new product wrapper must preserve core/profile identity,
actual admission, resource accounting and accepted state on partial failure.

`assemble_source` prepends fixed Init/authoring imports and a construction
prelude. It is **not** an arbitrary Lake-project importer. The user's existing
imports, tactics, generated declarations and namespace collisions require a
separate compatibility contract. Do not silently widen this trust boundary.
Reproducible packaging/build selection is assigned to `ordinary_api_flow`;
this checkpoint neither repeats that audit nor selects replacement sources.

## Strong comparator and the intended advantage

The comparator is ordinary Lean package/library sharing, with pinned versions,
the same useful index, retained compiled state, existing tactics and caching.
It may derive a short alternative proof, generalize once and reuse that result.
It is not a flattened library, an uninformed isolated prover or repeated cold
reconstruction. Both routes must reach the same explicitly specified assurance
endpoint; ordinary source compilation alone is not hostile-source validation.

The plausible additional value is selective acquisition and independently
checked inert exchange without automatically executing an unknown contributor's
Lean source/build scripts, combined with reciprocal discoverability/custody.
That value is conditional: a package workflow with adequate isolation and
checking can be preferable. Decentralization alone is not a performance win.
The footprint example wraps an existing standard-library update law and has
a short ordinary proof. Its abstraction is legitimate mathematics, but it is
unsuitable as evidence that our route beats an optimized package workflow.

## Decision rule, not a manufactured speedup

For a fixed assurance endpoint, workload horizon and nonnegative resource-price
vector, let P_i be each consumer's full incremental package-route cost and O_i
its ordinary-commons cost; let H be additional shared fixed/maintenance cost.
The commons has a positive cost margin only if sum_i(P_i - O_i) > H.
Use componentwise comparison if no defensible scalar prices are available.
Include integration/translation effort, failed searches, producer work, service
and retention; cancel shared costs only when actually shared. Both routes get
warm reuse. A cold consumer still pays for missing checked dependency evidence;
local durable acceptance does not establish universally ancestry-free imports.

The public wrapper removes a concrete integration barrier, not a theorem-proof
cost. Its value is operability and reuse of tested mechanisms. Do not report its
completion as a positive margin, sustained growth or final-v5 completion.
Adopt ordinary package mechanisms wherever they meet the same need more cheaply.

## Small decisive boundary and explicit stop rule

After source review and packaging selection, one changed-boundary lifecycle
check can establish normal open/contribute/close/reopen use without fixture
state copying. Reuse existing mathematical examples/evidence; no new proof
search benchmark, large corpus, peer campaign or certificate is needed.
Keep malformed profile/context handling in cheap nonnative controls where
possible; only the actual new wrapper-to-owner seam needs native evidence.

Next reassess an ordinary existing-project adapter: can a caller reuse acquired
results without reauthoring its project into a bespoke source-body environment?
If not, the scratch interface alone cannot support a broad Lean-user claim.
If equivalent safe package sharing needs less integration or total work, keep
the commons as a discovery/custody/checked-artifact layer over that workflow;
do not build a competing authoring environment to defend the current design.
Stop adding fixture variants once the public seam works. The unresolved value
question then concerns actual user integration and selective exchange, not
whether another elementary theorem can traverse the already tested checker.
