2026-10-23. Source-only recommendation by `ordinary_api_flow`; no implementation,
build, native check, service, external request or Git operation. Existing used

## Decision and integration order

For the present installed-owner workflow, add one thin direct-contact `peer.py`
surface next: `find`, `receive`, `publish`, `serve`; retain `owner contribute`.
This removes experiment callers from selective discovery, checking and reciprocal
availability using existing mechanisms, without changing mathematical acceptance.
It is an operability gain, not evidence of cheaper proofs or useful growth.

Then expose the trusted existing-project construction/export hook described in
`ORDINARY-EXISTING-PROJECT-DECISION.md`, initially as a recipe plus explicit local
invocation, not a Lake manager. That hook removes editor/tactic/reauthoring friction
but introduces project-dependency compatibility decisions absent from this seam.
There is no measured daily-user demand ordering: if the actual next contributor
works in an existing Lake repository, do its hook first and use the existing peer
APIs meanwhile. Do not polish peer routing while the contributor cannot author.

Ordinary pinned package sharing remains the strong comparator. When its trusted
imports, caching and established environment meet the same assurance endpoint
more cheaply, keep the commons as discovery/custody/checking support. Neither
scratch theorem assumptions nor protected local snapshots become portable proved
Lean libraries. No new growth fixture or certificate campaign is warranted here.

## Public operations and authority

- `find`: explicit owner contact map, supported semantic namespace, feature specs
  and finite search limits. Use `OrdinaryExportAdapter`, `compile_query`,
  `SearchSession` and `SearchClient.offer/candidates`. Return bounded candidates,
  provenance and incomplete-search accounting; never require one fixture match.
- `receive`: explicitly means **acquire and locally check**, with caller-selected
  candidate, exact local parent, custody and one finite allowance. Revalidate the
  selected record, fetch exact preview/evidence, call `portable_preview.resolve`,
  then run the existing preflight/missing-import loop and `owner.admit`. Return
  separate acquisition and admission facets plus the exact resulting local root.
  Failure after acceptance must retain/report that acceptance, not roll it back.
- Keep lower-level `OrdinaryAcquisition.preview/locator/evidence` publicly usable
  for inert-only acquisition. Do not disguise a successful fetch as acceptance.
  A small coordinator API can expose `find`, `acquire_missing`, `receive`,
  `publish` and `serve`; CLI commands only validate inputs and call these seams.
- `publish`: owner selects exact targets in an explicit protected local context;
  check its name-to-ExportID bindings against retained exact custody evidence,
  derive previews with `portable_preview.preview_from_evidence`, retain them and
  call `discovery_store.Store.admit`. This is local metadata indexing, not remote
  publication or another mathematical admission. A saved contribution report or
  PASS string is not authority. Index status always remains nonmathematical.
- `serve`: explicit public custody/index selection, bind address, finite lease,
  limits and optional approved TLS files; use the existing read-only `Provider`.
  No remote write, native check, source execution or automatic service renewal.

Verified candidate membership does not prove skipped-interval coverage, absence,
recency, global completeness, source feature honesty or mathematics. Exact paged
coverage is a separate existing API. Preview validation recomputes the entire
feature record; locator/evidence reads bind semantic ID, UnitID, ExportID, actual
output census and expected name. Only native admission under the selected local
parent creates new local acceptance; READY/previews/custody/index/TLS do not.

## Resource, contact and source boundaries

One original wall/CPU/memory grant covers parsing, search, acquisition, preflight,
native checking, persistence, reporting and cleanup. Native workers keep existing
Job containment; hard controller/service limits require outer Job supervision,
not a claim that cooperative checks bound hostile execution. Reserve cleanup.
Derive every child deadline/CPU allowance from the original remaining balance.
Use `OrdinaryBudget` for aggregate requests/reply bytes; prepay search subcaps
with `charge_external` before any fetch. Count request/header overhead separately;
failed/unknown fetches keep full reply-cap charges. Prepaid search and failed
attempts remain charged after early termination. Cap candidate selection, units,
bytes, frontier, attempts and preflight iterations; deduplicate exact units and
refuse no progress. No implicit retries, referrals, endpoint expansion or grants.
Separate human-invoked commands may have new explicit grants; a composed API call
must not manufacture them by re-entering the CLI or allocating per phase.

Use a bounded owner-selected label-to-Endpoint map: literal IPs, plaintext only
on loopback, verified TLS remotely, selected server name/CA policy. Pin contact
configuration and selected CA bytes for the call lifetime, or explicitly choose
system CA trust. Endpoint alone does not pin CA-file bytes. Do not log private
keys. Profile pins select local code; TLS/content commitments are not math trust.
Peer bytes stay inert; never import a peer catalog, snapshot, native `.olean`,
build script or claimed PASS. Only separately approved owner source can execute.

## Serving, privacy and persistence

Serving a custody directory exposes **every addressable object in that store**;
Provider has no per-object ACL. Require explicit authorization of that sharing
scope or select a separate public custody directory. Inert rehosting is allowed
without claiming local acceptance. Initially serialize publish/serve ownership;
do not advertise simultaneous SQLite writers without a locking design.
Provider request/reply/connection limits are not a service lifetime. Stop at the
original lease/deadline, close the listener, cancel/gather tasks, verify no server,
tasks or reserved bytes remain, then close all stores even if one close fails.
Uncertain cleanup is a reported failure. Store's internal 30-second publication
and 5-second summary limits do not renew the outer grant; enforce before/after
accounting plus hard outer containment for synchronous work and preserve costs.
