## Identity and metadata boundaries

The V2 reader validates the exact four-field envelope, canonical raw bytes,
semantic-ID encoding and unchanged raw-unit syntax. Its ordered import keys
must equal the complete duplicate-free external-name census. The identity
formula is exactly the selected `ordinary_semantics` V2 domain plus NUL plus
those canonical bytes. Export and foundation-symbol functions directly reuse
that helper. Thus neither a local implementation nor an owner path enters
portable identity; exact proof/unit/import choices still do. Logical equivalence
and proof-independent theorem identity are not claimed.

The reader deliberately accepts a syntactically encoded unknown S as an inert
claim. That is not adoption of S, F, an implementation, or mathematics. The
implementation-descriptor reader separately requires the selected S; even its
successful parse remains a support claim needing actual local adoption.

The preview reader validates the selected root-reachable type DAG and exact
ordered type bindings through the unchanged V1 grammar. Orphan levels/terms
refuse; shared terms are traversed by indices, not recursively expanded. The
export name, S, UnitID and regenerated header/bindings determine the metadata
binding. Internal generated-group type references receive the same unit's
member ExportIDs; external references take their exact envelope IDs. This
internal-group branch is supported by source inspection, not exercised by the
fifteen saved synthetic groups.

At public projection/resolution boundaries, a caller-made `Evidence` object is
not trusted: its raw bytes are reparsed, while mutable document/ID/census fields
are ignored. `resolve` checks the exact UnitID and S, regenerates the selected
preview and requires exact raw-byte equality. The separate locator has exact
fields, validated names/hashes and a detached name structure; it is neither an
existence claim nor permission to load a binary. All public description/binding
results explicitly retain `mathematical_acceptance=false`.

These functions perform no I/O, import of peer code, proof check or catalog
promotion. Preview reading depends on bounded type metadata; creation/resolution
additionally validates one complete selected evidence unit, including its body
syntax. No ancestor unit is followed. This distinction must survive index/API
integration: preview binding is not mathematical acceptance and does not prove
global index coverage. Foreign raw bytes still need transport-level bounds before
allocation; these parsers are not a complete hostile-input service sandbox.

## Catalog migration: concrete prerequisites, not a new authority shortcut

`PORTABLE-CATALOG-CONTRACT.md` (`26553e975ca5dbb788fe6a217e4ecf1e07144a74ac553fd4eae3604fa6ab993b`)
was read completely. Supporting source inspection confirms that the current
worker consumes concrete module-loading plans and raw units, not V1 envelope
IDs. `LocalSnapshot` checks embedded module/parent relationships. Therefore
keeping their actual names and bytes while translating metadata IDs does not
intrinsically require a native rebuild or proof replay.

The important implementation hazards are already addressed in the contract and
must remain explicit obligations, not unchecked input assertions:

1. **An authenticated copy is not an acceptance event.** The importer must be
   restricted to an actually adopted protected local V1 lineage with its exact
   original checker/basis/snapshot support. A peer catalog, matching record hash,
   implementation descriptor or `compatible=true` cannot supply that premise.
   The source-defined V1-to-S correspondence must be separately adopted; retain
   its exact support and original record bytes in the new lineage.
   Concretely record the actual adopted V1 profile/support against the fixed
   descriptor clauses for codec, primitive interpretation, foundation and
   extension policy. The first migration retains the exact native worker, ABI,
   codec and foundation support; its only new mathematical-data operation is
   identity translation with unchanged units and exact mapped dependencies.
2. **Do not rename embedded modules by new root IDs.** Imported roots require
   stored original module/parent names. Future worker plans, live grants and
   returned-report checks must all use that same authenticated mapping. Merely
   changing `context` while leaving a controller's `module_name(parentRoot)`
   assumption would break this boundary.
3. **Translate the entire selected snapshot lineage, not just the author's
   selected type closure.** Reconstruct exact old evidence/order/import IDs and
   compare complete old bindings/batch hashes before deriving new IDs. Missing
   accepted evidence must refuse, not become a type-only substitute. The raw
   unit remains byte-identical and each import maps to the same declaration;
   that is the induction premise permitting proof-free ID translation.
4. **Keep authority atomic and origins honest.** Normal V2 operations must
   reject IMPORTING state. Flush/validate copied artifacts and translated evidence
   before one activation transaction. Imported roots retain legacy-translation
   origin and original support; no new-native-check event is invented. An
   uncertain activation is inspected, never automatically replayed. A later
   withdrawal must target the active V2 authority; archival V1 marker edits are
   explicitly not an automatic propagation mechanism.
5. **Use a genuinely read-only legacy reader.** V1 `LocalCatalog.open` updates
   stale reservations, so it cannot be reused to inspect frozen source state.
   Source locking, no unresolved SQLite sidecars, exact manifest/hash checks and
   a bounded read-only query path are necessary for the proposed importer.

There is no source-only blocker to implementing that narrow same-runtime
migration. There is also no migrated catalog yet to adopt. First code review
must establish these predicates at actual entry/commit seams; one selected
postmigration new extension can test module-plan integration without repeating
the accepted corpus. Portable IDs alone do not solve cold full-context loading,
branch merging, globally complete search, availability or net growth benefit.
