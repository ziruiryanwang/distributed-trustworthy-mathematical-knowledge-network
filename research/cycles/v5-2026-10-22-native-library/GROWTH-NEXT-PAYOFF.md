# Next growth payoff: make contribution cheaper than adopting the whole commons

2026-10-24. Source-only decision challenge by `growth_payoff`. No product edit,
experiment, native invocation, owner opening, network request or Git mutation.
The ordinary-reference repair remains useful; this note does not select runtime.

## Recommendation

Finish the bounded current registration/authoring continuation. **Then expose the
existing owner-free producer and give its inert output an explicit candidate-offer
path, before another growth demonstration.** Preserve the current
accepted-publication route and the receiver's independent mathematical admission
unchanged. The exporter and representational binder already exist; do not write
new ones. Root identified these retained components during this review, and the
reviewer then read them directly.

Call this a *candidate offer*, not an accepted theorem or a certificate. It is a
claim accompanied by exact evidence bytes. Consumers still choose what to inspect
and check; index/custody operators still choose what to host. The same object must
be usable through a pinned repository, a file transfer or a peer. No new network,
identity system, semantic equivalence rule or global task list is proposed.

This is a better next decision than further external-library case shopping. We
already have a precise practical obstruction in the public API: a contributor
must obtain this software's local acceptance before its mathematics can enter
the advertised search path, although a recipient never trusts that acceptance.
Whether removing that requirement is economical is conditional, but the causal
mechanism is concrete and source-auditable. It directly answers the user's concern
that making a producer perform expensive additional work can suppress supply.

## Actual source boundary, not a hypothetical missing feature

The selected ordinary reference package preserves the existing peer/discovery
surface; `ordinary_reference_package/profile.py` explicitly retains it.

- `ordinary_preview_package/peer_api.py:publish` opens an ordinary owner, reads a
  local context, requires the exact target in `context["bindings"]`, retrieves
  evidence, constructs/resolves its preview, and only then admits metadata to
  the index. The first requirement is a **local producer admission policy**.
- `ordinary_lean/portable_preview.py:resolve` binds a preview to exact evidence
  but explicitly does not confer mathematical acceptance. Its syntactic evidence
  readers and identity checks do not need a producer warrant to describe bytes.
- The receiver path independently acquires/checks missing evidence before local
  admission. Another owner's verdict is not its trust premise.
- `ordinary_project_extraction_package/README.md` exposes extraction through a
  retained contribution, an initialized owner and an unchanged parent. It is
  not a standalone offer-export operation for an ordinary project's theorem.
- `ordinary_baseline/baseline_production.py:produce_bundle` already implements a
  separate owner-free approved-local-library extraction. Its exact selected
  profile supplies `BaselineExporter.exe`, worker and fixed inventory; it emits
  a manifest-last inert bundle with `mathematical_acceptance: false`.
  `baseline_bundle.bind_writer` already binds the full topological closure to
  the fixed seed without an owner or fabricated warrant. A recursive source
  search found this producer called by `production_controls.py`, not a public
  runtime entrypoint. The current reference assembly/profile omit its producer,
  worker and native executable roles. This is an integration gap, not a need
  for another proof extractor, binder or mathematical schema.
- `ordinary_reference/reference_authoring.py` intentionally combines local
  source compilation, extraction and actual admission. This is valuable when the
  author also wants a warranted local extension. It is not necessarily the

- Existing serving can already expose unaccepted inert custody objects, but that
  is not a complete public standalone offering workflow or a safe shortcut around
  the checked `publish` command.
- More precisely, `transport/ordinary_acquisition.py:OrdinaryStore.put_evidence`
  already stores bounded inert evidence and derives exact export locators;
  `put_preview` stores its preview, and both explicitly return no mathematical
  acceptance. Reuse these APIs. The selected `peer.py` CLI has only `find`,
  `preview`, `receive`, `publish`, and `serve`; its publication path requires an
  owner. `offer_enumeration/README.md` instead describes enumerating already
  hosted certificate-packet locators. That is not this ordinary producer path.

Thus this recommendation is not another preview, type index or generic reciprocal
exchange test: those already exist. It asks whether **offering and locally adopting
must be coupled**. They need not be coupled for receiver soundness, subject to the
unchanged admission premises below. They may reasonably remain coupled by an
individual index provider's anti-spam/quality policy.

## Minimal soundness argument and what it does not establish

Let the existing receiver algorithm take its own warranted environment, a selected
target identity, and acquired inert evidence. Assume its acceptance judgment is
sound under the existing checker, policy, identity, dependency and protected-state
premises. Suppose the new offer path changes only where those untrusted bytes are
obtained and which candidates are presented, never the receiver judgment.

For every receiver-accepted output, the original algorithm has accepted the same
environment and evidence. Therefore the original soundness implication still
applies. A producer's absent local warrant cannot weaken a premise which that
receiver never used. This is a preservation argument, not a new Lean soundness
proof and not a claim that the current code already implements candidate offers.

Important boundaries:

- An advertisement must never be inserted into a local warranted context.
- Missing dependencies must resolve to exact evidence or the receiver's existing
  warranted frontier. A publisher-supplied name map cannot replace that frontier.
- A producer may omit already named dependencies only if they remain actually
  obtainable; an unresolved offer can be described as incomplete but cannot be
  presented as immediately usable. Offers do not guarantee availability.
- Extracting evidence from the producer's own approved compiled project does not
  authorize a consumer to load its `.olean`, tactics, macros or initializers.
- Do not call `portable_candidate.bind_candidate` with a fabricated
  `warranted_symbol` callback. That API's stable protected-owner premise is real.
  The existing `baseline_bundle.bind_writer` supplies the appropriate distinct
  purely representational construction against the selected fixed inventory.
- More invalid candidates can waste bandwidth/checker time. Bounded syntax,
  per-provider admission policy, query/acquisition budgets and explicit trust
  labels remain necessary. Process limits are not a hostile-input sandbox.

No remote source execution, semantic-ID migration, unproved bridge or succinct
certificate is needed in this argument. A qualified local index may still choose
to check each item itself; the network should not require every supplier to do so.

## Growth justification: reduce an avoidable barrier, not invent a theorem

Fix the same producer's already completed ordinary Lean work and the same target
bytes, consumer opportunities and required receiver assurance. Common ordinary
proof construction cancels between routes. In the existing route let `P` be the
incremental cost of establishing a producer owner, rechecking/retaining the relevant
mathematics and registering a reusable local realization solely to offer it. In
the offer route let `E` be any extra standalone extraction/hosting cost beyond the
common work, and `J` the added aggregate cost of screening invalid/unhelpful offers
and operating their admission policy. With otherwise equal consumer outcomes,

    total cost(existing) - total cost(offer) = P - E - J.

This is a narrowly identified accounting difference, not measured profitability.
If `P > E + J`, the offered capability is delivered at lower aggregate cost. An
already participating producer may have `P = 0`; then there may be no benefit.
For an indifferent supplier willing to spend at most `b` additional resources,
the interval `E <= b < P` can make offering feasible when full adoption was not,
subject to its real privacy, compatibility and service constraints. We have no
evidence of the prevalence of that interval and must not manufacture an uptake
rate. Retention, failed search and consumer costs do not disappear.

The positive region is useful because its terms correspond to removable mandatory
operations, not conjectural hardness of proving a toy theorem. The actual failed
reference workflow supplies evidence that these operations exist and are nonzero;
its 120-second total is **not** an estimate of `P`: that total includes useful
receiver/local-authoring work and failure overhead which cannot all be eliminated.
Do not report that complete total as a predicted speedup.

Ordinary searchable Git/package sharing must get the same exporter and evidence.
Consequently the possible contribution is a reusable safe-interchange tool, not
an inherent advantage of a bespoke peer protocol. That is an acceptable useful
product. Source-based contribution, selective evidence and safe local import can
support sharing-enabled capability growth without claiming novel or exponential
mathematics from the network itself.

## Finite next decision and rejection conditions

The source question is now answered in principle: the owner-free exporter and
fixed-seed closure binder exist. **Recommended bounded implementation task:**
expose that producer through a pinned installed public command and expose a
separate optional inert-bundle-to-custody/index operation. Keep `publish`'s accepted
meaning unchanged. The new operation should validate exact manifest/unit/target
bytes, use existing `put_evidence`/`put_preview` and index admission, return an
explicit candidate-not-accepted result and require an explicit serialized custody
writer. This is source selection advice; root must separately select actual edits.

The wrapper/profile must not invent a commons catalog, fabricate a parent root,
invoke `init`, `intake-baseline` or `register-reference`, or import a peer binary.
An installed runtime/profile is still necessary; owner-free does not mean zero
setup. Compile/export complexity and supported-toolchain restrictions remain.
The local producer's approved artifact trust boundary is unchanged.

Use retained producer/export/binder evidence when selecting the wrapper. Do not
compile a new theorem, port CvxLean, repair an unrelated compiler-verification
library, launch a new network, or benchmark proof search. A later changed-boundary
check should establish public invocation and inert publication, not repeat the
exporter's already established mathematics or original intake. If a producer
profile needs file-only assembly, preserve the native executable and source
identity rather than launching a redundant build. The ordinary-reference
continuation's already tested prefix is unrelated and must not be repeated.

Reject or defer the standalone offer path if it requires another substantial
checker/proof language, silently changes semantic identities, makes unresolved
closures the usual outcome, or cannot avoid most producer setup. Also defer if
normal approved-package integration supplies the same practical capability more
simply. Retain candidate hosting as optional if useful provider quality filtering
would erase the expected saving. Do not relax receiver acceptance to salvage it.

Retained source already supplies the costly core; expose/use it instead of
creating a second one. If the uncertainty is actual uptake, no synthetic local
experiment will settle it: ship an operable adapter first, then obtain independent
use later. The existing intake/native-reference observations do not measure the
new facade's performance or independent demand.

Application recipes and joint-premise advice remain reasonable later options, but
there is currently no surviving independently motivated case showing that their
additional runtime beats explicit application or ordinary local automation. Do
not add that machinery now. Existing growth/comparator/philosophy arguments are
retained unchanged; this note's new contribution is the identified producer-side
coupling and the finite architectural decision it permits.
