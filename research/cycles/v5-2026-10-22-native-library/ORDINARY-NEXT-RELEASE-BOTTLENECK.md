# Next release bottleneck: make a common mathematical background usable once

2026-10-24. Source/theory-only decision by `project_intake_native`, incorporating
root's challenges to the initially considered approved-base alternative.
Canonical root: `E:\Distributed Trustworthy Mathematical Knowledge Network`.
No tests, builds, network calls, owner/catalog operations or Git mutations were
performed. This is a proposed next selection, not implementation authority or
release acceptance. The user has no existing Lean project to supply; do not ask
again or describe controlled fixtures as outside-user evidence.

## Decision

**The largest remaining practical workflow obstacle is establishing a useful
common library background once, and then using it through ordinary Lean without
repeated conversion or proof replay.** The next software consequence should be
a bounded, reusable, strictly checked baseline-bundle path, not more preview
polish, another ranker, or a mandatory certificate.

Prefer route **A: one-time strict checked baseline plus incremental deltas**.
Do not yet implement route **B: operator-approved compiled baseline plus checked
deltas**. B is a legitimate architectural alternative, but has a different
assurance premise and requires more namespace/import-policy work. The current
evidence does not establish that A is impractical. B must not become a silent
substitute for seed-derived acceptance merely because a public adapter is small.

This updates, rather than repeats, the preceding strategy. The approved-project
extraction adapter now exists. The preview seam is being completed. Their public
boundaries are no longer the reason that a normal library can remain unusable.
The next missing product boundary is **baseline establishment independent of a
retained small contribution**, including an actually usable ordinary-project
realization of that baseline. A generic retained-consumer rebase scheduler is
not required for that first slice.

still cannot realize. Likewise, splitting 2,852 units into 32-unit module calls
requires at least 90 modules, already beyond the 32-module chain and 1,024-unit

silently increased or worked around with repeated independent grants.

The historical [admission recovery outcome](ADMISSION-RECOVERY-OUTCOME.md)
already establishes one 1,024 / 1,024 / 804-unit checked closure and protected
prefix recovery. Its full admission/recovery cost was 271.15625 known inclusive
CPU seconds, including the failed original attempt. The retained evidence is
about 49.5 MB. This is neither final-bridge evidence nor a new product benchmark,
but it directly refutes the inference that this class of one-time strict cold
checking must be prohibitively expensive on the current PC. Do not rerun it.

## Route A: the minimal strict baseline consequence

Expose a separate, explicitly selected **baseline bundle intake** rather than
extending `complete` into an automatic research workflow. Its input is a finite
immutable manifest of individually bounded existing ordinary evidence units,
explicit desired target identities, an exact starting local context, and one
whole-operation allowance. It is not an imported saved catalog or `.olean`.
The producer may distribute a reusable bundle to many users; each strict cold
receiver checks its missing units once and retains its own local warrant.

The smallest coherent contract is:

1. Validate the manifest, per-unit bytes/IDs, finite counts, dependency edges,
   total storage bounds and selected targets before invoking checking where
   possible. A manifest is a locator/plan, not truth. Avoid one giant unbounded
   JSON parse or re-extraction of the whole source library for each batch.
2. Use existing exact-name/symbol identity and whole-unit rules. Each batch's
   imports must be available in the accepted prefix or earlier within the batch.
   Choose bounded batches by bytes/nodes/names/edges as well as unit count; the
   1,024-unit ceiling is not a guarantee that 1,024 arbitrary units fit.
3. Use the existing `OrdinaryAdmission` and durable catalog promotion. A
   committed checked prefix is the sole authority for continuation. A saved
   success message, prospective root, cursor or downloaded snapshot cannot
   promote mathematics. Preserve failed attempts and uncertain commit outcomes.
4. Reuse exact already accepted units. Missing/conflicting/partially present
   groups refuse. No axiom placeholder closes a dependency, no name-only match
   substitutes a definition, and no old budget is renewed after failure.
5. Account for the full finite session, including failed work, context loads,
   checking, controller work and spool storage. A later explicit continuation
   may have a new allowance, but retains the previous cost and authenticated
   prefix. No implicit endless batch loop or automatic retry is selected.
6. Produce a separately bounded **baseline realization** through the existing
   ordinary module bridge. Source analysis must first select compatible finite
   cold-baseline/module-chain limits and aggregate accounting. Keep ordinary
   interactive delta limits unchanged. The accepted internal snapshot cannot
   simply be imported beside Init as a substitute for this correspondence.
7. Only after the actual local baseline is both warranted and usable does a
   normal project author new contributions and prepare queries against it.
   This avoids rebasing a retained consumer in the first implementation slice.

The relevant theorem is already available in
[the cold-intake strategy](ORDINARY-COLD-INTAKE-STRATEGY.md): induction over checked
dependency-complete batches preserves seed-relative validity and all previous
bindings. Reuse it rather than commissioning a second proof of the same prefix
property. A baseline realization additionally requires the existing exact
private/public interpretation and fresh-reread obligations; admission safety
alone does not prove ordinary-project compatibility.

No new cryptography, distributed consensus, semantic-equivalence oracle,
long-lived prover or general package solver is needed. The new product work is
bounded orchestration, resumable plan/state binding, and a coherent baseline
realization profile over existing checking primitives. The manifest can travel
through existing exact-byte custody; network bundle discovery and automatic
fetch scheduling are not necessary to resolve this first boundary.

This is a proposal, not a selected implementation. In particular, the one large
historical closure is not an excuse to add a generic scheduler with every
future migration and recovery feature. First decide whether its real retained
unit/byte/name/artifact census fits a coherent source-derived baseline profile.

## Cost model: one-time baseline is not per-result verification

Let `E` be one-time evidence production/acquisition, `V` strict cold admission,
`R` ordinary baseline realization, `M` protected storage/maintenance, and `d_i`
the complete cost of the i-th later discovery/use/contribution. Then a user's
history costs

`C_A = E + V + R + M + sum_i d_i`.

Charge these terms to the participants actually paying them. Shared production
is not free, each cold receiver pays its own checking, and a private module
import can load substantial transitive artifacts. The catalog/context-loading
cost in the prior cold strategy can grow badly with many tiny batches; reducing
batch count within a justified finite envelope matters more than hiding it.

The observed admission/recovery term alone, spread over 100 uses, is about
2.71 CPU seconds per use by arithmetic. This is not a forecast of total `C_A`,
a measured steady-state cost, or evidence of benefit over normal Lean packages.
It merely explains why a one-time 271-second observation is not a reason to
weaken trust before considering amortization. No analogous bound for Mathlib
as a whole has been established.

The strong comparator gets the same pinned background, ordinary incremental
compilation, index, metadata previews, caches and existing mathematics. Its
shared-library route may be cheaper. The commons must earn extra costs through
selective independent acquisition, useful cross-provider discovery or reduced
integration effort under an actually relevant assurance policy. There is still
no demonstrated full-cost useful-growth margin or universal exponential gain.

## Route B: exact approved compiled base, only as an explicit alternative

B could have higher payoff for a large library the local operator already
trusts and uses. It avoids independently rechecking that common base and checks
only new inert deltas against its actual native environment. **It does not prove
the base derivable from our checked seed.** The user has allowed consideration
of compromises, not implicit permission to turn arbitrary libraries into axioms.
Implementation requires a distinct root policy selection; actual adoption
requires the operator's explicit choice of the exact base and assurance policy.

A clean proposed contract would identify a base by an immutable descriptor of:

- Exact supported kernel/toolchain and logical/declaration policy.
- Ordered imported modules and complete selected artifact dependency graph,
  including the relevant private/public parts and their exact hashes.
- The exact declaration interpretation used at the delta boundary, including
  definitions, universes, inductive/recursor groups and computation rules.

The derived `BaseID` must be domain-separated from current strict identities.
An apparent package version, a public signature, a matching name, a signature
by an operator or a source repository hash is not enough. Hashes identify the
chosen bytes; approval supplies a trust premise, not a theorem about those bytes.
Independent builds may have different artifact identities. Do not silently call
them the same base without a separately justified exact correspondence.

An inert delta declares its exact base, imported symbol references and complete
new units. The local receiver verifies that it has a locally eligible warrant
for that base, loads only the locally selected artifacts and checks the new
units with the existing bounded safe declaration/kernel rules. No remote
`.olean`, source elaborator, plugin, build script or assertion flag becomes
authority. Transparent definitions and type conversion retain their actual
semantics; a hash cannot replace computation that checking requires.

The conditional claim is:

`WellFormedSoundBase(Gamma_B, policy) and CheckDelta(Gamma_B, U)`
`  imply valid new judgments over Gamma_B under that policy.`

Under B, the first premise is operator-adopted rather than independently
established by this software. A forged/unsound approved base can therefore
invalidate downstream trust despite a correctly checked delta. The result must
state that base policy and assumption explicitly; it must never display the
strict seed-derived acceptance status. Merely filtering familiar axiom names
does not establish that a forged compiled theorem is valid.

There is no need to invent a second mathematical calculus. Existing bounded
declaration codecs, group reconstruction, kernel extension, name binding,
protected contexts and module reread machinery are the starting components.
However, current initialization, symbol namespace and module bridge cannot be
relabelled as B by a CLI flag; this is a consequential acceptance-profile change.
That implementation and review cost is why B does not win the present decision
without evidence that A's one-time cost or compatibility is unacceptable.

### A/B interoperability must not launder trust

| Sender / receiver situation | Permitted consequence |
|---|---|
| A receiver, current strict ordinary evidence | Existing independent missing-closure admission and local reuse; no B assumption is needed. |
| Two B participants with the same exact `BaseID`, each explicitly approving it | They may exchange complete inert deltas under that base. Neither participant's approval forces the other's policy. |
| B sender, A receiver with no strict warrant for the referenced base symbols | Refuse strict admission, or request ordinary complete evidence and check the missing closure. Metadata may remain inspectable. A B acceptance report or identical artifact hash is insufficient. |
| A receiver has independently checked exact meanings for all base symbols actually used by the delta | A separately checked symbol/environment correspondence can translate the delta into the strict lane. Merely rewriting IDs or reusing names is forbidden. No such adapter is currently implemented. |
| Different base versions or definitions | Refuse automatic mixing. Use an explicit new contribution/translation checked in the destination context; no semantic-equivalence assumption. |

Semantic identity and warrant strength are conceptually distinct. If a future
common exact-base representation supports both kinds of warrant, it should not
force duplicate mathematical objects solely because assurance differs. But
that future representation cannot erase today's boundary: current strict
export IDs commit to specific units/imports, and a new base-relative identity
does not automatically equal them. Start with refusal rather than an unsafe
cross-namespace conversion.

An owner-run source build may produce B's chosen local artifacts, but successful
compilation alone is not validation of hostile source or kernel-independent
truth. It still needs an explicit approved-source or actual sandbox policy,
fixed dependencies and the stated compiler/importer trust. The prior
`ACCEPTANCE-BOUNDARY.md` analysis of `leanchecker --fresh` already explains its
arbitrary axioms, unsafe/partial skipping, binary parser and missing finite
bounds. Do not rediscover, benchmark or portray that command as a turnkey fix.

## Smallest decision-changing next evidence and stop rule

Before implementation, resolve only these source questions:

1. Can an existing inert exported bundle be selected without a fixture or
   retained-consumer dependency, with exact per-unit records and cumulative
   bounds? Reuse the saved large-closure census; do not reproduce its proofs.
2. Can the existing admission/prefix machinery expose that bounded baseline
   operation with no semantic, foundation or trust-mode change?
3. Can the same selected closure become one or a few ordinary proof-complete
   modules under a coherent finite baseline profile, preserving the existing
   interpretation checks? This must account for the current 32-unit delta,
   1,024-unit total, module-chain and artifact limits together.

If these are viable, the first software slice is that strict baseline seam.
Changed-boundary controls later need only distinguish fresh prefix commitment,
an exact committed prefix on explicit resume, altered/conflicting units and
budget refusal. Native evidence should target only any newly uncertain ordinary
materialization boundary, not repeat the successful 2,852-unit admission or
every previous reciprocal test. Root owns exact input and runtime selection.

If source analysis reveals an unavoidable expensive conversion or incompatible
ordinary declaration boundary, record that concrete obstruction before choosing
B. Evidence of an actual needed background's unacceptable full cold cost, or a
normal project that already accepts a clearly selected native-library trust
policy, could reverse the choice. Lack of a supplied user project alone cannot.

Stop when the selected normal-library workflow has a coherent input-to-ordinary-
use contract and its changed implementation boundaries are resolved. Do not
turn baseline intake into a replacement Lean package manager or claim that it
solves indefinite availability, global recall, sustained beneficial growth or
final public deployment. The next high-payoff decision should again come from
an actual blocked user workflow, not from remaining interesting mechanisms.
