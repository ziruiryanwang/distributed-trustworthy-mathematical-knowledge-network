# Existing-owner module export: integration decision

2026-10-23. Root source selection; no module execution has yet been selected.

## User workflow and decision

A researcher discovers mathematics in the commons, checks it locally, then
wants to use it in an ordinary Lean project. Authoring scratch interfaces are
not suitable libraries: their theorem handles may be axioms, and receiver
snapshots are not automatically modern ordinary modules. A genuine checked
module is the missing practical boundary. If an already approved ordinary Lean
package supplies the result, importing that package remains the simpler option.

The selected bridge reuses existing complete evidence, the fixed foundation,
the pinned ordinary checker and Lean's module writer. It introduces no checking
logic, certificate, remote binary trust, package resolver or global task list.
Read the native and closure checkpoints beside this note for the exact relation.

## Controller

`software/v5/ordinary_module_bridge/module_export.py` exposes `export_module`
over one already-open `OrdinaryAdmission` and its real durable custody. The
caller holds the existing owner lock and supplies a nonrenewing parent allowance.
The existing `AuthoringProfile` is augmented with exact native/controller/worker/
collector source pins; all existing helper-directory bytes remain verified.

The controller:

1. Binds exact selected targets to the actual owner context. Locators identify
   bytes; only the protected context supplies warrants.
2. Collects every selected nonbasis proof dependency, with complete unit groups,
   exact import identities and aggregate bounds. No owner admission is performed.
3. Invokes the new Lean source through `module_worker.py` and the existing Job
   supervisor, using the already compiled modern helpers and `lean --run`.
   No extra executable build is needed. The worker excludes inherited Lean and
   Python paths, puts the approved runtime before selected helpers, and invokes
   one fixed builder command without Lake or network resolution.
4. Requires clean actual process closure, exact returned labels/inventories and
   all five normal module artifact parts. Records their actual sizes and hashes;
   writes `MODULE.json` only after checking the original inputs/support again.

Unknown native CPU remains unknown and receives a separate conservative charge.
Failure keeps partial output without a completion marker or automatic retry.
The controller does not add a new catalog warrant. Windows Job limits are not
a hostile-source security sandbox; this is trusted local construction from inert
evidence, not executing peer source or accepting peer binary modules.

## Cost and cache boundary

The first bridge pays one selected full-proof closure acquisition and two
unchanged checker passes. The first establishes exact private foundation/proof
correspondence; the second is a conservative normal-import visibility and
conversion gate. All required nonbasis proofs are real, not opaque assumptions.
This cost must be included before claiming a benefit from repeated ordinary use.

The generated module name/key binds selected export identities, semantics,
foundation, builder/runtime implementation, source policy and helper bytes.
It deliberately excludes local context root and absolute installation paths.
The originating warrant context remains in the local output manifest. Exact
export identities recursively commit their dependency identities under the
existing hash assumptions; the collector still resolves and checks them.

Automatic cache lookup, cache reuse validation and earlier generated modules as
new boundaries are not implemented by this first bridge. Therefore this does
not promise cold import without selected proof ancestry, arbitrarily large
closures, or unlimited network scalability. An ordinary compiler can reuse a
locally generated module without re-running its proofs; the next selected
consumer check must establish that this implementation actually supports that
workflow. The final v5 goal is not reduced to this component.

## Narrow evidence plan

Pure controls use three existing actual evidence units under explicitly mock
warrants, with native/database/network operations prohibited. A separate actual
discriminator opens the existing B owner at its already accepted reciprocal
root, exports `applyFour_eq` and its `applyTwice`/`applyTwice_eq` closure, and
checks a normal new-system consumer with no construction/meta helpers. It must
both apply the theorem and reduce the definition. Old artifacts are preserved.
The controller's report and matching file hashes alone are not that consumer
test. No repeated reciprocal campaign or new theorem-discovery workload is needed.

The independent source/actual review remains the existing
`ORDINARY-MODULE-BRIDGE-REVIEW.md`; no further registry is introduced.
