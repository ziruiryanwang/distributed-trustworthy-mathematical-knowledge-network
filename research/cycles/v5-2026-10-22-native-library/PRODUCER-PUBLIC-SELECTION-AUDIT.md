## Marginal payoff after the one selected boundary

The new facade closes a real operational omission: an approved ordinary Lean
project can supply inert evidence without first opening a commons mathematical
owner or re-adopting its own results. One installed direct invocation is a
proportionate check of that newly joined CLI/profile/layout boundary. It is not
an independent check of the unchanged native exporter's mathematics, and it is
not evidence of useful growth.

**Recommendation: close this boundary, then stop exporter expansion unless a
specific independently useful consumer path is blocked by it.** Retain the
working adapter as an optional conversion tool. Do not automatically follow it
with candidate ingestion, a remote export daemon, a persistent producer cache,
new benchmark fixtures or toolchain ports. A passing component test only removes
one uncertainty; it does not supply a reason for another implementation stage.

This conclusion uses the existing GROWTH-FIRST-ARCHITECTURE-DECISION and
DEMAND-DRIVEN-GROWTH rather than re-deriving their models. The actual retained
producer imports/censuses the private environment and exports a whole selected
closure outside the fixed seed. Removing owner initialization does not remove
those costs, repeated overlap, cold receiver checking, unsupported declaration
or toolchain limits, nor the work of finding a useful result. A normal approved
Lean package or already retained bundle may remain much cheaper. Those routes
must be available before asking a participant to convert anything.

For the next engineering choice, fix one real consumer endpoint and the assurance
it needs. Compare the least-cost feasible ordinary package/repository/bundle
route with the candidate intervention, including user/agent integration time,
checking, adaptation, failures and incremental service cost. The intervention's
justification is the avoided *remaining* obstruction, not all historical exporter
or registration cost. Source reasoning is sufficient to reject it when the
ordinary route already meets the same endpoint and assurance no less cheaply.
No contrived timing campaign is needed to manufacture a difference.

The highest-value unresolved question is presently whether a useful existing
method and its applicability bridge can be delivered and applied with less
consumer friction, using ordinary Lean tooling where it suffices. If the only
surviving difference is inert-data admission without approving a new publisher's
executable extensions, that is a legitimate narrower product value, contingent
on the real checker/parser/security boundary. It should be demonstrated at that
boundary, not promoted into a claim of faster mathematical invention or a unique
advantage of a bespoke network.

A later exporter optimization deserves priority only when all three conditions
hold: an actual selected useful path needs exact interchange; the specific
exporter cost/compatibility defect prevents it or materially dominates its full
cost; and a simpler package/cache/batch route does not remove that obstruction.
Otherwise leave the adapter unchanged and spend the effort on the missing
application/discovery premise. This is a decision rule, not an authorization for
new experiments or an attempt to declare v5 complete.

design economy, but it resolves a local application problem, not worldwide search.

Three boundaries must remain explicit in the resulting workflow:

- **Advice is not completion.** The inspected elaborator really calls `admitGoal`
  in the suggestion branch (including `config.all`), and the unsuccessful term
  form uses `mkLabeledSorry`. The retained checker traverses actual references
  and rejects `sorryAx`; successful default `exact?` is not inherently forbidden.
  Replay a suggested explicit term and finish its true residual obligations,
  then use the unchanged full proof/dependency policy. Do not infer completion
  from diagnostic compilation, a suggestion message or tactic spelling.
- **Ordinary import compatibility is a genuine premise.** Local checked module
  export preserves selected mathematical declarations, not arbitrary notation,
  typeclass/simp registration, executable code or another toolchain. Existing
  declaration collisions/private-public conversion and anchor/support identity
  requirements can still refuse. Native application helps only after the exact
  actual consumer environment contains compatible declarations. Do not present
  the broken original-reference branch as repaired by citing a narrower module
  success; the proposal correctly keeps those claims separate.
- **No automatic search or growth dominance.** The imported-signature cache is
  rebuilt per process, broad keys are deliberately filtered/fallback-searched,
  and speculative application consumes heartbeats. Local search may lose to
  direct explicit application or a specialized existing index. Unknown remote
  candidates, mathematical bridges, security and service capacity remain separate
  obligations. Consolidation can eliminate an avoidable workflow tax without
  proving faster research or asymptotically scalable global semantic retrieval.

The comparator distinction is also appropriate: a simulation argument precludes
claiming unique network superiority, but does not make a not-yet-built useful
interchange adapter free. Engineering/integration cost must be attributed to
the actual alternatives and amortized over a stated use horizon; historic sunk
work must not be charged only to a comparator or counted as a future benefit.
If both routes use the same adapter, its common cost/capability cancels when
isolating network value, while the adapter can still be a worthwhile deliverable.

No blocking theoretical defect was found in the proposal at this scope. Its next
action should remain command/workflow consolidation with explicit supported
semantics. Add a narrow adapter only after naming the actual missing boundary;
do not convert that conditional stop rule into another open-ended compatibility
campaign. These cautions are adoption limits, not a new implementation assignment.
