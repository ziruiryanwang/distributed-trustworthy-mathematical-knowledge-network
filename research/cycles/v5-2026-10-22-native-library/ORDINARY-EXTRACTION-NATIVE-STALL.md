## Why Eq or the theorem is not the observed blocking point

`software/v5/ordinary_lean/PortableOwnerConstructCommand.lean` executes:

1. Local environment checks and bounded identity/path parsing.
2. `phase "ENTERED_EXISTING_OWNER_ENVIRONMENT ..."`, which writes and flushes stdout.
3. Reading and validating `header.json`, then `HEADER_MATCHED`.
4. `OwnerConstruction.constructPrepared`, then `CONSTRUCTED_READY_FOR_AUTHORING_INSTALL`.

The generated source puts the Nat.add_zero consumer after this entire command.
The exporter is after the theorem. Successful comparator stdout contains all
three lines; native01 contains none. In the intended synchronous frontend path,
any ordinary completion of step2 would be externally visible before the theorem
or its exported missing imports were processed. Absence of that line does not
pinpoint the exact startup/import instruction, nor prove the process was never
created, but it supplies no evidence for a basis reconstruction or proof failure.

`author_worker.py` is a fixed `subprocess.call` of Lean with no piped child stdout:
the compiler inherits the selected regular output file. There is no intentional
stdin protocol wait (stdin is DEVNULL), Lake invocation, dependency resolution,
network request or Python queue in this branch. Import loading and operating
system behavior remain outside these source-only exclusions.

## Operational hypotheses and highest-payoff next action

The saved report itself records a wall resource stop. CPU/log bounds were not
approached. A total-process count equal to a configured active-process cap does
not prove a process creation denial; it is not a record of peak simultaneous
processes or a denial event. The successful comparator had the same 4/4 values.
Likewise, peak private commit below 1024 MiB does not disprove a refused larger
allocation: rejected commitment need not raise the recorded successful peak.
Thus the newly reduced per-native memory envelope is a concrete changed
operational condition, but not an established cause. No claim of insufficient
physical RAM, a compiler bug or a hostile-input failure follows.

Root can first use the independent supervisor review to decide whether there is
a concrete process-boundary defect. If none is found, the smallest defensible
fresh operational comparison is the **already successful 1536 MiB native envelope**
under the existing 2048 MiB aggregate outer cap, with fixed nonrenewing wall/CPU,
same mathematical source and no new runtime build. It is an explicit hypothesis
test, not a guaranteed remedy or an automatic retry. Returning to the previously
used finite profile needs no hardware purchase, OS tuning or RAM investigation.
Any selected successor must use fresh outputs and preserve native01 in full.

If a second startup stall occurs without the first phase, do not widen the wall
budget again. Stop the mathematical test and select a narrowly instrumented
startup boundary only if the unresolved distinction changes the practical route.
For example, a future worker can record a flushed controller-side "before Lean
spawn" and "Lean exited" marker without rebuilding Lean helpers; these markers
would distinguish worker setup from compiler lifetime, but not identify an
internal module-import stall. They are optional follow-up instrumentation, not
currently edited product code or a new acceptance condition.

The three-command workflow remains unqualified: no candidate was saved,
extraction was not invoked and combined admission was not attempted. This
