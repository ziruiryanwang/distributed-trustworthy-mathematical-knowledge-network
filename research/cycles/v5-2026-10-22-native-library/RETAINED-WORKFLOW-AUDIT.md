### Direct cause: importing private data is not a modern public environment

The runtime source is
`software/runtime/lean-4.34.0-windows/src/lean/Lean/Environment.lean`, freshly
rehashed to the previously recorded
`ee364e4788ce0560c87f621eeb3c4c3dfec62e8db4e15e099fd80e6adc533b86`.

1. `ReferenceSource02.lean:161` calls `importModules` with `level := .private`.
2. Lean `Environment.lean:2448` calls `finalizeImport` with the same level and
   no explicit `isModule` override. At line 2308 its default is
   `isModule := level != .private`, hence false for this call.
3. `ReferenceEnvironment.lean:411` immediately requires `env.header.isModule`
   to be true. The conjunction is unsatisfiable on this stock private import.

This is a deterministic API-contract mismatch, not a malformed theorem, an
insufficient resource grant, a missing artifact or a compiler-path failure.
The imported module records can individually have `data.isModule = true` while
the encompassing private-inspection environment has `header.isModule = false`.
Those properties are distinct.

**Removing that guard alone would be incorrect.** The same source later sets
`publicEnv := owner.setExporting true` to test target public availability. Lean
`Environment.lean:653` explicitly makes this operation a no-op when the header
is not a module. Additionally, the public constant map is constructed only when
`finalizeImport.isModule` is true, and `importModulesCore` defaults `isExported`
to false at private level (line 2103). A post hoc header flip is not construction
of an authenticated public view either. It would confuse full private theorem
records with the actual exported interface and could permit a private declaration
to pass the target-public check.

The defect is not confined to author extraction. `ReferenceModule.lean:498`
imports a private base and calls its duplicate modern-environment guard; its
private reread near line 597 does the same. Those later delta stages were not
reached. Treat them as source-confirmed affected paths, not observed failures or
already passing successor behavior.

### Minimal correction in principle, not selected implementation

The easiest semantics to justify is to keep **two distinct imported views**:

- Private inspection uses the exact selected artifacts with `.private`, expects
  the enclosing private-mode header, and still checks each imported module is
  modern, the exact private module order, full original/generated records and
  owned declaration census. It supplies complete proof bodies for export.
- Public interface checking imports the same pinned roots/artifacts with
  `.exported`, requires the modern header, checks exact public module order and
  the existing public/kernel projection records, and tests selected target
  membership in that actual exported frontend. A private owned declaration may
  be used internally where permitted, but is not thereby a public target.
- The author target must satisfy both original ownership/full safe declaration
  requirements and public membership. Receiver admission remains unchanged.
  Private/exported delta checks and rereads retain their separate inventory and
  projection obligations; their enclosing-header expectations must match the
  actual import mode instead of universally demanding true.

This is an explicit mode distinction, not deletion of the modern-module
requirement. The full data import still rejects legacy imported modules. Public
projection equality must remain checked, including theorem-to-axiom projections
allowed by the existing registered policy; public presence does not replace
complete private proof checking.

An alternative may construct one inspection environment with an explicit
`importModulesCore`/`finalizeImport` pair. That would need both exported import
flags and a properly built public constant map, with a justification that its
public projection agrees with the intended `.exported` view. Supplying only
`isModule := true`, `markAllExported`, or copying the private map into the public
map does not establish that condition. Do not select a lower-level importer
variant merely because it appears to save a second import.
