## Why the new pointer is custody, not inherited mathematical authority

`_selected_snapshot_origin` accepts only a 64-hex operation identifier beneath
this store's `operations` directory, not an external path. It requires a different
operation, original-reference kind, matching store binding, a closed selected
origin, and an origin selection with exactly the five original fields. The old
selection must equal the new selection with the retained locator removed.
Consequently it cannot silently change the original context, target set, approved
project, artifact report or bundle. The exact old support ID is not adopted.

Origin chains are deliberately excluded: an origin with its own retained locator
fails the exact original-selection field check. Both accepted closure reasons
only permit inspecting retained bytes. Neither is treated as a native success.
`CLEAN_FAILED_REFERENCE_REGISTRATION` may legitimately have failed before matching;
that cannot confer authority because the continuation still runs a new match.

The retained snapshot is reopened with its selected manifest hash and the current
unchanged installation hash. `snapshot_reopen.read_snapshot` checks the finite
directory/file census, no redirect paths, exact replay paths, metadata pins,
module/dependency closure and every artifact hash. It never opens the old source
project. Skipping `selected_project` in the retained controller branch therefore
avoids an unnecessary source-directory availability dependency, not snapshot
validation. The supplied exact selection/report bytes still match the origin and
the manifest at input binding.

The fresh registration reserves a new operation and produces its own current
request from the real owner context through `Q.prepare_request`. It binds the
current support ID and all current warrants, writes fresh event files, and runs
the actual native matcher. Fresh cleanup, report/request binding, profile checks
and a second complete snapshot validation precede commit. The old request,
supervision and match report are never read as registration success inputs.

## Record and reopened-use checks

Only `snapshot_manifest` gains a cross-operation path. `_snapshot_record_pin`
permits exactly `operations/<64-hex>/snapshot/prepared-manifest.json`; all request,
report, warrants and other event paths remain pinned to the fresh operation.
The record's manifest hash equals its snapshot ID. Commit derives the locator
from the actually bound snapshot after re-resolving the selected origin.

`load_reference` checks the fresh record address/current support binding and
current warrants, reads its reservation, requires current operation/store/support
identity, resolves the same selected origin, and checks pointer/snapshot ID,
source-context and target equality before reopening the snapshot. Thus a syntactic
same-store pointer alone is not enough to authorize reuse. Fresh report metadata
is rebound to the current support, snapshot, original registration context and
current warranted bindings. The record-last nonoverwriting commit is unchanged.

Changing support sources changes the reference support ID; it does not rewrite
the installed mathematical implementation or accepted owner roots. Old records
under a different support ID would not silently reopen. Root's selected case has
no old committed reference record; this is not a general migration design.

## Resource, failure and CLI boundaries

- Global census counts old snapshot storage once in its actual origin; the fresh
  locator does not copy or exempt its bytes. All existing operation and total
  byte/count ceilings remain. Reservation conservatively still holds the old
  maximum per-reference allowance, even though the retained path writes less.
- Exact bounded `supervision/command.json` handling is inherited from the reviewed
  source02 repair. No arbitrary supervisor file/directory is newly permitted.
- The same nonrenewing budget begins before retained validation. Actual matching
  CPU is accounted; unknown cleanup blocks and unknown commit stays unknown.
  Retained hashing still costs time proportional to selected artifact bytes;
  no claim of constant-time original-library access follows.
- `owner02` permits the two retained options only together, only for registration,
  and validates both as exact identifiers. Other operation meanings are unchanged.
- A wrong store, different origin selection, malformed/traversing path, incomplete
  snapshot, changed artifact or absent current warrant fails an explicit check.
  An old saved-PASS file cannot satisfy the fresh event path. These are source
  arguments, not newly executed negative tests.

All retained source/evidence remains necessary for subsequent reference use. No
deletion, garbage collection, retention horizon expansion or original-operation
revival is introduced. The same immutable-custody premise as the previous design
is necessary; future reclamation would need to preserve this new physical edge.
