# Actual Lean checking inside a RISC Zero guest: dependency-closure decision

Status: source-level feasibility checkpoint, 2026-09-27 Chicago. No guest was
built or executed, no software installed, and no proof generated by this work.
This note is not a general-Lean certificate qualification.

## Decision

The smallest identified native checked-declaration entry is
`Lean.Kernel.Environment.addDeclCore`, exported through `lean_add_decl`.
Calling the elaborator's `Lean.Environment.addDeclCore` / `lean_elab_add_decl`
would unnecessarily include the frontend. The native kernel entry is real:
it invokes `environment(env).add(declaration(decl, true))` and checks the
declaration, rather than accepting a host-side success bit.

This makes a kernel-only guest architecturally conceivable. It does **not**
make it an immediately available build: the checker uses generated Lean data
structures and environment functions plus Lean's C++ runtime. Initialization
currently pulls substantially more code than the narrow logical operation.
The concrete source closure below is a candidate manifest, not a measured
minimal linked closure. A full native Lean port is not a credible unqualified
overnight promise.

## Actual checked boundary and acceptance relation

`lean_add_decl` installs heartbeat, recursion-depth, and cancellation scopes,
catches kernel exceptions, and calls the checked `environment.add` operation.
`lean_add_decl_without_checking` is separate and is not an admissible shortcut.
The declaration switch covers axioms, definitions, theorems, opaques, mutual
definitions, quotients, and inductives. For a theorem it checks freshness and
universe parameters, closed/well-sorted type, proposition status, a closed
proof value, the value's inferred type, and definitional equality of the
inferred and declared types. This is actual proof checking.

A future guest relation must bind the checker program/version, serialization,
foundation and axiom policy, authenticated imported declarations, new
declaration bytes and accepted output digest. It cannot merely attest
`lean_add_decl` on an arbitrary host-supplied environment. Admitted imports
need a sound certified-import rule with compatible foundation/semantics;
the final user-facing claim must resolve its assumptions. Root's integration
and `SCALE-SOUNDNESS-DECISION.md` own this separate obligation.

## Initialization prevents naive dead-code elimination

The inspected generated `initialize_Lean_Environment` directly invokes these
20 module initializers:

```text
Init.Data.Array.BinSearch           Init.Data.Stream
Init.System.Promise                Init.System.CancelToken
Lean.Data.NameTrie                  Lean.Setup
Lean.LocalContext                  Lean.Util.Path
Lean.Util.FindExpr                  Lean.Util.Profile
Lean.Util.InstantiateLevelParams    Lean.Util.FoldConsts
Lean.PrivateName                    Lean.LoadDynlib
Lean.CompactedRegion                Init.Dynamic
Init.Data.Slice                     Init.Data.String.TakeDrop
Init.Data.Range.Polymorphic.Iterators Init.While
```

It also performs runtime/meta initialization, including extension registration.
Calling this initializer retains those edges; ordinary `--gc-sections` does
not eliminate reachable calls merely because a particular sample ignores
their functionality.

More importantly, `Lean/Compiler/LCNF/EmitC.lean::emitInitFn` emits
`lean_initialize` for a runtime module outside the `Lean` namespace which
uses a module from the `Lean` package. The native `lean_initialize` initializes
util, Init, Std, Lean, the kernel, printing, library core, library, and
constructions. A small ordinary Lean wrapper therefore does not automatically
produce a small initialization closure. Removing/replacing initializers needs
a justified manifest and tests; naming a wrapper `Lean.*` is not a correctness
argument or permission to omit necessary initialization.

## Concrete runtime and RV32 obstacles

The runtime target includes allocation/object/application, bignums, exceptions,
interrupts, memory/stack handling, IO/process/thread/mutex facilities, compact
regions, sharing/hashing, libuv networking/system/event-loop code, and OpenSSL.
`lean_initialize_runtime_module` explicitly initializes allocation, debugging,
objects, IO, threads, mutexes, processes, stack overflow handling, and libuv.
Many facilities are logically unnecessary for a pure deterministic checker,
but their reachability has not yet been removed.

Supported build choices help: `MULTI_THREAD=OFF`, `USE_GMP=OFF` (builtin `mpn`),
and `USE_MIMALLOC=OFF`; `lean.h` has a 32-bit layout. None completes the port.

1. **TLS remains:** `runtime/thread.h` has a no-multithreading fallback, but
   later `LEAN_THREAD_PTR`, `LEAN_THREAD_EXTERN_PTR`, `LEAN_THREAD_GLOBAL_PTR`
   and `LEAN_THREAD_VALUE` macros still use `__thread` outside MSVC. Turning
   threading off alone does not prove that guest TLS is unnecessary.
2. **Stack checks are platform dependent:** the ordinary non-Windows,
   non-Apple/non-Emscripten `stackinfo.cpp` uses `getrlimit(RLIMIT_STACK)` and
   thread-local stack bounds. `stack_overflow.cpp` uses POSIX thread/signal
   operations. A guest needs deterministic checked stack bounds; a success
   stub is not a justified implementation.
3. **C++ runtime:** target exceptions, ABI/unwinding, standard library,
   allocation/reference counts and bignums remain to be linked/qualified.
   Existing host `.a`/`.dll` files do not satisfy an RV32 target.
4. **Resource semantics:** `type_checker.cpp` initializes `LEAN_NAT_MAX_SIZE`
   from environment configuration (default 128 MiB). The certified relation
   must pin deterministic relevant limits/configuration and treat exhaustion
   as refusal, not successful acceptance.
5. **Input/environment support:** the intended guest must decode actual
   canonical declarations and construct the certified environment. `.olean`
   loading and source elaboration need not be in the relation, but replacing
   them with a custom decoder introduces its own checked binding obligation.

## Native-Windows RISC Zero build route: ingredients versus completion

RISC Zero documents Clang overrides through
`CC_riscv32im_risc0_zkvm_elf` / `CFLAGS_riscv32im_risc0_zkvm_elf`, including
`-target riscv32-unknown-elf -march=rv32im`. The existing Windows Clang is
therefore a plausible code-generation ingredient. It does not provide guest
libc/C++ ABI/exception libraries or the RISC Zero platform runtime.

The pinned experimental C guest's Makefile explicitly rejects `Windows_NT`.
Its platform library is built with `cargo +risc0 rustc` for
`riscv32im-risc0-zkvm-elf`; it is not a Clang-only example. The official ready
install documentation lists x86_64 Linux and arm64 macOS; its `rzup` platform
OS enum actually contains only Linux and macOS. The C++ component asset switch
also supports only those two host combinations. This demonstrates that the
unmodified official helper is not a native-Windows turnkey path, **not** that
a manually specified cross-build is impossible.

On root's explicit authorization, the retained stock Rust compiler was queried
once with `--print target-list`. It **does include**
`riscv32im-risc0-zkvm-elf`. Its retained rustlib directory contains only host
`x86_64-pc-windows-msvc` libraries and `etc`; guest std/source are not already
present there. Pure Rust may avoid the native Lean C++ closure; the separate
nanoda toolchain follow-up below must inspect std support rather than infer
impossibility from official installer support. This introspection is not a
compile, install, or guest execution.

## One finite prospective native-kernel build contract

This is a proposed next gate, not an execution authorization or a passing
result. Before allocating runtime, root would select fresh source, a pinned
target runtime/toolchain and exact resource ceilings; independently review the
entrypoint, initialization substitutions and input relation. No frozen code or
old evidence is modified.

The single bounded compile/link allocation must produce:

- an RV32IM ELF whose entry actually reaches the pinned checked-declaration
  path, not an unchecked-add path or host boolean;
- a full linker map and undefined-symbol report, generated-C manifest,
  initialization list, compiler/target/runtime identities and configuration;
- an explicit account of each replaced OS/runtime hook, with no success stubs
  on proof-checking, exception, memory, stack, or resource refusal paths;
- bounded byte/time/resource accounting and clean process closure.

Fail and stop on unresolved semantic/runtime symbols, unreviewed substitutions,
incompatible target/host tooling, or resource exhaustion. Do not turn one
failed allocation into an unbounded iterative port. Passing this gate proves
only a concrete build closure. Separate later gates must execute valid and
invalid actual Lean declarations, compare native outcomes, certify imports
without ancestral replay, and address adaptive recursive security. Linkability
alone does not establish mathematical fidelity, efficient proving, or growth.

## What this settles

The actual native checking seam is concrete and narrower than the elaborator.
The main remaining native-port risk is the runtime/generated-initialization
closure, not finding a kernel API. An alternative Rust checker can plausibly
reduce engineering closure, but mathematical correspondence then becomes an
additional named trusted component. Neither route can inherit arbitrary-Lean
or ancestry-independent contribution claims from the completed EQ-DAG1 test.

## Follow-up: pure-Rust nanoda guest on the existing Windows compiler

**Disposition: a specific build candidate exists; neither impossibility nor
successful compilation is established.** Official native-Windows installer
support is absent, but a patched compiler is not shown necessary for this
candidate. There is sufficient source evidence to justify one future bounded
compile/link discriminator after the root's native checker/bridge test; no
guest build is selected by this note.

### Exact proposed compiler and source pair

Retained compiler (identity from the frozen first-outcome/version evidence):
`rustc 1.90.0-nightly (35f603652 2025-06-29)`, full commit
`35f6036521777bdc0dcea1f980be4c192962a168`, host
`x86_64-pc-windows-msvc`, LLVM 20.1.7. Its actual `--print target-list` contains
`riscv32im-risc0-zkvm-elf`; its host `rust-lld.exe` exists. No target JSON is
required. Existing host libraries must not be relabeled as target libraries.

The exact official matching component is
[rust-src nightly 2025-06-30](https://static.rust-lang.org/dist/2025-06-30/rust-src-nightly.tar.xz),
SHA-256 `dffa4a26dfbff4b54ed4b641addc07930d2d195d0908e296f2338599999693c9`,
as advertised in that day's official `channel-rust-nightly.toml`. Only the
manifest was read; the archive was not downloaded. Fresh experiment-local
extraction must preserve the old toolchain/run: select the component's
`lib/rustlib/src/rust/library` source root and its complete build-std contents,
not a handful of copied std files. The RISC Zero builder itself supports an
external source root through `RISC0_RUST_SRC` and Cargo's
`__CARGO_TESTS_ONLY_SRC_ROOT`; use the exact root layout expected by the pinned
Cargo, or a fresh isolated toolchain copy with the conventional source layout.
Do not modify the frozen retained compiler directory.

The inspected exact upstream commit contains both the builtin target and
`library/std/src/sys/pal/zkvm/{mod.rs,abi.rs,os.rs}`. Its `std` has implemented
allocation, stdin/stdout/stderr and randomness for this target. Its ABI file
explicitly says that symbols are supplied by `risc0-zkvm-platform`. Therefore
the often-made inference "stock Rust std has no RISC Zero implementation" is
false for this actual compiler. Unsupported filesystems, threads, pipes and
time operations remain unsupported, not ordinary Windows operations inside
the guest. Target metadata's `std: None` is not evidence that these sources
are absent.

### Guest/library candidate and ABI obligations

Keep current RISC Zero revision
`3bbcd44d6459b9ef6ac0df3846dc9215514934e8` as the first candidate; no older
backend was surveyed or selected. Proposed dependencies are its guest-side
`risc0-zkvm` with `default-features = false, features = ["std"]`, plus
`ammkrn/nanoda_lib@3a2407216ee84a75f9e1aead6803d0578be06ae7` (0.4.19).
Use the library checker, not nanoda's host CLI. The wrapper needs
`#![no_main]` and the actual `risc0_zkvm::guest::entry!` startup, not a hand-made
"main returned success" runtime. Guest startup initializes the heap and
environment and finalizes the journal. Do not also enable the platform-only
`entrypoint`/`panic-handler` implementation, which would conflict with std or
the zkVM guest entrypoint.

The current platform's `rust-runtime` feature exports libm and syscalls.
The exact old std declarations and current platform signatures agree for
the needed allocation/read/write/panic/random entrypoints inspected:

```text
sys_alloc_aligned(usize, usize) -> *mut u8
sys_read(u32, *mut u8, usize) -> usize
sys_write(u32, *const u8, usize)
sys_panic(*const u8, usize) -> !
sys_rand(*mut u32, usize)
```

The std allocator is bump-only with a no-op deallocation; finite input and
guest-cycle/memory bounds are necessary. The default current platform bump
allocator matches this allocation model. Do not claim that enabling the
platform embedded allocator alone fixes std's no-op deallocation.

Some **unused ABI declarations differ**: the old std ABI declares `sys_halt()`
and `sys_cycle_count() -> usize`, while current platform definitions are
`sys_halt(u8, *const [u32; 8]) -> !` and `sys_cycle_count() -> u64`. This is not
automatically a blocker if no old-std call reaches those declarations; use
the current guest finalization path. The acceptance gate must inspect actual
linked/reachable calls and refuse any reachable mismatch. It must not demand
irrelevant ABI identity, nor silently waive a required panic/allocator/IO
mismatch. No success stubs are permitted.

Nanoda's direct dependency metadata gives no immediate MSRV contradiction:
indexmap 2.13.0 requires Rust 1.82; num-bigint 0.5.1 requires 1.60;
num-integer 0.1.47 requires 1.31; serde 1.0.228 and serde_json 1.0.111 require
1.56. These are selected direct versions queried through crates.io metadata,
not a fully resolved lockfile or proof of all transitive compatibility.
Pinning/resolving the complete actual guest graph remains a build prerequisite;
latest semver-compatible packages may impose different requirements. Do not
enable nanoda dev/test dependencies (including random generation) in the
proof-checking guest merely to compile the library.

Configure the guest library API for single-threaded checking; supply input
bytes through guest IO and an in-memory reader. Avoid host file configuration,
filesystem loading, thread-spawning, time measurement and CLI argument parsing.
Any reachable use must be removed through a reviewed pure library path or
cause the discriminator to fail, not be mocked as successful verification.
Root owns the exact parser/checker/canonical bridge and identified projection
annotation correspondence issue; this toolchain note does not adjudicate it.

### One actionable future build discriminator

After root selects a fresh experiment and numerical ceilings, the single
allocation should use the retained compiler **read-only**, separate Cargo
home/target/output directories, exact matching rust-src, locked sources and
the existing host `rust-lld`. Manually invoke Cargo for the builtin target
with the reviewed equivalent of:

```text
--target riscv32im-risc0-zkvm-elf --locked
-Z build-std=alloc,core,proc_macro,panic_abort,std
-Z build-std-features=compiler-builtins-mem
```

Match the pinned RISC Zero build helper's target flags:
`-C passes=lower-atomic`, `-C link-arg=-Ttext=0x00200800`,
`-C link-arg=--fatal-warnings`, `-C panic=abort`, and its selected
`getrandom_backend="custom"` configuration where applicable. The target is
single-threaded RV32IM with advertised atomics; omitting atomic lowering risks
unsupported instructions. Keep overflow checks enabled for the nanoda wrapper
as the library's intended release profile does; dependency package profiles do
not automatically control the top-level guest profile. Record all actual
flags, generated code and linker-map/symbol results.

Bypass only the unavailable host `rzup` orchestration, **not** runtime/image
semantics. `risc0-build` directly looks up a `rzup`-registered patched toolchain,
even when `RISC0_RUST_SRC` is supplied, so setting that variable alone does not
make the official helper work on Windows. Its current final guest image is
`ProgramBinary::new(user_elf, kernel_elf).encode()`, not an arbitrary raw ELF;
capture the exact matching kernel image and computed image identity before a
later executor/prover gate. A successful user-ELF build is only the first
build-closure outcome, not a valid proof image or proven native-Windows prover.

Pass this limited gate only on successful actual nanoda-library linkage with
the intended guest entry, no host-only reachable branch, a complete recorded
source/dependency/toolchain/ABI manifest and clean bounded closure. Stop on
compiler/MSRV/ABI/unsupported-platform/resource failure; preserve the failure.
Do not automatically switch backend versions, install WSL, add a C++ toolchain,
or build an entire patched Rust compiler. Separate later execution/proof gates
must check genuine accepted/rejected declarations and malformed inputs, bind
the canonical relation, and account for proof cost and certified imports.

Official `risc0/rust` release `r0.1.97.0` metadata was also inspected. Its assets
are `rust-toolchain-aarch64-apple-darwin.tar.gz` (442,966,921 bytes) and
`rust-toolchain-x86_64-unknown-linux-gnu.tar.gz` (528,796,425 bytes), no Windows
asset. That fact explains why the manual candidate is needed; it does not
invalidate the concrete stock-compiler/stock-std route above.
