## Variables: do not hide selected work inside constants

Use `SCALE-DATAFLOW.md`'s meanings:

- `N`: unrelated network corpus/history; `H`: selected lemmas' transitive
  ancestral proof/witness bytes; `k`: directly selected certified premises.
- `I`: exact interface/type bytes with needed semantic references; `D`:
  demanded, permitted definition/group bytes; `C`: certificate bytes.
- `L`: authenticated lookup/membership bytes. The present local receiver is
  given an exact bundle; it implements no global discovery query or scalable
  authenticated-index lookup. Its intake does not establish a bound on `L`.
- `p`: the newly authored proof/packet; `K(p; I,D)`: its actual checking work,
  not presumed linear, cheap or bounded solely by the statement length.

Add explicit implementation variables:

- `B_R`: fixed receiver installation/profile bytes and entries. The actual
  selected closure is 596 assets / 97,064,061 bytes plus the 78,872-byte profile.
- `B_P`: selected producer image/runtime/fixed foundation data. This is a
  fixed adopted profile, not all future mathematics hidden in a baseline.
- `T`: serialized coherent execution snapshot bytes for this **new** proof;
  `s`: its actual segment count; `a`: actual resolved assumptions (not assumed
  identical to the number of syntactic lemma uses).
- `W_j`: immutable campaign evidence/checkpoints/logs accumulated by stage `j`.

All statements of independence from `N,H` below hold with the selected profile,
requested interfaces/computational content and new task fixed. If those grow,
their costs remain chargeable. Arbitrarily large interfaces, selected
definitions or new proofs are not made constant-size by this design.

## Receiver: no old proof or producer witness input

The installed wrapper reads and validates an independently adopted profile,
hashes/censuses its exact installation, then reads exactly four bundle files:
manifest, named type capsule, 148-byte journal and real receipt.
`inspect_bundle` uses a bounded four-name `scandir`, not recursive corpus
enumeration. `inspect_capsule` authenticates the exact type DAG against the
fixed registry; it does not call the issuer-side packet projection helper.

`Operation.invoke` passes exactly:

```text
driver verify ADOPTED_IMAGE_ID receipt.bin journal.bin
```

The driver reads only these two explicit mathematical inputs, decodes the
receipt, requires a real Poseidon2 succinct receipt with dev mode disabled,
performs full SDK receipt verification against the adopted image, validates
the application journal and requires exact journal equality. It does not
read an ELF, execute the guest, request a parent certificate, retrieve a
proof packet, replay updates or enumerate an ancestor chain in this branch.
The output packet hash is a commitment, not an instruction to fetch the packet.

For this profile, receiver interface constants must be fixed-baseline names;
there is no dynamic `D` hydration here. Its semantic support is adopted fixed
data. It is incorrect to generalize this as implemented arbitrary definition
retrieval. The receiver certifies the adopted guest relation, not native
Lean admission, and does not by itself import the capsule into Lean.

Actual wrapper cost includes **two full installation hash passes**, bounded
installation censuses, capsule validation, repeated bundle framing/hashing,
snapshot writes/readback/rebinding and the cryptographic verification. The
successful-path explicit data volume has the form

```text
O(B_R + I + C + journal/manifest bytes)
```

with nonzero repeated constant factors. Verification work is the actual
selected `V(lambda,C,journal)` plus parsing/binding/OS/runtime work; this
audit does not prove a tight linear runtime bound. The fixed ~97 MB cannot be
reported as zero overhead or charged only once if the implementation rehashes
it for each invocation. Resource-monitor census repeats over that operation's
bounded directory, not `N` or `H`.

No Lean runtime, guest image file, SDK source tree or ancestor proof artifact
is required by the installed receiver closure. However, the executable retains
other compiled capabilities and the process has the owner's ordinary filesystem
permissions. This is a source/argument/install boundary under the cooperative
local-filesystem assumption, **not enforced OS inability to read ancestors**.
Copied-runtime startup has its own actual audit; real-receipt positive/negative
runtime gates are outside this cutoff.

## Guest relation: selected direct interfaces, not recursive proof packets

The guest receives one bounded header and one bounded new packet. Header
parents are exact application journals, not proof histories. `relation::check`
requires at most eight parents, strict rank decrease, exact interface matching,
one matching body-free parent axiom per supplied interface, fixed structural
authentication for baseline declarations, and a selected new theorem. It
rejects unsupported new nonbaseline definitions/inductives. It checks the
new theorem and the parent types using Nanoda; it does not recheck fixed
support proofs. `env::verify` records each direct parent journal as a same-image
assumption to be discharged by actual supplied receipts.

There is a census of **the selected packet's** declarations/names. That is not
a global mathematics census. Types of new outputs and parents must refer only
to fixed-baseline constants under this restricted profile; no arbitrary
transitive interface/definition closure is implemented here.

Guest checking can cost substantial `K(p; I,D)` and proof generation can cost
substantially more. Absence of an `H` input is meaningful, but says neither
that general Lean checking is certified nor that every useful mathematical
development fits this fixed foundation. Full correspondence of this
experimental Nanoda relation to the selected Lean kernel remains unproved.

## Producer: direct ancestry locality, repeated own-work cost

For **every** driver07 `stage`, including `snapshot`, `lift`, `join`, `resolve`
and `finish`, the code:

1. Reads the selected image, new input and expected journal; recomputes the
   image identity.
2. Reads and fully verifies every supplied immediate parent receipt, requires
   lower rank and distinct journals, then adds it as an assumption.
3. Re-executes the complete new guest computation, validates exact output and
   session bounds, collects all new segments, and integrity-verifies the actual
   proven succinct assumptions again.
4. Except for capture, reads/decodes/hashes the **entire** saved coherent
   snapshot, binds it to the fresh execution's operational identity/count/size,
   then reads the selected segment/prefix checkpoints.
5. Performs the chosen real proof/compression/aggregation operation and checks
   its output. Finish additionally verifies all segment seals, the composite,
   final succinct claim, image and exact journal.

New segment proving uses the saved coherent witness; it does not use unrelated
historical executions. The snapshot remedy retains compatible boundaries but
does **not** currently avoid fresh guest execution or whole-snapshot decoding
on each stage. Calling this incremental new-proof work without that qualifier
would be misleading.

For a fresh complete successful campaign with `s` segments and `a` assumptions,
the adapter selects `s` segment proofs, `s` lifts, `s-1` joins, `a` resolves,
one finish, one cold verify, plus the initial capture. Thus:

```text
segment/lift/join stages               = 3s - 1
guest executions including capture    = 3s + a + 1
whole saved-snapshot decodes           = 3s + a
separate final receipt-only verify     = 1
```

These are source-derived counts for an uninterrupted successful schedule,
not an actual child outcome. Failures, re-launches and split continuations
add work and are retained separately. Each execution also performs direct
parent verification and actual-assumption verification; it is not one
parent verification amortized over the whole campaign.

A faithful cost decomposition includes

```text
(3s+a+1) * [image/input work + guest execution + direct-parent checks]
+ (3s+a) * [whole snapshot read/decode/hash]
+ segment proving + lift/join/resolve + checkpoint/final checks
+ supervisors' repeated fixed-runtime/input/own-evidence work
+ final cold verification + all retained failed work.
```

Here direct-parent checks depend on `k`, their certificate sizes and actual
verification costs. Snapshot work depends on `T`, not `H`. SDK assumption
handling and finish add further checks, so the decomposition is not an exact
CPU formula. It identifies costs that must not be omitted.

The phase adapter's census walks only its selected stage allocation. Its
held environment checks/hashes selected compiler/runtime binaries even for
this research workflow; these are `B_P` overhead, not old mathematics. Its
`inputs` set must equal the stage's explicit command file arguments.

The campaign controllers are broader than one cold worker. Their `rebind`
rehashes every retained immutable input/evidence row before and after each
stage, including new checkpoints, logs and results. With stage count `m`,
this contributes a sum over `W_j`; if similarly sized records accumulate
linearly, repeated hashing can be quadratic in `m`. It is bounded **own
campaign history**, not a global `N` scan or proof-ancestry `H` replay, but
it remains a real scalability/engineering cost. Continuing a child campaign
also pins the immediate parent's finish/verify evidence; it does not walk
that parent's segment history or any recursive parent manifest.

## Actual ordinary child: no parent proof hidden in the input

The existing conditional native audit independently establishes actual use:

```lean
theorem CommonsV3.compose_congr
    {alpha : Sort u} {beta : Sort v} {gamma : Sort w}
    (f : alpha -> beta) (g : beta -> gamma)
    {x y : alpha} (e : x = y) : g (f x) = g (f y) :=
  ScaleIface.L g (ScaleIface.L f e)
```

The packet has three declaration rows: the fixed Eq group, a body-free L
axiom, and the new theorem. This audit reread those roles and independently
checked the binary framing: 7,639 bytes = two 4-byte frame lengths + 648-byte
header + 6,983-byte packet; rank 1, target name 19, one 148-byte parent journal.
The header JSON file is 649 bytes because its saved text has a trailing newline;
that extra byte is not in the framed header. There is no L proof packet or
recursive history in these bytes. The existing `OUTCOME.md` records an exact
named-DAG comparison and two actual L occurrences in the proof, not a claim
based only on source spelling.

The selected child adapter refuses substitution: exact image/input/journal
pins are hard-coded. Each non-verify stage takes those bytes, one actual final
L receipt, the child's snapshot when required and only selected child
checkpoints. It additionally binds genuine L finish/cold-verify result/log
evidence. Parent packet/trace/segment history is not a selected input.

Its final worker command contains just child receipt and child journal.
The surrounding controller still rebinds parent, snapshot and own evidence;
therefore the **entire research producer process tree** must not be described
as receipt-only merely because its last worker is. A later recipient using
the separate small receiver has the genuinely smaller boundary above.

Actual child source elaboration/conditional export is a passed earlier gate;
parent certification, child guest execution, assumption resolution and child
final certification remain separate. This audit supplies no such runtime pass.

## Decision and limits

No hidden mandatory ancestor-proof input or unrelated-corpus scan was found
in the inspected selected paths. The most consequential next evidence is a
genuine final L certificate and cold verification, then the actual ordinary
child with its direct premise resolved—not another generic index mechanism.
Preserve the whole producer/receiver costs when those outcomes arrive.

The implemented restricted boundary is consistent with removing mandatory
`H,N` replay. It has **not** established:

- enforced ancestor-inaccessible execution or a fixed-task history-expansion
  runtime test;
- general sparse Lean environments, new definitions/inductives or scalable
  semantic discovery;
- general Lean-kernel correspondence or exact-profile recursive cryptographic
  security (the separate assurance audit owns those obligations);
- cheap proof production, whole-loop speedup, net useful growth or exponential
  accumulation.
