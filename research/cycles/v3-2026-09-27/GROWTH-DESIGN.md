## Recommendation in one paragraph

Use **lower total cost for a fixed collection of newly checked, reusable
mathematical outcomes** as v3's first empirical growth target. Separately show
that the actual software makes an unchanged acceptance-and-reuse path cheaper.
Do not require a fitted reproduction matrix, global usefulness score, mandatory
task queue or cryptographic proof system for this tentative release. The two
references offer useful models, but a three-episode test cannot establish
supercritical reproduction or exponential growth. A positive, appropriately
scoped finite-horizon result is substantial progress without those claims.

## What survives scrutiny in the references

### Resource-sensitive inferential benefit

For fixed foundation F, reasoner policy pi, task distribution mu and effort
unit, let tau(K,q) be effort to the first accepted endpoint. Give noncompletion
tau = infinity and define R_B(K) = E[min(tau(K,q), B)]. The identity

```text
R_B(K) = integral from 0 to B of (1 - Pr[tau(K,q) <= b]) db
```

is correct for nonnegative extended completion time; endpoint conventions at
one exact time do not affect the integral. It provides a finite-budget
comparison without pretending an uncompleted proof merely took zero time.
Report success count as well: solving at exactly B and not solving are tied
by capped effort, despite their different certification outcomes.

The fixed-theory observation is also correct: adding an already proved theorem
does not enlarge deductive closure. It can sharply reduce the resources needed
to find or use consequences. Thus raw theorem count cannot be the primary
measure of productive knowledge growth. Existing canonical sharing is already
a compression mechanism; another short representation is not automatically an
additional benefit.

Needed qualifications:

- K includes both usable library and search policy. To isolate a software or
  library effect, hold policy, model setting, prompts and interface information
  fixed where possible. Changing all of them tests a combined intervention.
- mu is an **evaluator's declared workload**, never a mandatory mathematical
  agenda or input to the node's correctness predicate. Participating agents
  still choose their work independently in normal operation.
- A universal task-independent scalar ranking cannot follow from this model:
  libraries with crossed task advantages reverse rank when task weights change.
- CPU seconds, wall time, tokens, resident memory and bytes are not additive
  units. Retain the resource vector; predeclare one primary unit rather than
  inventing a post-result exchange rate.
- Distinguish production investment, receiver intake, and subsequent use.
  Do not charge the same admission in both one-time C and each tau; conversely
  do not omit it from both. See the ledger below.
- A small convenience sample supports a claim about those instances. It does
  not estimate performance across all mathematics or every local agent.

### Located dependency hypergraph

The hypergraph is a useful descriptive model: prerequisites jointly enable an
operation; exact proof dependencies remain well founded while capability
*classes* may enable one another across time. Custody, usable interfaces,
admission and search have independently observable effects. It helps identify
where an attempted productive episode stops.

Do not make a new hypergraph protocol or ledger merely to draw this model. The
current requests, package dependencies and outcome logs already expose the
needed event boundaries. A possible productive hyperedge is not evidence that
an agent actually discovered or executed it.

### Reproduction claims: valid conditional mathematics, unproved premises

For nonnegative irreducible R, finite nonnegative adapted outputs Z_n and
`E[Z_(n+1) | history_n] >= R Z_n`, the positive left Perron vector proof gives
`E[sum Z_n] >= c * rho(R)^n` from a nonzero fixed seed. This is a valid
conditional lower bound. The two-class threshold
`bc > (1-a)(1-d)` for `0 <= a,d < 1` is also valid. Neither establishes that
our logs obey that model.

The difficult assumptions are central, not details to be inferred from a
small passing example:

- Multi-parent useful outputs need one total credit, not one child per cited
  theorem. Choosing credit weights changes the fitted R; dependence-counting
  alone does not identify a causal reproduction rate.
- Complementarity, duplicate work, diminishing marginal benefit, changed
  agents and changing catalogs make a fixed linear R questionable. A bound
  must hold in a declared regime; fitting the same data used to report growth
  is not prospective prediction.
- Funding a fixed budget **per seed** while seeds grow requires growing total
  resources. Fixed total hardware and a positive minimum materialization cost
  prohibit indefinitely exponential explicit artifact count per elapsed hour.
- The reference's subcritical formula `(I-R)^(-1) Z_0` is an **equality only
  for the exact linear conditional-mean model**. Under only its more general
  lower-bound assumption it is, at most, a lower bound and need not describe
  total descendants. State which model is being used.
- For a fixed benchmark with nonnegative D, successive marginal gains
  telescope: `sum u(a_i | K_(i-1)) = D(K_0)-D(K_n) <= D(K_0)`.
  If every counted increment earns at least delta > 0, at most
  `D(K_0)/delta` such increments are possible. A permanent growth claim needs
  an independently specified growing workload, not repeatedly crediting the
  same solved task.
- `b^n` compatible choice sequences do imply that many syntactic combinations;
  semantically distinct meaningful tasks, affordable checked composition, and
  a matched baseline remain separate obligations. Handwriting branching
  wrappers does not establish exponential mathematical capability.
- The nonlinear threshold example is internally consistent for its stated
  parameters but is a proposed coarse model, not a derived law of our system.

Do not spend the release window estimating spectral derivatives, selecting a
network topology, or building a global ranking service. First measure a few
complete, genuinely useful downstream episodes.

## Concrete narrow workload: ordered merge and local replacement

This is a **candidate for root selection and one bounded feasibility gate**,
not yet a frozen workload or native-compatible theorem claim. It deliberately
extends, rather than repeats, the already exercised polymorphic right-fold
vocabulary. It avoids new inductive groups, dependent universe machinery,
arithmetic decision procedures, strings, notation extensions and Mathlib.

Let `R A op e xs` denote the exact previously checked right-fold definition.
Let `P` be the existing triple-level reduction theorem (`TripleNestedReduction`)
for that exact R. Both arms start from the same admitted R and P, not from one arm having a
different interpretation of those definitions. For exposition:

```text
R_A(xs) = R A opA eA xs
R_B(xs) = R B opB eB xs

h : A -> B
hunit : h(eA) = eB
hop   : for all x y, h(opA x y) = opB (h x) (h y)
```

All carriers can use the same universe level in this bounded test. Carrier
polymorphism remains real: A and B are independently quantified types. List
order is significant; no commutativity assumption is allowed.

### Initial reusable capability H: use existing Beta, do not re-prove it

The first draft proposed fresh fold homomorphism/chunk transport. A subsequent
repository-wide anti-duplication search found that this work already exists:
`BetaNestedHom`, audited under operator-onboarding, has a 128-node exact type
and actual two-universe proof. It is a better seed, not a new v3 target.
The already accepted `MapAggregateHom` helper in its closure must not leak
to a nominally withheld control through another provided package.

For exposition define (not new trusted constants):

```text
F(tree) = List.flatten (List.map List.flatten tree)
b(block) = R_B(List.map (fun row => R_B(List.map h row)) block)
S(tree) = R_B(List.map b tree)
H: h(R_A(F(tree))) = S(tree).
```

This is the existing Beta theorem under associativity/two-sided identity on A
and hunit/hop, with no B-monoid assumption. Reoffer its exact retained package
through ordinary custody/publication authority on a fresh selected-cut path.
Do not fabricate a new author publication or replay the prior author trial.
Historical producer costs have known partial accounting; report them as such.
An economic claim requiring exact original all-in production cost remains
unavailable. For a present receiver-benefit study the existing library is a
declared sunk investment, and all new custody/intake costs are charged.

### Episode 1: ordered merge J

With both operations associative and both identities two-sided, for
`xs ys : List (List (List A))`:

```text
J: h(R_A(F(List.append xs ys))) = opB (S(xs)) (S(ys)).
```

The exact statement expands F/S/b; future theorem IDs do not appear in its
type. This is an ordered two-input combination interface, not another nesting
depth or product projection. It can build on H plus an inductively proved
fold-append lemma. The treatment receives H through the peer path; the control
may independently derive H, use its own helpers and any equivalent result in
the frozen common permitted library. Neither is required to use a particular
proof strategy.

### Episode 2: contextual replacement K

Under the same algebraic assumptions, take arbitrary prefix/suffix trees and
blocks `old new : List (List A)`. Assume only `b(old) = b(new)`. Prove:

```text
K: h(R_A(F(prefix ++ [old] ++ suffix))) =
   h(R_A(F(prefix ++ [new] ++ suffix))).
```

This justifies changing a local chunk while preserving the whole observed
aggregate; it does not assume equality of the whole answer or equality of the
underlying leaf sequences. It can follow from two ordered-merge uses plus the
local summary equality. Distinct list order remains observable because
commutativity is not assumed. Actual new J dependency should be audited if
claimed; solving K by another route is still task success, not witnessed J
reuse. A control that proves J must retain and reuse it: forced forgetting
would manufacture an advantage.

This is a meaningful but elementary new capability for incremental aggregation,
not a deep mathematical novelty claim. A fresh no-history author must still
produce its exact native-accepted proof within the same budget as control.

### Optional episode 3: two-output local replacement L

For two homomorphisms `h:A->B`, `k:A->C` and associative/unital target
operations, assume the old/new block has equal B summary and equal C summary.
Prove equality of the **pair** of global B/C observed aggregates in an
arbitrary prefix/suffix context. This exercises K at two different carriers
and combines its conclusions. It is not the old Alpha theorem, which
factorized aggregation of pair-valued input; this input need not be a product.
Its strength is a second reusable endpoint, not a claim of semantic novelty.

Prefer the two central J/K episodes first. The third is optional only if its
exact statement and budgets are fixed before observing consumer results.
If feasibility fails, preserve that failure and choose a fresh explicitly
labeled protocol, not silently weaken a dispatched endpoint. A two-episode
study supports only a finite two-task benefit and a witnessed two-step trace.

An evaluator may use these mathematical sketches to freeze exact statements;
experimental authors receive statements and actual checked interface replies,
**not these proposed derivations, prior source, proof scripts or target IDs**.
No theorem is treated as true until the ordinary canonical/native boundary
accepts it. An independently captured proposition-valued statement checks the
target's feasibility, not its proof.

## Minimum fair comparison

### A. Engineering discriminator, separate from agents

Run exact same mathematical input and declared endpoint through baseline
source13 and the selected v3 cut under matched runtime/hardware conditions.
The endpoint includes acquiring/admitting and then submitting a genuinely
dependent result, not just decoding a package or checking an isolated receipt.
Measure cold and reused-local-state cases separately. This is the place to
evaluate package-reader changes or safe local caching. Deterministic harness
scripts are appropriate here; their output is **not autonomous growth**.

### B. New-knowledge comparison on the selected v3 software

Two matched no-history consumers, with the same initial checked R/P context,
allowed Init/library sources, API docs, model setting, prompts except for
declared peer availability, task order and resource ceilings:

- Treatment: ordinary access to existing exact Beta H and then its own checked J/K.
- Control: common library and its own newly proved lemmas/results, but the
  trial's H package withheld. It may independently derive H and use any
  equivalent result in the common permitted library.

Both use the same software. This estimates the benefit of shared mathematical
infrastructure **on v3**, not the software v3-minus-v2 effect. Compare A and B
before combining their claims. Running v2 without H against v3 with H would
confound software, mathematics and policy effects.

Use a predictable finite offering interval that covers the consumer's declared
deliberation budget, with explicit same-host custody and no midtrial silent
renewal. Root/evaluator provisions services before dispatch; agents send
their own ordinary requests. Unknown outcomes stop the affected allocation;
ordinary source refusals can be revised within the same predeclared attempt
budget. Do not build another operator-forwarding framework: the shipped
helper and request dispatcher already work.

Recommended starting envelope for root to size before freeze: two or three episodes
of 15 minutes each per arm, 36 ordinary post-setup requests, at most three
source submissions per episode, and enough declared native-stage/storage
capacity for nine submissions, H intake and own-result admissions. Native
Job CPU and retained-storage caps must be bound to the selected configuration
after feasibility, not guessed from the old Rose timing. Equal treatment
ceilings, not equal numbers of unnecessary calls, establish the resource
opportunity. All costs of actual calls remain charged.

One pair is a pilot with descriptive outcomes. If time permits, a second
independent paired run with reversed arm order provides a minimal robustness
check. It does not justify a population speedup estimate, a p-value from three
correlated episodes, or an exponential extrapolation. Time spent in product
queue/review and native resource contention must be visible.

### Current API route, without new protocol machinery

1. Owner configures fresh cut-pinned nodes and finite peer contacts/capacity;
   initial context packages include the five common packages.
2. `peer-find` returns untrusted receiver-owned remote handles. No exact-symbol
   remote filtering exists; small catalog enumeration is not a scalable-search
   demonstration.
3. `peer-acquire` returns a local candidate/acquisition and new P1 snapshot,
   not acceptance. `admit` checks selected union and yields exact local names.
4. `manage.py inspect` can reveal an ordinary definition's authenticated type
   and body when needed; it is not a theorem oracle or proof strategy.
5. `make_request.py submit --source-file ... --root ... --context ...` writes
   a request; `manage.py request` sends it. An accepted private artifact still
   requires a separate `publish` request.
6. The contributor must ordinarily `admit` its own published candidate before
   relying on it as part of a new checked context. Submission/publication alone
   does not advance that context. Freeze package counts below the 16-package
   maximum and 256 described-reference limit; batch admission supports 1–4.
7. For actual reciprocity, transfer a selected new result to a separately
   operated fresh local checker and require a new accepted dependent result
   or receiver admission as specified. One-entry offers demonstrate access,
   not difficult discovery. Every native stage remains accounted.

Source elaboration uses Init macros/tactics, but unseeded library declarations
must survive complete capture and fresh replay. A convenient tactic that
pulls unsupported declarations is a legitimate source refusal, not permission
to import arbitrary unchecked knowledge. Cooperative local source is executable
owner-authorized input; this study is not adversarial-source sandbox evidence.

## Exact endpoints, effects and decision rules

Freeze full polymorphic theorem types using their exact canonical R reference,
not names or pretty-printed `typeText`. Fix binder/law order and allow only a
mechanical substitution of actual receiving names. A statement definition,
weaker specialization or private compilation is not task completion.

Record these endpoints separately:

| Endpoint | Evidence | Permitted claim |
|---|---|---|
| Intake | Selected exact bytes, fresh `admit`, returned checked context | Trustworthy acquisition worked |
| Target | Exact full statement accepted and ordinarily published | New task solved through software |
| Witnessed reuse | Checked proof-producing dependency of H/J/K reaches root; challenge unused/cancelling citations | The earlier interface was actually used |
| Benefit | Matched arm success/effort comparison with all failures charged | Descriptive advantage on this workload |
| Return | Exact published result received and freshly admitted at another local node | Reciprocal exchange, not independent physical hosting |
| Amortization | Benefit exceeds separately recorded production/intake cost over observed horizon | Positive net benefit only for that horizon/cost unit |

For task i and arm a, primary effort is elapsed time from its release to the
exact ordinary publication, including API, inspection, thinking and revision;
noncompletion is capped at its full 900-second budget. Report complete end-to-end
time including common setup separately. Define

```text
paired_capped_gain = sum_i [min(t_control,i,900) - min(t_treatment,i,900)]
```

Positive gain with no fewer solved targets is descriptive evidence in favor
of shared H under this protocol. An allocation failure, unsupported target or
an unavailable service is still reported; do not reinterpret it as cleaner
causal mathematical evidence. If the treatment is slower or solves fewer,
publish that result and identify the measured bottleneck; v3 must not advertise
a successful useful-growth comparison. Complete proof witnesses can still
support a narrower capability claim.

Repeated references, identifier diversity, proof depth and source-line savings
are secondary diagnostics, not acceptance or primary outcome scores. Actual
proof dependency shows use, not logical indispensability or the amount of
work causally saved. Kernel soundness and exact-object correctness remain
unchanged whether the benefit comparison is positive or negative.

## Minimal cost ledger

Each event needs arm/episode, input/output identity, source-cut identity,
operation, start/end, status, CPU scope, native stages, request reservation,
bytes transferred/retained, and parent event so nested CPU is not summed twice.
Use existing receipts and one compact ledger; no new registry hierarchy.

Keep these disjoint accounts:

- Common preparation: installation/build, common R/P preparation and node
  onboarding, reported for both arms with explicit sharing/amortization.
- H production: retained historical cost, explicitly partial rather than zero;
  new offer/custody preparation charged once. Re-proving the same seed solely
  to manufacture a fully metered history is unnecessary duplicate work.
- Intake: discovery, download, admission and interface inspection per receiver.
- Downstream production: each target's authoring/revisions/checking/publication.
- Reciprocal distribution and next use: exposure/service/transfer/fresh checking.
- Evaluation infrastructure: reviewer/controller time and CPU, reported
  separately but not called zero. Unknown model computation remains unknown.

If task effort includes intake, net investment subtracts producer research and
offer preparation, not the same receiver intake again. Missing historical
producer/model cost prevents an exact original-investment net-benefit claim.
For a future use count
N, a projected break-even calculation is a projection with stated stationarity
assumptions; the observed three-task horizon does not validate those assumptions.

## Release prioritization and stop conditions

1. Finish the observed publication-syntax defect and preserve v2 bytes.
2. Measure and improve a real repeated acceptance/reuse cost without weakening
   the local trust boundary. Prefer existing-path changes to a new cryptographic
   verifier/importer architecture unless measurement changes that decision.
3. Execute the bounded comparison once its statements and feasible API path
   are frozen. A genuine negative result is more informative than another
   elaborately audited toy positive.
4. Package the actually qualified v3 cut with exact deltas, usage instructions,
   limitations and an honest result table. Do not wait for a universal theory
   of mathematical value or pretend that a deadline supplies missing evidence.

The tentative release can honestly say "v3 reduces [measured operation] by X
on [fixed workload] and supports [audited reciprocal chain]; the [matched
knowledge-benefit result] is positive/negative/inconclusive." It must not say
"mathematics grows exponentially" or "proof verification is now cheap" from
these tests alone.
