## Named storage modules versus a new trusted guest relation

The October 6 extension proposal discusses **kernel-level named environment
extensions**, which require a new checking relation/image. That does not imply
every persistent library needs a new guest. The following weaker-in-semantics
but potentially consequential construction is sound if implemented correctly:

1. Store immutable module descriptors containing local syntax, exact external
   module/slot identities, full universe/interface data and requested exports.
   An untrusted alias is presentation metadata, never declaration identity.
2. Resolve only the demanded finite acyclic dependency closure under explicit
   count/byte/depth/output bounds. Check every fetched object's canonical digest
   and import binding. Reject unavailable dependencies, cycles and ambiguous slots.
3. Deterministically lower that closure to the existing F-closed syntax. Bind
   any application request to the resulting exact full type/body, not merely the
   module ID or advertised signature. Native or certified checking accepts only
   this lowered object using the unchanged relation.
4. Retain the small named source descriptors for subsequent reuse. A lowered
   object is an operation output/cache with an exact mapping, not an authority
   to insert new trusted kernel constants. Imported transparent bodies remain
   required for demanded conversion. Opaque theorem dependencies must cross the
   existing certified-interface boundary, not become free axioms.

Conditional soundness: if expansion E is total on accepted descriptors and
all symbolic references resolve to their exact canonical source; if the caller's
claimed statement is exactly E's output; and if the unchanged checker accepts
that output under policy P, then the claimed lowered statement has precisely
the unchanged checker's warrant. An expansion bug may misimplement a requested
abbreviation even if its output is a true theorem, so the module-to-output binding
is a distinct acceptance/API correctness obligation, not dispensable because
the kernel accepted something. No human intention is needed to state this rule.

For the existing recurrence D(k+1)=composition(Dk,Dk), memoized DAG expansion
has Θ(k) semantic rows per final lowered body, while keeping all independently
flattened D0..Dn has Θ(n²) aggregate logical rows. Constant-size named source
steps plus dependency edges have Θ(n) rows before explicit encoding overhead.
This storage-layer scheme can realize that representational saving. It cannot
claim O(1) final expansion/checking/proving, suppression of demanded computation,
or a new certificate for a kernel environment extension. Exact physical-byte
savings need actual format accounting; hashing, indexes and custody are charged.

This is not a cosmetic alias layer if another agent can acquire and extend a
module without authoring or transferring an independently flattened copy at
every contribution, and the public API hides no trusted manual promotion.
If the protocol merely stores names beside the same repeated full capsules,
it has not closed the identified representation gap.

ill-typed or false contribution rejected by the actual checker. Pure parser tests
alone do not establish the native mathematical seam. Existing tests can cover

The semigroup identity and strict-loop multiplication counts in the new
`GROWTH.md` section are mathematically sound: associativity suffices, positive
powers do not require a unit, and `2^L-1-L` is positive exactly for natural
`L>=2`. The full-cost crossover algebra and its explicitly hypothetical L=10,
R>=11 example are correct. Polynomial overhead yields an eventual crossover
only in the stated unbounded model, not automatically within this implementation.

Distinguish three conclusions. First, an actually checked D2 and its acquired
law establish an available warranted method. Second, the persistent named
representation gives conditional storage/transfer savings against separately
retained/transmitted flattened prefixes, and can increase storage-limited
capacity for those same reusable endpoints. Third, executable computational
acceleration requires a conformant evaluator and a supported instance whose
whole-route bounds satisfy the inequality. The third conclusion does not follow
from the first two. Its evaluator/cost correspondence is an explicit unsupplied
premise, not something native type checking secretly provides.

A general evaluator can legitimately remain outside a mathematical commons;
it is not a newly invented release requirement for distributing reusable checked
methods. It *is* required before claiming this installed software realizes that
computational speedup. Likewise, option-capability monotonicity is not causal
discovery growth: preauthored fixture/program advice belongs to the declared
endowment and its production cost is not zero by default.

If the selected reciprocal module loop, exact acquired-law application, genuine
wrong-import-signature refusal and exact package pass, they will establish real
central infrastructure advancement rather than merely renamed old checkpoints.
They do not by themselves establish a positive full-cost research-growth rate,
universal mathematical-language support or all huge-network service premises.
Keep those broad goals and the present support envelope distinct. Do not add
