# Fresh-user deployment: finish the executable handoff, not another math backend

2026-10-25. Bounded source-only review by current_research_path. No product import,
database access, experiment, Git mutation, literature review or manuscript work.
This is a concrete recommendation, not a new implementation/runtime selection.

## Decision

**No new missing mathematical-command edge was found in the ordinary route.**
The highest-payoff deployment change found in this short review is an
operator-complete starter kit: exact configurations and report-to-next-input
recipes for the already implemented commands, tied to the selected package.
Today a new user can build the software, but must reverse-engineer implementation
schemas to start its ordinary reciprocal workflow. This is a handoff/usability
obstruction, not a demonstrated checker bug or an impossibility of using the API.

Do not replace it with another theoretical guide, discovery wrapper, concept
generator or native build. The kit should be a runnable configuration example,
with small contract checks and explicit user choices. Keep its initial scope on
the current supported Windows/Lean profile; do not imply cross-platform support.

The saved optional cut-timing comparison should wait. It does not remove this
entry barrier or qualify the ordinary default workflow. Root's independent
discovery/budget investigation may have higher payoff still; it owns that decision.

## Smallest improvement and evidence that changes a decision

Create a **separate versioned starter-kit directory beside the frozen package**,
not unmanifested files inside it or edits to used payloads. Include complete
bounded JSON examples for init limits, contacts, find, preview/inspect, receive,
publish and finite serve; explicitly distinguish state-free/stateful commands.
Give each placeholder a source: an operator decision, a local generated store
identifier, or a named field in an actual public report. Show exact structured
Lean names and hashes without substituting dotted strings or historical IDs.
Include the approved-project producer/intake path for concept/theory extensions;
reuse the already retained source-realization handoff, not a new math example.

Any convenience helper should only prepare fresh local configurations from
explicit choices and actual public outputs. It must not import product code,
open protected stores, invent acceptance, select the newest root, execute source,
silently approve TLS/project code, launch commands or renew grants. A helper is
optional: if complete templates plus clear extraction commands suffice, prefer
those. Avoid inventing a new persistent workflow registry.

First validate the finite example/config set against the exact selected schemas,
including booleans, all required nested limit keys, launcher argv allowlists,
state-free argument exclusion, output restrictions and explicit receive policy.
Check the handoff transformations on retained actual public reports and bundle
manifests. Negative cases should reject a failed/nonaccepted intake as a publish
authority, mismatched exact targets, missing user choices and output overwrites.
These are configuration/identity plumbing tests, not new mathematical tests.

Only if that exposes an unresolved executable boundary should root select one
small public-operation integration at a fresh relocated work directory. Do not
repeat the creative theory episode, native proof acceptance, package build or
certificate campaign merely to make the walkthrough look complete. A full live
reciprocal onboarding test is a later release question, not selected by this note.
