## Obstruction and smallest remedy

The used `ordinary_bounded_transport/assemble.py` identifies one preserved local
sparse assembly by three fixed PROFILE, INSTALLATION and ASSEMBLY receipt hashes.
Those are generated artifact identities, not the stable source interface. A new
supported source build may legitimately have different generated Lean files,
support commitments, paths, timings and receipt identities. Its last overlay
therefore refuses it even when its actual source and native-role layout match.

Merely deleting these three comparisons is insufficient: the original assembler
then checks pin shapes and file sets, not the exact supported source interface.
The smallest successor accepts explicitly owner-selected actual profile/receipt
hashes and independently fixes the interface described below. It copies existing
native bytes unchanged; no native rebuild or new network protocol is needed.

## Invariant versus owner choice

Let P be the actual selected profile, R its immediate sparse assembly receipt,
and I the installation manifest pinned by P. The file-only overlay accepts only
if all these conditions hold:

1. Actual bytes hash to the caller's P and R selections; I's actual bytes hash to
   P's installation identity. R binds those same P and I identities, the exact
   known sparse assembler and overlay, exact counts and six documentation pins.
2. P has the exact owner-profile schema, helper/worker bindings and 117 auxiliary
   roles. The pinned network-kit compatibility map supplies 45 exact noncompiled
   source pins and 72 distinct generated-native role names. Only the latter pins
   may vary with the explicitly approved build.
3. I has exactly the supported 36 roles/files: 19 copied noncompiled files, eight
   generated receiver objects, nine named external runtime files. Derive the 19
   fixed source pins from the already pinned bounded `source-map.json` by taking
   `copies` entries under `installation/` and looking up their `sources` pins.
   This covers foundation, checker, supervisor and Lean source; the 45 auxiliary
   source pins alone do not cover them.
4. The eight receiver object names may receive actual fresh-build pins. The nine
   external runtime pins remain exactly the supported values from the existing
   `ordinary_package/build.py` RUNTIME_PINS, not arbitrary owner substitutions.
   The bounded map's separate 14 `native_runtime_pins` are compiler/linker inputs
   and must not be mistaken for these nine installation runtime files.
5. I has exact supported roles, compiled directories and sorted support groups.
   Its descriptor keeps the fixed semantics, Windows x86_64 platform, snapshot
   format and named-support scope. Recompute each of five support commitments
   from its actual file pins, including roles/compiled_dirs in controller support.
   This allows coherent newly generated identities, not incoherent old support
   hashes. The sparse receipt has no implementation_id field; do not invent a
   requirement that every legitimate sparse receipt contain one.
6. The actual 152-file input census and every included byte match the resulting
   baseline map, within existing bounds. Repeat input/selection checks after the
   copy. Output is a disjoint fresh path; no overwrite; failures are retained;
   PROFILE commits last. External runtime files are not copied or executed here.

The support formula already used by admission is SHA256 of the ASCII domain
`DMKN-ORDINARY-INSTALLED-SUPPORT-V1`, NUL, and canonical UTF-8 JSON of
`{field, files}`; controller support also includes `roles` and `compiled_dirs`.
The implementation identity similarly uses
`DMKN-ORDINARY-IMPLEMENTATION-CLAIM-V1`, NUL, and canonical descriptor JSON.
These formulas check identity coherence, not source/binary correspondence.

## Pure seam and trust limit

Proposed source seam:

```text
validate_base_interface(H, profile, receipt, installation, compatibility,
                        source_map, *, profile_sha256)
    -> {auxiliary, installation_files, documents, implementation_id}
```

It validates parsed data without IO, imports, native execution or state access.
The outer assembler first pins/reads compatibility and source-map inputs and
the selected raw P/R/I bytes. The return installation map contains only the 27
bundled files; the nine external runtime pins remain validated manifest claims.

An owner-approved build remains an explicit premise. A caller can approve a
false receipt or malicious generated binary. These JSON/hash checks are not
remote attestation, certified compilation, a sandbox or mathematical acceptance.
The product's unchanged native checking, support adoption and source-execution
approval still apply. Neither synthetic positive metadata tests nor this overlay
justify executing their placeholder binaries.
