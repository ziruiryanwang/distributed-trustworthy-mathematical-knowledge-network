## Scale and growth: why this is not an escape from the hard questions

Let a local request select providers and finite budget B from a global network
of size N. The existing client does not enumerate all N peers/results; its work
is limited by B, while availability/relevance depend on the selected contacts.
For an honest maintained configured pair, pair-driver visits depend on the pair
intersection, with indexed navigation/proof costs still present. Neither fact
establishes useful global recall, a universally affordable cold import or benefit
from configuring arbitrary pairs. Independent ordinary Lean libraries remain the
baseline for growth, and cold checking can still need bounded dependencies.

These limitations remain important, but they do not identify a unique next
component. For example, new routing cannot repair absent custodians or an unused
corpus, and another index cannot establish whether researchers find the exported
concepts worth extending. Restarting expensive certificate production would again
assume its payoff instead of demonstrating a relevant reader demand. A real
chosen workflow is now more informative than a larger synthetic peer count.

The next handoff need not claim global scale or growth acceleration. It should
test whether the existing primitives fit an actual investigator's ordinary work.
It can reveal a precise representation, interoperability, setup or query-demand
failure that warrants a high-payoff source change. An operator choosing an easier
manual Git/library route is useful comparator evidence, not an invalid outcome.

## Simpler alternative and decision-changing evidence

The simpler present alternative is a supported-profile investigator using the
approved compact source handoff, ordinary Lean/Lake project and direct existing
CLI commands, with explicit contacts/approvals and bounded services. The new
offline kit removes representation friction but is not mandatory. Do not build
an installer, permanent daemon, source-approval broker, universal semantic index
or automatic research scheduler before this alternative fails in a specific way.

Root should resolve the **permission/participant boundary**, not start a test
campaign from this note: what may legally be shared, who will independently try
it, and which ordinary project and environment they are willing to approve.
An independent user on the same machine can expose onboarding/authoring friction,
but cannot establish independently hosted operation. If no external machine or
operator is available, preserve that limit; simulated identities do not supply
the missing evidence. The previously unavailable second machine is not silently
assumed to exist now, and no cloud purchase/provisioning is implied.

Decision-changing evidence would be one reproducible report of the first real
workflow obstruction, with the selected input/profile, actual public failure or
resource boundary, simpler workaround and its cost. Examples of interpretations,
not extra selected tests: failure due to an unsupported ordinary declaration may
justify a representation repair; genuine repeated cold-check cost may justify
a specific reuse investment; inability to find a relevant provider may justify
registration/routing work; absent rights or willing operators does not justify
another protocol. Successful use establishes that finite use, not accelerated
mathematical growth or a full worldwide release.
