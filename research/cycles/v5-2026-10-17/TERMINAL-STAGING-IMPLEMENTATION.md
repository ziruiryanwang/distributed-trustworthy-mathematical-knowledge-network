## Ordering repaired, acceptance unchanged

The former B path admitted FIRST before retrieving further semantic demands.
An expensive receipt check could consume the short-lived contact before those
later required dials. B now follows:

```text
unchanged unknown-ID discovery
  -> offered FIRST staged token
  -> bounded structural demands, BASE token, committed groups and bodies
  -> structural READY for all unconsumed tokens
  -> actual FIRST admission + evaluator target check
  -> actual BASE admission + exact target/shared receipt check
  -> one unchanged live import
  -> release ordinary source, author, inspect and publish
```

No semantic/network acquisition occurs after that first A verification. The
original reader stays open until normal client closure; contact age, requests,
reply ceilings, controller/worker allowances and deadlines are unchanged. Every
pre-admission dial still applies the old authenticated contact rules. A slow
transfer can still outlive its contact and fail; no refresh/retry is introduced.

The first `admit_staged` receives no evaluator expected J. Only after its actual
warrant exists do the existing checks compare FIRST/J/H2/receipt identity and
name. BASE's later admission takes the known exact BASE J and requires the same
actual header and receipt hash/length as FIRST. Its membership is checked even
when the existing live A receipt cache avoids a second B verification.

The final `import_context` receives both actual warrants, their actual whole Js,
and all acquired groups/bodies. It must itself return READY with no demands and
zero ancestral theorem-proof import bytes. There is no `extend_context` repair
or late network fallback if preview and actual import disagree. Only this real
import's context reaches `author`.

## Structural resolver contract

`demand_context(client, origin, original, entry, record)` receives only the actual
returned candidate/description/offer and an audit sink. It receives no assets,
expected FIRST/SECOND/BASE journal, source, live warrant or admission limits.
Its permitted modules are the actually discovered ModuleID plus the already
public BASE vocabulary; they must be distinct.

The resolver maintains four bounded maps:

- Same-client staged tokens and inert selected records by ModuleID.
- Returned candidates by exact `(module, name)`.
- Canonical groups by `(module, group_index)`.
- Canonical body expressions by `(module, universes, digest)`.

Each stage is described exactly once. The resulting inert record must match the
actual candidate's provider, locator, opening and descriptor, the offered packet
hash/size, and the whole-J module/summary. It is expressly not verification.
Every preview receives the **full accumulated arrays** reconstructed from these
maps; the generic pure planner carries no hidden incremental state.

`NeedModuleEvidence` stages BASE at most once, including multiple differently
named demands for it in one batch. Groups cannot enter an evidenced preview
before their module has a token. `NeedDeclaration` resolves only a new demanded
name/group. `NeedBody` verifies the acquired response's module/name/arity/digest
and recomputed body commitment. Shared body demands in one batch fetch once;
demands already satisfied before that batch refuse. Canonical group conflicts,
duplicate demand records and modules outside this fixed workload refuse.

All non-READY rounds must strictly increase the number of staged modules,
groups or bodies. Unchanged ceilings are MAX_STEPS32, MAX_NAMES64, MAX_GROUPS12,
MAX_BODIES11 and2MiB per semantic reply. Initial state has one module/group;
at most25 such objects can exist. Thus at most23 productive rounds and24
previews can reach READY, without assuming a measured round count. No whole
BASE inventory or theorem proof body is preloaded into the consumer. In
particular, the strategy does not fetch unused `binary_congr` to reconstruct a
historical witness representation.

Metadata preview does not re-read whole receipt packets each round and does
not promise present packet availability. Actual staging/description and the
facade's pre/post-admission readbacks retain exact held-evidence checks. Missing
or changed packet bytes after preview must therefore refuse real admission;
an inert READY status cannot issue a warrant.
