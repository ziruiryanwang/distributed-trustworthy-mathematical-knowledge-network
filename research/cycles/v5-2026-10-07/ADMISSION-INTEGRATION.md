## Why this is central

Current acquisition/custody proves structural commitments, not mathematics.
The actual compiled host already has a full `receive` command, but no public
library component owns its process invocation or turns its same-call result
into an authenticated interface. Connecting these boundaries is required for
actual safe agent reuse; another experiment-only success file is insufficient.

## Selected first implementation

An owner constructs a `ReceiptVerifier` from a local deployment configuration:
an independently adopted verifier image/foundation/policy, the exact compiled
host and runtime file pins, and an adopted existing supervisor installation.
This configuration is never supplied by a remote index or receipt. Use the
retained supervisor by exact installation manifest pin, without editing or
retesting its unchanged Job implementation. The first runtime adapter supports
Windows; it is not a claim of portable hostile-input isolation.

The public operation accepts opaque receipt bytes, an expected mathematical
summary and a fresh owner-controlled operation directory. It snapshots those
bytes, invokes only `receive ADOPTED_IMAGE RECEIPT EXPECTED_MODULE`, requires
clean supervised closure, rechecks receipt/runtime pins, and parses only that
call's bounded stdout. It checks every acceptance field against the exact
216-byte journal, independently recomputes ModuleID from the expected summary,
and checks adopted image/foundation/policy plus exact receipt hash/length.
No arbitrary command, supplied success JSON, native diagnostic, assertion of
parent verification or persisted acceptance flag is an admission input.

A successful operation creates a process-local handle registered in this
verifier instance. Opening a group requires that exact live handle and checks
the group against its authenticated summary. Revoking/closing the instance
invalidates all its handles. A different receipt witness for the same ModuleID
may be checked independently; neither mathematical identity nor custody grants
it authority. No persisted handle can be restored; cold clients reverify.

The Python process and its owner-controlled installation/state directories are
trusted. Private constructors and identity registration prevent accidental
forgery and serialized-token replay; they do not sandbox malicious code already
executing in the same interpreter. Windows Job supervision controls resource
use/closure, not filesystem, network or hostile-parser security isolation.
OS/runtime closure, an independently justified adopted profile, and release
isolation remain separate obligations. Refuse rather than inventing these.

## Budget and failure semantics

One verifier instance has explicit operation-count, submitted-byte, total
reserved CPU and wall limits. Each attempted invocation consumes its entire
requested CPU reservation, even on failed receipt verification; never refund
using an untrusted child's claimed work. Submission and directory preparation
are bounded. Actual worker/controller costs remain in retained process evidence
once an operation directory and child call exist. Earlier preflight failures
may leave only charged in-memory counters, not a retained operation record.
No automatic retry, certificate-ancestry crawl or hidden proof production.
The deadline covers preflight, child work and final evidence I/O. Failed child
operations retain evidence but mint no handle. Unexpected exceptions are refusals; partial outputs are not
promoted. Positive evidence is still pending an actual v5 receipt.
