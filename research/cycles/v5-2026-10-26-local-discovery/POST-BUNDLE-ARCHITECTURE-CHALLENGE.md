# Post-bundle architecture challenge: make the investigator boundary coherent

2026-10-26. `service_lifecycle`; independent source/theory assessment requested
by root. No product imports, tests, build, state opening, native execution,
networking or Git mutation. Root owns any later selection. This does not edit
the selected/frozen workflow-bundle source. All work is local and unpublished.

## Decision

**No new acceptance architecture defect is established. Do not reopen mandatory
certificates, persistent checking sessions, proof-erasing projections or theorem
identity migration.** The current implementation supports a credible, narrower
practical operating model: independent investigators do ordinary Lean work, use
selected persistent local warrants, and exchange/check completed contributions
at useful milestones. It is not an economical per-tactic remote proof service
or a demonstrated solution for repeated arbitrary cold-library onboarding.

The highest-payoff remaining local implementation/adoption decision exposed here
is the **formal source-to-discovery boundary**. Existing elaboration and binding
components exist, but a new generic source-query wrapper must not hide that a
query's source environment and its selected receiving context can assign
different meanings to the same names. Coordinate the operational recipe with
`cold_start_workflow`; do not build a second matcher or re-investigate that
agent's command wiring.

Root should select a small, explicit query contract before any wrapper:

1. First expose the existing supported Init/basis-only source route and its
   actual bounded invocation, using source files rather than hand-authored ASTs.
   The retained public query outcome already establishes that native capability.
2. For richer source queries, select either a coherent already-approved native
   project with explicitly asserted interpretation correspondence, or an actual
   owner-derived reconstructed interface. Merely resolving names is insufficient
   to establish the former. Prefer already available module/construction paths
   before proposing a new one.
3. Unknown vocabulary and unsupported realization must remain explicit outcomes.
   Do not automatically admit drafts, execute a foreign project, invent portable
   IDs or claim that arbitrary semantic search has thereby been implemented.

The independent operational trace now identifies that exact obstruction: the
current public launcher does not dispatch this native extraction, while the
standalone author worker supplies no equivalent resource envelope. Thus a
**fixed bounded query-extraction companion** is a justified next candidate if
the package is to supply the envelope itself. This is smaller than a generic
source-query/automatic-import facility. Root must select its exact scope; no new
code is selected by this note.

## 1. A practical audience, not a universal cost claim

Treat a model invocation, investigator, verification owner and network provider
as distinct roles. A new model conversation need not initialize a new owner or
recheck all the mathematics that the same protected local owner already accepts.
Conversely, two independently trusting owners cannot share acceptance merely
because their model instances cooperate. The current protected catalog, explicit
parent selection and ordinary custody already support this distinction; no new
identity/governance protocol is required.

The strongest presently justified user pattern is:

1. Retain a compatible, deliberately bounded mathematical workspace under one
   local verification owner; use ordinary approved Lean facilities for exploration.
2. Search/inspect at a selected reusable-method or connection boundary, rather
   than on every proof step. Reuse a suitable locally warranted target directly.
3. Deliberately pay for an unfamiliar useful target's bounded missing closure,
   or reject it under `selected-unit-only`. Neither option means all remote
   mathematics must be downloaded.
4. Build new definitions and theories locally, then admit/publish chosen finished
   outputs in supported batches. Do not require network consensus for exploration.
5. Reuse the protected local context across further investigators/processes while
   respecting serialization and storage-integrity assumptions.

This audience includes compatible Lean investigators and locally operated agents
that retain state and exchange substantive work. The current evidence does not
justify advertising a zero-setup service to arbitrarily many disposable,
independently trusting clients, each expecting immediate use of arbitrary theories.
Keeping that distinction explicit is product design, not weakening mathematical
acceptance or introducing human intention into it.

## 2. Counterexample to a stronger growth interpretation

Let a useful library interface require missing ordinary evidence costing C to
acquire/check under the chosen strict trust policy. Let a use cost a after
adoption, and let m investigations each avoid d units of local discovery effort.
Ignore nothing silently: write S for all service, search, failed-attempt,
maintenance, adaptation and restoration costs not already included.

With one persistent protected owner, a sufficient benefit condition is

`m*d > C + m*a + S`.

With m separate fresh owners each performing one use, the same interface can
instead require

`m*d > m*C + m*a + S`.

Choose positive C,a,d with `a < d < C+a`. Repeated use within a stable domain can
eventually amortize adoption (if S grows slowly enough), while fresh one-off use
never does in this model. Increasing the number of network agents alone does
not improve the latter inequality. The model is not a measurement, and the
optimized local-library comparator receives the same caching/batching abilities.

This counterexample identifies the necessary **adoption/reuse pattern**, not a
cryptographic lower bound. A short independent proof, a previously justified
common base or a genuinely economical optional certificate can change C. None
is automatically available, and a peer's Boolean success claim cannot replace C
without changing the trust premises.

The practical correction is to make retained local workspaces and batch-level
exchange the ordinary usage model, and expose cold costs/refusals truthfully.
Do not prescribe one giant everlasting context: the selected-context term and
cross-context re-admission remain charged. Existing smaller eligible parents,
bounded batches and independently checked re-admission already provide the
available strategy; there is no proof that every evolving theory fits it cheaply.

## 4. A genuinely consequential source-query counterexample

The current `ordinary_query_context/query.py:resolve_context_bindings` enumerates
names in the extracted native expression and obtains their portable IDs from
the selected local context. It does not compare the source project's definitions
with those represented by that context. Its README correctly describes the
result as the receiver's interpretation, not project equivalence.

Consider two individually well-typed Lean environments, E and K, containing the
same public name `Example.step : Nat -> Nat`:

```lean
-- Environment E
def Example.step (n : Nat) := n

-- Separate environment K
def Example.step (_ : Nat) := 0
```

In E, the source query is `forall n : Nat, Example.step n = n`. Its serialized
type refers to the name `Example.step`, not its definition body. Mapping that
name to K's exact accepted ExportID asks a different formal question: it is
false at n=1. Identical name/type syntax does not establish that the source
question and bound query have equal meaning. No malicious participant is needed.

This is **not an acceptance soundness bug**: query preparation makes no theorem
claim, and any later returned proof is checked against K. It is a practical
formal-interoperability issue if a convenience command claims to search the goal
written in arbitrary local source. It is not about recovering human intention:
the two formal environments themselves are different.

Therefore the documentation-only statement “run the source extractor, then bind
its names” is adequate only when it explicitly selects the receiver interpretation
or establishes the required environment correspondence by an existing route.
Adding an unqualified `--source` option cannot itself establish that condition.

## 5. Smallest actionable correction and stop rule

Coordinate with `cold_start_workflow`, which owns the exact public invocation.
The present native command `ordinary_formal_query/OwnerQueryCommand.lean` already
elaborates/checks a type, closes relevant section variables, refuses sorry and
writes a bounded AST without proof export or environment insertion. Its source
is executable local Lean support and requires an approved bounded launcher;
it is not a hostile-source parser or a network operation.

**First local decision:** expose the existing source-query recipe under an
operator-supplied equivalent execution envelope, or select a fixed bounded
query-extraction companion that supplies the missing envelope. The coordinated
public-source trace by `cold_start_workflow` finds no suitable current public
command: `run.py query` does not launch the native source extractor, the standalone
author worker has no resource caps, and the older stage CLI expects incompatible
source-layout roles. Do not call these existing public composition when they are
not. The existing supervisor/Job library and selected query helper can be reused;
the required new seam is approved fixed-operation glue, not a new elaborator.

Use Init/basis vocabulary and the actual current helper/runtime paths first.
Require all extracted references to have the selected fixed-basis interpretation;
do not silently substitute nonbasis same-name context symbols. Do not require
the nonexistent pre-existing user project. Preserve the proof-free command and
inert downstream query preparation, and state that ordinary exact type lookup
is only one candidate-generation mode. A native rebuild is not needed simply to
expose already-built support. This bounded source extraction is approval of local
source execution, not a new mathematical admission or a sandbox.

For queries involving a received definition, prefer an existing selected
owner-generated module or reconstructed interface so the elaboration environment
is known by construction. If its required frontier does not fit or a necessary
public invocation is absent, identify that precise obstruction before choosing
a narrowly scoped owner-derived query frontend. Reusing the contribution
construction machinery could be a candidate, but this checkpoint does not claim
such a query frontend exists or select its implementation.

For independent unaccepted local draft concepts, generic portable exact IDs may
not yet exist. Permit ordinary local-library or advisory search without turning
those hints into accepted mathematics. Do not force export/admission of every
draft merely to ask a question. The existing growth investigations already
separate unmaterialized hints from exact accepted exports.

**Stop after the supported public route is coherent, or at its first exact
semantic/operational obstruction.** Do not append a matcher, ranking scheme,
certificate, context optimizer or fresh growth experiment to this task. The
missing scientific fact remains how often the software saves investigators
worthwhile work; new convenience wiring cannot prove that fact. The architecture
is useful in principle under the stated operating pattern, and the next local
decision should improve that pattern rather than manufacture another scale claim.
