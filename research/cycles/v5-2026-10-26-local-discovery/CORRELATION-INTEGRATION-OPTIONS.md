## Recommendation

If the independent raw-instance argument and investigator-level benefit test
survive, use **one new ordinary feature with publication-side expansion**. Do
not change the wire protocol, store, candidate matcher, fair scheduler or search
session to implement a many-query OR. The proposed first profile now has two
fixed fn/arg paths, not three:

```text
[arg, fn, arg]
[fn, arg, fn, arg]
```

For the ordinary curried equality expression `op x y = op y x`, these observe
the first argument on the right and the first argument on the left: `y,x`.
For `op x y = op x y`, they observe `x,x`. The profile is meaningful on other
raw syntax too; it is not a declaration that every selected expression is an
equality, well typed, or an applicable theorem.

There are just two endpoint equality partitions, DISTINCT and EQUAL. A source
whose two terminal observations are the same stripped telescope parameter
emits only the EQUAL-goal key. Every other source emits both goal keys. The
query computes its one exact endpoint equality partition and emits one feature
spec. Missing endpoints count as distinct singletons. A source parameter met
before the path ends supplies no correlation constraint.

This **transpose** changes the meaning of keys from the earlier exact-source-
partition proposal. It needs its own pinned profile/domain and namespace; do
not reuse old fingerprint keys. The theory agent independently reported that
the transpose preserves conditional raw-instance coverage. Their completed
theory and challenge notes, not this integration note, must be adopted by root
before implementation.

Costs are at most two extra source postings and one ordinary finite search.
There is no token vector and no new OR budget. The tradeoff is deliberate:
every unconstrained source survives both partitions, and an EQUAL query cannot
reject any source on correlation alone. This is a targeted repeated-variable
filter, not general unification or a broadly selective mathematical search.

## Minimal end-to-end successor contract

The following is a design option for root selection, not edit authorization.

1. **Adapter successor, existing logical role.** Keep
   `support/discovery/ordinary_export_adapter.py` as the public implementation
   role. Add fixed two-path/profile constants, source correlation extraction,
   one feature tag with an exact bounded value, and a public query-spec function.
   Keep all inherited features and their validation. Bump `FEATURE_REVISION` and
   commit the new profile in `namespace_for`; exact mathematical semantic IDs,
   ExportIDs, preview bytes and evidence bytes do not change. The selected
   two-path list is not an uncontrolled caller-supplied index dimension.

2. **Query helper from existing input.** The adapter can consume
   `formal_query.read_query` and its already validated ordinary DAG/bindings.
   Compare endpoint subterms by bottom-up exact structural interning, never by
   expanded trees. Retain binder-independent canonical equality conventions;
   false equality from hash collisions must not be silently treated as a proven
   syntactic relation. All endpoints share the same ambient depth because paths
   do not enter binder bodies. Subterms themselves may contain binders.

3. **Explicit wrapper boundary.** Add one optional numeric query-CLI selector,
   such as `--conclusion-context-binders N`; absence preserves existing exact
   search. Presence selects the fixed correlation mode and strips exactly N
   leading query foralls. This is not the existing `--context-root`, which
   selects portable symbol bindings, not the number of ambient binders. Do not
   infer N by stripping every query forall. The query remains a closed raw
   expression; no native exporter or Lean command needs rebuilding.

4. **Honest result labels.** Both `run_manual` and `run_context` need the same
   selection branch. Preserve `QUERY.json` as the bounded inert input syntax and
   `SPECS.json` as a one-element ordinary conjunction. Report the actual search
   profile and wrapper count; replace the exact-type-only claim in this mode.
   A successful preparation is neither applicability nor mathematics. No new
   required query input schema is necessary.

5. **Existing launcher and kit.** Admit the optional numeric flag in a successor
   of the actual contact-overlay launcher. The existing kit does not prepare
   query CLI commands, so do not add a new kit query action merely for symmetry.
   It does prepare find/directory requests; its `query_specs` must accept the
   exact new feature form. A successor selector/map pins that helper and the new
   package's noncompiled payloads. Contacts, providers, request schemas,
   candidate mode, leases and mathematical intake remain unchanged.

6. **Publish, find, acquire, check.** Public publication deterministically derives
   the extra postings from accepted target previews. The query's one spec enters
   unchanged `find`; matches remain preview metadata. Existing `preview` binds
   the selected exact preview; `receive` acquires evidence and invokes ordinary
   admission; ordinary Lean later applies the theorem and discharges remaining
   obligations. No inference or acceptance rule changes. Existing kind/symbol/
   head conjuncts may be explicitly added, but raw-instance coverage then also
   requires that the source possesses them. Do not automatically conjoin every
   symbol occurring in a specialized goal.

7. **Fresh namespace, not in-place migration.** Construct a fresh bounded index
   and republish only owner-selected targets from retained accepted custody.
   Do not rewrite old records or snapshots. The store compares its exact saved
   config and rejects old namespaces. New and old packages can coexist; a single
   current provider process serves one selected index, not an invented plural-
   namespace service. Existing theorem evidence/portable identities remain
   reusable, subject to the already documented local implementation context
   rules. Exact old index keys do not become new ones by relabeling a file.

## Feature headroom is a real design decision

`discovery/formal_features.py:22` caps records at 128 features and 16,384 bytes.
The current adapter fails before adding feature 129. Adding two postings can
therefore make some formerly publishable types fail. Do not silently increase
this constant or claim the new feature is free.

The least disruptive option is deterministic **all-or-none eligibility** for the
correlation group after inherited extraction: emit the whole one-or-two-key group
only when it fits the existing feature/record limits; otherwise retain ordinary
features and report/describe the omission explicitly. The recall theorem must
include this eligibility premise. Never truncate a group's key family, because
that creates profile-dependent false negatives. If public omission reporting
requires a tiny publish-report change, root must select it explicitly; its cost
is more defensible than breaking existing ordinary publication at the cap. A
distinct narrower selected profile that refuses overflow is another honest but
less usable option. The source selection must settle this before tests.

## Why not a bounded OR planner here?

The full token-plus-correlation design had up to 15 alternative keys for three
paths. Current `find` permits one immutable query and prepays its whole network
slice. Calling it repeatedly with separate grants does not yield one original
aggregate allowance. `OrdinaryBudget` only centralizes requests/reply bytes;
provider slots, snapshots, pages, examined candidates and retained results also
need aggregate handling across sessions. Proper multi-query integration would
need a local coordinator with these dimensions and a common deadline, explicit
early stops, duplicate control and settled failures. It might avoid wire changes,
but it is not one helper call, and it adds a new public preparation contract.

The two-path transpose avoids this work entirely. Its query is an ordinary
single exact-feature conjunction; existing scheduling/accounting semantics apply
without pretending that alternative queries are free. The original OR design is
not forbidden forever, but needs a later workload whose extra selectivity pays
for those costs. Neither a new distributed unifier nor a discrimination tree is
justified by this integration gap.

## Cost boundary and rejection conditions

Let I be incremental source observation, posting and migration cost; H ongoing
holding/maintenance; Q extra query extraction cost; and S saved candidate/provider/
local application work against an equally optimized existing workflow. Adoption
needs a plausible nonempty repeated-use region `sum(S - Q) > I + H`. Publication
has at most two extra postings per eligible theorem, but all inherited records
must be rebuilt if an entire namespace is migrated. Provider ownership, chosen
corpus extent and future workload matter; node-count growth alone is not evidence.

The filter still misses source/goal relations requiring reduction, vocabulary
transport or a different supported profile, and does not solve malicious omission,
global coverage, premises or proof production. Unknown-ID candidate discovery is
the only changed capability. Reject this implementation if generalized exact
queries or already trusted Lean/Loogle search economically serve the intended
workflow, if unconstrained sources dominate the relevant buckets, if EQUAL queries
dominate, or if the reindex/maintenance cost defeats the plausible reuse benefit.
Do not add three paths, extra token families, new transport or a broad benchmark
unless a consequential further gap pays for it.

This note identifies a small coherent software change, not evidence that its
remaining selection gates pass or that full v5 is complete.
