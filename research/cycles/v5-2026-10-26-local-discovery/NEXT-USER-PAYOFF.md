## One decision

**After the current exact-module/query seam, consolidate its supported public
workflow before selecting another mathematical or growth mechanism.** The next
concrete obstruction is that the authoritative distributed startup route cannot
select the new package through its prescribed preparer. This is a compatibility
and operator-handoff problem, not evidence that the mathematics architecture
needs another layer.

The scope should be one current investigator entrypoint with an exact package
selection and a complete public-command path. Initially make it documentation
only: use existing direct public commands where a convenience preparer rejects
the selected package. Change a preparer only if the source trace below exposes
an input that cannot reasonably be supplied through the existing interface.
Do not repack the frozen archive, rebuild helpers, or start another concept
episode merely because two newer companions now exist.

## The precise incompatibility

The current source handoff is coherent for its preserved base: 154 payloads,
one root guide and a four-overlay build; see its
[adoption](../../../software/v5/ordinary_workflow_bundle/ADOPTION.md).
Its root guide prescribes `ordinary_bounded_transport/prepare_selected.py`
as the final selector, including for fresh initialization.

That selector's `known_layout` checks equality of **all 45 noncompiled role
records**, not merely the peer configuration schema. Its exact test is
`all(files.get(name) == pin for name, pin in sources.items())`; failure is
`SELECT_UNKNOWN_INTERFACE`
([source](../../../software/v5/ordinary_bounded_transport/prepare_selected.py),
lines 49–69). The exact-module successor changes three of those payloads under
its explicit [overlay](../../../software/v5/ordinary_exact_module/OVERLAY.json).
Therefore feeding the new package to the old selector is not a supported
composition even if the selected action never imports the changed modules.
Do not describe the old preparer as compatible or tell users to edit its pins.

The no-project reuse recipe already uses direct bounded `owner contribute` and
`peer publish`, with full report-to-input mappings. The public launcher and the
configuration schemas are therefore the simpler integration substrate. The
received-query owner should identify that seam's exact commands; this note does
not rederive or extend that assignment.

## Cheap falsifiable completion test

Before any new runtime campaign, trace one hypothetical ordinary investigator
using **only the chosen current entrypoint and its operational references**:

1. Start with approved runtime/source/package inputs, no existing project and
   no protected owner. Every required file must be either supplied explicitly,
   authored as an ordinary input, or produced by a named preceding public call.
2. Trace receive or offline intake, exact vocabulary realization, the separately
   established proof-free query path, contribution, explicit publication and
   subsequent use. A later investigator chooses the law; the guide supplies no
   proof, fixed theorem target or compulsory research agenda.
3. For each transition record the producing report field, receiving flag/schema,
   exact package/semantic identity, approval boundary and terminal-success test.
   Stop at the first mismatch. No experiment path, private root, mutable database
   edit, copied historical PROFILE, or bypass of a pin is an operational input.
4. Verify that all named executable inputs and helper imports belong to the
   selected source handoff/explicit adjuncts. A historical evidence link may
   remain outside it; a required executable may not.

This is a finite source trace, not a new general audit hierarchy. Existing
native, mathematical, service and archive results remain evidence for unchanged
components. If the trace closes through direct public commands, ship that small
current composition guide and stop this task. If it exposes a real unsupported
transition, name that exact transition and select only its minimal repair with
changed-boundary tests. A new archive or complete workflow run needs its own
decision-changing reason; this note does not select either.

## Why this beats another mechanism now

For the supported persistent-local-investigator pattern, the product already
has the logical operations for concept formation, checked exchange and continued
work. The remaining concrete cost here is forcing users to recover a compatible
route from several historical packages and reports. One truthful composition
reduces that cost without changing trust, mathematical semantics or research
policy. A new matcher, certificate, scheduler, cap increase or frontend metadata
system does not repair the selector mismatch.

This decision does not establish worldwide deployment, beneficial sustained
growth, hostile-source isolation, unrestricted Lean compatibility or independent
hosting. License/publication and real external use remain deliberately separate.
It does establish a narrow next product question with an inexpensive negative
answer if the existing APIs do not compose, rather than selecting more work
merely because it is implementable.

## Smallest user-facing successor after the pending composition test

Source-only decision; **not implementation or execution authority**. Select a
new one-file source-side companion, provisionally
`ordinary_anchor_query/query.py`, as a narrow successor of the frozen
`ordinary_basis_query/query.py`. Preserve the basis companion and all package
bytes. Reuse its fixed-operation parent/worker supervision, bounded inputs,
generated query source, pinning, output census and terminal-publication pattern.
Add only local owner/context/AnchorID selection and realized-vocabulary binding;
keep existing native AST, query/spec, mathematical identity and wire formats.
One README and changed-boundary controls belong to a later implementation
selection, not a new registry, builder, elaborator, prover or acceptance policy.

**Prefer existing anchor APIs under one owner lock over warm-export orchestration.**
Warm `export-module` already verifies a protected registration and returns module
name/directories/selected targets, but not the complete realized export census.
Its targets omit unselected dependency exports; using every context binding would
permit unrelated same-named source interpretations. Reopening/parsing private
record files outside the Store would duplicate its trust logic. An added public
census endpoint could solve that, but changes more product surface than needed.
The existing `Store.load` returns validated `AnchorView.plan_raw`/frontier with
all chain exports while checking current context agreement and artifact hashes.
Use that public-in-code operation internally, not private database editing.
