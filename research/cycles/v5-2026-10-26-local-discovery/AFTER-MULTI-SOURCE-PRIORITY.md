2026-10-26. Source-only recommendation by inert_rehost_relation. No runtime,
package assembly, publication or new source selection is authorized by this note.
The multi-source implementation is not yet adopted; complete its existing review
and focused controls before applying this recommendation. Full v5 remains open.

## Decision

The next highest-payoff capability is **publicly operable integration of the
already implemented investigator and optional availability roles**. Select one
coherent source handoff and request-preparation route, with an explicitly selected
multi-source package overlay. Do not add another generator, retrieval mechanism,
certificate scheme or concept-development demonstration at this boundary.

This is not a claim that packaging is the deepest remaining mathematical problem.
It is the nearest concrete obstruction to using the newly implemented capability:
an operator following the current supported route cannot request it successfully.
The ordinary Lean route already supports agent-chosen definitions, consequences,
module reuse and return. No missing concept representation is established here.

## Alternatives and whole-cost payoff

1. **Ordinary Lean/Git/Lake or a complete static bundle:** retain as the cheaper
   route when a known project or complete holder is sufficient. This commons
   must not claim an advantage for work ordinary library reuse already solves.
2. **Current investigator plus manually selected companions/configuration:**
   adequate for an expert maintainer, but leaves the new receive policy outside
   the supported preparer and requires knowledge of repository history.
3. **One explicit overlay plus matching public selector/preparer and role guide:**
   removes the demonstrated boundary, reuses existing checking/transport work,
   and leaves the native implementation untouched. Recommended.
4. **Another search, concept-generation, replication or certification subsystem:**
   no remaining source-supported necessity is demonstrated for this immediate
   workflow. Its construction would not repair items 1-3 in the table.

Let C_integrate include implementation, review, focused validation and future
maintenance; let C_manual,i and C_supported,i be complete operator preparation
and error-recovery costs for the same successful workflow. This integration has
a positive reuse region when

    sum_i (C_manual,i - C_supported,i) > C_integrate.

This is a conditional cost criterion, not a measured saving or theorem-discovery
speedup. The finite source/configuration mismatch already justifies repair for
supported operability; no speculative scale test is required to demonstrate it.
Do not claim network benefits for local mathematical checking that is unchanged.

## Smallest implementation boundary

- Preserve all existing archives, sources, reports and catalogs. Produce a new
  selected source revision, actual PROFILE and receipt; never relax the old
  selector's exact pins or edit a frozen helper to accept new input silently.
- Reuse the file-only overlay pattern in `ordinary_exact_module/assemble.py`.
  Replace exactly the three selected pure-Python roles. Keep the native roles,
  checking implementation, portable semantics and admission policy unchanged.
- Provide a corresponding explicit selector and offline request preparer that
  accept all three optional receive fields together, validate their bounded
  shape/contact membership, and forward them without changing default requests.
  Avoid introducing a general plugin loader or permissive schema passthrough.
- Make the current method-discovery recipe and adopted mirror02 role discoverable
  from the same current entry point. A storage-only operator must not need Lean
  or a mathematical owner. Keep companions outside the built package; retain
  their actual pinned predecessor source dependencies rather than rebinding them
  silently to changed payloads.
- State clearly that source identity is not supplier authentication, hostile-code
  isolation or mathematical authority. Keep the current supported runtime profile
  and local/unpublished restriction. No independent participant is authorized.

The transport-only update policy already distinguishes a package PROFILE change
from a checking-implementation change: see `software/v5/UPDATE-AND-RECOVERY.md`.
Do not bootstrap new mathematical owners or recheck old mathematics merely to
exercise source-distribution changes when the checking identity is unchanged.
However, the public preparer separately requires PROFILE-exact parent and find
reports (`ordinary_network_kit/prepare.py:209-216,377-405`). Mathematical catalog
compatibility therefore does **not** imply old-report preparer compatibility.
Keep the new preparer for new-profile workflows; document the existing explicit
raw `run.py` peer-receive route for intentionally selected old-profile reports
and roots. Do not rewrite old reports, silently broaden their acceptance or
start a report-migration framework to hide this distinction.

## Minimum decision-changing validation and stop condition

After the existing multi-source controls/review pass, inspect the complete
assembled file map: exactly the selected pure-role differences, unchanged native
and checking identities, new actual PROFILE/receipt, and no unselected files.
Use a small native-free public-boundary suite to establish old-request
compatibility, optional-field forwarding, rejection of partial/invalid policies,
source-map mismatch refusal and fresh-output/source-root independence. Exercise
the resulting configuration through the already tested receiver seam rather than
inventing another mathematical example. Check that the consolidated mirror route
still selects its exact approved source map without Lean.

A fresh extraction may be warranted to test self-containment. A full native
rebuild, repeated bootstrap, repeated concept proof or repeated mirror campaign
is not justified by these pure source/configuration changes. Reuse their retained
evidence with its original scope; do not relabel it as execution of new bytes.

Stop this slice once a recipient can follow one supported source selection to
the intended investigator or storage role, including optional multi-source
receiving, without private repository-history knowledge. Then choose the next
actual obstruction afresh. This closes a public operability gap, not worldwide
availability, hostile-input isolation, broad utility evidence or final v5.
