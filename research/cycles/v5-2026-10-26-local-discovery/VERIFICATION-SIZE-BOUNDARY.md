## Decision

**There is no new high-payoff verification fix established by this audit.** The
ordinary system does not require a node to possess, scan or check the world's
mathematics. It does require the selected local branch, whose contents can include
results irrelevant to the immediate theorem. Smaller explicit eligible parents,
bounded batch admission, and selected re-admission already address that case
without a new checker or trust mode. They do not make cold acquisition free.

The consequential unresolved boundary is successful *cold* reuse when its missing
proof closure exceeds an acceptable consumer budget. Strict receive deliberately
refuses that work; it does not solve its acceptance. No new concrete workload
showing that existing alternatives fail economically was supplied or discovered
here. Do not spend another experiment demonstrating the same source loops.

## What is local, and what is not

| Operation | Work the current source requires | Work it does not require |
|---|---|---|
| Exact custody retrieval | Indexed selected-object/export lookup; bounded complete selected bytes and validation | Decode every stored proof or enumerate the network |
| `context(parent)` | All selected parent-chain records, their bindings and protected snapshot integrity | Other mathematical branches' snapshots or the world's theorem history |
| New ordinary admission | That context; the complete selected new units; native parent restoration; kernel checking of new declarations | Kernel replay of old accepted derivations |
| Already-admitted exact whole-unit reuse | Context validation, evidence validation/staging/readback | A fresh native admission worker |
| Owner authoring | Context lookup plus selected semantic/materialization frontier | Traversal of singleton theorem proof-only ancestry solely to construct its signature |
| Anchored local module export | Current-context eligibility, registered anchor frontier/artifacts, unanchored selected delta | Fetch/decode old anchored proof evidence merely to re-export it |

The last two rows are not new findings. [REUSE-FRONTIER](REUSE-FRONTIER.md)
already distinguishes the 21-unit authoring frontier from its 36-unit full proof
closure and 106-unit bundle. Neither figure makes `context(parent)` sparse.
An ordinary authoring signature is not a transferable acceptance certificate.

## Strongest supported locality statement

Let N be the world's mathematics, h the selected local chain length, b its
snapshot bytes, n its names, s the selected input bytes, m its units, and e its
import edges. Let r be local catalog roots and o its retained operation records.
Fix the supported installation, actual selected parent and inputs, explicit
contacts, limits, and storage/OS trust premises.

For the default native-bootstrap mathematical admission path, no source loop
ranges over N. Its data
dependencies are the selected parent, selected evidence, fixed installed support,
and bounded local bookkeeping. Adding unrelated remote mathematics introduces
no mandatory proof-validation step. This is a **dependency/locality argument**,
not a guarantee about network latency, available memory, database cache behavior,
unlimited useful cold imports, or search completeness.

It cannot be strengthened to independence from every local history variable:

- A fresh `context` hashes b bytes and reconstructs n bindings from h records.
  Under ordinary indexed-lookup/hash-table models its bookkeeping is roughly
  `O(b + h log r + n)` with name-byte/record parsing costs charged separately.
  Repeated calls in the same owner process omit repeated artifact hashing, not
  repeated lineage/binding reconstruction. No worst-case constant-time Python
  hashing or filesystem promise is implied.
- Native new-unit admission includes an explicit `Omega(n)` parent-name census,
  plus actual Lean import/deserialization costs. No claim that Lean eagerly
  copies every old proof term is needed to establish this lower bound.
- Preflight adds parsing/identity work in s and import bookkeeping in e; its
  topological heap contributes `O(m log m + e)` under the usual map model.
  Conversion/kernel checking is a separate actual cost, **not** polynomially
  bounded by this graph formula. Resource limits permit refusal, not fast success.
- `portable_catalog.py:238` scans for interrupted operations without a state
  index; `:557-559` aggregates operation reservations. These may touch o records
  even for a small selected branch. This is local bookkeeping, not proof replay.
  Unrelated local additions can also exhaust shared capacity and change success.
- A legacy-import catalog additionally validates its activation's selected root
  when opened (`portable_catalog.py:239-240`), even if a later operation chooses
  an earlier parent. That nondefault path adds the imported activation closure;
  it must not inherit a stronger chosen-parent-only bound. No migration is
  selected by the ordinary handoff.
- Repeated bounded-closure preflights parse the accumulated batch again. With d
  dependency-expansion rounds and final selected byte size s, `O(d*s)` parse work
  is possible before actual checking; caps bound the attempted work, not usefulness.

Consequently a complete cost decomposition retains fixed support validation,
local-history bookkeeping, selected snapshot integrity/loading, selected evidence,
new checking, custody/commit, and acquisition. It is invalid to label the entire
operation `O(new proof)` or `O(log N)` merely because old proofs are not rechecked.

The declared defaults (4096 roots, 8192 operations, 1,048,576 names, 4 GiB total
snapshots; admission up to 1024 units/64 MiB) are ceilings across different
layers, not a practical performance target. Smaller authoring/module limits
remain separate. Their intersection and the actual allocated CPU/RAM decide
whether an operation succeeds; increasing them is not a scaling design.

## Cold trust boundary and the available choices

For an unwarranted premise, an identifier, index result or another node's saved
success flag alone is not mathematical justification. The current ordinary lane
either independently checks suitable evidence to ground it, uses an already
grounded exact local parent, or refuses. A shorter direct proof could replace a
long historical derivation; optional compatible certificates could justify a cut
under their extra assumptions. Therefore **do not assert a universal theorem
that every historical proof step must always be downloaded**. The limitation is
of the selected evidence/acceptance route, not all conceivable mathematics.

Before any new mechanism, use existing batch admission and a deliberately small
eligible parent; for a known complete retained bundle, ordinary baseline intake
already supports that parent. Charge re-admission, setup and duplication. A
registered local module anchor amortizes repeated module generation, not another
peer's first independent acceptance and not arbitrary parent restoration.

Only reopen design for a concrete high-value history where those choices cannot
serve repeated use economically. Identify whether the dominating term is cold
missing evidence, local branch restoration, authoring semantics, or bookkeeping;
they require different remedies. No new mechanism or runtime is selected here.

This closes the requested size-boundary question; it does not establish full v5
completion, broad cold-library compatibility or a mathematical-growth advantage.
