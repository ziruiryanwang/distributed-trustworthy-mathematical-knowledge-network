# Custody-role separation: useful release seam, not the next growth bottleneck

2026-10-24. Independent source-only decision by investigator_public_path_audit.
No implementation, runtime, state access, network request or Git mutation.
Read with ordinary_research_distribution/PUBLIC-PATH-AUDIT.md and the adopted
CREATIVE-GROWTH-DECISION. All code references below are selected source donors.

## Decision

**Defer a custody-only CLI until a concrete operator workflow requires it.**
The missing turnkey facade is real, but it is not shown to dominate creative
investigation or full-cost growth. Do not promote it merely because its code
seam is visible. Nor does this decision automatically select another search client:
existing formal-search integration should first be challenged against a specific
available corpus and meaningful investigator query, using maintained tools.

## What realistic users can already do

| Workflow | Existing route | Consequence |
|---|---|---|
| Investigate while others read old work | Ordinary Lean source work and owner-free production continue during the finite serve lease | The catalog lock does not stop creative theory development |
| Publish the next checked contribution | Cleanly stop serving, intake/publish, then serve again | Possible now; incurs interruption, not a missing mathematical operation |
| Continue work while another provider serves | A different initialized owner's supported serve, or dedicated-store SDK rehosting | Role separation exists; no second physical PC is needed for lock separation |
| Volunteer to host exact inert bytes only | SDK controller prepares separate custody/index; serve takes no owner | Feasible but expert-facing; shipped CLI imposes an unnecessary owner setup |
| Find an independently named analogous theory | Ordinary formal-pattern tools over an appropriate corpus | More custody replicas cannot supply missing corpus coverage or discover an unwritten bridge |

No row proves that willing providers, useful indexed content or continued source
repositories exist. Separate same-PC processes/stores are not independent failure
domains. The owner-based provider also incurs setup/checking costs the inert SDK
host avoids. These limitations prevent calling the existing roles a complete
worldwide deployment solution; they do not make a new facade the dominant next step.

## Exact smallest facade boundary, if later selected

The current selected ordinary_authoring_offers/peer.py parses modes at40, treats
serve as owner-bearing at172-224, and retains owner/custody through cleanup at
263-269. peer_api.serve:485-558 already takes only loaded package,custody,config,
allowance; _state:79-84 and _index:405-419 accept owner=None. No native admission
or acceptance-policy change is needed to invoke this existing serving behavior.

An explicit new custody-only mode could reuse package bootstrap,reporting,budgets,
serve and cleanup; require custody/custody-limits but reject catalog/store-id;
skip ADOPTION.json/catalog opening; retain existing-index/create=false. Do not
silently change old serve's lock behavior. This is a facade over approved support,
not a runtime-free lightweight host: profile.load still verifies installed support
and the selected Lean/Python runtime mappings without opening mathematical state.

Required preserved boundaries:

- Pairwise-disjoint output,custody,index,package and runtime roots; ordinary paths,
  no links/reparse traversal; package/config/file pins and protected OS storage.
- Existing custody object/export/logical-byte/database-page quotas, index object/
  posting/snapshot/byte quotas, and HTTP connection/request/reply/operation limits.
- Explicit disclosure of **all** selected custody; no per-target ACL, exact
  IP/TLS checks, original allowance, finite lease and reserved cleanup. Hard process
  containment remains external; a memory argument alone is not a controller cap.
- Actual provider/index cleanup before custody closure; report partial failures.
  Read-only means no remote mutation route, not filesystem-read-only SQLite opens.

**The difficult boundary is exclusion, not serve dispatch.** exclusive=true is
an asserted premise. OrdinaryStore and discovery.Store supply no shared owner
lock. A new custody lock does not exclude existing owner commands that ignore it.
A safe SDK-equivalent facade must be limited to dedicated, separately prepared
stores under an enforceable operator/OS serialization arrangement. Alternatively,
a common lock protocol must cover every supported preparer/refresher as well as
serving. Removing the contributor lock or merely adding a boolean is insufficient.

Preparation can already use OrdinaryStore.put_evidence/put_preview and
discovery.Store(...,OrdinaryExportAdapter(S),...,create=True).admit(preview), then
close the index before serve opens it. Use selected exact inert bytes, not a live
SQLite copy. These operations do not certify truth or promise complete ancestry.
Refresh must stop and cleanly close the dedicated service before mutating its
stores, or prepare distinct stores and switch only after separately justified
ownership/lifecycle handling. Atomic rolling refresh and repair are not supplied
by the proposed small facade. Shipping preparation/refresh too is a larger scope.

## Marginal payoff and release relevance

The facade saves host initialization and custom-controller effort, and may avoid
some contributor service interruption. It does not reduce cold mathematical
checking, native project trust/compatibility work, search ambiguity or failed
analogy search. Existing SDK/provider routes already avoid compulsory catalog
coupling; a new CLI changes onboarding more than the network's mathematical power.

There are no measured setup costs, volunteer demand or reader outage losses here
that establish hosting as the dominant cost. Do not invent such magnitudes. For
creative growth, corpus accessibility and continuation of unfamiliar mathematics
are more direct candidate obstructions; the adopted sources identify them, not
a need for yet another provider abstraction. Assess those with source reasoning
before spending on a new matcher,client,benchmark or hosting campaign.

Reopen this seam when a selected independent operator needs inert-only hosting,
or the release promises contributor publication without interrupting readers and
existing replicas cannot satisfy that requirement. Then select the facade plus
explicit preparation/exclusion contract, not a daemon or weaker trust mode.
For broad public release the role needs usable instructions or tooling eventually;
it is deferred priority, not a waiver of availability or deployability.
