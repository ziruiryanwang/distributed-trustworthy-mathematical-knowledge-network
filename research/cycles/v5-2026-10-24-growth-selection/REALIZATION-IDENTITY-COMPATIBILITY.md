# Rebuilt realization identities: coexistence is not an in-place upgrade

2026-10-24. SOURCE ONLY; no execution, DB access, source normalization or Git.
**Decision:** preserve exact evidence identities. Treat the standard Lake rebuild
as a separately identified source realization; use explicit source dependency
pinning and, when independently admitting it, an eligible nonconflicting branch.
No merger, global semantic-ID scheme or canonicalization is justified by this case.
The existing public branch route is sufficient in principle for a revised handoff,
not proof that this fresh bundle has already been accepted or fits every budget.

## What changed, and what the observation does not establish

The independent actual auditor reports 106 units in both exports, 84 byte/ID-exact
and 22 changed; all twelve endpoint IDs changed. Three changed units are definitions
(`choose`, `ClosureBridge.installLeft`, `ClosureBridge.propagateRight`); nineteen
are theorem units. Some payloads differ; others differ only in imported IDs.
The twelve endpoint type DAGs are byte-structurally equal. This is NOT type equality
in one common environment: constants in those DAGs can bind different exact IDs.

The auditor explains payload differences by diagnostic substitutions of module
components `TheoryB02`/`TheoryB` and generated helper `choose._proof_3`/`_proof_1`.
The generated `installLeft._proof_1` type itself has module-dependent binder labels.
Those observations are not adopted semantic normalization, checked transports,
general alpha-equivalence or evidence that every changed definition is equivalent.
Do not rewrite old IDs or count the rebuilt declarations as new mathematical ideas.

`ordinary_semantics` hashes the entire canonical evidence envelope: declarations,
inventory and exact import bindings. ExportID hashes semantic profile, UnitID and
public name. The shared `semantic_id` identifies the interpretation/foundation
contract, NOT equality of the mathematics in all units sharing that profile.
The expression projection erases metadata only; it does not quotient all harmless
proof, binder-label, generated-name or module changes. Cascading IDs are expected.

## Native preflight and intake: exact reuse, no silent rebinding

`ordinary_admission._plan` compares each output name with the selected parent's
binding. If present, it requires the same ExportID (`ADMISSION_PARENT_NAME_CONFLICT`).
An atomic unit is reused only if all outputs are present exactly; partial presence
refuses. Imports also require exact selected-parent or selected-unit identities
(`ADMISSION_PARENT_IMPORT_CONFLICT`/`ADMISSION_SELECTED_IMPORT_CONFLICT`).
No theorem-only exemption applies here, even if only its proof changed.

`baseline_intake._plan_all` runs this same planner over the entire manifest before
any checking batch. It does not replace old declarations, infer equivalences or
repair IDs. `portable_catalog.reserve_extension` separately refuses overwrites;
its lineage reconstruction forbids a shadowed name. Dropping the conflicting
unit from the incoming list does not fix consumers whose imports require its new ID.

| Selected receiver context | Consequence from source |
|---|---|
| Fresh warranted fixed basis | New coherent closure can be independently checked, subject to bounds and actual worker success; no old A/B-name collision |
| Warm old A root | Full rebuilt bundle conflicts already at `RepairTheory.choose`; old/new helpers do not make its public name fresh |
| Warm old A+B root | Changed same-name outputs/imports conflict; equal endpoint type syntax does not override this |
| New branch from the same catalog's basis or a suitable earlier root | Both realizations may be retained in separate lineages; selected operations see only one lineage |

`context(root)` follows that root's parents, not every stored branch. Public
`intake-baseline --parent-root` accepts any eligible protected root. A second store
or a second basis build is therefore not logically required merely to separate
versions. Custody keys objects by exact identity and locators by ExportID, so it
can hold both variants. Retention and rechecking still cost resources. Selecting
a branch is not replacing the old root, importing both branches together, or
guaranteeing that old branch-specific downstream results work in the new branch.

## Materialization and authoring do not secretly provide an upgrade

`module_closure` checks each requested name/ID against the selected local warrant.
An anchor supplies only exact registered whole units; conflicting anchor/import
IDs refuse. It cannot combine old and new definitions under one name or reinterpret
a new endpoint as the old one simply because their printed statements coincide.

`OrdinaryModule04.classifyUnits` has one narrow installed-name match: a singleton
theorem whose complete private inventory agrees, including proof value; the public
axiom-shaped handle then receives a separately checked signature comparison.
It is NOT proof-insensitive theorem deduplication. Non-theorem/group collisions
refuse. Exact registered anchors are a different path, not a collision waiver.
Consequently fresh native intake does not imply successful generated materialization
beside the original source package; existing closure/size/frontend limits remain.

Do not confuse authoring with acceptance. `OwnerRebind` can match an existing
theorem interface while requiring exact concrete inventories, but it neither
updates native catalog identities nor establishes whole-package correspondence.
The current constructive contribution helper is weaker intentionally: existing
safe local names stop demand traversal; missing theorem types become scratch
assumptions with receiver-selected interpretation labels. It promises no semantic
match to existing source records. Complete NEW proofs are independently checked
under the chosen receiver context. Old theorem re-export is not an upgrade:
`SuccessorExport.selectedDeferred` refuses a target already in its boundary.

## Cheapest legitimate choices, in order

1. **New standard-source handoff:** retain both historical artifacts; advertise
   the actual new endpoint IDs and source realization. A cold recipient or a new
   same-catalog branch can select this version. Do not advertise the source tree
   as exactly rebuilding the old endpoint IDs. No new identity mechanism needed.
2. **Existing user's continuation:** pin one ordinary source revision/import
   graph and continue it. Keep the old branch usable. To move to the rebuilt
   source, rebuild affected dependent work and independently admit its actual
   new results on the corresponding branch; this is an explicit version change.
3. **Reuse a new consequence in an old context:** a newly named application or
   bridge can be authored for the old receiver meanings and checked there using
   existing contribution APIs, if compatible and within limits. Success is not
   guaranteed by equal endpoint syntax; no direct dual-version merge is inferred.
4. **If exact reproduction is required:** preserve the actual old artifacts and
   all needed source/build inputs. Restoring the old logical module name is a
   diagnostic candidate, not a guarantee against generated-proof selection drift.
   Do not rerun merely to make IDs look stable or alter frozen old evidence.

There IS a practical warm-upgrade/composition limitation: two independently
recompiled packages with shared public names cannot simply be unioned into one
accepted environment. Separate roots handle selection/coexistence, not joint use.
Ordinary Lean also requires coherent dependency resolution; Git sharing alone does
not make conflicting declarations jointly importable. If a valuable real workflow
requires joint use, select explicit namespaces/checked transports or a narrowly
specified correspondence mechanism then. This case alone does not justify that
investment or a proof-erasure policy for definitions containing theorem references.
