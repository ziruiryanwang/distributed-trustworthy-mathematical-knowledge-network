# After grounded cuts: preserve mixed concept-and-theorem evolution

2026-10-24. `current_scale_obstruction`; bounded source/theory follow-up while
root completes the selected cut controller. No experiment, new mathematical
artifact, code, package, protected-state access or Git mutation is selected here.
The current source slice remains unfinished, not an accepted v5 release.

## Decision

The existing architecture can **support open-ended concept development by local
investigators**: ordinary Lean projects allow definitions, structures, inductives,
models, counterexamples and independently chosen laws; the retained concept
episode supplies a real bounded example. It does not follow that the node itself
autonomously invents theories, that arbitrary new concepts fit the current inert
frontend, or that this workflow is faster than ordinary Git+Lean+search.

Do not commission another concept generator, matcher, bridge registry, philosophical
growth model or creative episode. The highest-payoff next architectural discriminator
is **affordable mixed-declaration continuation after using the cut lane**. A real
investigator must be able to turn newly established laws into further definitions,
structures and models, not only add theorems indefinitely to a fixed vocabulary.

This is a continuity/cost requirement, not an instruction to immediately broaden
the new checker. First identify the complete public ordinary re-entry route and
its incremental cost. If retained ordinary source plus existing export/admission
already supplies an affordable route, use it. If no useful workload is impeded,
no further mechanism is justified. The source-only cut remains an optional local
accelerator, never the replacement authoring system.

## A concrete mixed-theory discriminator

Consider a supported checked theory containing a function `f : X -> X` and an
invariant `P`. An investigator obtains a new theorem through the cut lane:

```text
h : forall x, P x -> P (f x)
```

Later, another investigation introduces a concept of invariant-preserving actions,
with data `run : X -> X` and law `stable : forall x, P x -> P (run x)`. Its concrete
model packages `f` together with `h`; further composition/iteration laws concern
these newly introduced actions. The exact chosen concept need not be this one;
this example witnesses a normal structural dependency rather than a test task
to prescribe to an agent.

The instance definition's body references `h`, even if its proof field does not
affect extracted computation. That is a **concrete-unit-to-theorem dependency**.
The first cut source explicitly refuses this edge because concrete units are
checked before theorem signatures. It also accepts only one new theorem, not the
new structure or definition. Those are deliberate soundness/investment restrictions,
not proof that such mathematics is invalid or impossible in Lean.

Ordinary approved source can already express and build this continuation. Thus
there is no expressiveness impossibility and no need for a new theory language.
The unresolved product question is narrower: how does work using a **cut-accepted
result** return to the ordinary independently checked contribution path, preserving
exact identities and support, without a private intervention or a hidden expensive
full-prefix reconstruction at every conceptual revision?

`grounded_cut/CONTRACT.md` and `GROUNDED-CUT-CONTRACT` promise retention of complete
new proof claims for ordinary inert return. They explicitly do not promise native
snapshot compatibility or direct native-project materialization. The new catalog's
only extension kind is `theorem-cut`. Ordinary authoring availability therefore
must not be conflated with an already implemented cheap cut-to-native transition.
The controller source is still being completed: this note identifies its next
boundary, not an observed failed operation or a demand to change it mid-review.

## Three routes, ordered by justified investment

| Route | What it can supply | Main cost or limitation |
|---|---|---|
| **Native-first authoring, cuts only for selected admissions** | Retain an approved Git/Lake project as the ordinary realization; develop new concepts there and use existing inert export/admission when needed | Source/frontend work remains real; a later native catalog may independently check cut results again; exact source-to-export correspondence is not assumed |
| **Proof-parametric ordinary interfaces** | Make a reusable definition accept its preservation proof as an explicit parameter; specialize only where needed | Often removes a fixed proof dependency, but changes the interface and does not admit a new structure for free; arbitrary definitions cannot be generalized blindly |
| **Later mixed cut extensions** | Check fresh definitions/groups and grounded signatures in a correctly ordered small environment, commit all names as one genuine event | Substantially extends worker, projection, realization, freshness and public-return obligations; requires a demonstrated continuation bottleneck first |

Prefer the first route. The second is ordinary mathematical abstraction available
equally to the comparator, not a new trusted module system or automatic generalizer.
For the third, interleaving signatures and concrete groups is not merely moving
two loops: exact computation rules, complete generated groups, earlier-warrant
grounding and the realized environment must remain coherent. Prove that relation
before implementing it. A native replay option is also legitimate when its full
cost is affordable and explicitly selected; it is not automatically a design failure.

## The growth argument and its fair comparator

Let a finite research history alternate semantic revisions and blocks of new laws.
Both routes receive the same initial mathematics, actual discoveries, sources,
approved tooling, ordinary incremental builds, search capabilities, caches, mirrors
and independent acceptance obligations. Do not require the Git+Lean baseline to
recreate an available bridge, flatten its library or wait for an invented central
permission. Our interoperable adapters can still be a useful public good without
an exclusive mathematical capability or a speed advantage over an ideal stack
that already incorporates equivalent adapters.

For the selected history, write:

```text
net cut benefit
  = avoided native admission/restoration cost during theorem blocks
    - initial summary derivation
    - cut checking/index/retention/failed-attempt overhead
    - additional cross-lane re-entry cost at semantic revisions.
```

Only **additional** re-entry cost belongs in the last term: common authoring,
checking and source distribution work must not be charged solely to the cut route
or silently removed from either side. No magnitude is established by this note.

A fixed-vocabulary advantage does not by itself settle this mixed-history sum.
If an implementation reconstructs a growing prefix at each of `m` semantic
revisions, with revision `j` doing at least `a*j` additional units of work, that
term is at least `a*m*(m-1)/2`. This is a conditional algorithmic warning, not a
measured current cost or a theorem that conceptual research necessarily has this
pattern. Conversely, long theorem blocks, infrequent revisions or cheap existing
native re-entry can leave a substantial benefit region. Batching and small
compatible native roots retain their full credit.

The product's growth criterion remains increasing **obtainable and extendable
warranted capability per resource**. A theorem-count increase is insufficient if
each useful conceptual revision becomes unaffordable. Keeping both an inert proof
realization and a practical ordinary authoring realization can be more valuable
than forcing every operation through the newest local acceptance backend.

## Source availability and cross-vocabulary reuse still matter

Retained sources must include the chosen dependency/build closure and compatible
toolchain; a metadata offer is not possession or execution approval. Rebuilding
different source/module arrangements does not automatically preserve exact export
identities. Compare actual derived units before using an old identity association.

Exact-symbol neighborhoods can expose existing connections whose signatures
mention a known concept. They cannot reveal every independent representation
before a bridge exists. Existing approved project-pattern search or advisory
providers remain the reasonable route for that exploration. A bridge subsequently
published as an ordinary named declaration can create new exact-index links.
No new search mechanism is supported merely because this limitation persists.
Without a relevant obtainable corpus and meaningful continuation, another search
wrapper would not supply the missing growth evidence.

## Decision-changing evidence and stopping rule

After the current finite cut source boundary, one bounded **source trace** should
answer the mixed-history question using existing APIs and retained evidence:

1. Identify what a user receives after a committed cut: complete new proof claim,
   exact imports, current support and the independently obtainable authoring source.
2. Identify an existing public ordinary route for a new definition/model using that
   result. Trace identity/authority conversion and the exact proof/semantic reads;
   do not execute another creative episode or silently treat a cut root as native.
3. Compare its additional re-entry work with native-first authoring and ordinary
   batching. Check whether proof-parameterization already eliminates the concrete
   obstruction for the actual use, without requiring a new protocol.
4. If the route is complete and affordable in its stated region, document it and
   stop. If it has a concrete high-cost or unavailable transition in a worthwhile
   workflow, choose the smallest corresponding adapter or mixed-extension rule.
   Only a residual decision-changing runtime uncertainty justifies a later test.

If no worthwhile mixed-history use is identified, select **no new growth mechanism**.
Continue the real release's integration/assurance/availability obligations instead
of inventing a larger speculative research service. This closes the present bounded
investigation; neither another note nor a source-feasible cut is final v5.

## Bounded source discriminator: ordinary re-entry from a cut proof

Root requested this single follow-up. Source inspection only; no protected state,

The selected ordinary package map is
`software/v5/ordinary_bounded_operations/source-map.json`: it installs
`ordinary_native_package/owner.py` as `owner.py`,
`ordinary_project_return/ordinary_contribution.py` as its authoring controller,
and the existing baseline intake, producer and anchored module helpers.
The current grounded-cut source is a separate candidate, not already shipped

### What a cut retains, and what the public package does not accept

`grounded_cut/cut_controller.extend` calls `custody.put_evidence(raw_new)` and
checks exact readback before its conditional worker. The ordinary custody code
(`ordinary_authoring_offers/ordinary_acquisition.py`, `_put`/`_export_locators`)
stores the full V2 proof claim and every exact output locator. Custody explicitly
grants no mathematical acceptance; failed checking can therefore leave inert
claim bytes without an accepted cut event. The committed cut root is not an
ordinary native root or a transferable certificate.

Current packaged `owner.py` has no cut operation. Before ordinary owner work it
requires the native catalog's exact ADOPTION fields/schema/implementation and
opens `OrdinaryAdmission`. `receive`, `publish`, `contribute` and `export-module`
then validate their selected parent/context via `PortableCatalog.context`.
Passing a cut-store directory fails the native marker boundary; passing a cut
root into a real native store cannot create a native root record. This rejection
is required, not a compatibility bug to bypass.

There is a concrete current return-facade gap. A cut event retains evidence and
locators but does not itself create a baseline file bundle, preview or discovery
index record. Packaged `peer.publish` first demands the exact target binding in
an accepted **native** context, then creates the preview/index record. It cannot
publish a cut-only binding by substituting the cut root. Therefore an immediately
discoverable, cut-native public return path has not been supplied by the current
ordinary CLI. This is distinct from losing the proof bytes or lacking an
independent receiving/checking implementation.

### The existing native re-entry seam

At the already existing library seam, an owner can supply complete exact V2 units
to `OrdinaryAdmission.preflight(native_parent, raws)` and then
`OrdinaryAdmission.admit(native_parent, plan, original_budget)`. The implementation
does not inspect who produced those bytes. An exact cut-produced V2 claim is
ordinary input, not special authority. If all imports are present in the chosen
native parent, only the fresh cut theorem needs native kernel admission. Its
full proof is read and checked; its short cut summary cannot replace that proof.

If imports are missing, resolve their complete exact V2 units until the closure
reaches the selected native parent or fixed basis. This can include earlier cut
theorems and their proof-only dependencies. Every absent whole unit is checked;
already present exact units are not kernel-checked again. The parent snapshot
chain is restored once per actual admission batch, not once per theorem unit.
Thus this is selected missing-proof rechecking, **not** unconditional replay of
every proof in the whole native library. It is nevertheless not the ancestry-free
warm rule of the cut backend.

The packaged file entrypoint is `owner.py intake-baseline`, with explicit native
parent, bundle directory, manifest and manifest hash. It needs the documented
ordinary bundle layout, not a custody database path. Existing pure
`baseline_bundle.split_units`/`make_manifest` already validate and describe
selected bounded batches; they are not a public custody-to-bundle collector,
dependency planner or acceptance shortcut. A later bounded cut-return adapter
can reuse them instead of exporting through a fresh approved project merely to
recover bytes already held. No such adapter was implemented by this trace.

The packaged network entrypoint is `peer.py receive` **when an actual provider
record/preview and locatable proof closure are available**. `selected-unit-only`
fetches only that unit and refuses missing grounded premises. `bounded-closure`
explicitly retrieves the missing proof frontier, then invokes the same native
admission. The current cut-only publication gap above prevents claiming this
entire network route already starts automatically from a new cut event. A
different genuine native provider/independent index may supply the candidate;
one must not invent its availability or count it as a completed cut return.

### Introducing a structure after native re-entry

Once the result has been independently admitted under native parent `N`, the
current package has two ordinary authoring choices:

1. `owner.py contribute --parent-root N --source ... --acquired-targets ...
   --output-names ...`, with the usual pinned runtime/profile, state, fresh output
   and original finite resource envelope. The source body may introduce a new
   structure, a model using the acquired theorem and new laws. The installed
   `ordinary_project_return.ordinary_contribution.contribute_source` prepares
   selected grounded old interfaces, invokes approved source authoring, binds
   the resulting complete candidate units, and independently admits them.
   Successful output includes durable evidence/previews and exact publication
   targets; `peer.publish` can then index those genuine native bindings.
   New meanings use the existing full checker rather than cut signatures alone.
   This route has explicit 32-group/4-MiB/131072-node authoring limits and does
   not restore all foreign notation, class or tactic metadata.
2. Obtain/retain an approved compatible ordinary Git/Lake project containing the
   theorem, develop the new structure normally, then `owner.py produce-baseline`
   with explicit approved compiled-project selection and output names. That
   operation is owner-free and creates inert selected proof closure, not
   acceptance. `intake-baseline` subsequently admits it above a native parent.
   A source availability hint is not the project itself, its execution approval,
   or evidence of exact correspondence to the original cut identity.

For an investigator **already maintaining** the ordinary project containing the
proof of `h`, the second route does not need native re-entry before creative
authoring at all. Keep using the same source/import realization and publish the
next selected finished development. A remote recipient with only inert custody
cannot assume that project exists. Native-first authoring therefore avoids a
one-way creative dead end for the intended paired-source workflow, without
making the inert-only route equally convenient or cheap.

An additional existing choice, `owner.py export-module`, materializes a native-
accepted selected closure into an ordinary local module. It is not a cut-root
converter. Cold materialization gathers the complete selected proof closure;
a registered exact local module anchor can stop traversal above already realized
whole units. The existing 32-unit/4-MiB new-delta limits, ambient-name restrictions
and frontend-metadata limitations remain. The known 66-unit retained A closure
already exceeds the cold limit; this trace does not retest it or propose increasing
the limit. The approved ordinary source route is the practical general fallback.

### Source-level passes, not timing guesses

The following counts isolate named successful paths. They exclude initial support
loading, owner opening, activation checks, SQL-internal work, report checks and
other subordinate validation; they are not total CPU or even total parsing counts.

| Path | Direct source-level work |
|---|---|
| Peer receive, `p` acquisition preflights, new work | `p+4` direct `PortableCatalog.context` calls: initial parent check, `p` preflights, admission re-preflight, admission context, reservation context; one native parent restore and new-unit kernel batch |
| Baseline intake, `B` batches of which `N` contain new units | Two explicit file-read passes per bundle batch: full planning and actual intake; `1+2B+2N` direct context calls in intake/admission/reservation; `N` actual native restore/check batches |

| Cold `export-module` | One selected complete proof-closure collection; one supervised worker with build, private reread and exported reread phases; build checks added units in private and public views, with exact matches handled separately |
| Maintained approved project plus `produce-baseline` | Normal local authoring/build costs plus one selected exporter allocation, canonical bundle conversion and later intake; no catalog admission is required merely to author the new source |

For `contribute`, current `portable_owner_request.prepare` reads each selected
old evidence unit in full from local custody before discarding old theorem values
and following only their type dependencies. Thus the authoring request omits old
proof ancestry from its packet, but still reads the selected theorem's own full
proof bytes. That fact must not be replaced by the new cut-summary cost claim.
The final native admission restores its parent and checks only newly contributed
units. Source checking is not a claim that this particular mixed-theory workflow
has been executed or succeeds within any proposed allocation.

These counts follow `peer_api.receive`, `baseline_intake.intake/_plan_all`,
`ordinary_admission.preflight/admit`, `portable_catalog.reserve_extension`,
`ordinary_project_return.contribute_source`, `module_closure.collect_closure`,
`module_worker` and `OrdinaryModule04`. Every `context` may revisit its selected
ancestor records; retained-artifact hashing has its separate process-local cache.
Counting context calls does not imply kernel rechecking of all ancestral proofs.

### Decision: ordinary route first; one integration gap, no broader checker now

This trace finds **no missing mathematical rule or necessary mixed-cut extension**
for the next creative step. Ordinary maintained source can introduce the proposed
concept, and existing native admission accepts complete cut-produced claims under
its own independent premises. Proof-parameterization is a useful optional source
design when it avoids binding a reusable definition to one proof, but it neither
manufactures a native warrant nor removes the need to distribute a concrete model.

The concrete missing edge is narrower: expose the cut's retained inert claims
through a bounded ordinary return/handoff operation without pretending the cut
root is native. This is a current **integration completeness** issue, not measured
evidence that conversion dominates research cost. After the cut controller is
reviewed, finish that selected public boundary using existing custody/bundle/
receiver mechanisms if needed for the accepted slice; do not add another checker,
source registry, generalized module system or larger test campaign to solve it.

No extra code is selected by this research note. Stop the discriminator here.
Reopen mixed checking only for a worthwhile actual sequence whose additional
native conversion/rechecking is shown by source bounds or retained measurements
to erase the useful cut savings. Preserve native-first authoring in the meantime.
