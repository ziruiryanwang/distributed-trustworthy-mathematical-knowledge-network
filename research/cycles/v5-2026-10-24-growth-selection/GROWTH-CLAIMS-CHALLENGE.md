# Growth justification that can lead to a release, not perpetual qualification

2026-10-24. Independent challenge by `preexport_tools`; source/theory only.
No experiment, new source, package, installation, service or Git operation.
Root selects the concrete mathematical case and any subsequent implementation.

## Decision

The software does **not** need to predict future discoveries, recruit an outside
user, or outperform every conceivable combination of Git, Lean and search to
justify release. It does need to deliver a complete reciprocal workflow with a
defensible public-use case, explicit assurance/cost boundaries and a constructive
account of how contributions become another agent's useful inputs.

A theoretical, source-grounded account can justify that capability and a
conditional benefit region. Population prevalence, measured productivity and
sustained actual uptake are different claims. Requiring the latter before the
former can be released would impose an empirical gate the user never requested.
Conversely, promising possible future uptake cannot excuse an unusable integration.

**The next software boundary should be a supported consumer capability, not
another discovery transport:** from an ordinary published method to a real local
use, an exactly warranted finished output, and a reusable returned contribution.
First use source analysis to identify which link, if any, still requires code.
The already reviewed producer/list-of-targets capability is not that missing link.
Root's parallel opportunity selection should supply the mathematical case; this
note defines what would make its selection adequate without inventing a benchmark.

## What is reused, and the correction this note adds

The prior PHILOSOPHY-OF-GROWTH already resolves logical closure versus finite
warranted capability. GROWTH-COMPARATOR-CHALLENGE already separates accumulation,
access, productivity and implementation advantage, proves the comparator
simulation lemma, and exposes faulty exponential-growth proxies. GROWTH-DECISION
already gives endpoint-warrant checking; BRIDGE-INVESTMENT already explains why
consumer-created intermediate adapters deserve ordinary named publication.
Those arguments are adopted, not rederived here.

The needed correction is **the evidential burden at the release boundary**.
The useful question is not whether an omnipotent engineer could reproduce this
software with other tools. It is whether this supported distribution supplies a
justified usable capability for an explicitly stated class of agents, at an
acceptable cost, without falsely advertising stronger guarantees.

Calling the product an integration layer is legitimate only if it actually
integrates the whole workflow. A pile of individually tested components plus
instructions requiring private state edits or author intervention is not an
integrated release. A custom subsystem with no advantage over a maintained
dependency should be removed even if its tests pass.

## A useful mathematical claim has three levels

### Level A: guaranteed conditional capability

Specify a workflow class W by observable mathematical and operational conditions:
supported Lean version and declaration kinds, adopted foundation/axiom policy,
initial local libraries, package-execution permission, data availability,
compatibility requirements and finite resource limits. These are assumptions,
not a human-intention field or a global list of research tasks.

For a selected instance w in W, give a concrete map from its available inputs to:

1. A locally usable method/interface, not just a theorem name or receipt.
2. A complete checked application with its real residual obligations discharged.
3. A distinct local extension or independently reusable intermediate declaration.
4. A public contribution another supported client can acquire and use.

Prove the correspondence between actual endpoint records and accepted mathematics
under the exact policy; account for the acquisition, checking, application and
return path. The accepted-output theorem is conditional on its checker and trust
boundary. It need not prove all of Lean correct or assume that an operator cannot
ever make a mistake. A resource cap guarantees bounded refusal, not successful
completion: the witness must separately establish completion for the selected w.

For a parametric family, prove what varies and which construction is uniform.
One theorem instantiated many times is a useful reusable capability but is not
many independent discoveries. An adapter may be the substantial returned object;
a forced alias or trivial wrapper is not satisfactory merely because its bytes
are new. No general semantic-novelty algorithm is required.

This is enough to justify **support for useful accumulation** for the stated
class. It is not yet a theorem that the software accelerates every researcher.

### Level B: justified benefit for a stated workflow

Name one concrete obstruction removed by the product: an unavailable supported
adoption path under the receiver's execution policy, duplicated manual glue,
avoidable reconstruction, or a specific availability/integration failure.
Do not conflate these. A safety-constrained capability gain is valuable even
when it is slower than a less-assured route, but must be advertised that way.

Source-derived bounds and a constructive procedure can suffice. For example,
an ordinary output-only checking route may eliminate a mandatory intermediate
module conversion in a specified workflow. Its control flow can prove that the
conversion is no longer performed. A documented finite input bound can prove
bounded work/space for a parser. Neither fact needs a wall-clock experiment.
Claims about actual elapsed seconds, human time, library prevalence or a model's
success probability require evidence for those particular quantities.

The assumptions must describe a plausible allowed practice, not a contrivance
designed to make the baseline fail. A consumer who declines to execute unknown
package code is plausible. A consumer who inexplicably forbids ordinary source
search while our product may use it is not a fair comparator. A supported small
application is acceptable; a huge padded proof invented to repay certification
is not a realistic argument for the default architecture.

Theoretical conditional value does **not** require a currently recruited user.
An independently specified mathematical endpoint, existing reusable source, and
a clean supported client can supply a constructive witness. Actual external
participation later tests demand and usability; it is not a logical premise of
the current theorem. The absence of the user's own Lean project is not a blocker.

### Level C: realized aggregate growth

Statements such as faster research in practice, positive lifetime net benefit,
many independent users or sustained increasing capability require the matching
observations/model premises. They should not be promised at release without
them. A release can truthfully claim Levels A and B and invite those observations.

This separation does not downgrade the goal to a prototype: release still needs
all its promised integrated functions, security, recovery and scale conditions.
It changes which scientific proposition the release must substantiate, not
whether unfinished engineering may be labelled complete.

## Fair baselines without an impossible novelty requirement

Use the strongest **available, executable** ordinary route appropriate to the
same workflow: pinned Lean/package versions, existing search, tactics, mirrors,
caches and approved validation tools. Allow source or proof shortcuts that
actually exist. Do not demand a centralized merge or a scheduled release when
ordinary branches already suffice.

Keep three questions distinct:

| Comparison | Question it can answer | Misuse to avoid |
|---|---|---|
| Same agents and ordinary tools, without cross-agent access | Does delivery of already funded work enable these downstream applications? | Claiming superiority over ordinary sharing |
| Present maintained ordinary stack versus supported commons workflow | Does this distribution remove a real operation, trust or integration obstacle? | Hiding existing upstream export/search capabilities |
| Ordinary stack furnished with this new useful adapter | Can the benefit be retained outside our preferred transport? | Treating successful reuse of our adapter as proof it had no product value |

An infinitely resourceful hypothetical engineer is not an installed comparator;
nor may an implementation advantage be claimed merely because an ordinary stack
could use the same checker only after doing integration that we have not measured.
Say precisely whether the evidence establishes a mathematical capability,
eliminated operation, reduced measured cost, or reduced integration burden.
Do not turn unknown engineering labor into a fictitious numeric gain.

Cost matching includes producer preparation induced by this workflow, recipient
checking and semantic imports, failed candidates, maintenance and service. Common
already-funded work can cancel in an incremental comparison but remains part of
the history. A warm local cache is not charged as a cold derivation. A comparison
that gives both arms the finished discovery tests delivery, not induced discovery.

## A finite release evidence contract

This contract uses existing evidence for unchanged components. It does not select
a new campaign or require one experiment per row.

| Obligation | Feasible evidence | Falsifier requiring redesign or repair |
|---|---|---|
| Usable mathematical capability | One substantive existing method/family with an explicit supported application and reusable returned work; source-derived composition and cost argument | Only names/receipts travel; use requires unsupported metadata, arbitrary new axioms or bespoke hidden edits |
| Genuine reciprocal public path | One documented producer-to-clean-consumer-to-next-consumer path using public commands/APIs; retained evidence can satisfy unchanged links | Root must edit private accepted state or bypass a documented failure; second use merely replays the same wrapper |
| Equal mathematical assurance | Exact endpoint/policy/basis binding and rejected unsupported/false data; independent boundary review | Success is only a compiler exit code, remote opinion or a receipt for a different target |
| Affordable optional contribution | No mandatory independent proof campaign for every offered theorem; bound the selected export/check/import operation and state its supported input region | A normal contribution requires unconditional expensive certification or repeated full independent checking without an acceptable route |
| Honest scalability | Source-level dependence on selected corpus/interfaces/semantics, bounded search fanout, sustainable provider role assumptions, and the promised proof-ancestry boundary | The normal path secretly scans all worldwide results or necessarily replays complete ancestry despite an ancestry-free claim |
| Continued decentralized operation | Replaceable providers, exact identity independent of mutable host names, documented retrieval/return and recovery behavior | One privileged operator/private cache is indispensable, or provider disappearance loses a promised retained contribution |
| Deployable product rather than a component kit | Supported installation, executable workflow, hostile-input boundary, state recovery, release/update identities and clear operator documentation | Safety requires trusting arbitrary downloaded programs, unsupported tooling is required, or no user can complete the documented loop |

The clean consumer may be an automated or independently reviewed local workflow;
no outside recruitment is required. A single PC cannot establish independent
failure domains, global latency or public operational independence. Those remain
appropriately scoped claims, not reasons to halt all useful development.

For the growth argument, declare the chosen endpoint and ordinary comparison
before interpreting the result. Do not force the proof to cite our chosen lemma;
allow the cheap ordinary tactic to win. A case can establish Levels A/B through
formal/source reasoning even if no speed experiment is warranted. If actual
code execution is needed, run only the changed uncertain boundary. Do not repeat
the proof-production or package campaign to make the evidence look larger.

## Legitimate compromises versus changing the goal silently

Legitimate choices include finite supported platforms/versions; explicit local
base trust; advisory incomplete search; optional policy-selected caches/rankers;
ordinary approved package authoring; selective intermediate validation; optional
certification; and reusing maintained third-party search/storage. These simplify
the implementation while preserving truthful mathematics and local autonomy.
They need documented conditions and a workable supported path, not universal
success for every possible library and network condition.

Illegitimate substitutions include calling a valid proof receipt usable knowledge
without an interface; substituting full-ancestry cold checking for a promised
ancestry-free route; calling a single service decentralized merely because its
URL is configurable; or calling possible hypothetical uptake completed growth.
Resource limits are not a hostile-code sandbox. A theorem about a separate model
does not certify its implementation.

**Current unresolved scale conflict:** GOAL.md still explicitly requires cold
acceptance without proof-ancestry download/replay. GROWTH-DECISION explicitly
acknowledges that the current ordinary producer emits its selected closure and
that native-first reuse does not solve that cold case. This note does not waive
the requirement. A receiver-adopted checkpoint/base can be a reasoned practical
tradeoff, but trusting that checkpoint changes the assurance premise; it is not
a proof that a cold untrusting recipient verified its history. Optional succinct
evidence likewise still needs a feasible producer-side role. Root must resolve
this exact architecture obligation before claiming the unchanged final goal.

The user's permission for practical compromises authorizes careful redesign,
not quiet relabelling. State the tradeoff and why it serves actual use before
counting the corresponding release condition as met.

## Consequences for the next implementation decision

1. Keep the pre-export transport deferred. Its source comparison found existing
   adequate candidate-search routes; better transport without a useful corpus
   or adoption path does not resolve the central growth uncertainty.
2. Preserve ordinary rich Lean projects as the working/publication interface.
   Avoid a parallel mandatory authoring, metadata or recipe language. Consumer
   bridges are ordinary named declarations, not a new global registry.
3. Use the parallel opportunity/model work to select **one complete supported
   capability path**. Require a named surviving API/assurance/cost obstruction
   before writing code. Do not require an external user to certify that path.
4. If existing producer/intake/publication APIs already support the selected
   path, integrate and document them as the product rather than inventing a new
   growth mechanism. If they do not, the next code task should repair that exact
   consumer-use or return boundary, not polish packaging or measure a surrogate.
5. Resolve maintained-upstream reuse by exact contract, not reputation. The
   already inspected Lean 4.35 export/replay may remove custom maintenance, but
   it does not supply receiver axiom anchoring, bounds, warm authoring metadata
   or cold ancestry-free checking. Migrate only if that comparison changes the
   supported whole workflow economically; a new cold wrapper alone is not v5.
6. Do not demand a universal usefulness score, novelty oracle, long-run growth
   multiplier, compulsory global research agenda or online model training.
   Locally selected use and optional empirical heuristics are enough for the
   surrounding system once exact warranted contribution/reuse works.

The release decision should therefore be: **does the actual supported product
implement the stated reciprocal capability, with an honest defensible value
case and its promised assurance/scale boundaries?** Not: have we proved the
future behavior of the mathematical community? This is a high but attainable
bar, and it can reject both speculative mechanisms and premature release labels.

## Follow-up challenge: consumer-native domain witnesses

Root proposes an optional route in which a locally warranted domain checker
turns an inert exact-instance witness into a Lean theorem, without importing
the producer's solver or its proof-search history. The general ordinary-library
plane remains. This is a promising **specialized proof route**, not a replacement
for general mathematics or a resolution of every cold-import problem.

### Soundness and the exact next boundary

Let D and W be explicit instance/witness data types, `check : D -> W -> Bool`,
and `Meaning : D -> Prop`. An adopted theorem has the form

```text
sound : forall d w, check d w = true -> Meaning d.
```

A recipient must construct a real kernel-checkable proof of `check d w = true`
and apply `sound` to the exact received d and w. It may instead use a maintained
proof-producing checker yielding the corresponding direct derivation. A native
Boolean, a solver status string, or serialized proof-erased positive branch is
not the missing Lean proof. Proof normalization and term construction costs
remain chargeable; the Boolean checker operation count is not their bound.

The mathematical result is precisely `Meaning d`. If the local application
needs a different proposition P, an actual checked transport
`Meaning d -> P` is required. The network may accept an unintended valid
`Meaning d` without understanding anyone's intention. It may not advertise
that result as a proof of P without the transport. Defining the public domain
interface on canonical normalized instances can avoid a mandatory raw-input
normalizer in the core; raw/local representation bridges can remain local.

The **highest-payoff implementation discriminator** is therefore whether the
chosen maintained tool already supplies that complete proof-producing path to
an exact ordinary Lean statement, with acceptable selected-instance costs.
If it does, reuse it and connect the resulting declaration/tuple to the existing
contribution path. If it only supplies a native report, the proof-production or
local-statement binding seam is the real work. A new solver service, transport,
registry or generic certificate format does not repair that seam.

### What counts as growth rather than a result cache

Caching a checked answer can still expand resource-bounded access. It should be
called that, not proof of novel discovery. The stronger route is that a finite
certificate can establish a reusable **universal mathematical lemma**. For
example, an appropriate linear-inequality certificate can justify a statement
of the form

```text
forall x, A x <= b -> c*x <= d.
```

Such a theorem applies to many local objects satisfying its hypotheses. It can
be composed with separately produced representation/invariant lemmas and then
offered as ordinary checked mathematics. The network's contribution is warranted
delivery and reuse of that capability, not counting an optimizer's status codes.
For rational certificates applied to real-valued objects, the rational-to-real
interpretation itself must be supported by the actual proof, not presumed.

There are three distinct reusable objects: the verified checking method, a
particular certified mathematical statement, and a checked parametric transport
or adaptation that extends where statements can apply. Existing ordinary Lean
and optimization software may already supply all three. Use them. A parametric
transport is new theorem work if it is absent; do not treat it as free metadata
or commission it solely to manufacture a showcase.

### Whole-system challenge

Allow the ordinary baseline the same solver, checker, proof caches and artifact
sharing. Merely moving a solve to a remote machine does not reduce aggregate
solve work. Reasonable margins are reuse of an already solved exact instance,
reuse of a proved family/adapter, avoiding executable-producer trust, or a
demonstrated deployment/access obstruction. An independently operated solving
service can be useful without being mathematical authority, but its resources,
fees, availability and failures are not free. Durable archive tuples should
remain usable after the solver stops; an online solver is optional production,
not a permanent prerequisite for trusting its earlier answers.

The recipient's relevant work can avoid producer ancestry because it checks a
domain witness through a fixed adopted soundness theorem. It still pays for
the exact instance/witness, arithmetic and needed semantic data. Adoption of
the checker/soundness theorem is not free. This is a genuine special-domain
locality statement; it does not certify an unknown arbitrary new checker without
either checking its proof or using an explicit trusted/certified base.

Stop or narrow a growth claim if normal local tactics already solve the selected
case more cheaply, if exact normalization dominates the work, if certificates
are unavailable for useful cases, or if the new route needs a custom semantic
bridge for essentially every consumer. None of those facts makes a valid domain
checker useless; they determine its appropriate role rather than its truth.

## Offline witness backend: pre-implementation contract review

Read `software/v5/ordinary_witness_backend/CONTRACT.md`, the opportunity note's
appended API section, and the pinned upstream Contract, Registry, Dispatch and
BackendOption sources. **No logical blocker in the selected narrow contract**;
runtime/source compatibility and completed integration remain unestablished.

The actual APIs are `LP.registerStaticBackend` and
`LP.Backend.SoplexJSON.decodeResponse`, the latter returning `.solution` or
`.wireError` inside `Except`. Explicit named dispatch bypasses probes and returns
that backend's failure without trying others. An always-failing probe can keep
the offline backend out of accidental automatic selection; callers must still
explicitly select it to exclude unrelated installed solver backends.

Implementation review must resolve these concrete bounds, not create a framework:

- Charge callback attempts atomically before expensive encoding or matching;
  failed and concurrent calls consume the same finite counter.
- Bound the actual local sparse-entry array and rational magnitude before
  `encodeRequest`, not only typed dimensions. Dimensions alone do not bound an
  arbitrary array's length; a post-encoding length check is too late to justify
  pre-encoding resource bounds.
- Bound malicious JSON nesting, numeric tokens and rational-string payloads
  before the maintained decoder performs expensive parsing/conversion. A small
  deliberately restricted ASCII/no-escape envelope is acceptable if documented;
  no replacement rational parser or tactic fork is justified.
- Reject ambiguous duplicate retained request entries; keep each acquired pair
  fixed in memory, and preserve exact locally generated request matching. No
  response field may select another file, import, executable or fallback.

These controls support finite inert ingestion, not a kernel-work bound or OS
sandbox. The final locally constructed proof remains the mathematical gate.
Findings were sent to author/root before implementation review; source verdict
will follow in this same checkpoint, without an extra test campaign.
