# Growth and discovery: preserve cheap options before buying adoption

2026-10-24. `growth_user_economics`; source/theory only. No code, runtime,
experiment, download, service, state change or Git operation. This note reuses
the existing growth models, crowding counterexample and search analysis; it
does not present another composition theorem or synthetic search benchmark.

## Decision

**Keep ordinary specialist discovery ahead of optional exact export, and make
the adoption route an explicit local decision. Do not build a new ranker,
plural HTTP client or generic compatibility/cost oracle now.** Existing search,
owner configuration and exact-evidence interfaces can express that decision.
Their present limitations must remain visible rather than being described as
solved worldwide discovery.

The concrete design tension is that demand-triggered export saves production
cost, while our exact-evidence index can describe only already materialized
exports. Requiring every potentially useful theorem to enter that index before
anyone can discover it recreates the expensive up-front publication obligation.
Ordinary package/formal-search hints break this cycle. They remain hints until
selected mathematics is acquired and checked; they must not be given invented
proof-derived identities. Searchable opportunity and accepted evidence are
different layers, not competing definitions of mathematical truth.

The strongest immediate payoff remains making the already selected usable
interchange route deployable. A new search mechanism needs a demonstrated
consumer failure that existing approved tools cannot remedy at lower cost.

## Can more mathematics make the system worse?

More *available options* need not reduce the ideal capability of an agent that
can retain its old methods and ignore additions. That elementary observation
does not establish monotonic performance for an actual search policy. Its
candidate order, budget, working context and service contention can all change.

In particular, a larger corpus can impose:

- More candidates before an applicable result, even with no malicious sender.
- More incompatible library versions or independently represented definitions.
- More successful type matches whose remaining hypotheses are expensive.
- Larger first-use dependency closures, or unavailable exporters/retained data.
- More frontend reconstruction than ordinary package approval would require.
- Provider work and waiting time hidden by a small returned result count.

The existing v3 crowding fixture already shows candidate starvation: renamed
reflexivity types occupy the bounded prefix and conceal a different type. It
does **not** show lost mathematical capability or slower research, because the
consumer may have another cheap proof. Do not rerun it or upgrade its claim.
Likewise, diversity filters can avoid some duplicate slots but do not establish
applicability, premise discharge or useful growth.

The optional local-first portfolio argument is already retained elsewhere.
Its lesson here is architectural: additional knowledge must not force import,
export, proof replay or search before an unchanged local route can run. The
bounded-downside argument requires genuinely reserved/preemptible resources;
shared memory pressure, CPU contention, storage and provider costs do not vanish.
An existing endpoint client without hard aggregate bounds does not implement
that stronger guarantee merely because its returned list is short.

## The small pre-adoption decision that actually matters

Before starting expensive conversion or adopting foreign code, distinguish the
following routes. This is a local workflow rule, not a new wire protocol or a
mathematical acceptance policy.

| Available route | Rational next action | What must not be inferred |
|---|---|---|
| Already approved, compatible ordinary project | Search and use its existing APIs; export selected outputs only if interchange is useful | An inert round trip is necessary for every local use |
| Retained inert evidence, supported receiver base and usable interface | Select bounded intake and then needed local realization/application | Intake success guarantees notation, tactics or affordable materialization |
| Unapproved foreign package, no retained evidence | Locate an already authorized producer able to export, or leave this route unavailable | The recipient must run the foreign package to obtain safety from it |
| Incomplete source/version/foundation or dependency information | Report unresolved; investigate only within a chosen local allowance, or use another route | Unknown means false mathematics or proven incompatibility |
| A known unsupported boundary of the chosen tool/profile | Decline this route or explicitly select another supported route | No implementation could ever use the mathematics |

One declaration may have several routes. The same theorem name at two providers
is not one globally identified object. A locally approved project is not a
mathematical warrant for every imported axiom, and an exact evidence commitment
does not establish executable-package safety or practical usability.

For a selected candidate the useful preflight questions are only:

1. Which asserted corpus, source locator, revision and toolchain supplied it?
2. Which precise statement/definitions does the consumer actually need?
3. Is there a currently supported ordinary or inert adoption route, and who can
   perform its executable producer work under their own approval?
4. Which exact receiver context and supported profiles will check/use it?
5. What costs are known before execution, which are bounded only by refusal,
   and which remain unknown?

This can be recorded in ordinary local notes/configuration today. A single
`compatible=true` flag would conceal the relevant distinctions. The useful
output is **route available / unavailable / unresolved**, with reasons and
cost limits, not a claim to decide semantic equivalence or future proof search.

Toolchain/version/source declarations are advisory until appropriately bound.
Even a pinned repository revision need not identify dirty builds, resolved
dependencies or every compiled plugin. Exact helper profiles and local project
approval are different assurances. Current producer configuration hashes bind
selected configuration bytes, not an entire transitive executable environment.

## Why another automatic preflight is not yet selected

PREEXPORT-TOOLS establishes that Loogle already returns useful ordinary formal
hints, and existing clients support configurable endpoints. Its JSON lacks
package/revision binding, query echo and verified corpus coverage. A configured
corpus descriptor supplies an operator assertion, not the missing proof.

PREEXPORT-CODE-GAP proposed a bounded plural adapter; PREEXPORT-SELECTION
explicitly deferred it. This note agrees. A new parser could preserve metadata
and refuse malformed responses, but could not determine the absent information
or make providers cover useful mathematics. It also would not predict the
consumer's definition conversion, proof adaptation or dependency-closure cost.

Current native-first APIs already separate `produce-baseline`, inert
`intake-baseline`, optional `export-module`, and ordinary `contribute`.
Source inspection therefore identifies **no new mandatory software boundary**
for the route decision above. The selected native clean-source distribution
repair is a real deployment obstruction and is owned by root, not this note.

If automation later matters, the smallest justified addition is a local
advisory report that preserves supplied facts, distinguishes absent information,
and selects among these existing operations. It must not fetch/build/import
merely to fill its fields, invent globally meaningful names, or bypass existing
approval and mathematical gates. Do not implement even that report until its
absence causes a named workflow to repeat avoidable expensive work.

## What this does and does not establish at huge scale

Ordinary specialist providers allow an agent to search a selected finite corpus
without each agent downloading all mathematics. They are a reasonable practical
fallback, not a demonstrated solution to huge-scale useful discovery.

Conditional corpus-size independence requires all of the following:

- The query can select a bounded number of relevant corpus/cell providers from
  information available before its answer is known.
- Those providers cover the promised search scope and bound their local index
  work; additional unrelated corpora need not be contacted.
- Selected providers have adequate capacity/retention and reachable replicas.
- Failed attempts, provider selection, returned candidates, adaptation and
  acquisition fit the original consumer budget rather than resetting it.

These assumptions can hold for stated query classes within a shared formal
ecosystem. They are not guaranteed for an unfamiliar method whose useful
connection requires a new representation bridge. Local known symbols and
approved package context can be strong discriminants, but routing only by
them can miss cross-representation or cross-field work. That miss is an honest
scope limit, not a reason to certify all mathematics in advance.

The earlier SHARDED-DISCOVERY-DECISION already identifies the stronger remaining
network obligation: admitted selective placement, query-directed coverage and
bounded selected-anchor work. A DHT, extra hash partitions or more providers
does not supply this invariant. If no searchable feature separates one useful
candidate among indistinguishable records, a finite query budget can miss it.
Provider response caps guarantee neither recall nor bounded server computation;
the pinned Loogle implementation sorts before truncation.

Thus neither this local workflow nor a finished native build closes scalable
discovery. The outstanding task is to justify a useful query/corpus class and
its routing/coverage assumptions, not to repeat a generic transport benchmark.

## Cheapest discriminator and stopping condition

No new theorem run or external search request is needed for this decision.
The retained `stable_compose` receiver case already has a real candidate,
exact evidence, dependency acquisition and successful downstream use. The
`mapFour` project return separately supplies ordinary use and reusable return.
Do not combine their different profiles into a new end-to-end qualification.

For the route decision, compare their actual input requirements with the pinned
ordinary-search JSON: a name/type/module hint alone does not furnish an exact
bundle, producer approval or receiver-context fit. Existing public operations
accept explicitly supplied evidence/configuration rather than treating that
hint as admission. This source-level discriminator establishes the missing
*information*, but does not establish a missing new *mechanism*: an operator
can already select the route and provide the required inputs.

Reopen implementation only when one named supported workflow has useful
independently served content and cannot cheaply resolve or retain that route
through existing configuration/tools. Identify the unavailable field or action,
the decision it changes, and the saved cost before selecting a component.
If the obstacle is absent indexed content, a missing authorized exporter,
oversized closure or unusable frontend metadata, a new client is not its cure.

The release claim supported here is narrow but meaningful: the architecture
can expose remote reusable mathematics without forcing every recipient to
approve producer code or every producer to export everything in advance.
Net useful growth still requires successful bounded discovery, actual supported
use and full-cost benefit in a stated domain. Those conditions are not waived
by the absence of a user's external Lean project or by more internal examples.
