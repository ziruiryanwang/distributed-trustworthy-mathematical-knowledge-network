# Product delta: keep the mathematical work in its ordinary package

2026-10-24. Source-only decision support by growth_product_selection. No product
edits, runtime, native build, package assembly, state opening or Git mutation.
Root selects subsequent implementation. This note does not qualify final v5.

## Decision

The primary approved-package loop should be:

1. Discover a package/result through ordinary repositories or replaceable indexes.
2. Explicitly approve any executable project/tooling used locally; resolve its
   ordinary Lean dependency/toolchain compatibility using existing package tools.
3. Investigate, adapt and prove in that ordinary project, preserving its notation,
   class instances and tactics. Draft results are not independently admitted facts.
4. Select completed declarations, use existing `produce-baseline`, then independently
   `intake-baseline` their inert proof data under a receiver's own policy and parent.
5. Publish the ordinary package/delta and optionally its exact checked-evidence
   targets through existing sharing/peer facilities. Recipients choose their route.

**Generated modules are not required in this loop.** They remain useful when a
receiver does not approve an unfamiliar executable environment and wants supported
inert results made usable locally. Nor does the loop require the failed original-
reference registration path. This distinction removes an unnecessary architectural
prerequisite; it does not repair either optional path or discard its evidence.

The next justified software increment is a **clean reusable file-assembly recipe
for the already-reviewed native facade**, not another checker, applicability engine,
preflight schema or growth experiment. The actual producer recipe still depends on
an historical reference assembly containing parked commands and unrelated helper
roles. The clean facade currently has no assembly recipe at all. Closing this small
gap yields a coherent supported artifact while leaving the new upstream-validation
decision separable. Merely writing another guide would leave that gap unchanged.

The intake manifest is a bundle census, not a statement that every claim in
`PRODUCTION.json` is true. Consumers must use actual admitted bindings/evidence
for target correspondence. Existing publication checks can enforce that boundary.
An intake success does not register or bless the original `.olean`, executable
metadata or a mutable repository revision. It warrants admitted mathematics only.

Both expensive import metadata and ordinary source execution remain locally
approved activities. Post-hoc checking prevents a false final mathematical warrant;
it cannot undo malicious code execution, leaked data or wasted exploratory work.
When early mathematical assurance is useful, validate selected inputs first.
There is no mandate to defer every check until publication.

This is not an argument that packaging itself proves useful growth. It is the
smallest remaining software investment needed to expose the already-justified

## Costs, growth relevance and remaining limits

Avoiding obligatory generated-module reconstruction removes its conversion,
public-view, metadata-loss and narrow materialization-fit prerequisites from the
approved-package loop. It does **not** remove independent validation: current
production still scans its imported environment and exports selected full closure
outside the fixed seed; intake still parses/plans and checks missing mathematics.
The 8,192-unit/64 MiB produced-bundle bounds remain. This is not arbitrary-library
compatibility, ancestry-free cold checking, or a whole-network scalability proof.

Package acquisition, execution approval, version adaptation, failed exploration,
selected export, receiver checking, discovery, custody and upkeep all belong in
the full cost. Ordinary Git/packages can use precisely these useful adapters.
No unique bespoke-network advantage is needed or established. A consumer's new
bridge can return as normal checked Lean declarations without converting its
entire workflow into a new ecosystem; whether it benefits others remains a
conditional demand/compatibility question, not a theorem-count claim.

The finite recipe is justified by removed integration/dependency friction and
small source scope. It is not permission to spend another cycle polishing every
optional branch. After this coherent artifact boundary, return to the selected
growth hypothesis and its concrete decision-changing evidence.
