# Realistic growth case: reuse mathematics without approving its producer's code

2026-10-24. Bounded source/theory challenge by `growth_user_economics`.
No code, runtime, download, dependency survey, state or Git mutation. The parallel
SUPPORTED-METHOD-PATH investigation owns detailed current API/evidence mapping.

## Decision

The strongest present product case is **separating mathematical reuse from
execution approval**. A contributor works in its rich ordinary Lean package.
A recipient wants a small reusable method, law or adaptation, but does not want
to authorize that package's plugins, initializers or solver machinery on its own
computer. Selected inert declarations, independently checked and locally usable,
can cross that boundary. This is a practical capability, not a claim that our
network discovers better mathematics than ordinary Lean users.

Keep the ordinary approved-package route for rich authoring. Keep inert selected
interchange for recipients whose already approved infrastructure can use those
declarations. Do not try to make either route replace the other universally.
The important distinction is not "Git versus commons": Git can distribute the
same artifacts, and should receive equal credit when coupled to the same checking
and use machinery. The software's useful contribution is making that boundary
operable, independently warranted and reusable, not owning the transport.

## One concrete friction removed

The current native-first contract separates owner-free `produce-baseline` from
receiver `intake-baseline`; selected outputs can include useful adaptations, not
just terminal conclusions. Producer-side compiled-project loading requires local
execution approval. The receiver's mathematical intake consumes inert evidence;
it does not endorse the producer's binaries or restore its frontend extensions.
Eligible checked declarations can be locally realized and used in an ordinary
project, whose new proof returns for independent checking.

For the stated workflow, this can remove the recipient's obligation to execute
or separately approve the producer's entire executable authoring environment.
It does **not** remove the mathematical dependencies of the selected outputs,
their first validation cost, actual demanded semantics, or local proof work.
The producer still pays to generate/export evidence; custody and discovery still
cost resources. The operational trust boundary has moved to the receiver's
approved checker/decoder, not vanished.

Crucially, if the recipient has to run the exporter against an unapproved foreign
package itself, the proposed approval saving has not been realized. Export must
already have happened at an authorized producer or other suitably authorized
party. A provider disappearing is harmless only for artifacts actually retained
by another available holder; keeping a search hint or URL is insufficient.

This is a more defensible claim than assigning speculative hours to code review
or assuming every imported library contains malicious code. The mechanism removes
a particular required action under a reasonable policy. Whether its remaining
costs are lower than other allowed routes is a separate question.

## Assumptions that make the case useful rather than merely possible

- The recipient already has a warranted, compatible local base and approved
  authoring/checking support. Its adoption cost is real and remains in the history.
- The selected method and required definitions fit the supported declaration,
  size, foundation and resource profiles. All actual premises are closed by
  warranted local mathematics or newly checked evidence.
- The method can be applied with the recipient's existing notation/classes/tools,
  explicit theorem application, or a modest approved local adaptation. A constant
  that checks but cannot be used through the supported interface is insufficient.
- The method has an actual supported application: domain premises can be proved,
  the conclusion is precisely bound to the local statement, and the resulting
  proof is checked. Reusing it at another input need not contact the old solver.
- When a consumer develops a reusable intermediate, it can choose to return that
  named declaration through the same public contribution path. Producing such a
  result is new local work, not an automatic consequence of downloading a method.
- Selected evidence and semantics remain obtainable through the stated custody
  horizon. Neither truth nor a content ID promises continued availability.

No human intention, compulsory global agenda, provider reputation or popularity
score enters mathematical acceptance. Local selection and execution approval
are operational decisions, not votes on whether a theorem is valid.

## Counterexamples and fair alternatives

**Rich API counterexample.** A consumer needs a newly imported class hierarchy,
structure elaboration, coercions, custom notation and a specialized tactic.
Kernel declarations alone do not restore those facilities. Reconstructing them
individually may cost more than approving/building the ordinary package and may
not reproduce its behavior. The inert lane must decline that automatic promise;
do not use it to justify a general metadata-replay subsystem.

**Cheap local alternative.** The consumer's current tactics already establish
the desired statements cheaply. Search, closure acquisition and independent
adoption can then be extra work. Keep local use; do not count a forced citation
to the shared method as evidence that sharing helped.

**Other permitted delivery.** An ordinary package may already include portable
proof evidence, or a suitable source-validation/isolation route may be available.
Allow those alternatives the same base, caches, method and assurance policy.
If our path is the same mechanism under a different transport, claim integration
and availability benefits only where established, not unique mathematical power.

**Oversized first use.** A small theorem can require a huge missing dependency
closure or expensive conversion. Warm reuse does not make that cold acquisition
cheap. The earlier blanket cold-ancestry obligation is not solved by this case.
Requested ancestry-free delivery must retain its explicit evidence requirement;
ordinary closure checking cannot silently substitute for it.

## What this justifies about growth

Under the displayed conditions, previously remote mathematics becomes a locally
warranted reusable input under a stricter execution policy. Subsequent supported
applications and returned adaptations provide a constructive path for reciprocal
accumulation. That is a **conditional useful-capability case** for the product.
Its plausibility does not require an outside recruit or a new solver benchmark.

It is not proof that the method is new to humanity, that users will choose it,
that total scientific output increases, or that a fixed budget yields a measured
speedup. The full-cost comparison must retain export, discovery and failures,
first adoption, local application, return validation, retention and maintenance.
Existing ordinary caches and sharing receive identical credit. No new economic
theorem is needed: the earlier comparison and investment models already state
the relevant conditions. This note identifies the concrete removable obligation.

The reasoning also does not release an unfinished product. Current software must
actually realize the admitted-interface-to-local-application-and-return path.
The parallel source/evidence map determines which parts have already been shown;
this note does not promote a README promise to execution evidence.

## Stop work that does not serve this case

Do not build another LP backend, region protocol, universal method schema,
metadata-replay engine, special global usefulness registry or mandatory expensive
certificate merely to supply a more impressive growth story. Do not repeat the
existing method-composition examples to increase a result count. The general
method shape is already ordinary Lean mathematics; a domain illustration does
not create a new interchange requirement.

**One next practical responsibility:** make the recipient's supported
**no-producer-code mathematical reuse path** explicit and complete, including
local use and return, using the already selected public software. The mapping
must expose any point where a recipient must instead approve foreign execution,
where admission fails to produce a usable interface, or where hidden state edits
are required. Repair one such actual obstruction if found. If existing APIs and
retained evidence already cover the path, document that exact route and stop
inventing a new "growth component"; advance the remaining whole-release risks.

This is not an instruction to run a new campaign. Reuse authoritative retained
evidence for unchanged links. Only a genuinely changed, uncertain boundary can
justify a small new execution. No amount of auxiliary growth theory substitutes
for general-cold assurance, scalable useful discovery, sustainable independent
operation and deployment obligations still open in the full v5 goal.
