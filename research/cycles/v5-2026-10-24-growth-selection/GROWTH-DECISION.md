# Put validation at the mathematical boundary, not every research step

2026-10-24. Root architecture decision, pending independent challenge. This
complements existing growth arguments; it does not claim measured uptake,
exponential novelty, or a final deployable v5.

## Concrete change to the default workflow

Work normally in locally approved, versioned Lean projects, including their
notation, instances and tactics. Search and try external mathematics there.
When selected completed work is to receive an independent warrant, export its
actual formal outputs and check the required proof data under the receiver's
policy. Share ordinary packages and any selected inert evidence through
replaceable providers. Another agent can extend that work in its own project.

This is different from requiring every candidate to pass through
`intake -> generated module -> special authoring -> small returned delta` before
it can participate in local investigation. That route remains useful where
execution of the publisher's package is not approved; it is not the universal
workflow. Existing produce-baseline/intake-baseline already implement the
selected-output boundary for their supported Lean 4.34 fragment.

Two permissions remain separate throughout: allowing code to run, and having
mathematical grounds to rely on a result. An approved package can still contain
false assumptions or compiler bugs. The final independent check must reject
unsupported mathematics regardless of how plausible the local investigation was.
No automatic source execution or new hostile-source sandbox is introduced here.
The approved execution must preserve the checker, adopted basis/policy, protected
accepted state and the evidence selected for validation. Same-user malicious code
can tamper with those resources; process budgets do not prevent it. Thus this
workflow currently assumes approved local execution that preserves that boundary,
or a separately justified isolation boundary. Independent checking cannot defend
itself after its implementation or trusted inputs have been compromised.

## Conditional endpoint-warrant theorem

Fix a receiver policy P, an actually warranted base K, and selected formal outputs
T represented in immutable evidence E. Let D be the exact supported declaration
closure required to interpret and justify T above K, including definitions,
indivisible declaration groups, allowed assumptions and relevant primitive
semantics. Suppose the receiver's checking operation:

1. Binds the actual E, selected T, P and K; no package status supplies acceptance.
2. Reconstructs D through the adopted checking rules, refusing unresolved or
   unsupported dependencies and prohibited assumptions.
3. Ties the warranted formal output records to those actually checked and commits
   only after success and clean closure.

Then the accepted outputs are warranted under P and K independently of whether
the research process that proposed E was sound. The process may have searched
with unchecked conjectures, used untrusted advisory indexes, or tried false
intermediate candidates. None is an accepted premise unless covered by the
actual checking argument.

**Proof.** Apply the checker's sound-extension property to the actual finite
dependency construction above K. Each required non-base declaration is established
by an accepted inference/group construction; leaves are exactly the permitted
base/assumptions. Thus T is derivable under P and K. The history of discovery is
not a premise in this induction. Exact output binding prevents substituting a
different unverified claim after the check. This is conditional on checker and
binding correctness, not a new proof of those implementations.
In the existing intake API, target correspondence must come from actual admitted
bindings/evidence, not the producer's PRODUCTION target list alone. An output
omitted from the checked domain does not inherit a warrant from bundle success.

The theorem concerns the returned formal statements. It does not endorse a
separately supplied .olean, the whole originating repository, its original proof
witness under a different comparison rule, or an informal description. An
unwarranted input does not become a safe compiled import merely because one of
its consumers' outputs was independently checked. No human-intention predicate
is needed to state this boundary.

## Why this can help growth, and where it does not

It permits **speculative combination followed by strict acceptance**. Agents can
try mathematics using existing rich tools without paying independent adoption
and interface reconstruction for every abandoned branch. Successful consumer
adaptations can be offered as ordinary bridge/adapter declarations, not only as
terminal theorems, so later consumers need not repeat the same integration work.
The latter uses the existing method/bridge theory; no new ontology is required.

For a fixed comparable investigation history, partition incremental whole-cost
differences into:

- A: prevalidation, interface reconstruction and duplicate processing avoided
  by the endpoint route, including abandoned candidates;
- F: any extra final closure export/checking, binding and custody cost it incurs;
- W: any extra wasted local search/adaptation caused by delaying detection of
  false or incompatible premises;
- S: net additional service, failure and maintenance cost.

Relative saving is A - F - W - S, by accounting, not by a proof-search lower
bound. Existing ordinary packages may already use precisely this route; they
receive the same credit. No need to assign eager checking to the comparator.
This decomposition identifies the actionable change: eliminate compulsory
generated-module conversion and prevalidation, while retain early inspection
or checking when it cheaply prevents expensive failed investigations.

There is no universal best validation schedule. False premises can make W huge;
final cold closure checking can make F huge; an already warranted local base can
make both routes almost identical. Exact selected evidence can be reused rather
than regenerated. Intermediate checking is an optional investment at high-risk
or high-reuse boundaries, not a rule that every new line must be independently
exported and admitted. All work remains locally bounded; accounting failures do
not grant a fresh allowance.

This is a practical enabling argument, not observed causal growth. A useful
result can create many affordable applications, but extra theorem counts,
citations or valid wrappers are not evidence for new resource-bounded capability.
No perpetual positive-growth law follows from endpoint checking.

## Scale and decentralization

Each participant selects its own finite project, evidence, accepted base and
service providers. No node needs a ledger of every research action, proof attempt
or theorem in the world. Discovery hints are advisory; exact locators, retention
and independent checking are separate services. No provider becomes mathematical
authority merely by storing or ranking work.

Cost depends on the selected environment and missing supported closure, not a
mandatory scan of the global corpus. That is a locality property, **not cold
ancestry-free verification**. Current producer export still walks a private
environment and emits full selected closure outside its fixed seed. A very large
relevant closure can exceed this PC or the supported bounds. Ordinary warm native
reuse, independent local-frontier checking, explicit base trust and optional
succinct certificates have different assurance/cost contracts; none is silently
substituted for another. This decision does not close the remaining scale gate.

## Software consequence selected now

The product map identifies an actual, small delivery gap: the latest producer
package's assembler depends on a historical reference assembly and exposes parked
commands. Assemble the already reviewed native facade from the pinned preview
payloads plus only the producer/intake roles. Make source/output/runtime paths
explicit, retain exact pins and leave all old installations/state untouched.

This removes a concrete dependency from distributing the useful optional adapter.
It is justified by the simpler selected-output workflow, not by sunk costs or a
need to repeat the six-unit fixture. It does not select a native rebuild, a new
checker, upstream migration, remote service, benchmark or public release.

The remaining growth hypothesis is chiefly about **affordable usable interfaces
and consumer-created adapters**. Before further protocol work, ask which actual
application is blocked and whether ordinary Lean already supplies its remedy.
BRIDGE-INVESTMENT and PRODUCT-DELTA record independent focused checks; their
conclusions can reject speculative additions. Full v5 still requires deployable
service, security, recovery, supported platform and independent-use evidence.

## Adopted decision and bounded implementation outcome

Root read/adopts DECISION-REVIEW's conditional approval, including preserving the
validating authority and binding every target to actual receiver evidence. Root
also read/adopts BRIDGE-INVESTMENT and PRODUCT-DELTA. They reject a new bridge
miner, registry, automatic generalizer or preflight oracle: existing ordinary
packages and multi-target export supply the selected function.

The finite distribution change is implemented. One selected file-only check
assembled 141 payloads and loaded all 111 profiled roles after the intended
wrong-map refusal, with clean closure. It used 7.1383519 wall seconds and 3.9375
known inclusive CPU seconds. Saved-evidence review is in ASSEMBLY-OUTCOME; no
new native, theorem, admission, network or growth experiment was performed.
Old installations, accepted state, anchors and failures remain unchanged.

Do not follow this by another packaging or certificate campaign. The remaining
growth-relevant product question is how a consumer finds an unfamiliar compatible
ordinary package/adapter before paying for materialization, using replaceable
providers and bounded search. Ordinary source discovery is allowed; the current
exact evidence index must not be mislabeled as a pre-export package index.
Any next change must identify an actual gap not already supplied adequately by
ordinary package/search tools. This is a decision boundary, not authorization for
another registry, format, test campaign or unrestricted external service.
