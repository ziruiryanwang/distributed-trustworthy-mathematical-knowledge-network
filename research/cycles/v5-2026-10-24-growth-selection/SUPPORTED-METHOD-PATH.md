## Decision

**No new method-shaped interchange mechanism is needed.** The existing ordinary
path can carry a definition, a universally quantified applicability theorem and
a new consumer theorem. It does not constrain the theorem to one numerical input
or require a live solver. Existing retained execution evidence already exercises
parametric acquisition, different arguments/types, independent local checking and
return of a reusable consequence. Do not manufacture another simple theorem or
repeat those unchanged controls to establish the same capability.

This does not turn the illustrative methods into demonstrated research speedups,
the optional LP source into a supported application, or all Lean packages into
compatible imports. The highest-payoff concrete software obstruction found here
is **a portable source-build route for the current native-first distribution**,
not another mathematical object or transport format.

## Why the general method/domain shape adds no core API requirement

For a supported Lean declaration

    method : forall x, Domain x -> Correct x (run x),

`run`, `Domain` and `Correct` are ordinary definitions; `method` is an ordinary
theorem. Its application is an ordinary proof term with real local parameters and
premises. The consumer can publish a named domain lemma, bridge or consequence as
another ordinary declaration. Names/types and exact evidence bindings matter;
there is no need to add a human-intention field or certify a method's importance.

Current `ordinary_native_package/owner.py:285-319` reads the caller's selected
target-name list and passes it to the existing `produce_bundle`; no one-endpoint
or concrete-input restriction is introduced. Its `:524-539` baseline-intake branch
delegates to the existing independent receiver. `:543-559` retains explicit
local module export, and `:586-593` retains ordinary source contribution and
actual admission. These are semantic dispatches, not a new pass obtained by this
inspection. The facade's previous source-equivalence and file-assembly audits
remain the evidence for its consolidation.

Thus the minimal method workflow is already expressible: retain compatible
ordinary definitions and a method theorem, prove current premises, apply it, and
select useful named returned declarations. It still must fit actual declaration,
closure, resource, foundation, version and authoring-policy limits. The explicit
`mapFour` return is a reusable mathematical transport theorem; its easy proof
does not justify a performance story. The two-parameter LP theorem is a separate
possible application, not missing generic API semantics.

## One concrete high-payoff obstruction: current source distribution

The current native-first package has 141 payloads and 111 helper roles. Its
file-only assembly is real, but its current source recipe cannot be reconstructed
merely by composing existing portable commands:

- `ordinary_native_package/assemble.py:22-28` pins one exact historical preview
  PROFILE/ASSEMBLY/installation and the 809,472-byte BaselineExporter hash.
  `inspect_inputs` (`:147-205`) requires those identities and the retained
  predecessor census. It is intentionally not a general source-build assembler.
- `ordinary_preview_package/build.py` supplies a portable 134-payload source
  recipe; its `NATIVE` list does not include BaselineExporter, and its final
  profile/output census remains the preview distribution. Fresh build hashes are
  not promised equal to the retained assembly's hashes.
- `ordinary_baseline/build_native.py` compiles the exporter only through a
  fixed experimental ROOT/shared-object/runtime-template route. Successors
  `build_native02/03/04.py` additionally require exporter build01 provenance and
  preserved object bytes. They are finite experiment adapters, not portable
  clean-source release recipes.
- The current native source map declares BaselineExporter as a retained payload,
  not a generated target. No `ordinary_native_package/build.py` exists in the
  inspected source inventory. The distribution's current pointer explicitly
  distinguishes file assembly from a clean-source compiler build.

This is a genuine user/deployment obstruction: a new operator should not need
this investigation's private experiment directories to obtain the current
recommended software. Shipping only the old portable recipe would omit the
current native-first producer path rather than reproduce it.

The repair need not change mathematical acceptance. The producer's
`baseline_production.py:85-117` already resolves the executable's exact bytes
from the approved package profile; `baseline_worker.py:63-105` receives and
checks that selected size/hash. Neither requires the historical exporter hash.
The missing responsibility is a successor portable build/map that compiles
BaselineExporter from its actual source plus the existing shared modules, adds
the four baseline Python roles and current facade, and generates the new profile
from those actual outputs. Do not compile unused reference/artifact modules or
relax the frozen assembler's pins. Preserve its prior package/evidence.

Source-map and build-recipe review can resolve this in principle before any
compilation. A new recipe is not by itself proof of clean-build success,
bit-for-bit reproducibility, supported ordinary LP use or public release.
