# Growth value: preserve the recipient's working mathematical environment

2026-10-24. `growth_value_challenge`; bounded source/theory decision. No product
change, experiment, dependency installation, network operation or Git mutation.

## Decision

**Keep the existing conditional growth thesis; stop seeking a stronger abstract
speedup theorem. Make same-base, theorem-only extension of an existing ordinary
Lean project the next concrete growth capability target.** This is narrower than
general library migration or frontend recreation. It need not revive the failed
`contribute-reference` workflow or commission another reference campaign.

The material risk is not a missing philosophy or a missing universal proof-search
lower bound. It is that our preferred safe-transfer lane can require recipients
to leave the mathematical environment in which they already work. That can defeat
the point of transferring a small useful result, even when its mathematics checks.

## What the existing argument already justifies

GROWTH-COMPARATOR-CHALLENGE already proves constructive capability delivery and
separates it from comparative productivity. Adopt that result, rather than give
the same algebra a new title. The substantive product claim is:

> Independently funded, compatible mathematical work can become a recipient's
> reusable warranted input, without repeating its discovery or approving its
> producer's executable environment, when exact intake and local use fit the
> recipient's resource and compatibility envelope.

"Without repeating its discovery" describes the supplied execution path, not
a lower bound on another agent's ingenuity. The resulting method can support
changed arguments and returned reusable consequences; SUPPORTED-METHOD-PATH
contains scoped evidence for those operations. It does not establish broad
speedup, novelty, or expected uptake. No further theorem is needed to justify
building that capability well. There is still a real engineering/assurance bar.

An **isolated optimized library** lacks genuinely later remote information but
keeps its own tactics, generalization and caches. Transfer may improve its options;
its actual productivity improvement needs a specified policy/workload comparison.
An **ordinary sharing stack** gets the same available remote artifacts, indexes,
mirrors and checking tools when it actually has them. Our software need not beat
a simulator containing those same mechanisms. Its contribution can be supplying
the missing interoperable implementation. Neither comparator gets a handicapped
solver or fictitious approval/review delay.

Thus the evidence standard should reject unsupported acceleration claims, not
require an algorithmic separation theorem before shipping a useful importer.
Conversely, an importer pass does not complete worldwide discovery, availability,
hostile-input assurance, practical compatibility or the full v5 release.

## The surviving concrete friction

Consider a recipient already using an approved, locally warranted base P. An
independent contributor has a theorem-only extension e over **that same exact
base**. The recipient wants to apply e in its present project, retaining its own
notation, classes and tactics, without executing the contributor's extensions.
No arbitrary cross-version interpretation or new producer frontend is required.

This is a reasonable target class, not an assertion about its market prevalence
or an external user's supplied project. The user has no project to nominate.
Unlike inventing a hard theorem, choosing this class exposes a source-level
interface obligation that ordinary collaborative library use naturally creates.

Current source does not generally implement that target:

- `ordinary_module_anchor/OrdinaryModule04.lean:639-681` restores Init or registered
  generated anchors, not an arbitrary existing original-project base.
- `classifyUnits` permits the exact installed-singleton-theorem case, but refuses
  installed non-theorem/group collisions. Intake supports more than realization.
- NATIVE-FIRST-WORKFLOW-SELECTION explicitly says not to co-import the original
  library's duplicate definitions with generated replacements.
- GROWTH-REUSE-FIDELITY establishes that regenerating the mathematical base does
  not regenerate its original authoring metadata. That is not a cosmetic loss.

These are existing findings; the new priority judgment is that their combination
can block the *most economical recipient workflow*, not merely an optional rich
API luxury. It is particularly relevant to a very large network: most useful
transfers should not require each recipient to rebuild its project around a
second synthetic copy of a widely shared base.

## Why the simpler alternatives do not universally close this case

Approved ordinary producer packages remain the right rich-authoring route. They
also allow independent checking of completed exported outputs. But the recipient
approving that new producer package gives up the selected no-producer-code
property; endpoint validation cannot retroactively make execution unneeded.

A generated module in a fresh project is useful and already supported in a
bounded region. It is not evidence of seamless reuse inside the recipient's
existing P project. Recreating P's metadata or renaming its definitions can cost
more than the desired theorem application and may change the interface.

A named checked bridge helps when the recipient can import both endpoints and
prove their relation. It cannot by itself resolve an import/name collision that
prevents the two environments from coexisting. An individually written local
proof may instead be best; retain that choice without claiming every transfer
requires this capability.

The remedy is not to support all original library behavior. It is to preserve
the *recipient's already approved* behavior while installing a small inert delta.

## Smallest architecture consequence

Use an explicit **same-base thin-delta** contract as the target, not a new format:

1. Bind the recipient's approved base artifacts and their exact independently
   warranted mathematical interpretation. Execution approval alone is not a
   warrant; matching printed names or theorem signatures is not enough.
2. Require the incoming delta's external references to match that interpretation
   with the supported declaration/group/universe semantics. Reject incompatible
   bases; do not infer a generic equivalence or hidden proof-erasure theorem.
3. Check the new declarations under those warranted bindings and materialize only
   the delta importing the approved base. Preserve private/public conversion
   obligations and exact output binding. No producer extensions are loaded.
4. Author with the recipient's normal approved project and return complete new
   proofs through existing contribution/extraction/completion when supported.

The induction is the existing checked-extension argument with a real base warrant;
it does not need a new calculus, certificates, usefulness oracle or global agenda.
The original-reference store/matcher/delta sources already address parts of this
contract. Their presence is not execution qualification. Retained continuation02
failed `MODERN_ENVIRONMENT_REQUIRED` in `contribute-reference` after compilation;
the unrun later delta/use stages remain unrun. Do not delete the guard or relabel it.

**Root's next consequential choice should be this exact capability, not general
reference-authoring repair.** Compare the existing registered-reference delta
path plus ordinary project authoring with locally generated explicit proof source
checked in the approved recipient project. The latter must not execute downloaded
producer tactics or substitute artifact approval for the base warrant. Neither
requires the failing special authoring command as a premise. Identify the single
missing interpretation/import boundary of the cheaper viable route before a
successor. No build, fixture, runtime or migration is authorized by this note.

Do not commission another growth essay, easy composition test, ranker, closure
collector or resident checker in its place. If the exact same-base route itself
cannot be made economical, revise the product's intended recipient workflow
explicitly; do not conceal that by treating generated empty projects as universal.

## Scope of this recommendation

The complete-ancestry cold problem and lifetime costs remain. Prioritizing a
warm compatible base does not solve them. There is no proof of positive aggregate
research gain or demand prevalence here. This note selects a practical growth
boundary whose absence can nullify an otherwise sound transfer, using existing
theory and source rather than manufacturing a benchmark or new abstract theorem.
