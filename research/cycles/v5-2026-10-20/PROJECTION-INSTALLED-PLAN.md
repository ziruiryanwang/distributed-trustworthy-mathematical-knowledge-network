## Decision: inspection alone versus one launch

Map and source inspection are sufficient to establish **which exact bytes the
candidate contains**, assuming the separately audited builder/map result. They
do not establish the distinct observed claim that those modules load through
the installed launcher's exact source whitelist at relocated runtime origins.
The component controls use explicit overlays; that bypasses the installed
bootstrap's selection mechanism. A missing or wrong logical source dependency
can therefore pass an overlay test and fail the real installed importer.

If root wants that observed installed-import claim, select **one synchronous,
import-only owner invocation** through the ordinary installed `run` entry.
This is the smallest nonduplicative check. Do not repeat query generation,
projection, workspace creation/reopen, service startup, mathematical owners or
any control suite. Do not rebuild a second package to test imports.

Inspection could close a narrower shipping-map claim without execution, but
must not be described as an actual installed import. No general Python import
equivalence theorem is supplied by this plan.

## Scope, limits and stopping rule

- Use the existing isolated installed interpreter and ordinary `launch ... run`
  path, including its pinned boot/source snapshot and original bounded Job.
  Root's already selected combined installation location is the input; do not
  manufacture a second installation or copy the large runtime for this check.
- Retain a valid explicit `runtime_mode` as required by the `run` launch
  contract. The predecessor's `aggregate` mode is adequate; it only causes
  inert preparation configuration to be materialized here. Supply no
  `runtime_adoption` or `foundation` placeholder and construct no RuntimeProfile,
  trust domain, mathematical issuer, operation grant, client or store.
- The owner is synchronous. Do not create an asyncio event loop, socket,
  listener, location process, native checker, prover or service invocation.
  Ordinary import definitions do not imply any such runtime work.
- Reuse the earlier legal 60-CPU-second / 120-wall-second / 384-MiB /
  four-process launcher envelope unless root selects a smaller justified one.
  Keep the unchanged launcher's required output floor of 64 MiB and 1,024
  entries; the earlier 32-MiB preflight failure must not be repeated. These are
  caps, not expected use or an instruction to reclaim/reserve physical RAM.
- No second adoption, source-control campaign, service publication, new proof,
  trust-domain lifecycle, useful-growth experiment or hardware tuning is part
  of this boundary. Builder/map audit and algorithm evidence remain separate.
- One reviewed launch either supplies the requested installed-origin evidence
  or leaves a concrete saved failure. There is no automatic retry, cap increase
  or substitution of inspected maps for failed execution.

The marginal value is closing a real packaging/import seam at roughly the
cost of a small ordinary startup, while avoiding repeated mathematical and
network experiments. It is not final-v5, scale, search-recall or growth evidence.
