# Growth decision: make the existing capability usable before another cost model

2026-10-20. Source/theory review by `core_growth`; no runtime, native checker,
proof, Git mutation or product change. Canonical workspace guard passed.

## Selected recommendation

**Prioritize a release-owned, non-fixture client constructor. Do not implement
another growth calculator, economic ledger or search-budget scheduler now.**

The construction gap prevents an ordinary local agent from conveniently using
the present discovery, verification, semantic import, authoring and publication
APIs with its own inputs. Closing it advances the real usable software goal
without requiring a new aggregate A proof. It does not discharge the separate
scalable-certification obligation or make the current software a final v5.

Root accepted this ordering. `core_release` owns the constructor design;
`core_growth` will author focused changed-boundary tests only after root names
the exact new files and scope. No runtime follows from this note.

## Smallest useful economics increment, later

Attach accounting to ordinary command finalization rather than create a
parallel economic subsystem:

1. Name the exact target journal and profile, command, input evidence and
   initial cache state. ModuleID alone is insufficient for a same-target
   comparison when evidence/journals differ.
2. Reference the existing closed client report and the exact enclosing
   `DMKN_V5_CLIENT_LAUNCH_RESULT_V1` result. The enclosing Job CPU includes
   nested workers/controllers; their observations are a breakdown, not extra
   additive CPU. An outside wrapper measurement is separate only where its
   process is demonstrably outside the Job.
3. Retain failures and explicit unmeasured startup/finalization tails. Client
   `report()` already labels provider work and DHT wire bytes unknown.
   Submitted input bytes are not physical network bytes; budget reservations
   are not measured consumption.
4. Produce only an operation cost envelope. An ordinary comparison needs a
   matched optimized local/shared route and the same accepted target, cache
   state, horizon and supported algorithm. No such route is currently supplied
   by the client report, so it cannot justify a positive benefit verdict.
5. Preserve upstream certificate production and service/retention costs in the
   full comparison. For a forward action decision a retained artifact can be
   initial state; it cannot silently become free in a from-genesis comparison.

Concrete available sources are `client/workspace_atomic.py:report`,
`client/workspace_evidence.py:report`, `client/launch.py:main` and the historical
binding example `client/actual_resume_owner.py:retained`. Reuse their semantics,
not the fixture-specific prior IDs or costs. Unknown remote costs should remain
unknown unless a declared conservative bound or measured operator record is
provided; an untrusted peer's self-report is not a certified physical cost.

This accounting increment becomes justified when ordinary commands exist and
have real terminal results. Building it first would emit mostly unknown fields
without deciding which software route to fund.

## Minimal validation for the selected constructor

The new test seam should exercise only construction, not repeat admitted
mathematics or the entire reciprocal campaign:

- user-selected profiles/configuration and bounded allowances, with no
  BASE/FIRST/SECOND constants or development-output paths;
- the factory's minimum selected source pin closure, with complete deeper
  installation/source closure still enforced by the unchanged real owners;
- original finite grant/deadline propagation and nested, nonadditive worker
  allowance derivation;
- exact receipt/aggregate/delta owner pairing for the explicitly chosen lane;
- successful ownership transfer versus cleanup after each partial
  construction failure, including a failed cleanup;
- no granting mathematical authority from saved reports, substituted owner
  objects or a convenience configuration field.

Use existing inert test fixtures and the existing runner, not a new framework.
Native/proof invocation is excluded. Source tests cannot qualify real profile
adoption or full public deployment; those remain later genuine boundaries.

## Scope and stop condition

The next useful deliverable is a reviewed ordinary constructor and its focused
tests. Do not add route optimization, a demand predictor, a new usage ledger or
automatic certification. Economic measurements should follow actual ordinary
use and answer a concrete route-choice question. The original full v5 goal,
including scalable warranted reuse and justified useful growth, remains open.
