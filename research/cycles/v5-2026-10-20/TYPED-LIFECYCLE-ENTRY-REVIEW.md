## Source assurance argument

The statement supported here is conditional on the trusted local owner selecting
the actual isolated Windows interpreter, exact entry/profile/configuration,
ordinary stable files and enclosing resource owner. It is not a hostile local
filesystem or interpreter-isolation proof.

1. **Pre-import origin boundary.** The stdlib bootstrap requires Windows and
   isolated/no-site/no-bytecode/nonoptimized execution; checks the entry pin;
   reads all 29 exact producer pins rooted at the explicit source-root; cross-binds
   them to the support runtime pins; and verifies the separate existing operator
   helper. It refuses preloaded product packages. After imports it checks every
   selected module's origin, the declared producer closure and the source pins
   again, restoring the original `sys.path`. The entry is not silently added to
   the stable producer profile. Source hashes authenticate bytes selected by the
   owner, not the truth of arbitrary untrusted source.
2. **Action separation.** The parser offers exactly snapshot and request. The
   snapshot branch requires the explicit actual outer selection, binds its copied
   entry, expanded real `sys.orig_argv`, input/profile hashes and run name, then
   calls existing `prepare` and `snapshot` once. The request branch forbids that
   switch and requires the generic five-role evidence grammar, calls
   `production_request` once and never directly calls `preflight` or `run`.
   The inherited request method performs the one preflight itself. A request's
   future proof output must remain absent before and after report finalization.
3. **Completed-snapshot boundary.** A returned Python object alone is insufficient:
   its canonical bytes must match the saved snapshot `RESULT.json`; the existing
   `N.result_shape` requires actual PASS, matching profile, known closure, exactly
   one host call, zero proof calls and no mathematical admission or binding error.
   Referenced generated pins are collected and rebound. An exception before a
   returned report keeps host-dispatch extent unknown, rather than inventing zero.
4. **Output separation and ownership.** All future outputs have existing ordinary
   parents, are fresh and are pairwise separate from each other, selected inputs,
   stable source and installation. Constructor return changes creation status
   from attempted/unconfirmed to opened. Any returned owner is closed in `finally`;
   failure to close or observe actual closed state prevents PASS. Constructor
   failure is not relabeled confirmed closure. The outer owner remains responsible
   for startup/construction/finalization tails and actual process containment.
5. **No success before final binding.** Success requires an established action
   outcome, no action/closure error, closed owner and rebound source/input/generated
   evidence. Generated requests are saved only afterward. Durable report writing
   and late rebinding can still downgrade to failure. A safely writable
   `OWNER_REPORT.FINALIZATION-FAILED.json` overrides both apparent report and
   generated request; failures to create even that sentinel remain nonzero exit
   and stdout failure. No automatic retry, budget selection or phase transition
   exists. An outer successful completion and absence of overrides are necessary
   adoption conditions, not optional details.

Thus, for these reviewed bytes and assumptions, neither action introduces a
