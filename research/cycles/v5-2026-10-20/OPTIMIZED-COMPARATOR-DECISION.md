# Smallest strong ordinary-library comparator

2026-10-20, `core_growth`. Source/data inspection only; no runtime, new
mathematics, implementation or Git mutation. Canonical guard passed. This
specializes the existing GROWTH-WORKLOAD/GROWTH-CRITICAL-PATH, not another
break-even model.

## Decision: use the existing zero-assumption native DAG path

The smallest credible ordinary shared-library comparator O is **one native
batch check of the complete, deduplicated selected proof DAG**, followed by
the same selected semantic context. Do not make O reprove fusion, flatten a
proof tree, recheck the base for each child, or start three checker processes.

This path already exists in source:

- `aggregate_claims/input.py:encode` permits `claims=[]`, `frontiers=[]`.
- `aggregate_claims/relation.rs:check_reader` checks each supplied module
  witness once, resolves every exact parent against previously checked graph
  nodes, enforces ranks and requires complete target closure.
- The retained aggregate native driver executes that relation in one process.
  Its result still says conditional/not-admission. A trusted same-call owner
  must check the exact pinned executable/input/output and **zero assumptions**
  before assigning local authority; a saved success JSON or aggregate header
  is not a receipt, A evidence or an accepted importer token.

For an empty assumption set, induction over the already enforced topological
graph establishes all members under the adopted foundation/checker assumptions.
There is no recursive cryptographic premise left to discharge. This reuses the
existing mathematical checking relation, not a weaker verifier or new kernel.

## What can presently be claimed

**No positive O-to-V cost margin is established.** There is already contrary
size evidence for this fixture: the complete base witness is 91,311 bytes,
whereas its retained I receipt is 223,594 raw bytes, before the current packet's
hex expansion. This is not a total-cost result, but it rules out citing that
base receipt as a demonstrated proof-byte saving. Shared fusion's algorithmic
merit remains real and equally available to O.

The current service's 75-second retention lifetime is not consumer latency.
Use its actual reader completion time for latency and actual charged service
work/retention for cost; enclosing Job CPU includes its children. A future
genuine A may remove native ancestors, but its entire receiving/production
cost must still beat this O route. A receipt's existence alone changes no sign.

Implement a **bounded local native-closure admission option**, initially at the
owner/comparator seam, using the retained batch checker and exact zero-assumption
binding. Give it a distinct live handle/profile and reuse the existing pure

never weaken the I/A paths or impersonate their handles. The selected native
artifact must match the currently adopted relation/refinements. No new guest,
proof production, corpus or network protocol is needed to establish this seam.

The first selected check should compare these retained exact endpoints and
source-derived operation counts, not run a benchmark campaign. If O is cheaper
for the fixture, retain that result and make ordinary checking an explicit

labeled verification-component comparison rather than claim full read/use.
Larger-than-supported DAGs still need an explicit refusal or real seal: O does
not replace v5's mandatory scalable certified route or its full-cost growth gate.

### Proposed minimal boundary

New package `software/v5/native_closure/`, initially two substantive files:

- `binding.py`: pure bounded output binding, explicitly no authority. Bind the
  native schema/status, exact input digest/length/wire length, adopted profile,
  empty assumptions, member journals/order/count/commitment/max rank, and exact
  requested targets. Zero-claim aggregation has seal height 1; check that fact
  rather than accepting a header with an unexplained recursive claim. Check
  primitive types before coercion, including excluding Boolean-as-integer values.
  The header alone does not commit to the selected target list: bind the original
  exact target J bytes through the same immutable input and checked member table.
  The configured executable's identity is separate from the aggregate image
  field in that input; an arbitrary image field cannot adopt an executable.
- `owner.py`: exact `NativeClosureOwner` and distinct opaque
  `VerifiedNativeMember`; no inheritance from or impersonation of I/A/mixed
  issuers. `check(witnesses, targets, ...)` receives immutable witness bytes and
  exact 184-byte target journals, constructs its own wire with
  `input.encode(claims=[], frontiers=[], ...)`, and calls the adopted executable
  once. No caller-supplied stdout, saved acceptance, frontier, receipt or live
  I/A donor parameter exists. `describe(member)`, `members()` and `close()`
  expose only this owner's local checked membership and accounting.

One initial owner admits one complete closure. It retains the exact checked wire
and member table; a map keyed by the actual token object, not public token fields,
binds each token to one exact J. Multiple J variants may not be silently merged
by ModuleID. Each description revalidates the owner and returns copied data.
Exported witness bytes remain ordinary untrusted proof data at a new recipient.

The controller must verify the local supervisor manifest and source origins,
native/controller/runtime pins, fresh nonoverlapping operation directory and
isolated interpreter conditions. Reserve the input bytes, one operation and
worker allowance **before** launch. Recheck unchanged input and pins after the
supervised child exits, require clean process/Job closure and actual CPU/wall
within the reservation, bind the same-call output, then perform a final live
check before publishing tokens. Any entered failure closes this owner and
revokes all its tokens; no automatic retry, owner recreation or budget renewal.

All phases share one monotonic deadline and controller/input/output allowances.
If called from a wider client operation, the owner inherits that operation's
remaining deadline and charges its original shared acquisition/verification
budget; it does not create fresh allowances per phase. The native checker is
local and makes no network request. These controls are resource supervision
under a trusted owner/installation/OS, not a hostile-code sandbox.

Estimated source scope: about 80–140 lines of binding and 220–320 of owner
mechanics, plus small package glue and focused tests; these are planning ranges,
not an implementation or runtime claim. Prefer one opaque membership type over
copying the full mixed multiverifier session. No frozen production file changes
are required for this component.

## Native semantic-context decision after inspecting the actual public path

**Decision:** a thin, useful native semantic-read primitive is practical; a
drop-in replacement for the existing public reader/authoring client is not a
100-line change. Select the former only as an explicit SDK capability, not as
a timing-only imitation or an allegedly interchangeable `AuthorContext`.

The current semantic reader's final step is
`SemanticReader.finish -> client.import_context -> MixedImportSession.materialize`.
It returns a live `AuthorContext`; the client's `author` then requires that
same client's exact context/session and constructs exact `MixedSourceOperation`.
`MixedOwnerPreparation.author` independently requires that exact operation.
`RuntimeProfile.open_operation` also requires an I owner in atomic mode or an A
owner in other modes and creates `MixedDeltaVerifier`. There is **no existing
public zero-receipt native context path** hidden behind these APIs. Do not
create dummy cryptographic owners, impersonate their tokens or relax their gates.

### Smallest genuinely reusable implementation

One new `native_closure/context.py`, estimated **150–220 substantive lines**,
can expose `NativeContextSession(owner, limits=...)` with one consuming
`materialize(selected_members, batch_bytes, foundation_bytes, foundation_sha)`
and a distinct opaque `NativeContextView`. `view_context(view)` returns a copy
of the same context packet schema; `close()` revokes the view. It does not close
or impersonate the independently owned native verifier.

Use actual `VerifiedNativeMember` tokens from exactly one live
`NativeClosureOwner`; obtain and snapshot their exact J/module/summary through
`describe`, explicitly reject multiple selected J variants of one ModuleID,
and retain the owner/profile/deadline/token identities. Bracket construction
and view reads with that unchanged live owner and its immutable membership
state. Expiry, foreign tokens, changed pins/state or any entered construction
failure must yield no view. Preserve the original owner thread and CPU/deadline
envelope; reserve the single context byte/data suballocation in its enclosing
operation, not a renewable grant per materialization. View inspections must
consume the owner's existing finite inspection allowance.

Accept a bounded canonical byte batch with `openings` and `bodies`, not arbitrary
mutable object graphs. Binding the selected tokens is the only new authority
rule. Before the existing walker, require each opening's exact summary to match
the selected J; each supplied body must be committed by a selected declaration
at its exact universe arity. Enforce duplicate/address/group/body/input limits.
The existing `transport.semantic_staging.preview` shows these validations, but
**is not itself sufficient**: it deliberately accepts inert staged records and
returns a whitelisted demand/cost report without a context packet or live token.
Do not run it first merely to repeat its whole walk.

Call `_context_limits`, `_decode_context_foundation`, and `_build_context`
directly and exactly once, after those owner/commitment checks. No new expression
traversal, mathematical normalization, topological ordering, foundation decoder
or body-demand policy is needed. Preserve a single immutable packet behind the
new view on complete demands; otherwise return a non-authoritative demand report.
Use a native-specific selection-binding domain containing exact selected J,
the native input digest, chosen semantic batch and foundation identity. Do not
reuse a mixed selection binding or claim its receipt/warrant accounting.

### The real import footprint is larger than the new code

Directly importing the pure helpers also imports class definitions transitively:

```text
mixed_claims.imports_atomic
  -> authoring.context -> authoring.imports -> transport.receipt_client
      -> transport clients/providers + custody stores + discovery helpers
  -> I/A/mixed/delta owner class modules and production.producer
```

Source inspection identifies 29 Python leaf modules plus nine existing package
initializers for this retained helper graph; `transport`, `custody`, and
`discovery` are namespace packages, not nonexistent `__init__.py` files. The
runtime-efficient admission overlay additionally imports `admission.pin_phase`.
Pin the **actually selected** graph and namespace search paths, including the
new context source, using the native owner's existing additional-pin facility.
This remains below its 128-pin cap with the small native runtime; it does not
require rebuilding or duplicating the installed runtime. These imports define
classes/functions; importing them does not construct cryptographic owners,
launch a process, open a service or verify receipts. Do not mistake loaded
I/A class definitions for a cryptographic runtime dependency.

Extracting a new common pure module now would require reviewed successor wiring
for both lanes. Copying the walker or reconstructing its module with `exec` is
not a justified shortcut. Reuse the existing bounded helper graph for this
increment and retain the original source pins.

### Endpoint and scope that must remain explicit

This primitive can establish **the same mathematical semantic closure** as the
retained reader: base+target, nine groups, twelve declarations and nine demanded
bodies, with a live native owner and identical foundation/imported descriptors.
Compare canonical mathematical packet fields after removing only lane-specific
selection binding/accounting, not merely matching the four counts. A distinct
`NATIVE_SEMANTIC_READY` status is appropriate; saved packet data remains untrusted
outside the live originating context.

It is **not yet the same product-use endpoint**: the current installed client's
`author` cannot consume this new view. Full ordinary reciprocal contribution
needs explicit runtime/client dispatch, native source/preparation handling and
onward complete witness closure. That spans at least the runtime factory,
client-context gate, source adapter and preparation/closure path; estimate it
separately rather than hiding it in this small helper. No existing certified
acceptance path should change merely to get matching timings.

The near-term payoff is a reusable local API for sound, demand-complete semantic
reading after inexpensive ordinary checking, and the removal of an artificial
extra semantic-fetch disadvantage. If that API is not itself wanted next, stop
at the already implemented membership component; do not build a private mock
READY route solely to claim a whole-workflow cost result.

## Final priority decision: defer another native context or authoring lane

**Recommendation: do not implement `NativeContextView` now, and do not immediately
expand this comparator into a second ordinary-contribution product path.** This
supersedes any suggestion above that feasibility alone warrants the view. The
native membership component is already implemented, independently audited and
executed once successfully: three exact members, zero cryptographic assumptions,
1.3125 known whole CPU seconds and 1.5337696 wall seconds. Preserve that useful
result without claiming semantic READY, matched whole-workflow performance or
ancestry-independent verification.

The tempting contribution shortcut is mathematically possible but not a thin
integration. `authoring.worker.run` can consume an untrusted context/request;
it does not require a live Python membership token. A complete native check of
the resulting descendant and all ancestor witnesses could establish validity
without trusting that frontend context. This does **not** remove the required
source/selection/root binding, bounded Lean preparation, exporter decoding,
parent-journal construction, custody and final same-call acceptance machinery.
`MixedSourceOperation.finish` contains a largely pure export-to-V2-witness
conversion, but its public entry/exit are deliberately exact-session/mixed
interfaces. Reusing that mathematics properly requires a separately reviewed
common conversion seam and explicit successor wiring, not copying its conversion
logic or loosening the existing gates. No such implementation is selected here.

Consequently the alternatives have different payoffs:

- A standalone view adds semantic inspection but cannot complete the current
  `client.author` workflow. Its immediate use would mainly be benchmark parity.
- Native contribution adds a real receipt-free local workflow, but crosses the
  runtime/client, preparation/conversion and onward-closure boundaries. It still
  downloads/checks complete selected proof ancestry and therefore does not solve
  the large-network cutoff requirement.
- Keeping the audited component needs no further software or experiment. It
  establishes that an equally represented ordinary check is inexpensive for the
  retained small DAG, constraining any honest growth/certification argument.
  Existing I-plus-native-delta contribution remains the operative product route.

The third choice has the highest immediate marginal payoff. Continue improving
the existing scalable-reuse/contribution route instead of manufacturing a new
native lane to complete a comparison. The missing matched full-cost endpoint
remains an explicitly open evidence obligation; this decision does not infer a
positive sharing/certification margin from component timings.

**Activation condition for revisiting:** an actual supported user workflow needs
receipt-free contribution, or a specific pending economic/admission decision
cannot be resolved by analytic bounds plus the existing component evidence.
Then select one end-to-end contribution seam with shared conversion logic and
unchanged trust boundaries; include semantic preparation as its internal step,
not as a separately marketed half-integrated READY utility. Do not revisit it
merely to create another timing point. This decision required source reasoning
only: no import, test, build, native run, RAM probe or Git mutation was performed.
