## What the fixture does and does not establish

Each case creates fresh exact-class structural receiver/I-owner shells. This
explicitly bypasses constructor adoption; it is not an owner installation test.
The shell has a fresh real persisted local TrustDomain/binding, pinned selected
source files, a pinned inert text file in place of the native executable, and
real owner/request/packet/output files. Real `_active`, `_check`, `_census`,
`receive`, current graph parsing, `bind_native`, readbacks, handle descriptions,
export and revocation bodies are used. There are no I/A receipt claims or
frontiers. Receipt-owner `receive`, actual subprocess creation, `os.system` and
socket construction are forbidden.

The fixture's trusted supervisor is simulated. It writes a fabricated exact
native transcript and a fabricated clean-process report; it does not execute a
checker or process. Process reports carry an explicit test-only tag. Native
stdout retains the exact production schema because `bind_native` rejects extra
fields. Structural witness rows are not mathematical proofs. An apparent live
test handle only demonstrates controller behavior under the fabricated relation
transcript, never mathematical admission. Its configured 0.25-worker-CPU number
is an accounting probe, not measured worker cost.

The fixture's path/pin/bounded-read operations use actual local files and reject
redirected paths. Its `limits_checked` copies the supplied dictionary; tests
inspect original CPU/process/memory caps, but do not requalify the supervisor's
limit validation. Existing independent source review supplies the argument for
unchanged production supervision, receipt/frontier and mathematical boundaries.
