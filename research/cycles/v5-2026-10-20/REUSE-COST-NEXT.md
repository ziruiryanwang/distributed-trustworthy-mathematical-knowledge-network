## What the actual pair does and does not establish

The saved paired result reports both exact endpoints successful but the unchanged
investment screen failed. General/RC padded rows are9240576/10354688; complete
standalone known CPU is2.171875/2.5seconds. The smaller witness is not a faster
guest: original W is35091bytes and RC frame6408bytes. This separates compact
transport from computation rather than demonstrating scalable proof efficiency.

Arm controller CPU is0.65625/1.046875seconds; host Job CPU is0.859375/0.796875.
Shared preparation/setup/final binding is0.65625seconds and is fully charged to
both. There is no controller-phase timing, so these observations cannot identify
a particular parser, path check or hash as the cause of the difference. Removing
common preparation from one arm, dropping output validation or relaxing the
screen would be benchmark cosmetics, not product improvement.

The pair adapter checks every segment and capsule and repeats exact adopted
input binding before execution and on completion. The host retains each segment
and a capsule containing all segments (`AggregateSnapshot.segments: Vec<Segment>`).
This explains duplicate evidence storage by construction, not a timing claim.
The fixture is deliberately immutable differential evidence. Optimizing that
preparer or replacing its emitted W cannot repair this completed comparison.
Growth owns the separate RC checker-cost diagnosis and successor decision.

## Avoid duplicating mechanisms that already exist

Current installed-source paths already provide:

- `client/workspace_mixed.py::_admit_packet`: exact whole-packet live cache.
- `runtime_efficient/mixed_claims/receiver.py::receive`: exact receipt-claim cache.
- `interface_views/imports_atomic.py`: sealed immutable context views, complete
  chosen-J ancestry and receipt deduplication.
- `interface_views/projection.py`: interface-only ordinary definitions, with
  original authenticated descriptors retained for final checking.
- `origin_phase/admission/pin_phase.py`: scoped installation/trust/origin check
  reuse with fresh successful-exit observations. No cache crosses a subprocess,
  network operation or authority boundary.
- `modules/native_rows.py`: interned native rows and incremental byte accounting.

Thus another generic cache, promise of deferred definition bodies or pin-phase
framework is not a new central capability.

## Best distinct product opportunity: exact repeated native-delta reuse

For different packets sharing an uncertified proof prefix, whole-packet caching
does not apply. The current mixed receiver still launches the unchanged native
checker separately for every witness in every packet (`receive`, roughly
lines279-303). Receipt caching avoids repeated boundary verification, but there
is no native-witness-result cache. This is a source-established repeated-work
opportunity independent of the decision on RC.

A bounded **same-owner, exact-witness** cache could retain only successfully
checked native transitions, never imported acceptance flags. Key it by the
original verifier/profile and semantic-image/foundation/policy identities plus
exact immutable witness bytes (or digest/length with retained-byte equality),
ordered exact parent journals and exact target J. A hit must still:

1. Check current owners, origin, pin, trust, expiry and resource conditions.
2. Re-establish every parent in this call's current validated graph, including
   exact ranks, live terminal receipt frontiers and chosen derivation closure.
3. Match immutable W and the exact result previously obtained from a clean native
   process and `bind_native`; ModuleID alone is insufficient.
4. Fail closed on revocation and erase the cache with the owner. No persistent
   acceptance file, peer-supplied token or authority survives owner close.

The assurance argument is simple: a previously checked deterministic conditional
judgment for the identical W remains the same judgment under the same checker
and foundation; re-establishing its exact premises permits the same conclusion.
This changes operational provenance from "native process in this receive call"
to "native process earlier in this live owner". That change needs an explicit
successor contract and report mode; it must not masquerade as the old same-call
claim. It adds no cryptographic authority or mathematical axiom.

For m distinct descendants each carrying k identical prefix witnesses and one
new witness, native invocations can fall from m(k+1) to k+m. This is conditional
on all admissions occurring under the same finite owner and cache capacity, not
an asymptotic claim about the whole network. Let Cj be actual native+supervision
cost of repeated witness j, hj the exact cache lookup/binding cost, and M the
memory/maintenance cost. Benefit requires

`sum_over_avoided_checks(Cj - hj) > M`.

No numeric coefficient is borrowed from the RC pair. Existing conservative
reservation charges should initially remain unchanged; cache hits save observed
work, not automatically purchased allowance or budget. Any later relaxation of
reservation accounting is a separate resource-safety change.

Practical limits: `trust_withdrawal/client/runtime.py::open_operation` constructs
fresh owners per grant. This cache helps multiple distinct acquisitions under
one grant, not separate grants or fresh machines. The mixed envelope already
limits deltas to16 and packet size to32MiB. A fixed-entry/byte bound, immutable
stored results and eviction-as-miss suffice; no global cache is needed.

One future changed-boundary discriminator would use two different packets with
the same exact prefix and changed successors under one owner, require a hit
only for the common prefix, then reject changed W, parent J/rank, closed owner
or withdrawn trust. Compare actual native invocation counts and full admitted
work, not repeated copies of the same packet (already cached today). This is a
proposal, not a selected test or runtime authorization.

## Semantic import payloads: do not confuse representation with trust

`interface_views/imports_atomic.py::onward_packet` already deduplicates receipts
and selected ancestor nodes inside one packet. It deliberately includes all
selected uncertified W ancestry. `authoring_atomic.py::finish` and
`delta/reprepare.py::emit_relation_rows` carry both authenticated descriptors and
their native encoding so the unchanged relation can bind them. Their duplication
is not permission to omit authenticated imports or to trust frontend projection.

The proposed local cache does **not** remove repeated packet bytes/parsing, make
uncertified ancestry succinct, or satisfy fresh-receiver independence from that
ancestry. Portable I/A certificates remain the existing mechanism for cutting
that ancestry. Optional content-addressed transport chunks could reduce repeat
transmission only when recipients already hold exact bytes; reconstruction and
checking must retain the same W. That larger schema/acquisition change has lower
immediate payoff without evidence that bandwidth, rather than checking or
certification, is decisive. Do not start it now.

## Controller-cost priority

There are repeated pure parse/serialization and validation boundaries, but their
costs are not separately identified by this screen. In particular, wrapping a
whole receive in the existing pin phase is invalid because it spans native
subprocesses. Smaller synchronous scopes may be eligible, but independent nested
phases can also add final sweeps. Do not redesign owner validation merely to
alter this tiny paired timing result.

Recommendation: keep the RC derived-support successor as root's currently chosen
highest-payoff checker task. Retain exact same-owner native-delta reuse as the
next distinct product-level option, preferably when a real multi-acquisition
workload demonstrates repeated prefix checking. No permanent rollout, proof
investment or full-v5 completion follows from this recommendation.
