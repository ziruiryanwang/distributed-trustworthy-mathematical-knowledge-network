## Fail-closed finalization

The independent reviewer found that best-effort negative markers alone cannot
prevent a saved success from surviving both a failed final check and a failed
negative write. The source repairs this before any execution:

1. Create `FINALIZATION-PENDING.json` before selection/entry/worker/result writes.
2. Preserve pending on every failure, including failed diagnostic persistence.
3. Save the provisional result, then finish all validation, rebinding, output
   bounds, exact pending-pin checks, stdout and original deadline checks.
4. Remove pending as the final authority-bearing filesystem operation, then
   return zero without further validation or reporting.

Consumers must refuse both pending and failed records. The shared helper's
`completed_outer` implements that rule; the current parent can validate its
worker while its own pending marker still exists. If deletion fails, completion
fails and pending remains. A process dying before commit leaves unadoptable
evidence. If commit succeeds and the process dies before its exit is observed,
the saved operation has nevertheless crossed its explicit commit boundary.

This is a trusted local-filesystem commit convention, not a transaction proven
durable against power loss or arbitrary owner/OS mutation. Printed success is
provisional until the saved-result completion rule holds. A profile is ordinary
configuration; profile creation has its own analogous completion convention,
not mathematical or funding authority.
