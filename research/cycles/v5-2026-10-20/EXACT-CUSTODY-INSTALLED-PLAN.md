## Consequential question and recommendation

Can the installed client discover a theorem at P, encounter its actual selected
`NeedBody`, locate Q that was never an index contact, fetch Q's exact committed
body, and continue the **same** semantic reader and original operation?

Recommend one three-Node loopback integration using an existing retained valid
packet. Exercise the real installed V3 body-only service, maintained location,
adaptive query, capability pool, HTTP transport and structural reader together.
After structural closure, close network roles and perform the retained packet's
one ordinary admission/import in the same live client. This last phase checks
that the new acquisition path really feeds the existing warranted reuse path;
it creates no proof and changes no checking relation.

Do not repeat import-only installation checks, the old explicit-Q split test,
the focused controls, or a proof-production campaign. Three nodes are sufficient;
no fourth routing seed, remote host, broad simulation or RAM study is needed.

## Three-node topology without a startup cycle

P and Q each have one HTTP service plus one Node locator. R has one Node locator
and the original installed client in the owner process. HTTP servers need no
extra OS process. All sockets are loopback under one explicit owner egress
allowlist; public-network access is outside scope.

1. Open P's retained workspace under its normal exclusive owner lock. Start
   the installed `CompositeProvider` and V1 `ServiceLocationProcess` through
   their existing SDK interfaces, but do not publish yet. Public `.start()`
   returns P's PeerID, permitting the bootstrap multiaddress without reading
   private child files or changing any configuration after startup.
2. Start Q through the actual new `serve_advertised.serve(context)` V3 path:
   one exact `body_routes` row above, empty index routes, `index_view=null`,
   and bootstrap P. Its normal pre-start read-back validates actual custody;
   its body publication to P precedes its ready record.
3. When Q is genuinely ready, P publishes its one existing theorem-index key
   through its normal `publish` command. Q is now available as a routing peer;
   require the normal dispatched-hint census rather than fabricating success.
4. Construct R with V2 role `reader`, matching body domain and bootstrap P.
   **Do not start R yet.** Reserve the ordinary located-query envelope and
   body allowance while the original child remains pristine, then invoke
   `next_located_query` once. Its first call starts R normally.
5. Discover P's index through the actual index route/descriptor and perform
   the ordinary snapshot/page/packet selection. Candidate ID is obtained from
   this query, not inserted from the known fixture. Only P becomes an index
   and original acquisition contact. Q's endpoint may appear in the owner
   egress allowlist but must not appear in either original contact map.
6. Stage the returned root in one `SemanticReader`, using eager semantics for
   this fixed changed-boundary fixture. Process actual preview demands. Resolve
   declarations from P. At the exact selected body demand, after its declaration
   is held, call `locate_body` once and use its one issued capability with
   `try_fetch_body_from` once. Do not try P's known-missing body first; that would
   add no discriminatory evidence beyond the focused settled-miss controls.
7. All remaining demanded bodies are obtained through their ordinary P path.
   Continue the same reader until the exact structural closure is ready.
   No second query generation, contact-map mutation, new grant or reader occurs.

Starting R first to obtain a bootstrap PeerID would violate the pristine-reader
reservation precondition. Starting P and Q through mutually dependent ready
files would create a cycle because service ready follows publication. The
sequence above avoids both without a new product callback or extra process.

Port selection is the existing bounded distinct-port pattern: reserve all five
loopback ports together (P/Q HTTP plus P/Q/R location), record them, release the
temporary sockets, and bind once. A race produces a preserved failure; no silent
port substitution or retry. Distinct peer IDs do not imply independent hosts.

## Admission phase and its exact claim

Once all semantic bytes are staged, stop P and R locators cleanly using their
public stop/close paths; close P's HTTP/workspace. Let Q's already finite V3
service reach its normal terminal cleanup, rather than canceling a successful
service and relabeling cancellation as PASS. Require all three child closures
before the retained mathematical phase. Do not close the client, retire its
query, replace its acquisition or close the semantic reader at this boundary.

Then call this same reader's `finish({root: admission_limits})` once. Source
inspection supports the separation: local staged admission/import does not
require fresh provider dialing; client/grant and structural-owner deadlines
still apply. A clean locator-only closure is not an arbitrary cleanup waiver.
If closure is uncertain or a deadline has expired, fail rather than reconstruct
a client or replenish its allowance.

Require one actual retained I receipt verification and one mixed-admission
attempt with the existing two native checks; zero aggregate verification,
authoring, preparation, new proof and publication attempts. Require the live
warrant-derived context and zero post-closure acquisition requests/reply bytes.
The retained no-ancestor-replay observation remains
`frontend_theorem_ancestor_proof_bytes == 0` for the selected import.

Distinguish these results precisely:

- Structural ready alone is not mathematical acceptance.
- The final admission checks the existing packet and issues its live original
  mathematical warrants. Imported authoring context is still represented as
  untrusted context; it is not a newly accepted theorem or transferable report.
- `SemanticReader.finish()` deliberately reports `mathematical_acceptance=false`
  in its data wrapper. Do not change that flag or infer new mathematics from it.

Root could choose the structural-only scope instead, but must prospectively
omit final-admission claims and counters. Recommendation is the single combined
scope: it resolves one real end-to-end composition question using retained bytes
at small additional cost, rather than arranging a later duplicate network run.

All statuses and costs survive failure. Failed routing, corrupt data, unexpected
stderr, child exit, uncertain cleanup or final verification must remain failed;
successful structural staging cannot erase them. No token minting, direct Q
endpoint insertion, receiver substitution, deadline extension or fixture repair
may rescue the same allocation.

same-reader located-body reuse boundary, not independent operators, worldwide
availability, arbitrary semantic recall, net useful-growth advantage or final
v5. The next decision should then target the remaining reciprocal-use/growth
obligation, not repeat this already discriminated integration.
