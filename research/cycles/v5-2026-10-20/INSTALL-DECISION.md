# Ordinary installation and launcher: source decision

2026-10-20; `core_release`. Source-only; no code, package, runtime or Git change.

## Decision and order

Do not package the current pieces as a completed workflow yet. First close the
ordinary direct-contact search/acquisition seam identified in USER-PATH:
`serve_workspace` produces an HTTP endpoint, but `CommonsClient.find/resolve`
currently require an exact located handoff/Node service. A package alone would
still leave users reconstructing a workload recipe.

Prefer a small **explicit owner-selected contacts** entry to making DHT service
wiring mandatory. Existing `SearchClient`, `SearchSession` and typed acquisition
constructors already support endpoint-based operations. Bind them to one query,
the original grant/deadline, explicit egress policy and shared acquisition
budget. Do not forge a located handoff, silently reset budgets, trust endpoints
mathematically, or weaken exact issuer pairing. Existing DHT discovery remains
an optional contact source; direct configuration provides no routing coverage.

The alternative requires two Node roles, runtime/MJS adoption, bootstrap,
route/stripe planning, advertisements and extra process cleanup just to contact
a known service. That is useful later, but not the smallest current repair.
Exact Workspace typing in `RuntimeProfile` also means a new client subclass
needs deliberate factory integration, not pretending it is the atomic class.

## Smallest following product increment

Create one relocatable Windows SDK installation and a small public launcher:
`run` executes an explicitly owner-selected local strategy; `serve` invokes
the existing finite service. Users supply workspace/configuration, endpoints
and finite limits, not SDK source maps, fixture assets or research paths.
Local agents still choose their own mathematics; no workflow language or
global task scheduler is needed.

Layout: immutable `base/` (exact existing supervisor/runtime installation),
`sdk/` (release-selected v5 and portable sources), `assets/` (selected native
and mathematical-runtime roles), release manifest, public launcher and docs.
State, operations, receipts acquired by users and TLS secrets live outside it.
Ship a release-owned relative source map and role map once; launcher resolves
those against its installation and produces the unchanged old launch plan.
Caller-owned strategy code is separately explicitly adopted as trusted local
code. Nothing received from a peer can select executable code or a checker.

## What can be reused unchanged

- `client/launch.py` and `boot.py`: exact source snapshot, isolated bundled
  Python, original monotonic deadline, Windows Job and output/cleanup evidence.
- `RuntimeProfile`: exact owners, source-origin checks, grant suballocation;
  Workspace/schema, HTTP service and mathematical acceptance remain unchanged.
- Prior `named-library-01/package_library01.py` archive rules: streamed exact
  file map, ordinary paths, case-alias rejection, bounded ZIP metadata, fresh
  extraction and read-back hash checks. Its hardcoded root/deadline/counts make
  the old experiment script unsuitable as the public installer; reuse the
  policy in a small parameterized release utility, not another research runner.

## Pinning and relocation boundaries

`launch.py` deliberately pins base manifest
`a93714ecd267984d2bdc7830fc28027151d650d5b0aeea13fac850b52ba5beed`.
Its installation path is already relocatable. Nest that exact base; do not
change its manifest merely to add v5 files or replace the fixed pin with an
untrusted self-declared digest. Its manifest has 6,652 payload entries totaling
235,662,448 bytes; this is a one-time file-copy issue, not a proof/RAM problem.

RuntimeProfile rebases only manifest-backed Python/runtime roles and selected
source/worker paths. The preparation host, guest image, native checker,
AuthorLean frontend and six selected Lean runtime files remain external
absolute pins today. A release-owned relative role map must bind each role to
its already adopted bytes, then construct a fresh absolute preparation profile
under the chosen install root. Revalidate image/foundation/policy relationships;
do not infer native dependency closure merely from an executable's hash.
No `experiments/`, original project root or old absolute path may be required.

Hashes establish exact identity, not checker correctness, publisher identity
or mathematical validity. The owner must adopt the release/role selection from
an independently accepted digest or eventual release-signing policy; a peer's
manifest is not an authority root. Receipt/image and same-call mathematical
checks remain necessary. Binary relocation is not new A certification.

## Finite acceptance and stop rule

After the direct-contact seam is ready: one file-only install to a fresh path
with spaces, exact-map audit, then one tiny relocated ordinary workflow using
retained genuine I data and the newly connected endpoint path. Check absence
of repository/research-path dependencies, source/runtime binding, finite
service cleanup and retained workspace reopen. Reuse existing component
passes; do not repeat proof generation, broad networks or all historical tests.
Use focused refusal cases for changed manifest/role/path inputs only.

Build the directory/launcher first; archive mechanics are last. Explicitly
expose unsupported A production, platform/security/license obligations rather
than auto-falling back or calling this increment final v5. Full release remains
the unchanged goal. If packaging starts recreating strategies or routing policy,
stop that expansion and finish the direct-contact product boundary instead.
