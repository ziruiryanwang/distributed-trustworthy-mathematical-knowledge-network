## Recommendation and evidence

**Expose a complete, bounded dedicated-custodian workflow over the existing inert
storage, index and provider SDK.** An operator should be able to retain selected
exported mathematics and serve it to independently checking recipients without
initializing a mathematical owner, grounding its library, or holding a contributor's
catalog lock. Start with exact local inert inputs and finite existing service;
no daemon, replication policy, new wire protocol or automatic source acquisition.

This is the next public deployment seam, not a claim that hosting dominates
research cost. [ROLE-SEPARATION-PAYOFF](../v5-2026-10-24-growth-selection/ROLE-SEPARATION-PAYOFF.md)
already identified and correctly deferred it while usable concept continuation
was the more direct uncertainty. Reuse that analysis rather than commission it
again. The present rationale is that the selected continuation path now works,
and a usable nonchecking provider is part of the intended deployed network.

## Source call graph and precise obstruction

Current selected sources, not historical candidates:

```text
ordinary_sparse_access/peer.py: run(serve)
  -> validate catalog + custody + index selection
  -> OrdinaryStore(custody)
  -> OrdinaryAdmission.open(installation, catalog, store_id, custody)
       -> PortableCatalog.open(...) and exclusive owner lock
  -> ordinary_multi_source/peer_api.py: serve(loaded, custody, config, allowance)
       -> _state(loaded, None, custody)
       -> _index(loaded, None, custody, ...)
       -> HTTP Provider(index, ordinary=custody, ...)
  -> provider/index cleanup, then owner/custody close
```

The owner's opening at `peer.py:220-227` is mandatory for this public `serve`.
Its source comment explicitly says the same owner lock serializes supported
mutation and serving. In contrast, `peer_api.py:893` declares the owner-free SDK
signature; its `_state` checks owner identity only when owner is supplied.
The provider accepts no remote source/native execution or mathematical admission.
Thus a missing public lifecycle boundary, rather than a new verification theory,
prevents a volunteer from using the existing nonchecking role directly.

This does **not** stop all creative work: ordinary Lean research and owner-free
production can continue during service. The obstruction is simultaneous supported
catalog operations and service from that same owner, and unnecessary mathematical
owner setup for a participant who only wants to preserve and serve inert content.

## Compare the simpler alternatives first

1. **Stop serving, mutate, restart.** This already works and is appropriate for
   occasional personal sharing. Preserve it. It imposes an interruption but
   requires no new role or store copies.
2. **Use a second initialized owner.** This separates locks on one PC without
   any new protocol, but asks a byte-only custodian to initialize/check mathematics
   it is not relying on. Do not count that checking as required for inert custody.
3. **Use the existing dedicated-store SDK.** This is the preferred implementation
   basis. An expert can already prepare stores and call the provider. The missing
   deliverable is an ordinary bounded operator route with explicit lifecycle,
   preparation and exclusion, not another backend.
4. **Relax the contributor lock.** Reject this shortcut. The existing custody
   and index stores assume serialized operations. A new lock ignored by current
   owner commands does not make shared live-state access safe.

If the final supported workflow can be supplied entirely through an existing
public command, select that route and add no implementation. The current selected
call graph above establishes that `serve` itself is not that command.

## One bounded next action

Root should select a **source-only public dedicated-store facade** with these
two lifecycle phases treated as one operator workflow:

- Prepare a fresh dedicated custody/index pair from explicitly selected, bounded
  inert units and previews using existing `OrdinaryStore.put_evidence`,
  `put_preview` and index `admit` primitives. Derive/validate exact existing
  locators and preview identities through current codecs. Do not copy a live
  SQLite database, import source, create an owner or infer complete ancestry.
- Serve that separately prepared pair using the existing finite provider.
  Report readiness/availability observations only. The contributing owner is
  neither selected nor opened. Serving retains the same budgets, TLS/address
  policy, complete-custody disclosure and cleanup rules as the existing route.

Before code, settle the small exclusion contract: dedicated stores must be
created for this role, must not alias authoring state, and every supported
preparer/server/refresher must obey one exclusive lifecycle. An asserted
`exclusive=true` alone is insufficient. No mutation/refresh while serving is
needed in the first public route; close service before any later explicitly
selected refresh. Enforced dedicated ownership plus existing protected-OS
premises is preferable to changing locks for every mathematical owner.

Reusing the current full package/runtime verifier is acceptable initially.
Removing the catalog/grounding obligation does not imply a Lean-runtime-free
installation. A separate lightweight packaging effort is not selected here.
Root should stop the facade design if safe exclusion would require a broad
catalog migration; retain the SDK route and record the specific obstacle.

## Why this preserves trust and can pay for itself

Let `r` be an inert record served by custodian `C`, and let recipient `V` use the
unchanged acceptance predicate. `C`'s storage action asserts neither that `r` is
true nor that all dependencies are available. Acceptance remains

```text
Accept_V(r) only if V's ordinary identity/dependency/checking policy succeeds.
```

Since no custodian status is an input granting mathematical acceptance, removing
custodian grounding does not remove a recipient premise. Altered or misleading
bytes may waste bounded discovery/acquisition work, but cannot become a theorem
through the custodian's authority. Keep that distinction in every public report.

The expected benefit is concrete: retain service independently of the originating
author's catalog operations, and avoid unnecessary mathematical owner setup for
byte custodians. Charge preparation, duplicate storage, metadata validation,
service and maintenance. Relative to a second-owner provider, a benefit region is

```text
avoided owner setup/checking + valued avoided author-service interruption
    > dedicated preparation + additional retention/maintenance + facade overhead.
```

This is conditional accounting, not a measured net saving. A small personal
library may rationally choose stop/mutate/serve instead. A same-PC custodian
does not create an independent failure domain or permanent availability.
Ordinary Git/source mirrors remain necessary for rich authoring facilities when
inert realization alone does not provide them; this role preserves evidence,
not an entire executable development environment.
